# Benchmarking

GeoBrix ships a benchmark suite. It times each function at every implementation level a compute offers, on the same inputs. It also checks that the levels give the same output.

This page is the method and the measured matrix. For guidance on which compute and surface to use, see [Performance](./performance).

:::note Runtime support and benchmark environment
GeoBrix is [supported on DBR 17.3 LTS, 18 LTS and 19 LTS](../installation#supported-databricks-runtimes). Each result below states the runtime it ran on. The stamp records the run. It does not say that another supported runtime is faster or slower.
:::

## What the suite measures

**Levels.** A function can run at up to four [levels](./execution-tiers#the-levels).

| Level | Implementation |
|---|---|
| L0 | SQL expression (no UDF, no JAR) |
| L1 | JVM Catalyst expression (needs the JAR) |
| L3 | Python (no JAR) |
| L4 | Unity Catalog function |

**Timing models.** Each function runs under two models.

- **Pure-core.** The operation in isolation. It opens one tile, calls the function and measures. There is no Spark and no serialization in the path.
- **Spark-path.** The registered function over a DataFrame of *N* rows. It includes the per-row overhead of the level. It sweeps a row ladder, for example 10, 100, 1,000 and 10,000 rows.

Both models run `--warmup` untimed passes, then `--measured` timed passes. The reported figure is the median of the timed passes. Locally the defaults are 2 and 5. On a cluster they are 1 and 3 for pure-core, and 1 and 1 for spark-path.

**Consistency.** Every pure-core result carries an output fingerprint of per-band statistics. The levels are then compared:

- **exact.** Every statistic is bitwise equal.
- **within_tol.** Every statistic agrees to a relative or absolute tolerance of `1e-3`.
- **divergent.** Neither tolerance holds.

**Computes.** Compare times within one compute. The suite runs on:

- **Dedicated** and **standard** clusters, where a fixed set of workers gives repeatable seconds.
- **Serverless**, where workers scale with the job. Read a Serverless run for single-task time, per-task memory and per-task failures (out of memory) only. Do not compare forms, scales or computes from its job times, and do not compare it with seconds from a fixed cluster.
- A **SQL warehouse**, for Unity Catalog functions.

**Corpus.** The suite generates a seeded corpus of GeoTIFF tiles, with a manifest. `--tile-px`, `--bands`, `--dtypes`, `--srids` and `--nodata-frac` shape it. The row pool is generated once and reused by every level, so the levels compare fairly. Generate it on Databricks with `gbx:bench:gen-data --on-databricks`.

:::note
The benchmark runs from the GeoBrix source repository. It uses the repository's `gbx:bench:*` commands and a job notebook. A wheel-only install does not include these tools.
:::

## Running on a cluster

A cluster run executes every level on the same hardware, against the same corpus. Results append to a `bench_results` Delta table. A `comparison.csv` and a `summary.md` land on the configured Volume.

### Prerequisites

Provision a compute and stage the artifacts as the [installation guide](../installation) describes.

| Compute | Artifacts |
|---|---|
| Dedicated, DBR 17.3, 18 or 19 | The env wheel, the GeoBrix JAR and the bench tests JAR (`geobrix-*-tests.jar`), all as cluster libraries |
| Standard, ARM, or Serverless | The env wheel for the runtime (`+env6` on Serverless environment 6 and DBR 19, `+env5` on environment 5 and DBR 17.3 and 18) |

Then fill in `examples/tests/databricks_cluster_config.env` with your cluster ID and Volume paths.

### Run

```bash
# Spark-path ladder on a provisioned cluster
bash scripts/commands/gbx-bench-cluster.sh \
  --cluster-id <your-cluster-id> \
  --run-id cluster-2026-11 \
  --modes both \
  --row-counts 10,100,1000,10000
```

The levels leg times each form of one function set at every level the compute offers. It runs without the tests JAR:

```bash
# The raster read forms on a dedicated cluster, at the set's own scales
bash scripts/commands/gbx-bench-cluster.sh --profile <name> \
  --existing-cluster-id <cluster-id> --levels IO --levels-only \
  --run-id levels-io-ded

# The same forms on Serverless environment 6
bash scripts/commands/gbx-bench-cluster.sh --profile <name> --serverless \
  --env-version 6 --levels IO --levels-only --run-id levels-io-s6
```

| Option | Purpose |
|---|---|
| `--modes pure-core \| spark-path \| both` | The timing model. Default `both`. |
| `--row-counts 10,100,1000,10000` | The spark-path row ladder. Each value is the number of distinct tiles in one timed iteration. The largest value must not exceed the corpus row pool. |
| `--set core \| full` | The representative set, or every benchmarked function. Default `core`. |
| `--functions rst_slope,rst_ndvi` | Restrict the run to these functions. It overrides `--set`. |
| `--levels S\|G\|A\|H\|SE\|IO` | Add the levels leg for one set: session functions, generators, aggregates, helpers, the GDAL spec engine rows, or the raster read forms. |
| `--levels-scales 1,4,16` | The multiples of each form's base row count. Each set has its own default ladder. |
| `--levels-forms b,d-py,floor` | Time only these forms. |
| `--levels-uc <catalog.schema>` | Where the Unity Catalog functions live. Without it, the L4 forms record a skipped row. |
| `--serverless`, `--env-version <N>` | Submit to Serverless, pinned to environment version *N*. |
| `--warmup` / `--measured` | Warmup and measured iteration counts. |
| `--no-wait` | Submit the job and return. |

A spark-path iteration processes `max(--row-counts)` distinct tiles. If the corpus pool is smaller, the run refuses rather than under-fill. Generate a larger pool or lower the ladder.

Every levels form prints START, DONE and RUNNING lines in the job notebook, so a long run shows its progress.

### Output

- **`bench_results` Delta table.** Every measured row, tagged with environment and run ID.
- **`summary.md` and `comparison.csv`** on the Volume. The speedup and consistency report.

Each levels row also records the compute and the bytes sent to and from Python workers. It records Python-worker task-seconds, shuffle and spill bytes, peak execution memory and the Python workers' peak memory.

## Running locally

The local pipeline generates the corpus, runs the JVM level in the `geobrix-dev` container and the Python level in an isolated virtual environment, then compares them. Local runs time one tile for pure-core. Row ladders at scale belong on a cluster.

```bash
# Generate the corpus, run both levels, compare
bash scripts/commands/gbx-bench-all.sh --run-id local-1 --modes pure-core
```

The two legs run one after the other, so they do not contend for CPU. Outputs land in `test-logs/bench/<run-id>/`.

`--set core` runs a small set that covers each family. `--set full` runs every benchmarked function. The set controls how many functions run. Pure-core is the timing model. They are independent.

For the raster read forms, time them locally before a cluster round:

```bash
# Three sizes on local[8]; exits 1 when a form does not scale with n
bash scripts/commands/gbx-bench-local-timing.sh --set IO
```

| Corpus option | Purpose |
|---|---|
| `--tile-px 256,512,1024,2048` | Tile sizes in pixels per side. Default `256,512`. |
| `--bands 1,4` | Band counts. Default `2`. |
| `--dtypes uint8,int16,float32` | Pixel types. These three are the full set. Default `float32`. |
| `--srids 4326,3857,32618,27700` | Projections. These four are the full set. Default `4326,32618`. |
| `--nodata-frac 0.0,0.25` | Fraction of NoData pixels, from `0.0` to `1.0`. Default `0.0`. |
| `--row-counts` | The spark-path row ladder. Default `2,4` locally. |

The stages are also standalone commands: `gbx:bench:gen-data`, `gbx:bench:heavyweight`, `gbx:bench:lightweight` and `gbx:bench:compare`.

## Reading the output

The comparison `summary.md` opens with insights: the biggest differences, a consistency tally and the tile scale. A per-function table follows.

| fn | hw_iter_s | lw_iter_s | hw_per_tile_s | lw_per_tile_s | speedup | consistency |
|---|---|---|---|---|---|---|
| `rst_dtmfromgeoms_agg` | 175.10 | 9.94 | 0.17510 | 0.00994 | 17.61 | within_tol |
| `rst_slope` | 7.31 | 7.57 | 0.00731 | 0.00757 | 0.97 | timing-only |

- **`hw_iter_s`, `lw_iter_s`.** The median wall-clock of one full iteration over all *N* tiles. `hw` is the JVM level and `lw` is the Python level.
- **`hw_per_tile_s`, `lw_per_tile_s`.** The iteration time divided by *N*.
- **`speedup`.** The JVM time divided by the Python time. A value above 1 means the Python level is faster.
- **`consistency`.** The label defined above. `timing-only` means the output cannot be fingerprinted for a direct comparison, as with readers and metadata accessors.

A pure-core summary uses `hw_ms`, `lw_ms` and megapixels per second instead. Each level also writes its own summary.

On a standard cluster, the Java UDF of `gbx_bng_eastnorthasbng` was also slower. It took 1.9x the time of the Python batch form at 4 million rows (3.24 s against 1.70 s). At 16 million rows it took 1.3x (5.42 s against 4.27 s). The function now has a SQL form that needs no JAR, with the Python batch form as the fallback.

The same rule decides each raster accessor that returns one value. Against the Python form that moves tiles in Arrow batches, two keep the JVM form: `gbx_rst_boundingbox` and `gbx_rst_worldtorastercoordy`. The other 19 stayed under the 1.2x bar, so they have no JVM form. A function that keeps it runs on the JVM for a materialized tile. A virtual tile runs at the Python level. A SQL function routes the two. An accessor or statistic that returns an `ARRAY<...>`, `MAP<...>` or `STRUCT<...>` can sit under `explode` or `inline`, where that routing function is refused and a virtual tile would raise. These have no JVM form, even where it was faster, as `gbx_rst_avg` was.

On Serverless, the grouped merge of tiles with bytes failed at every size tried, and the by-reference form ran. Read this as a per-task failure, not as a timing.

### Raster read

The raster reader returns virtual tiles by default. With `virtualTiles=false` it decodes whole files in bounded batches of at most 64 MiB. A file over the worker read cap fails the read with a retile `Fix:`.

The table shows the last full ladder on a dedicated cluster. The tiles are 1024 by 1024 GeoTIFF. The unit is seconds. Lower is faster.

{/* refresh: the measured performance matrix */}

| Form | 1,000 tiles | 4,000 tiles | 10,000 tiles |
|---|---|---|---|
| The retired Scala reader | 103.90 | 335.87 | 866.09 |
| `raster_gbx` reader | 40.61 | 178.73 | 400.85 |
| Bytes-free decode (`d-py`) | 29.58 | 122.35 | 329.67 |
| Floor (read the files, decode nothing) | 7.39 | 22.27 | 53.07 |

The Scala reader was 2.6x to 3.5x slower than the bytes-free Python decode at every scale, so 0.6.0 retired it. The `raster_gbx` figures come from before the reader decoded in bounded batches. The batched reader is not yet re-measured at this scale. A local ladder shows it at 0.4x to 0.6x of the bytes-free form.

The rows are one compute. Do not put Serverless seconds beside them.

### Reader plan-time listing {#reader-plan-time-listing}

Before it reads a tile, the reader lists the source directory to plan the tile windows. The default listing is a walk without file stats. It plans about 10,000 files in 1.5 s on a Volume. It runs once at plan time, even with `virtualTiles=true`.

Measured on a 10,002-file corpus on a dogfood workspace, driver side, warm run:

| Method | Median (s) | Compared with the default |
|---|---|---|
| Default directory listing | About 1.5 | Baseline |
| Pre-computed manifest or tile table | 0.037 | About 37x faster |

A manifest or tile table skips the walk and the header opens. Planning becomes one file or table read, whatever the tile count. This is an optional gain. It helps most when you already keep a tile index, or when a job repeats very many times.

A Delta table with a FILE column resolves each tile reference in the scan, with no per-tile open. A directory scan opens each tile on the worker. See the [capability tiers](../readers-writers#capability-tiers) and [Serverless & Memory](../serverless-and-memory).

```python
# Option 1: a manifest (JSON or Parquet) with a path and window per tile
df = spark.read.format("raster_gbx") \
    .option("manifest", "/Volumes/catalog/schema/vol/tiles.json") \
    .option("virtualTiles", "true") \
    .load("/Volumes/catalog/schema/vol/rasters")

# Option 2: a tile index in a Delta table. It is a saved file listing, not tile pixels.
from databricks.labs.gbx.ds.raster import read_tiles_table

df = read_tiles_table(
    spark, "geospatial.myschema.tile_index", {"virtualTiles": "true"}
)
```

### Virtual and materialized input tiles {#virtual-vs-materialized}

A virtual tile saves work when an operation is deferred. Metadata reads and edits (set CRS, set SRID, NoData, band select) finish from the header, without reading pixels. Chain deferred edits before a materializing step to pay the pixel cost once.

> **Environment:** Databricks · DBR 18.x · 20 workers · 512 by 512, 4-band `float32` tiles · 1,000 tiles per iteration.

| Disposition | Result for a virtual tile |
|---|---|
| Deferred | About 1.5x faster on average. The edits that carry no pixel work (`rst_setsrid`, `rst_setcrs`, `rst_initnodata`, `rst_band`) run 4.7x to 12.5x faster. |
| Materialized | About 2x slower. Every pixel is read, so the path and window indirection is overhead. |
| Not a single-tile operation | The grouped aggregates sit at parity. The byte constructors swing with how the bytes arrive: `rst_fromcontent` 2.8x faster, `rst_tryopen` about 4x slower. |

| Function | Materialized (ms per tile) | Virtual (ms per tile) | Virtual is faster by |
|---|---|---|---|
| `rst_initnodata` | 12.49 | 1.00 | 12.5x |
| `rst_setsrid` | 11.25 | 0.95 | 11.8x |
| `rst_setcrs` | 11.51 | 1.04 | 11.1x |
| `rst_band` | 4.77 | 1.00 | 4.7x |
| `rst_scalex` | 3.24 | 1.75 | 1.9x |
| `rst_srid` | 2.92 | 2.22 | 1.3x |
| `rst_slope` | 3.83 | 12.96 | 0.30x (slower) |
| `rst_ndvi` | 3.57 | 12.75 | 0.28x (slower) |

#### FILE versus FUSE: large-COG multi-window results {#file-capability-cog-multiwindow}

Without open amortization, FILE is not a throughput gain. FUSE's flat open cost and block-level I/O beat the per-tile HTTP stream setup. With amortization (the grouped executor and `ORDER BY path`), byte-range stream reads win by 10x to 290x. See [Virtual tile read performance](./performance#virtual-tile-read-performance).

| Leg | Setup | FILE on | FUSE (FILE off) | FUSE advantage |
|---|---|---|---|---|
| High reuse | 1 COG of 648 MB, 1,000 windows | 27.4 s | 13.1 s | 2.1x |
| High reuse, misaligned window | 1 COG of 648 MB, about 840 by 384 px windows | 26.7 s | 18.9 s | 1.42x |
| High reuse, 2.5 GB COG | 1 COG of 2.58 GB, 1,000 windows of 256 px | 22.8 s | 16.7 s | 1.37x |
| Low reuse | 25 COG copies of 648 MB, 1 window each | 16.2 s | 1.4 s | 11.4x |
| Real COG, NAIP (DEFLATE, 512 px blocks) | 324 MB, 1,000 windows of 256 px | 23.4 s | 16.2 s | 1.44x |
| Real COG, Sentinel-2 (DEFLATE, 1024 px blocks) | 22 MB, 1,000 windows of 256 px | 19.4 s | 17.7 s | 0.91x (a wash) |

### NetCDF readers

The `netcdf_gbx` benchmark has two legs, one for each data shape.

- **Raster leg.** `netcdf_gbx` in raster mode reads a directory of regular-grid `.nc` granules. The benchmark counts the `(source, tile)` rows it emits. It decodes CF `scale_factor` and `add_offset` to physical values.
- **Vector leg.** `netcdf_gbx` in vector mode reads a directory of Sentinel-5P L2 CH4 swath granules. It measures how fast the reader turns swath cells into points.

Stage each corpus once, apart from the read:

```python
from databricks.labs.gbx.bench import readers
# NASA-NEX GDDP-CMIP6 regular 0.25-degree grids, anonymous on Planetary Computer.
readers.stage_nasanex_corpus(spark, f"{CORPUS}/netcdf",
                             bbox=[-104.5, 31.0, -101.5, 33.0],
                             temporal="2021-01-01/2021-01-08",
                             variables=("tas",))

# Sentinel-5P L2 CH4 swaths, anonymous on Planetary Computer.
readers.stage_netcdf_corpus(spark, f"{CORPUS}/netcdf-swath",
                            bbox=[-104.5, 31.0, -101.5, 33.0],
                            temporal="2021-01-01/2021-01-08")
```

If a pool is empty or missing, that leg skips with a message and the run goes on. Run the leg with `gbx:bench:cluster --netcdf-only --row-counts 1000`.

### NetCDF writer

The `netcdf_gbx` writer has two legs for its two write modes. Run both with `gbx:bench:cluster --netcdf-writer-only --row-counts 1000`.

- **Raster leg.** Each `(source, tile)` row becomes one CF grid `.nc` file. It measures whole-job wall-clock over 1,000 rows.
- **Vector leg.** Each Spark partition becomes one CF `.nc` file. The input is points derived from the Sentinel-5P swaths.

Each mode runs three write shapes, recorded as separate rows:

- **parts** (default). One `.nc` file per row or per partition.
- **singleFile** (`singleFile=true`). The partition fragments merge into one `.nc` on the driver.
- **merge** (`merge=true keepParts=true`). A fold of the parts already on disk, without re-running the DataFrame.

### Tiled output (PMTiles writer) {#tiled-output-pmtiles-writer}

The PMTiles writer packages a tile pyramid into one `.pmtiles` archive. The `pmtiles_gbx` writer takes a `(z, x, y, bytes)` input. The benchmark writes 1,000 tiles to one archive. Run it with `gbx:bench:cluster --pmtiles-only --row-counts 1000`.

> **Environment:** Databricks · DBR 17.3 LTS · 1,000 synthetic PNG tiles to one archive · whole-job wall-clock median.

| Writer | Whole-job median (1,000 tiles) |
|---|---|
| `pmtiles_gbx` | 18.4 s |

The writer has two phases. Executors write intermediates, then the driver assembles the archive. The intermediates sit on a shared filesystem, not on node-local disk.

The `pmtiles_agg` aggregate folds a group of `(tile, z, x, y)` rows into one archive per key. On a dedicated cluster a JVM aggregate ran at 0.81x to 0.91x the speed of the Python one, with the same tiles. So the JAR holds no JVM form of it.

### Vector readers

The vector readers run on a scaled corpus. It holds five files of 1,000,000 features each, about 5 million polygons per format. The benchmark reads them from a Volume into a Delta table, one measured iteration per format. Cluster: DBR 17.3 LTS. Run it with `gbx:bench:cluster --vector-only --vector-scale`.

{/* refresh: the measured performance matrix */}

| Format | Rows | `*_gbx` reader |
|---|---|---|
| GeoJSON, FeatureCollection (`multi=false`) | 5M | 29.6 s |
| GeoJSON, GeoJSONSeq (`multi=true`) | 5M | 31.9 s |
| Shapefile | 5M | 27.8 s |
| GeoPackage | 5M | 23.5 s |
| FileGDB | 1M | 13.8 s |

The readers are Arrow-native: columnar `pyogrio` batches, with no per-row Python. They stage GeoPackage and FileGDB to worker-local temp for random-access reads. GeoJSON reads one partition per file, because the driver parses the whole `FeatureCollection` on each open. For each format the benchmark checks that the row counts match the source.

### Vector writers

The vector writers are all `*_gbx` writers. Each single-file writer writes a 14,000,000-feature Delta table to one file. The two-phase writer merges the partition fragments on the driver. Run it with `gbx:bench:cluster --vector-only --vector-scale --vector-legs writer --writer-rows 14000000`.

{/* refresh: the measured performance matrix */}

| Format | Rows | Time | Throughput |
|---|---|---|---|
| GeoJSON (single file) | 14M | 279.1 s | About 50k rows/s |
| Shapefile (single file) | 14M | 152.6 s | About 92k rows/s |
| GeoPackage (single file) | 14M | 155.9 s | About 90k rows/s |
| FileGDB (single file) | 14M | 97.2 s | About 144k rows/s |
| GeoJSONL (sharded, `geojsonl_gbx`) | 14M | 16.4 s (80 shards) | About 855k rows/s |

The single-file writers are driver-bound, because the merge runs on the driver. GeoJSON is slowest, because of text encoding. The sharded GeoJSONL writer skips the merge. It writes one shard per partition, in parallel, and runs about 17x faster than the single-file GeoJSON writer at 14M rows. It is the recommended writer for large output. `maxRecordsPerFile` caps the features per shard.

The FileGDB commit is the one single-file writer whose driver memory grows. GDAL's FileGDB writer keeps per-feature index state until the file closes. For the 14M polygons above, the driver's Python worker peaked at 1.9 GB of resident memory, about 120 bytes per feature. Size the driver for the feature count.

The format sets the limit, not GeoBrix. 14M box polygons sits near the Shapefile ceiling.

| Format | Ceiling | Cause |
|---|---|---|
| Shapefile | 2 GB per `.shp` or `.dbf` (about 15.8M box polygons) | 32-bit record offsets |
| GeoPackage | About 17.6 TB | SQLite `page_size × max_page_count` |
| FileGDB | 2.1 billion rows, 1 TB or more per feature class | OBJECTID is a signed 32-bit integer |
| GeoJSON | None (RFC 7946) | Text, bounded by disk and parse memory |

### Geometry-aware expansion at scale (`geomkring`, `geomkloop`) {#geomk-at-scale}

The geometry-aware functions grow grid rings outward from a geometry's covering set. This section shows how the output grows with the number of geometries *N* and the ring distance *k*. The inputs are synthetic building footprints. They come in five shapes (rectangle, L, U, courtyard with a hole, irregular) and three sizes (about 15, 50 and 200 m). They are scattered over a city-scale extent, so each building lands on its own cells.

> **Inputs:** `geomkring` and `geomkloop`, `boundary-out`. Target cell size about 65 m: H3 resolution 10, quadbin 19, custom 65 m root cell, BNG resolution 4 (100 m, the nearest BNG step). H3 and quadbin use WGS84. Custom and BNG use EPSG:27700. The figures are cell counts, which do not depend on the compute. No seconds are reported, because a Serverless job time depends on the workers it got.

**Headline.** 10,000 footprints, H3 resolution 10, `geomkring` with `boundary-out` and `k=10` produce 3,573,051 cells.

Cells across grids (10,000 buildings, `k=10`, `geomkring`):

| Grid | Resolution (about 65 m cell) | Cells |
|---|---|---|
| H3 | Resolution 10 | 3,573,051 |
| Custom | 65 m root (EPSG:27700) | 3,651,174 |
| Quadbin | Resolution 19 | 4,951,123 |
| BNG | Resolution 4 (100 m) | 4,762,643 |

H3 polyfill uses the C-backed `polygon_to_cells_experimental`, and its neighbor step is integer index math. Custom is a pure-Python lattice walk. Cell sizes and CRS differ per grid, so the cell counts differ.

| k | Ring cells | Loop cells |
|---|---|---|
| 1 | 113,181 | 84,430 |
| 5 | 1,050,901 | 324,430 |
| 10 | 3,573,051 | 624,430 |

The filled ring grows with about *k* squared. The hollow loop grows with about *k*. At *k*=10 the loop emits about 6x fewer cells.

| 1,000 | 357,031 |

### LiDAR and EXIF readers and the LiDAR writer {#lidar-exif-io}

The `lidar_gbx` (LAS and LAZ point clouds) and `exif_gbx` (image EXIF and GPS) readers have one implementation each. These are single-level spark-path timings: read cost per file (header-only `metadata`), per point (`lidar_gbx points`), and with pixel decode (`exif_gbx qc`). The `lidar_gbx` writer is timed in its two output modes.

> **Environment:** Databricks · DBR 18.x · classic (rd-fleet.xlarge) · synthetic corpus of 100 `.laz` files × 50,000 points and 100 JPEGs · median of the measured iterations after warmup. Run with `gbx:bench:cluster --benchmark-lidar --benchmark-exif`.

| Reader | Mode | Items | Median | Per item |
|---|---|---|---|---|
| `lidar_gbx` | `metadata` (header only) | 100 files | 0.84 s | 8.4 ms per file |
| `lidar_gbx` | `points` | 5,000,000 points | 1.09 s | About 0.22 µs per point |
| `exif_gbx` | `metadata` (header only) | 100 files | 0.79 s | 7.9 ms per file |
| `exif_gbx` | `qc` (decodes pixels) | 100 files | 1.66 s | 16.6 ms per file |

Header-only `metadata` is the fast path for both readers. `lidar_gbx points` streams point rows in Arrow batches, so 5 million points read in about 1.1 s. `exif_gbx qc` adds sharpness and brightness from the decoded image, at about twice the metadata cost.

| `lidar_gbx` writer mode | Points | Median |
|---|---|---|
| `parts` (one `.laz` per partition) | 5,000,000 | 6.3 s |
| `singleFile` (merged on the driver to one `.laz`) | 5,000,000 | 31.6 s |

`parts` is about 5x faster than `singleFile` at 5 million points, because `singleFile` funnels every partition through a driver merge. Use `parts` for large point clouds. Keep `singleFile` for small outputs that must land as one file.

### Land-cover classification (`rst_land_cover`) {#land-cover-bench}

`rst_land_cover` classifies a tile of three or more bands into per-pixel land-cover class IDs. It has one implementation, so these are absolute throughputs.

> **Environment:** Python level, pure-core, synthetic RGB tile, `n_clusters=6`, `smooth=3`, measured locally.

| Method | 256 by 256 (ms) | 512 by 512 (ms) | 1024 by 1024 (ms) | Throughput |
|---|---|---|---|---|
| `spectral` | 5.3 | 19.3 | 74.1 | About 14 Mpix/s |
| `hybrid` (default) | 64.6 | 276.6 | 1,238.7 | About 1 Mpix/s |

`spectral` is a fast threshold pass. It runs about 15x faster than the default `hybrid` at 1024 by 1024. `hybrid` adds a k-means refinement that improves class boundaries. Choose `spectral` for throughput and `hybrid` for class quality.

## Caveats

- Absolute timings depend on the machine, the corpus and the install. Treat the ratio and the consistency label as the durable signal.
- Pure-core isolates the algorithm. Spark-path adds the per-row overhead of the level and predicts end-to-end job cost better. Use spark-path to decide which level a workload should run at.
- Consistency is checked on output statistics with a tolerance, not on bytes. GDAL and NumPy can differ in the last bits. Neighborhood and NoData-boundary operations can differ on the one-pixel kernel border. The benchmark labels those `divergent` so they stay visible.
