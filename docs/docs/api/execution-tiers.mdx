# Surfaces and levels

GeoBrix has one function set. You choose a **surface**: where you call a function from. GeoBrix chooses the **level**: which implementation runs it.

You never pick a level. The compute decides, and GeoBrix says why when it falls back to another level.

## The four surfaces

| Surface | Form | Use it for | Runs on |
|---|---|---|---|
| **SQL (session)** | `gbx_*` after `register(spark)` | Notebooks, jobs and pipelines | Every compute except a SQL warehouse |
| **SQL (Unity Catalog)** | `<catalog>.<schema>.gbx_*` after `gbx.uc.install` | Warehouses, dashboards, governed and ad-hoc SQL | SQL warehouses, and any compute through a three-part name |
| **Python** | `rasterx`, `gridx.<grid>`, `vectorx`, `pmtiles` | DataFrame code, readers, writers and helpers | Every compute except a SQL warehouse |
| **Scala** | `com.databricks.labs.gbx.<package>.functions` | Scala code on a dedicated cluster | Dedicated clusters with the JAR |

A function has the same name on the SQL surfaces. The Python and Scala names drop the `gbx_` prefix.

Not every function exists on every surface. The [availability page](./availability) lists each function and the surfaces it runs on. Each function section shows the same badges.

A name that exists on both SQL surfaces takes the same arguments and gives the same result. Where a UC function differs, the [Unity Catalog page](./uc-functions) says how.

## One registrar

Call `register` once per session:

```python
from databricks.labs.gbx import register

register(spark)   # every gbx_* SQL function and every *_gbx reader and writer
```

- The call registers the functions and the lightweight data sources.
- The Python API also registers a function on its first call, so `register(spark)` is optional for Python-only code.
- Scala registers no SQL. A Scala caller relies on the Python call. See [Language bindings](./language-bindings).
- The old per-package `register` calls (`rasterx.functions.register` and the like) raise an error. The message gives the fix.

Pass `only=` to register a subset. Names are case-insensitive and take the SQL name or the short name.

```python
register(spark, only=["rst_slope", "rst_clip"])   # just these two
```

A name that no function matches raises a `ValueError`. `only=[]` registers nothing.

## The levels

A level is one implementation of a function. A function has one to four levels.

| Level | What runs | Where it is available |
|---|---|---|
| **L1** | JVM expression (Scala and GDAL) | Dedicated clusters with the GeoBrix JAR |
| **L3** | Python (rasterio, NumPy, Shapely and the other libraries named in each function's note) | Everywhere the env wheel installs: Serverless, standard, dedicated, Lakeflow pipelines and the UC sandbox |
| **L4** | Unity Catalog function | SQL warehouses, and any compute through a three-part name |

Every function has an L3 level, so the wheel alone runs the whole library. The JAR adds L1 where it is faster. The [Unity Catalog page](./uc-functions) covers L4.

## How GeoBrix picks a level

The wheel ships a table that lists, for each function, the levels to try and in what order. The order comes from measurements. Where a function has not been measured, GeoBrix tries the highest level first.

For each function, `register` takes the first level that works on this compute. It skips a level when the JAR is missing, when the session is Spark Connect, or when a library is absent.

Most functions run on L3. Raster tile operations default to L3, because the Python implementation measured as fast or faster, or because the JVM form cannot read a virtual tile. On a dedicated cluster with the JAR, GeoBrix picks L1 for these families:

- the BNG, custom-grid and H3 cell functions that have a JVM form, and the BNG explode, tessellate, `gbx_bng_kring` and `gbx_bng_cellfill` functions;
- `gbx_rst_frombands`, which is not measured yet;
- `gbx_rst_fromcontent` and `gbx_rst_bng_rasterize_agg`;
- the raster accessors that return one value (`gbx_rst_width`, `gbx_rst_height`, `gbx_rst_numbands`, `gbx_rst_srid`, `gbx_rst_crs`, `gbx_rst_format`, `gbx_rst_memsize`, `gbx_rst_boundingbox`, the pixel size, scale, skew, rotation and upper-left functions, and the single-axis coordinate functions). A virtual tile goes to the Python level, as described below;
- `gbx_rst_slope`, `gbx_st_triangulate`, `gbx_st_transformcrs` and `gbx_st_interpolateelevationbbox`.

### GeoBrix says why

When a faster level cannot run, `register` prints one line that names the level and the reason. A reason that applies to several functions prints once, with a count. Each line prints once per session.

```text
geobrix: heavy (Catalyst) unavailable: Spark Connect session (standard access mode)
```

`register` returns a dictionary of the level it chose for each name. Use it to check a session:

```python
chosen = register(spark)
chosen["gbx_bng_eastnorthasbng"].level   # 'L0' (SQL) or 'L3'
```

A name that no level can serve on this compute is skipped, with a line that says why. The other names still register.

### Test-only controls

`register` also takes `_levels` and `_prefer`. They force or favor a level so that tests can compare levels. Do not use them in a job. They carry no compatibility promise.

## Generators are table functions

A generator returns many rows for each input. Call it as a table function:

```sql
SELECT gbx_out.*
FROM my_cells AS t, LATERAL gbx_bng_kringexplode(t.cellid, 1) AS gbx_out
```

This form works at every default level. The select-list form (`SELECT gbx_...(args)`) and `LATERAL VIEW` work only when you force the JVM level (L1) on a dedicated cluster. The Catalyst generator resolves there and a Python table function does not. Use the `FROM t, LATERAL` form unless you force L1.

## Where the JAR helps

Install the JAR only when you want the JVM level on a dedicated cluster. The wheel works alone everywhere.

- Dedicated clusters can use the env wheel and the JAR as cluster libraries, or a [DCS image](../installation/dcs.mdx). See [Choose an install path](../installation.mdx#choose-an-install-path).
- `databricks.labs.gbx.stage_jar(vol_dir)` copies the wheel's JAR to a Volume folder.
- A cluster runs one GeoBrix JAR. `stage_jar` refuses a second JAR in the same Volume folder, with a fix.
- Serverless cannot load the JAR, so it runs L3 and L4. A SQL warehouse runs L4 only.

For measured differences between levels, see [Performance & Benchmarking](./performance).

## Virtual tiles and the JVM level {#light-heavy-bridge}

A virtual tile has no raster bytes. It holds a path and a window, and a Python worker reads it lazily. A materialized tile carries the encoded raster in its `raster` field. See [Virtual tiles](./virtual-tiles).

The JVM level reads bytes only. In SQL, GeoBrix routes the two kinds for you:

- A virtual tile goes to the Python implementation.
- A materialized tile goes to the JVM implementation, when the JVM level is the chosen one.
- An error tile comes out unchanged at every level.

The accessors and statistics that return an `ARRAY<...>`, a `MAP<...>` or a `STRUCT<...>` (`gbx_rst_avg`, `gbx_rst_georeference` and the like) have no JVM form and run at the Python level. Such a function can sit under `explode` or `inline`, where Spark refuses the SQL function that does the routing.

A few functions run on the JVM level without that routing when you force L1 (`gbx_rst_contour`, `gbx_rst_isoband`). A virtual tile raises an error there. To use one, materialize the tile first: pass `materialize=True`, or write with a raster writer and read the output back. Every writer is a materialization boundary.

The Python tile functions take three optional keywords: `virtualize_dir`, `virtualize_prefix` and `materialize`. SQL has none of them. See the [force-output parameters](./raster-functions#virtual-tile-overrides).

### Virtual and materialized advice {#virtual-materialized-advice}

Ask which operations need pixels and which can stay lazy.

| Operation type | Behavior on a virtual tile | Notes |
|---|---|---|
| **Metadata accessors** (`rst_width`, `rst_height`, `rst_srid`, `rst_boundingbox`, `rst_format`, `rst_georeference`, `rst_metadata`, `rst_rotation`, `rst_scalex`, `rst_scaley`, `rst_skewx`, `rst_skewy`, `rst_numbands`, `rst_type`, `rst_getnodata`, `rst_upperleftx`, `rst_upperlefty`) | Free. No pixels are read | The header opens lazily |
| **Pixel accessors and statistics** (`rst_avg`, `rst_min`, `rst_max`, `rst_median`, `rst_pixelcount`, `rst_summary`, `rst_histogram`, `rst_sample`, `rst_isempty`) | Read the window, then return a scalar or array | Pixels are held only for the computation |
| **Reference and passthrough operations** (`rst_clip`, `rst_setsrid`, `rst_initnodata`, `rst_band`, and `rst_transform` to the tile's own CRS) | Record an instruction or a region. No new pixels | The instruction applies at the next read. `virtualize_dir` has no effect |
| **Pixel-producing operations** (slope, aspect, hillshade, terrain, focal, map algebra, spectral indices, rasterize, resample, `rst_transform` to another CRS, `rst_merge`, `rst_combineavg`, `rst_frombands`) | Materialize and return bytes | Pass `virtualize_dir` to write the result to a durable path and get a virtual tile |
| **Writers** (`raster_gbx`, `gtiff_gbx`, `cog_gbx`) | Always materialize | A virtual DataFrame is directly writable. `cog_gbx` converts whole-file virtual tiles path-direct |

**Short rule:** chain deferrable operations as long as you like. Materialize when you need pixels.
