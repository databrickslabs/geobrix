Complete reference for all GridX discrete-global-grid functions — CARTO Quadbin v0 and British National Grid (BNG).

## Overview

GridX is GeoBrix's discrete-global-grid indexing package. It ships **CARTO quadbin v0** for web-mercator-aligned global indexing, **British National Grid (BNG)** for Great Britain workloads, and **custom user-defined grids**. It pairs with the product's native H3 for global hex indexing.

- **Quadbin (CARTO v0)** — a global zoom-indexed tile addressing scheme aligned with web-mercator slippy maps, compatible with CARTO's CDB_QuadKey IDs. Cell `(z, x, y)` coordinates align with the same XYZ tile grid that PMTiles / MVT readers consume — natural for slippy-map heatmaps and global analytics.
- **BNG (British National Grid)** — the Ordnance Survey National Grid (OSGB36) used in Great Britain for spatial indexing and location-based services. Specialized for UK-based spatial data.
- **Custom user-defined grids** — define a regional or equal-area grid and get cell math, polyfill, and tessellation on it.

:::note Import paths
- Quadbin: `databricks.labs.gbx.gridx.quadbin`
- BNG: `databricks.labs.gbx.gridx.bng`
- Custom grids: `databricks.labs.gbx.gridx.custom`
- H3: `databricks.labs.gbx.gridx.h3`
- Helpers: `databricks.labs.gbx.gridx.helpers`

Scala has the BNG functions in `com.databricks.labs.gbx.gridx.bng`. For other names, use `call_function("gbx_...", ...)`. One call registers all grids: `register(spark)`.
:::

## Key Features

- **Grid Cell Operations**: Create, manipulate, and query BNG grid cells
- **Area Calculations**: Calculate areas of grid cells at different precisions (returns square kilometres)
- **Coordinate Conversion**: Convert between grid references and coordinates
- **Spatial Indexing**: Use BNG or quadbin for efficient spatial indexing
- **Multi-Resolution Support**: Work with different grid resolutions (BNG: 1–6 integer indices; Quadbin: zoom 0..26)
- **K-Ring / K-Loop Neighbourhoods**: Filled rings and hollow rings for both grid systems
- **Polyfill and Tessellation**: Cover geometries with cells; tessellation returns per-cell clipped chip geometries
- **Custom Grids**: Define your own regional or equal-area grid systems (cell math, polyfill, tessellation)

:::note Coordinate reference systems
GridX functions operate in their grid's fixed native CRS and do not take an explicit CRS parameter for cell operations. **BNG** (`gbx_bng_*`) functions work in EPSG:27700 (OSGB36); output geometries are plain WKB in EPSG:27700 — assign the SRID when reading them back (e.g. `ST_GeomFromWKB(bng_geom, 27700)`). **H3** and **quadbin** functions work in EPSG:4326 (WGS84 lon/lat). Raster-to-grid functions (`gbx_rst_*_rastertogrid*`) auto-reproject the input raster to the grid's native CRS when the raster carries a different CRS. See [Coordinate reference systems](./coordinate-reference-systems) for the full CRS model.
:::

## Setup {#setup}

With GeoBrix already [installed](../installation), register the functions once per session. One call registers every GridX grid:

```python
from databricks.labs.gbx import register

register(spark)  # every gbx_bng_*, gbx_quadbin_*, gbx_custom_* and gbx_h3_* SQL function
```

The Python API also registers a function on its first call.

The tabs operate on the **same input fixture** with the **same arguments**. Where the output differs in form, the affected tab carries a labeled `:::note`. A difference without a label is a documentation error.

In each Python example, `df = spark.table("<view>")` or an equivalent inline `spark.sql(...)` call loads the canonical fixture. Each SQL example reads `FROM <view>` or uses an inline literal — no separate `CREATE TEMP VIEW` step is shown.

### Output representation

The output cells in every function table follow a uniform convention so readers can compare tabs at a glance.

**Cell-id strings** — BNG cell-ids (e.g. `'TQ3080'`) and quadbin cells (e.g. `5233961839712272383`) are shown in full when short.

**Binary geometry ([E]WKB)** — geometry returned as `BINARY` is elided with one token and a format annotation. Use `(WKB binary)` when no SRID is embedded; `(EWKB binary)` when an SRID is embedded (quadbin functions embed SRID 4326):

```
... (WKB binary)
... (EWKB binary)
```

**WKT strings** — short WKT strings are shown in full; longer strings are truncated with a type annotation:

```
POLYGON ((530000 180000, ...))
POLYGON (... (WKT)
```

**Cell-id arrays** — arrays of cell-ids show the first few entries followed by `...` when the array is long:

```
['TQ2979', 'TQ2980', 'TQ2981', ..., 'TQ3181']   (9 cells)
```

**Doubles / numeric scalars** — shown as the real value (e.g. `1.0` for `bng_cellarea`).

**Cell width** — output cells are capped at approximately 60 characters. A longer value is truncated with `...` and annotated with its type.

**Identical values** — when all tabs produce the same result (e.g. `'TQ3080'` from `bng_pointascell`), each tab shows that value identically with the same annotation. Real differences are called out in a labeled `:::note`.

### BNG domain rules

The following rules apply to **all BNG functions** (`gbx_bng_*`):

- **Coordinate system** — BNG geometry inputs (points and polygons) must be in **EPSG:27700** eastings/northings. WGS84 lon/lat coordinates (e.g. `POINT(-0.1278 51.5074)`) yield **empty arrays or null results** — this is the most common source of confusion.
- **Resolution** — accepts **integer indices ±1..±6** **or** string keys from the resolution map (e.g. `'1km'`, `'100m'`, `'10m'`). The indices are 1 = 100km, 2 = 10km, 3 = 1km, 4 = 100m, 5 = 10m, 6 = 1m, and negative values are quadrants. **Never** pass metres-as-integer (e.g. `1000`) — that interpretation is not supported by `BNG.getResolution` and raises an error.
- **`bng_cellarea` returns square kilometres** — not square metres. A 1km cell returns `1.0`.
- **Cell-id format** — standard BNG grid references (e.g. `'TQ3080'`). At resolution 3 (1km), the format is two letters + four digits; the resolution level is encoded in the string length.

### Explode generators

The explode functions return one row per cell. They are table functions: call them in the `FROM` clause with `LATERAL`, at every implementation level.

```sql
SELECT t.*
FROM (SELECT 'TQ3080' AS cell, 1 AS k) src,
LATERAL gbx_bng_kringexplode(src.cell, src.k) t
```

The Python entry takes the input DataFrame first and returns it joined with the generated rows:

```python
from databricks.labs.gbx.gridx.bng import functions as bx

bx.bng_kringexplode(df, "cell", 1)  # one row per cell, beside the input columns
```

The cell ids stay `BIGINT` (quadbin, custom grid, H3) or `STRING` (BNG) end to end. A NULL argument and a geometry that cannot be read give no rows. A resolution the grid does not define, or an unknown `mode`, raises and names the value.

## Quadbin (CARTO v0)

Quadbin runs on the Python level, with identical `gbx_quadbin_*` SQL names on every compute. It uses the **quadbin** library and shapely. Geometry outputs are EWKB with SRID 4326.

GeoBrix v0.4.0 adds a `gridx/quadbin` subpackage implementing the [CARTO quadbin v0](https://github.com/CartoDB/quadbin) 64-bit packed `(z, x, y)` tile encoding used by Snowflake, dbt, Felt, and CARTO. Coordinates are EPSG:4326 lon/lat on the user-facing API; cells are encoded as web-mercator XYZ tiles internally. Resolutions range from `0` (whole world) to `26` (sub-metre).

:::note Registration
Quadbin functions are under **gridx.quadbin**, independent of `gridx.bng`. `register(spark)` installs the `gbx_quadbin_*` SQL functions.
:::

CARTO Quadbin v0 cells encode `(z, x, y)` web-mercator tile coordinates as a single `BIGINT`. Cell IDs are interoperable with CARTO's CDB_QuadKey and align with the slippy-map tile grid used by `gbx_rst_xyzpyramid` and `gbx_st_asmvt_pyramid`.

Resolution (zoom) range:
- `gbx_quadbin_pointascell`, `gbx_quadbin_resolution`, `gbx_quadbin_kring`, `gbx_quadbin_distance` accept zoom `0..26`.
- `gbx_quadbin_polyfill` and `gbx_quadbin_tessellate` accept zoom `0..20`.

### Geometry-Aware Expansion (Quadbin)

Geometry-aware functions polyfill a geometry into the grid and then expand outward (or inward at holes) using the dilation engine. They generalise the cell-centric `quadbin_kring` / `quadbin_kloop` to operate on arbitrary geometry shapes — polygons (with holes), lines, and points. The optional `mode` parameter selects the expansion direction and hole handling; the optional `coverage` parameter (after `mode`) selects how a cell is judged to belong to a region. This section is the canonical description; the BNG, custom, and H3 geometry-aware functions share the same `mode`/`coverage` contract.

#### Dilation modes {#dilation-modes}

The `mode` argument (**default `'boundary-out'`**) takes one of these exact hyphenated values — each produces a `k`-thick band; polygon holes are handled only by the `hole-*` modes, never by `boundary-*`:

| Mode | Behaviour |
|------|-----------|
| `'boundary-out'` | Default. The geometry's **boundary band** (`k=0`) plus the outward band — cells within `k` steps **outside** the boundary; the fully-interior cells are excluded. `k=0` follows the coverage: `coveras`/`core` = the whole straddling band, `polyfill` = the centroid-outside cells. The outward `k≥1` rings are identical across coverages. Works on aligned and non-aligned geometries alike. |
| `'boundary-in'` | Inward setback band from the outer boundary, stopping at holes. |
| `'boundary-in-ignore-holes'` | Like `'boundary-in'` but treats the polygon as solid — the band can cross holes. |
| `'hole-in'` | Fills each hole inward from its edge. |
| `'hole-out'` | Band in the solid around each hole, bounded by the outer geometry. |
| `'hole-out-ignore-geom'` | Band outward from each hole, not bounded by the outer geometry. |

#### Coverage {#coverage}

The `coverage` argument (**default `'coveras'`**) takes one of these exact values — it selects how a cell is judged to belong to a region:

| Coverage | A cell belongs to a region if it… |
|------|-----------|
| `'coveras'` | **Default.** …*overlaps* the region (inclusive; boundary cells kept — no false negatives). |
| `'polyfill'` | …has its *centre* inside the region (standard polyfill). |
| `'core'` | …is *entirely* inside the region (strictest; no false positives). |

Nesting: `coveras ⊇ polyfill ⊇ core`. Point and line geometries are covered only under `'coveras'`. They have no cell whose centre is inside them or that fully contains them, so `'polyfill'`/`'core'` return empty for them.

## British National Grid (BNG)

BNG runs on every compute with identical `gbx_bng_*` SQL names. The Python level is a **pure-Python port of `BNG.scala`** plus **shapely**. Cell IDs are `STRING` references. Geometry outputs are plain WKB in **EPSG:27700** coordinates with **no SRID**, unlike quadbin's EWKB SRID 4326. Cell-id math has exact parity with the JVM level.

The British National Grid is the national coordinate system for Great Britain, based on the Ordnance Survey National Grid (OSGB36). It divides Great Britain into grid squares identified by letter-based prefixes and numeric coordinates.

### BNG Structure

- **Grid Squares**: 100km x 100km squares identified by two letters (e.g., "TQ" for London, "NT" for Edinburgh)
- **Eastings and Northings**: Numeric coordinates within each grid square (EPSG:27700)
- **Resolution Indices**: Integer indices 1..6 (1=100km, 2=10km, 3=1km, 4=100m, 5=10m, 6=1m); negative indices select quadrant sub-cells. String keys (e.g. `"1km"`, `"100m"`) are also accepted via `BNG.resolutionMap`.

### BNG Grid Reference Format

BNG references follow the format: `[Letters][Eastings][Northings]`

Examples:
- `TQ 38 80` — 1km precision (Tower of London area)
- `TQ 3800 8000` — 100m precision
- `TQ 38000 80000` — 10m precision
- `SU 12 34` — Different grid square

### Precision Levels

| Precision | Grid Size | Example | Use Case |
|-----------|-----------|---------|----------|
| 100000m | 100km x 100km | TQ | Regional analysis |
| 10000m | 10km x 10km | TQ38 | District-level |
| 1000m | 1km x 1km | TQ3080 | Local area analysis |
| 100m | 100m x 100m | TQ308808 | Neighborhood level |
| 10m | 10m x 10m | TQ30808080 | Building level |
| 1m | 1m x 1m | TQ3080080800 | Precise location |

### Major Grid Squares

Major 100km grid squares in Great Britain:
- **TQ** — London area
- **SU** — South Hampshire
- **NT** — Edinburgh area
- **SD** — Lake District
- **ST** — Bristol area

## Custom Grid Functions

Custom-grid functions run on every compute with identical `gbx_custom_*` SQL names. The Python level is a **pure-Python port of the custom-grid system** plus **shapely**. It needs no external grid library. Cell IDs are `BIGINT` values. Geometry outputs are plain WKB with **no SRID**, and the grid's `srid` is metadata only. Geometry inputs accept **WKB, EWKB, WKT, or EWKT**. Cell sets have exact parity with the JVM level. `gbx_custom_grid` returns the same descriptor struct at every level.

A custom grid is a user-defined regular rectangular grid specified by its spatial extent, root cell size, and a recursive split factor. Cell IDs are `BIGINT` values; hierarchy is controlled by `cell_splits` (each level subdivides root cells into `cell_splits x cell_splits` sub-cells). Use custom grids when neither BNG nor quadbin matches your coordinate reference system or cell-size requirements. An example is a national grid in EPSG:27700 with non-standard tile sizes.

## H3 Geometry-Aware Expansion (Python Level Only)

H3 geometry-aware kring/kloop run on the Python level only. They have no JVM implementation. They work like the other grids: one **geometry-taking** function does the whole job in pure Python with the `h3` library. It uses the `polygon_to_cells_experimental` polyfill for the covering set and `grid_disk` for the neighbour walk. They run on every compute, and SQL and PySpark call them the same way:

```python
from databricks.labs.gbx import register
from databricks.labs.gbx.gridx.h3 import functions as hx

register(spark)
df.withColumn("kring", hx.h3_geomkring("geom_col", 9, 1))
```

**Dilation modes** work the same as for BNG/quadbin/custom, and all six operate on holed geometries. The modes `'hole-in'`, `'hole-out'`, and `'hole-out-ignore-geom'` expand from the geometry's holes. The mode `'boundary-in-ignore-holes'` treats the polygon as solid, expanding inward across holes as if they were filled.

## H3 Viewshed (Python Helper)

:::note Python helper only
`h3_viewshed_towers` is **not registered as a SQL function**. It is a PySpark DataFrame function in `databricks.labs.gbx.gridx.helpers`. It runs on Serverless and needs no JAR.
:::

### h3_viewshed_towers

`h3_viewshed_towers` runs a per-tower line-of-sight viewshed entirely in H3 cell space and
returns one row per `(tower, visible cell)`. It is the H3-native sibling of the raster
`rst_viewshed_towers`. For each tower it tests the in-buffer H3 cells with the exact
`h3_los_visible` line of sight. The blocker is the surface map (DSM, or DSM + canopy). The
observer sits at the tower-top absolute elevation. Each target receiver is the ground
(DTM) elevation plus `target_height`. The two surface/ground maps are collected once to the
driver (bounded at `viewshed_res`). The per-tower work is fanned one-tower-per-task with
`mapInPandas` over the towers frame repartitioned by `tower_id_col`. The same code path
therefore runs on Databricks Serverless and on classic clusters. This is the mechanism that lets the Wireless
Coverage tower siting scale across Spark. H3 cell ids flow as `BIGINT` (the integer H3
representation) in every column, matching the Databricks product H3 convention.

**Signature:**
```python
from databricks.labs.gbx.gridx.helpers import h3_viewshed_towers

result_df = h3_viewshed_towers(
    towers_df, surface_df, ground_df,
    radius_m=2500, viewshed_res=12, target_height=1.6,
    tower_id_col="tower_cellid", observer_z_col="observer_z",
    cell_col="cellid", surface_z_col="z", ground_z_col="z",
    num_partitions=None,
)
```

**Parameters:**

- `towers_df` — DataFrame of towers; must carry `tower_id_col` (`BIGINT` H3 cell) and
  `observer_z_col` (observer-top absolute elevation in metres, e.g. DTM at the tower plus the
  mast height).
- `surface_df` — blocker-surface (DSM, or DSM + canopy) map at `viewshed_res`; must carry
  `cell_col` (`BIGINT` H3 cell) and `surface_z_col` (metres). A missing or NULL surface is
  transparent (no blocker at that cell).
- `ground_df` — bare-earth (DTM) map at `viewshed_res`; must carry `cell_col` and
  `ground_z_col` (metres). A target whose ground is NULL or missing is skipped, not fabricated.
- `radius_m` — analysis radius in metres (> 0); sizes the per-tower H3 `grid_disk` buffer. The
  line of sight is still bounded by the surface/ground maps.
- `viewshed_res` — H3 resolution of the surface/ground maps and the output cells.
- `target_height` — receiver height above the ground at each tested cell, in metres; defaults
  to `1.6`.
- `tower_id_col` / `observer_z_col` — tower identity and observer-elevation column names;
  defaults `"tower_cellid"` / `"observer_z"`.
- `cell_col` — cell-id column shared by `surface_df` / `ground_df`; defaults `"cellid"`.
- `surface_z_col` / `ground_z_col` — elevation column names of the two maps; both default to
  `"z"`.
- `num_partitions` — fan-out for the per-tower stage (`repartition` by `tower_id_col`); defaults
  to the distinct tower count (~one tower per task).

**Returns:** DataFrame with one row per `(tower, visible cell)`: `tower_id_col` (`BIGINT`) and
`cell_col` (`BIGINT` H3 cell visible from the tower top).
