# Performance

GeoBrix picks the implementation level for each function. You do not choose a level. The compute decides, and GeoBrix says why when it falls back to another level.

This page has two parts. The first part lists what 0.6.0 streamlined. The second part shows how each level performs, by function family. The later sections cover reads from virtual tiles and how the Python functions run on Spark.

For the method behind the numbers, see [Benchmarking](./benchmarking). For where each function runs, see [Availability by surface](./availability).

## What 0.6.0 streamlined

Each item below has the measurement behind it. The [release notes](../release-notes-0-6) list the breaking changes.

- **Readers and writers.** Python everywhere. The Scala readers and writers are retired because the bytes-free Python path was faster.
- **Raster tile functions.** The Python implementation is the default. A JVM companion stays only where it measured at least 1.2x faster on a dedicated cluster. `gbx_rst_gridfrompoints` lost its JVM form, because it measured slower.
- **Grid functions.** The JVM (Catalyst) form stays for BNG tessellate, the BNG explodes, `gbx_bng_kring` and `gbx_bng_cellfill`, where it measured at least 1.2x faster. `gbx_bng_eastnorthasbng` lost its JVM form, because the Python batch form is faster. The other grids use the Python form.
- **Aggregates and generators.** Each compute has its own route. [Aggregates by compute](#aggregates-by-compute) lists them.
- **Rust.** A compute kernel is used only where it measured clearly faster than the Python form. Today that is `gbx_bng_eastnorthasbng` and the triangulation of the TIN functions.
- **SQL registration.** One registrar, written in Python. `register(spark)` installs every function, and the compute chooses the level.

## Performance by level

GeoBrix has three levels, named by what you install.

| Level | What you install | Where it runs |
|---|---|---|
| Light | The env wheel. No JAR. | Serverless, standard, dedicated, and a SQL warehouse through Unity Catalog Python functions |
| Heavy | The env wheel and the GeoBrix JAR | Dedicated clusters. Standard access mode only where a Java handler exists. |
| UC functions | `gbx.uc.install` | SQL warehouses and any compute that reads Unity Catalog |

GeoBrix keeps a heavy level only where it is at least 1.2x faster than the best light form. The test runs on a dedicated cluster at 4x or 16x the base row count, and the output must decode the same. The JAR then makes the heavy level the default. A function with no measurement yet runs at the light level, except a few. [Functions the JAR speeds up](./jar-functions) lists every function that runs the heavy level by default.

Every function not on that page runs at the light level. Compare times within one compute only. A Serverless time describes per-task behavior, not speed against a fixed cluster.

### UC functions

A Unity Catalog function runs on a SQL warehouse or any compute that reads the catalog. The [Unity Catalog functions](./uc-functions) page lists the functions and how to install them.

- **Without the JAR.** Each function is a Unity Catalog Python function.
- **With the JAR.** `gbx_bng_kring`, `gbx_bng_aswkb` and `gbx_bng_centroid` run as Unity Catalog Scala functions when the install folder holds the JAR of this wheel. They are verified on a SQL warehouse.

A Scala function that needs GDAL is not proven on Unity Catalog. GeoBrix does not offer GDAL raster functions on Unity Catalog with the JAR.

{/* refresh: the measured performance matrix */}

| Measure | Result |
|---|---|
| Cost of an empty statement (`SELECT 1`) | 0.53 to 0.63 s |
| One Python function call over 1 million rows | About 10.3 to 11 s per statement (median) |
| Same function, Python against Scala, 1 million rows | 15.4 s against 10.7 s |
| Scala BNG function at environment version 6, X-Small PRO warehouse | 11.2 to 11.6 s per 1 million rows |
| Aggregate that collects tiles in the function | Passes with 10 tiles of 512 by 512 (4.2 MB each). 50 tiles fail with out-of-memory. |

The first three rows come from separate runs. Do not subtract one from another.

Unity Catalog functions refuse input they cannot read correctly, and each refusal carries a `Fix:` line.

- A geometry whose SRID does not match the function: BNG functions need 27700, and quadbin and H3 functions need 4326.
- A `BINARY` value passed where a `GEOMETRY` is expected. Use `st_geomfromwkb(wkb, srid)`.
- A CRS in a form other than an integer SRID, `EPSG:<n>` or `ESRI:<n>`.

Data that a function cannot serve gives `NULL`. The session raises an error for some of the same data. For example, `gbx_quadbin_polyfill` raises in a session when the polygon needs more than 1,000,000 cells, and gives `NULL` on Unity Catalog.

Raw files do not reach Unity Catalog through functions. Read them with a session reader, write a Delta table, and query the table.

### Grouped merge and combine

The aggregates `gbx_rst_merge_agg` and `gbx_rst_combineavg_agg` stream their group under the worker read cap. The cap is 64 MiB on Serverless and 256 MiB on classic compute.

- **A result over the cap refuses.** The error carries the VRT-mosaic `Fix:`. Keep the tiles as files on a Volume. Build the mosaic with `rasterx.helpers.mint_vrt`, or use the `cog_gbx` writer in mosaic mode. Then read the VRT.
- **Members that do not fit in memory.** Pass virtual tiles (the readers' default): they merge as files, whatever the group size. Tiles with bytes must fit the task, or use `merge_by_key`, which keeps them in scratch files.
- **Members on different CRS or pixel size.** Bring them to one grid first with `gbx_rst_transform` and `gbx_rst_resample_to_res`.
- **A combine over the cap.** Retile first with `gbx_rst_retile`, or use `combine_by_key`.

The array form, `gbx_rst_combineavg(collect_list(tile))` and the six other `gbx_rst_combine*` functions, receives a whole group as one row. The rows cross to Python as Arrow batches, so the executor's JVM heap does not hold the tiles. A task still holds every group of its shuffle partition at once. That is the encoded tiles in the batch, plus a few times their size in Python. With large groups (tens of MB per tile, many groups per task), use one of two routes. On a classic cluster, give the shuffle more partitions. Or use `combine_by_key` (`avg` or `max`), which reads a key's tiles one at a time. Serverless fixes the shuffle width, so use `combine_by_key` or retile there.

`combine_by_key` and `merge_by_key` (in `rasterx.helpers`) shuffle by key and fold each group once. `merge_by_key` hands each tile to the merge as it arrives, so a key's memory does not follow its tile count. It shuffles with `repartition(N, keys)`, where `N` is `num_partitions` or the session's task slots (at least 64). At 1,000 groups on dedicated compute:

{/* refresh: the measured performance matrix */}

| Route | Merge | Combine |
|---|---|---|
| Helper (`merge_by_key`, `combine_by_key`) | 48.2 s | 59.7 s |
| Light aggregate | 67.9 s | 129.6 s |
| JVM aggregate | 96.3 s | 62.5 s |

These times were measured before the light aggregates streamed their groups, and before `merge_by_key` stopped holding its groups. The helper's peak execution memory was 40.3 GB for the merge, against 7.4 GB for the light aggregate. On Serverless, `merge_by_key(method="vrt")` finished 1,000 groups in 28 minutes, before the shuffle had a fixed width. The streamed aggregates and the new shuffle are not yet measured there.

`retile_virtual` is not the large-raster path. It ran 1.16x slower than the plain retile on a dedicated cluster (58.4 s against 50.4 s) and ran out of memory on Serverless.

The scalar twins serve the finalize route for rasterize on every compute. A twin takes the whole group as one array, `ARRAY<STRUCT<cellid, value>>`, for example `collect_list(struct(cellid, value))`. | Scalar twin | Aggregate it matches | Cell ids |
|---|---|---|
| `gbx_rst_bng_rasterize` | `gbx_rst_bng_rasterize_agg` | `STRING`, for example `'TQ3080'` |

A twin holds the group in one value. Use it for a group that is already collected. Do not use it for a group of millions of cells.

For large groups, two table functions stream the group one row at a time. They read `TABLE(...) PARTITION BY (key)`:

- `gbx_rst_merge_tvf` merges each key's tiles into one mosaic.
- `gbx_rst_bng_rasterize_tvf` burns each key's BNG cells onto one canvas.

Both need less memory than the grouped aggregate and produce the same pixels. Neither runs on Serverless, whose table-function engine fails `PARTITION BY` once a task holds more than one row: call the aggregate there. A key whose mosaic is too large to build raises with the VRT-mosaic `Fix:`.

Some aggregates have no twin. They are session aggregates, called with `GROUP BY`:

- `gbx_bng_cellunion_agg` and `gbx_bng_cellintersection_agg`, whose scalar names are two-argument chip functions.
- `gbx_h3_cellfill`, `gbx_quadbin_cellfill`, `gbx_bng_cellfill`, `gbx_custom_cellfill`, `gbx_st_asmvt` and `gbx_st_coverage*`.
- `gbx_pmtiles_agg`, whose archive can reach 100 MiB.

### Generators in SQL

On every compute a generator is a table function. Call it with `LATERAL`:

```sql
SELECT z, x, y, tile
FROM   your_table,
LATERAL gbx_rst_h3_rastertogridavg(tile, 8);   -- one row per H3 cell at resolution 8
```

## Virtual tile read performance {#virtual-tile-read-performance}

:::note Key takeaways
- **Deferred edits run 1.5–12× faster on virtual tiles** — metadata operations (set-CRS/SRID/nodata/band-select) complete without pixel I/O. Chain several deferred edits before a terminal step to materialize once and pay pixel cost only at the end.
- **Open amortization is the lever** — grouping same-source windows (via `ORDER BY path` or repartitioning) cuts per-tile open cost from ~multiple-seconds to ~2 ms per window. Without amortization (per-tile-open), stream reads grow expensive with file size; FUSE becomes viable.
- **FILE-on ≈ FILE-off for reads on dedicated clusters** — FILE is a governance/access mechanism, not a per-tile read optimization. Amortization (grouped executor) is the performance lever. FILE is available on Serverless too, in a workspace with the File type preview.
- **COG + amortization beats FUSE** — byte-range stream reads are 10–290× faster than FUSE for windowed COGs when opens are amortized. Choose COG format and group by source path for best throughput.
:::

Virtual tiles are read on demand. Reading cost is dominated by **opening** the source raster, not by the pixel read itself. A pipeline that reads many tiles from the same source raster should open that source once. It should amortize the cost across all its windows, not open the source once per tile.

### Two access modes: stream and FUSE

GeoBrix's virtual tile reader supports two access modes:

| Mode | Per-open cost | Typical per-window cost | Memory per open source | Best for |
|---|---|---|---|---|
| **Byte-range stream** (`.open()`) | Scales with file size and layout | ~2 ms (COG, with amortization) | **RAM ≈ source file size** | Grouped reads on small-to-moderate files |
| **FUSE** (`.as_local_file()`) | Flat ~7 ms at any size | ~124 ms (cold read baseline) | Low — reads only requested bytes lazily | Large files, per-tile-open, RAM-constrained workers |

When the open cost is amortized across multiple windows from the same source, byte-range stream reads are **10–290× faster** than FUSE for windowed COG reads. Without amortization (one open per tile), FUSE's flat open cost wins: stream's per-open header parse grows with file size and becomes prohibitive at scale.

**You don't choose stream vs FUSE — GeoBrix does, automatically, per source.** The reader inspects each source's size and layout and picks the access mode that's correct for it. This table is what GeoBrix does for you, not a decision you make:

| Source (per file) | GeoBrix auto-selects | Why |
|---|---|---|
| Tiled / COG, ≤ 256 MiB | **byte-range stream** | random-window reads are efficient on a tiled layout; the source buffers into executor RAM |
| Large (over 256 MiB) **or** striped | **FUSE (lazy)** | fetches only the bytes each window needs — no whole-file RAM, safe at any size |
| stream **or** FUSE open fails | **staging fallback** (temp file) | correctness over speed |

The 256 MiB stream cutoff (`GBX_STREAM_MAX_BYTES`) is an optional environment override — the default handles the common cases, so you normally set nothing.

**Executor RAM is auto-managed by a byte-budgeted LRU cache — you don't size or clear it.** Open sources are held in a per-partition LRU keyed by source path, capped at a byte budget (`GBX_LRU_MAX_BYTES`, default 4 GiB). Stream handles count their buffered size against the budget; FUSE handles count only a small nominal (they don't buffer the file). When the budget would be exceeded, the least-recently-used source is evicted and closed. So a partition **never blows executor RAM no matter how many sources it touches**. Repeated windows from an already-open source are ~2 ms cache hits (the amortization in the next section).

:::note Why the auto-rules look the way they do — the striped-file trap GeoBrix sidesteps
Opening a large source via byte-range buffers it into executor RAM. For a **large striped GeoTIFF**, parsing the strip-offset table over byte-range can reach **47–54 seconds per open at 10 GB**. The open consumes **10 GB of executor RAM**. That is exactly why GeoBrix routes large or striped sources to FUSE (lazy, low-RAM) automatically rather than streaming them. For best windowed-read throughput, **prefer COGs** — a tiled COG under the threshold takes the fast stream path and amortizes across its windows.
:::

### Sidecar files and folder listings

When GDAL opens a raster it looks for the raster's sidecar files: external overviews (`.ovr`), masks (`.msk`), `.aux.xml` metadata and world files (`.tfw`, `.wld`). By default it lists the whole folder to find them, at every open. On a Volume that listing gets slower the more files share the folder. For a folder of 745 GeoTIFFs on a Serverless worker it took from 0.3 s to 10 s per open in our runs. It took about 2 s for 5,000 files and about 14.5 s for 40,000. Checking each sidecar by name instead (GDAL's `GDAL_DISABLE_READDIR_ON_OPEN=TRUE`, 5 to 7 names an open) costs about as much as a small listing. That is because a check for a file that does not exist is slow too. Unlike the listing, the cost does not grow with the folder.

The lightweight implementation lists a folder once per Python worker. It lists the folder when the worker opens a second, different file of it. A folder where the worker opens only one file, however often, is never listed. From then on the worker uses the listing to decide, for each open, where GDAL looks:

- **No file in the folder can be a sidecar of this one.** **The file is also a GeoTIFF, PNG, JPEG, JPEG 2000, netCDF, HDF or GRIB file** (`.tif`, `.tiff`, `.png`, `.jpg`, `.jpeg`, `.jp2`, `.nc`, `.h5`, `.he5`, `.hdf`, `.grib`, `.grb`, `.grb2`, `.grib2`, in any case). GDAL then looks for none. On a Serverless worker an open of a fresh file in the 745-file folder took a median of about 165 ms this way. The same open took about 415 ms with the checks by name.
- **The file has sidecars GDAL finds by name** (for example `x.tif.ovr`, `x.tif.aux.xml`, `x.tfw`): GDAL checks the names.
- **Anything else.** This includes a sidecar whose name mixes case, such as `x.Tfw`. It also includes another file with the same name and a different extension. It also includes a vendor metadata file such as `METADATA.DIM` or `*_MTL.txt` in the folder. In these cases GDAL lists the folder itself and matches names in any case, as it does by default.
- **A file of any other kind** has its sidecars checked by name. This covers a VRT (also one named `.xml`), a GDAL tile index, a `.SAFE`, `.json` or HFA `.img` dataset, a `.zarr`, or an unknown extension. Such a file may open other files that have sidecars of their own.

Before a folder is listed, GDAL checks sidecars by name. The open that lists a folder waits for the listing. On a Serverless worker that is about 0.5 s for 1,000 files and 14.5 s for 40,000. A Volume returns a folder's names only once it has fetched them all. The worker lists a folder once, whatever its size, up to 100,000 files. Each file then takes the mode its own sidecars call for. So a file with no sidecar in a folder of 10,000 files opens with no sidecar look-up. In that folder the checks by name cost a 10,000-tile read 1.7 to 3.1 times the time of the same read with no look-up. A folder over GDAL's own listing limit never gives the `NO` choice. That limit is `GDAL_READDIR_LIMIT_ON_OPEN`, 1,000 unless you set it, and GDAL counts `.` and `..` in it. GDAL would list such a folder at every open and then drop the listing, so the open checks sidecars by name instead. A folder of more than 100,000 files is not listed, and its files are opened with the checks by name. Tiles read with `raster_gbx` from such a folder skip that listing too. The reader counts the files of each folder when it plans the read. It puts the count of a folder over 100,000 in each tile's metadata (`path_folder_files`). The count only ever spares the listing; it never makes GDAL skip the sidecar look-up. A file missing from the listing (written after it) has the worker list the folder again. That happens at most once every 10 seconds per folder, and no sooner than 10 times the time the last listing took. The same wait holds for a folder whose listing the worker dropped to save memory. A sidecar added to a folder after a worker listed it is not seen until the folder is listed again or the worker restarts. To pick up a new world file or overview at once, start a new job, or set `GDAL_DISABLE_READDIR_ON_OPEN` yourself. Files read through a cloud path (`/vsis3/`, `s3://`, ...) are opened with the checks by name. The check GeoBrix makes before it reads a Volume file directly never looks for sidecars.

**The setting reaches the rest of the Python process.** Importing the lightweight implementation (anything that imports `databricks.labs.gbx.core.crs`) sets `GDAL_DISABLE_READDIR_ON_OPEN=TRUE` in the environment of the whole Python process, unless it is set already. Your own rasterio, GDAL (`osgeo`) or Fiona code in that process, and the programs it starts (`gdalinfo`, `tippecanoe`), then check sidecars by name too. The vector readers are not affected. GDAL's shapefile driver uses no folder listing either way. It looks a shapefile's `.prj` up by name (lower-case extension, then upper-case). For rasters, two kinds of file are then found only with GDAL's listing. One is a sidecar whose name mixes case (`x.Tfw`). The other is a vendor metadata file (`METADATA.DIM`, `*_MTL.txt`, `DIM_*.XML`) whose name differs in case from the one GDAL builds. To keep GDAL's own behavior, set `GDAL_DISABLE_READDIR_ON_OPEN=NO`. Set `YES` for the checks by name without the per-file choice. Set the value in the environment of the Python workers before GeoBrix is imported there, as an environment variable of the cluster or the job. A notebook's `os.environ` or a `rasterio.Env` on the driver does not reach the workers.

**Your value decides every open.** If you set `GDAL_DISABLE_READDIR_ON_OPEN` before the import (any value, `TRUE` included), or in a `rasterio.Env` around your own reads in the same process, GeoBrix makes no per-file choice. GDAL uses your value. The value `NO` gives its own listing at each open, `YES` or `TRUE` gives the checks by name, and `EMPTY_DIR` ignores sidecars. A GDAL configuration option set to `TRUE` later (for example with `gdal.SetConfigOption`) cannot be told apart from GeoBrix's own value, so the per-file choice still applies then.

**A `rasterio.Env` that names the option fixes it for the process.** When the outermost `rasterio.Env` entered with `GDAL_DISABLE_READDIR_ON_OPEN` exits, rasterio sets the value it found on entry as a GDAL configuration option for the whole process. From then on that option, not the environment variable, decides, and a later change of the environment variable has no effect. Set the environment variable before the first such `rasterio.Env`.

### Per-partition open-amortization (the grouped executor)

GeoBrix's grouped executor holds a small per-partition LRU cache of open stream handles, keyed by source path. The first access for a source in a partition opens it (cache miss). All subsequent windows from that source in the same partition are cache hits (~2 ms each). When tiles are sorted by source path within each partition, even a partition holding several sources fully amortizes at LRU size ~2.

Measured on a 647 MB COG corpus (15 sources × 12 windows = 180 tiles):

| Write layout | Read approach | Opens | Total time |
|---|---|---|---|
| Scattered (no alignment) | Dumb (as-written) | 135 | 173 s |
| `ORDER BY path` | Dumb (as-written) | **15** | 37 s |
| `ORDER BY path` | Smart (re-partition) | **15** | **11 s** |

To enable amortization after a join or reshape that has scattered tiles across partitions, re-align before processing:

```python
df = df.repartition(n, "tile.path").sortWithinPartitions("tile.path")
```

Size `n` for parallelism, not for file count:
- **Classic clusters (fixed workers):** `n ≈ 3–5× total worker cores` — e.g. 20 workers × 4 cores → `n ≈ 100`
- **Serverless (elastic workers):** `n` is the parallelism signal; smaller values pull in fewer workers, larger pull in more

Do not set `n = number_of_files` for large corpora — over-partitioning produces tiny tasks and scheduling overhead.

### MANAGED vs EXTERNAL: identical read performance

A tile column declared `FILE MANAGED` and one declared `FILE EXTERNAL` perform identically for reads. Both resolve to the same underlying paths; the open-cost and windowed-read cost are indistinguishable. The choice between MANAGED and EXTERNAL is about **governance and lifecycle**, not read speed. MANAGED tiles carry governed lifecycle (tied to the table) and `content_type` detection; EXTERNAL tiles reference files managed independently in a Volume. Choose based on governance requirements, not on any expected read-latency difference.

### Write-side layout for efficient reads

The GeoBrix writer optionally lays tiles out source-aligned at write time, so the reader can amortize for free on the first read. No re-partition step is required after a normal read-write round trip.

| Write strategy | Effect on reads |
|---|---|
| `INSERT … ORDER BY tile.path` | Immediate physical grouping — dumb reads amortize without any re-partition |
| `CLUSTER BY (tile.path)` on the table + periodic `OPTIMIZE` | Durable layout after Delta applies liquid clustering |
| `CLUSTER BY (tile.path)` on the initial insert only (no `OPTIMIZE`) | May not be grouped yet — combine with `ORDER BY` in the `INSERT` for insert-time grouping |
| No alignment | Scattered — requires explicit `repartition + sortWithinPartitions` on every read |

:::caution Avoid `partitionBy("tile.path")`
`tile.path` is high-cardinality — one value per source file. Using it as a Delta partition column creates thousands of partition directories, causing metadata explosion and slow query planning. Use `ORDER BY` and `CLUSTER BY` instead.
:::

### FILE type and `path_mode`

FILE is available on Databricks Runtime 19 dedicated clusters and Serverless, in a workspace with the File type preview. When it is, the tile struct's [`path_mode` field](./tile-structure) records how the virtual tile was stored:

| `path_mode` | Meaning |
|---|---|
| `null` | Materialized tile (raster bytes present), or a plain FUSE-path virtual tile |
| `"external"` | FILE EXTERNAL virtual tile — opened via byte-range stream |
| `"managed"` | FILE MANAGED virtual tile — opened via byte-range stream; lifecycle governed by the table |

On runtimes without FILE support, `path_mode` is always `null` and virtual tiles use the FUSE path. These runtimes are DBR 17/18, the Databricks Container Service image, and any compute in a workspace without the File type preview. Behavior there is correct and unchanged. Writers default to `file_mode="fuse"`; pass `"auto"` or `"external"` to opt in to FILE.

## How the Python functions run

The light level picks a Spark execution shape for each function. Fan-out generators use streaming UDTFs. Aggregators use grouped-aggregate Arrow UDFs. Per-tile transforms use Arrow scalar UDFs.

### Streaming UDTFs

A **Python UDTF (User-Defined Table Function)** is a class with an `eval` method that `yield`s rows. Spark calls it as a `LATERAL` table function. One input row fans out to any number of output rows without buffering the whole result.

This shape fits **generator operations**, where one input tile produces many output rows. Buffering all rows in a list would hold the whole result in worker memory. Streaming with `yield` releases each row as soon as it exists.

The generators that stream:

| Family | Functions |
|---|---|
| Tiling | `gbx_rst_retile`, `gbx_rst_tooverlappingtiles`, `gbx_rst_maketiles`, `gbx_rst_separatebands`, `gbx_rst_xyzpyramid` |
| Vectorize | `gbx_rst_polygonize` |
| Raster to grid | `gbx_rst_{h3,quadbin,bng,custom}_rastertogrid*` |
| Tessellate | `gbx_rst_{h3,quadbin,bng}_tessellate`, `gbx_bng_tessellateexplode` |
| BNG explodes | `gbx_bng_{kring,kloop,geomkring,geomkloop}explode` |
| Vector tiles and TIN | `gbx_st_asmvt_pyramid`, `gbx_st_triangulate`, `gbx_st_interpolateelevationbbox`, `gbx_st_interpolateelevationgeom` |

### Grouped-aggregate UDFs

A **grouped-aggregate `pandas_udf`** works on one group at a time. Spark shuffles the rows for a key to one worker. It calls the UDF once with all values in the group and gets one result.

This shape fits **aggregators**, which reduce many rows to one output per key, such as one merged raster or one vector tile. They sit inside a standard `.groupBy(...).agg(...)` call.

| Family | Functions |
|---|---|
| Raster | `gbx_rst_merge_agg`, `gbx_rst_combineavg_agg`, `gbx_rst_frombands_agg`, `gbx_rst_derivedband_agg`, `gbx_rst_rasterize_agg`, `gbx_rst_gridfrompoints_agg`, `gbx_rst_binpoints_agg`, `gbx_rst_dtmfromgeoms_agg` |
| Grid | `gbx_rst_{h3,quadbin,bng,custom}_rasterize_agg`, `gbx_{bng,quadbin}_cellunion_agg`, `gbx_bng_cellintersection_agg`, the `*_cellfill` functions |
| Vector | `gbx_st_asmvt`, `gbx_st_coverageisvalid`, `gbx_st_coverageinvalidedges` |
| Archives | `gbx_pmtiles_agg` |

:::note Memory scales with group size
A grouped aggregate realizes its whole group in the worker, so memory follows the rows per group. For most tile aggregators that is a few tiles per key. **Point binning** (`rst_binpoints_agg`) takes one row per point, so a full-resolution LiDAR tile can exhaust worker memory. The helper `rasterx.helpers.bin_points_tiled` avoids this with a two-stage aggregation. Peak memory is the raster grid, not the point count, and the output is identical for `max`, `min`, `mean` and `count`. See [RasterX › rst_binpoints_agg](./raster-functions#rst_binpoints_agg) and [Serverless & Memory](../serverless-and-memory).
:::

### Arrow scalar UDFs

A **vectorized Arrow scalar `pandas_udf`** receives an Arrow batch of rows, calls the function once per batch, and returns a `pd.Series`. The JVM and Python boundary is crossed once per batch, not once per row.

This shape fits **one-row-in, one-row-out transforms**: tile accessors, warps, edits, band math, terrain and the vector scalars. Functions that return `MapType` use a plain `@f.udf` for SQL registration, because Arrow does not support `MapType` in every `pandas_udf` build.

### Chaining functions

Compose tile functions in **one expression**, for example `rx.rst_slope(rx.rst_setcrs(col("tile"), "EPSG:32633"))`. Do not split them across separate `.select()` or `.withColumn()` steps.

Spark fuses chained Column calls into a single Python worker. The intermediate tile passes between functions as a live object. The JVM and Python boundary is crossed once for the chain. Separate steps send each intermediate tile back to the JVM and re-serialize it. Chaining also composes with virtual-tile deferral: deferrable operations stay lazy and stay in one worker.

### Vectorized cores

The compute under each UDF shape comes from established Python libraries.

| Library | Role |
|---|---|
| **rasterio** | Tile open and decode, clip, COG conversion, band I/O |
| **NumPy** | Array operations |
| **SciPy** | Focal filters (`rst_filter`, `rst_convolve`). Delaunay triangulation for the TIN functions where the env wheel's Rust module is absent. |
| **rio-tiler** | XYZ and web-tile output (`rst_tilexyz`, `rst_xyzpyramid`) |
| **GDAL** (`raster` algorithms) | Terrain, color relief, band math, warp and resample, fill NoData, summary, contour, polygonize, viewshed, and `gbx_rst_gdal` |
| **shapely** | WKB geometry handling: clip, rasterize, grid aggregation, legacy-struct decode |
| **pyogrio** | Vector reader I/O in Arrow-native columnar batches |
| **mapbox-vector-tile** | MVT protobuf encode and decode (`st_asmvt`, `st_asmvt_pyramid`) |

Each library is called directly by the UDF. There is no subprocess and no native bridge.

## Streaming versus consolidated returns

Not every fan-out function is a streaming UDTF. The choice follows the cost.

**Stream (UDTF)** when one input row fans out to many output rows and the consumer needs individual rows. A consolidated `ARRAY` return carries three costs. It buffers the whole fan-out in worker memory. It serializes the nested array across the boundary. It explodes the array again downstream. These costs grow with the fan-out.

The clearest case is `rst_separatebands` on a hyperspectral raster. Each band tile carries its own bytes. A consolidated return holds all band tiles of one input row at once: 200 times the tile size for a 200-band scene. The streaming UDTF yields one band tile at a time, so worker memory stays flat whatever the band count. The same logic applies to fine tessellation, deep XYZ pyramids and retiling, where the output tile count grows with the input raster.

**Consolidate** when the collection is the answer. An aggregation (`*_agg`) produces one result per group, and the consolidation is the reduction. The `*_agg` reductions are the only consolidated returns. Every fan-out generator streams.
