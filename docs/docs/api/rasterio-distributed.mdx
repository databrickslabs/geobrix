# Rasterio Distributed

[RasterX](./raster-functions)'s lightweight implementation is, in large part, `rasterio` plus a best-of-breed Python raster stack: rio-tiler, scipy, scikit-image, shapely, pyproj, h3 and quadbin. They run as Arrow-vectorized Spark UDFs and UDTFs across the cluster. It is not a single-node `rasterio.open` loop, and it is not a reimplementation. The same `rasterio` functions you would call locally run inside a vectorized Spark UDF, once per tile, on every executor in parallel. No JAR and no native GDAL install separate from rasterio's bundled GDAL.

If you already know `rasterio`, you already understand what `pyrx` does. The coverage matrix below maps the surface, and the side-by-sides show each operation in rasterio next to its distributed `pyrx` form.

## Gaps and divergences

### Distributed in pyrx today

Everything in the matrix above. Every `rst_*` function runs on the lightweight implementation. A dedicated cluster with the JAR adds the heavyweight one where it is faster.

### Heavyweight differences (minor)

A small number of capabilities run only on the heavyweight implementation:

- **Conforming TIN mode.** The VectorX function `st_triangulate` (`gbx_st_triangulate`) supports two triangulation modes. Constrained mode, `mode='constrained'` (constrained Delaunay, the default), works in both tiers. Conforming mode, `mode='conforming'` (Steiner-point conforming Delaunay), requires a C-level refinement library not available in the lightweight stack. It raises in `pyrx` with an informative message.

See [Surfaces and levels](./execution-tiers) for how GeoBrix picks an implementation.

### Known behavior divergences

Where the lightweight and heavyweight implementations use different underlying algorithms, their outputs may not be pixel-identical on edge cases:

| Function | Heavyweight | Lightweight | Divergence |
|---|---|---|---|
| `rst_resample` | `gdalwarp` with a rounded-up size | GDAL `raster reproject` with a size rounded to even | A target size that ends in .5 pixels differs by one pixel |

See [Benchmarking](./benchmarking) and [Performance](./performance) for per-function timing data across both implementations.

With the plain GeoBrix wheel, `rasterio` brings the GDAL bundled in PyPI's `rasterio` wheels, which has a narrower driver set than GeoBrix's own GDAL build. The GeoBrix env wheels (environment 5 and 6) give `rasterio` that build instead, the one the JVM loads from the same wheel.

## How it is distributed

The lightweight implementation distributes rasterio and NumPy compute over Spark via three mechanisms, none of which require the Spark JVM internals:

- **Arrow scalar UDFs** (per-tile functions): each scalar `rst_*` function invoked via the Python Column API is a `@pandas_udf` (`tile_scalar_udf` / `tile_scalar_udf2` in `pyrx/_udf.py`). It receives a batch of tiles' raster bytes as a Pandas Series, calls rasterio/NumPy once per tile within the batch, and returns transformed bytes. The Arrow batch crosses the JVM↔Python boundary **once per batch**, not once per row. The same functions are also registered as plain `@f.udf` for SQL use (so `DESCRIBE FUNCTION` and SQL calls work). The Python Column API always routes through the `pandas_udf` path.
- **Grouped-aggregate pandas UDFs** (merges and combineavg): `rst_merge_agg`, `rst_combineavg_agg`, and similar grouped aggregators use `@pandas_udf(BinaryType())` — Spark 4 auto-detects the grouped-aggregate eval type. Each receives all tiles in a group as a Pandas Series and merges them in one Python call.
- **Streaming UDTFs** (fan-out): `rst_h3_tessellate`, `rst_quadbin_tessellate`, `rst_bng_tessellate`, `rst_maketiles`, `rst_retile`, `rst_xyzpyramid` use `@udtf` to yield one output row per chip or tile without materializing the full output in memory first.

No `_jvm` access, no `.rdd`, no Spark driver-side collect before distributing. Data-source readers and writers (`raster_gbx`, `gtiff_gbx`, etc.) use the DataSource V2 API. See [Performance](./performance) for partitioning guidance and per-tier timing benchmarks.
