# Rasterio Distributed

[RasterX](./raster-functions)'s lightweight (`pyrx`) tier is, in large part, `rasterio` plus a best-of-breed Python raster stack — rio-tiler, rio-cogeo, scipy, xarray-spatial, scikit-image, shapely, pyproj, h3, quadbin — run as Spark Python UDFs and UDTFs across the cluster. It is not a single-node `rasterio.open` loop, and it is not a reimplementation. The same `rasterio` functions you would call locally are called inside each Spark Python UDF, once per tile, on every executor in parallel. No JAR, no init script, no native GDAL install separate from rasterio's bundled GDAL.

If you already know `rasterio`, you already understand what `pyrx` does. The coverage matrix below maps the surface, and the side-by-sides show each operation in rasterio next to its distributed `pyrx` form.

## Gaps and divergences

### Distributed in pyrx today

Everything in the matrix above. Every `rst_*` function runs in both the lightweight (`pyrx`) and heavyweight (`rasterx`) tiers.

### Heavyweight-only for now (parity tracked)

A small number of capabilities run only in the heavyweight tier for now:

- **OGR vector readers** (`*_ogr` data sources — `shapefile_ogr`, `geojson_ogr`, `gpkg_ogr`, `file_gdb_ogr`, `netcdf_ogr`). Lightweight vector reading uses [pyogrio](https://pyogrio.readthedocs.io/) via the `pyvx` readers, but the named `*_ogr` reader variants are not yet exposed as lightweight data sources. Parity tracked.
- **Conforming TIN mode.** `rst_tin` with `conforming=True` requires a C-level Delaunay refinement library not available in the lightweight stack. `constrained=True` (the default) works in both tiers; `conforming=True` raises in `pyrx` with an informative message. Parity tracked.
- **Advanced PMTiles writer options.** The `gbx_pmtiles_agg` aggregate function is available in both tiers. Advanced DataSource-level `pmtiles_gbx` writer options (multi-part, spatial index tuning) are heavyweight-only for now. Parity tracked.
- **SQL default-argument convenience.** SQL calls that rely on overloaded registered signatures with more default arguments work in the heavyweight tier. `pyrx` functions accept keyword arguments in Python; the SQL registration exposes the same signatures. Parity tracked.

See [Execution Tiers](./execution-tiers) for how to choose and switch between tiers.

### Known behavior divergences

Where the lightweight and heavyweight implementations use different underlying algorithms, their outputs may not be pixel-identical on edge cases:

| Function | Heavyweight | Lightweight | Divergence |
|---|---|---|---|
| `rst_color_relief` | `gdal.DEMProcessing` | NumPy `np.interp` | Color ramp interpolation can differ at boundary values; `default` keyword not available in `pyrx` |
| `rst_convolve`, `rst_derivedband` | GDAL halo convolution | NumPy `pad(mode='edge')` | Border pixel handling differs at tile edges |
| `rst_resample` | GDAL resampler | rasterio resampler | NoData and boundary pixels can differ |
| `rst_contour` | `gdal.ContourGenerateEx` | `skimage.find_contours` | Contour tracing algorithm differs; vertex positions near NoData may diverge |
| `rst_viewshed` | `gdal.ViewshedGenerate` | `xrspatial.viewshed` | Visibility computation differs in algorithm; results agree on clear line-of-sight and fully obstructed pixels, but may differ at grazing angles |

See [Benchmarking](./benchmarking) and [Performance](./performance) for per-function timing data across both tiers.

Rasterio's bundled GDAL also has a narrower driver set than the heavyweight custom build. If you are reading an obscure raster format (HDF4, GRIB2 with specific subtype handling, certain radar formats), the heavyweight tier is more likely to support it.

## How it is distributed

The `pyrx` tier distributes rasterio and NumPy compute over Spark via three mechanisms, none of which require the Spark JVM internals:

- **Spark Python UDFs** (per-tile functions): each scalar `rst_*` function is a plain `@f.udf(TILE_SCHEMA)` Python UDF — it receives a tile struct, calls rasterio/NumPy on the tile's bytes, and returns the transformed bytes. Data crosses the JVM↔Python boundary via serialization once per row.
- **Grouped-aggregate pandas UDFs** (merges and combineavg): `rst_merge_agg`, `rst_combineavg_agg`, and similar grouped aggregators use `@pandas_udf(BinaryType())` — Spark 4 auto-detects the grouped-aggregate eval type. Each receives all tiles in a group as a Pandas Series and merges them in one Python call.
- **Streaming UDTFs** (fan-out): `rst_h3_tessellate`, `rst_quadbin_tessellate`, `rst_bng_tessellate`, `rst_maketiles`, `rst_retile`, `rst_xyzpyramid` use `@udtf` to yield one output row per chip or tile without materializing the full output in memory first.

No `_jvm` access, no `.rdd`, no Spark driver-side collect before distributing. Data-source readers and writers (`raster_gbx`, `gdal`, `gtiff_gdal`, etc.) use the DataSource V2 API. See [Performance](./performance) for partitioning guidance and per-tier timing benchmarks.
