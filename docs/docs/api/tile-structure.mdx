# Tile Structure

Understanding the internal structure of GeoBrix tiles is essential for advanced use cases like custom UDFs, direct data manipulation, and performance optimization.

## Overview

In GeoBrix, a **tile** is not a simple binary column—it's a **structured type** (struct) that represents a raster dataset along with its metadata, grid-cell information, and — when the tile is a bytes-free reference — the source path, window, and clip/CRS provenance. The same struct is shared by both execution tiers.

## Tile Schema

A tile has the following structure:

![GeoBrix tile schema — cellid (bigint, nullable), raster (binary, nullable), path (string, nullable), path_mode (string, storage mode: null / 'external' / 'managed'), window/clip_polygon/clip_crs/crs provenance fields, metadata (map of string to string, last field)](../../../resources/images/diagrams/rasterx/rasterx-tile-structure.png)

```
struct<
  cellid: bigint,                                -- Grid cell ID (nullable)
  raster: binary,                                -- Raster bytes (NULL when virtual)
  path: string,                                  -- Source path (virtual) or provenance (materialized)
  path_mode: string,                             -- Storage mode: null, 'external', or 'managed'
  window: struct<col_off,row_off,width,height>,  -- Pixel window
  clip_polygon: binary,                          -- Optional clip geometry (WKB)
  clip_crs: string,                              -- CRS for clip_polygon
  crs: string,                                   -- Working/target CRS
  metadata: map<string,string>                   -- Driver, extension, size, etc.
>
```

A tile is **materialized** when `raster` carries the encoded bytes (the common case, and the only form the heavyweight tier consumes). A tile is **virtual** when `raster` is `NULL` and `path` + `window` are set — a bytes-free reference that materializes pixels on demand (a lightweight-tier capability). For the full virtual/materialized model, see **[Virtual Tiles](./virtual-tiles)**.

### Field Descriptions

| Field | Type | Nullable | Description |
|-------|------|----------|-------------|
| `cellid` | `bigint` (Long) | Yes | Grid cell identifier for tessellated rasters. `null` for non-tessellated rasters. |
| `raster` | `binary` | Yes | Encoded raster bytes when materialized; `null` when the tile is virtual (bytes-free). |
| `path` | `string` | Yes | Set on a virtual tile, where it is the source the pixels are read from. On a materialized tile it is provenance of where the bytes came from (a reader's tile, a `materialize=True` output, a lightweight retile-family output); the bytes in `raster` are the data and are always read in preference to `path`. `null` when the tile has no single source file. |
| `path_mode` | `string` | Yes | Storage mode for a virtual tile. `null` = materialized (raster bytes present) or plain FUSE-path virtual. `"external"` = FILE EXTERNAL virtual tile. `"managed"` = FILE MANAGED virtual tile (governed lifecycle). |
| `window` | `struct<col_off,row_off,width,height>` | Yes | The pixel window (offset + size). On a virtual tile it is the window to read; on a materialized tile it is provenance of the window already extracted. The lightweight `rst_retile`, `rst_tooverlappingtiles` and `rst_maketiles` record the window relative to their immediate **input** tile, so windows from different parents can repeat; one output that covers its whole input keeps the input's own window instead. The heavyweight versions leave it null. |
| `clip_polygon` | `binary` | Yes | Optional clip geometry (WKB). Instruction on a virtual tile; applied-provenance on a materialized tile. |
| `clip_crs` | `string` | Yes | CRS for `clip_polygon` (e.g. `"EPSG:4326"`). |
| `crs` | `string` | Yes | Working/target CRS. |
| `metadata` | `map<string,string>` | Yes | Key-value map containing driver name, file extension, size, and other metadata. The lightweight `rst_separatebands` also sets `band` (1-based) on each output. A tile read from a Zarr store carries the keys listed in [Zarr tile metadata](#zarr-tile-metadata). |

:::note Reference vs. instruction
On a **materialized** tile, `window` / `clip_polygon` / `clip_crs` / `crs` are **provenance** — a record of what was already applied to produce the bytes. On a **virtual** tile they are **instructions** — pending operations applied when the tile is read. See [Virtual Tiles](./virtual-tiles#reference-vs-instruction).
:::

### Comparing `rst_fromfile` vs `rst_fromcontent`

`rst_fromfile` takes a path and returns a **virtual** tile in the light tier (bytes-free by default; pass `materialize=True` to force bytes). `rst_fromcontent` always returns a **materialized** tile — it takes bytes you already have (e.g. from `spark.read.format("binaryFile")`) and embeds them directly.

### Zarr tile metadata

A tile cut from a [Zarr store](../formats/zarr) with [`gbx_zarr_read(..., output="tiles")`](../readers/zarr#output-geobrix-tiles)
is virtual, and its `metadata` holds everything a task needs to read its window. `window` is a window of one
2-D plane of a variable (its latitude and longitude); `sliceDims` says where the tile sits along the other
dimensions. A table of these tiles can be saved and opened later by tasks that have no session and no manifest
table: see [Zarr tiles](./virtual-tiles#zarr-tiles).

| Key | Holds |
|---|---|
| `format`, `driver` | `zarr` and `Zarr` on a virtual tile. Both are `GTiff` once the tile is materialized, because its bytes are then a GeoTIFF |
| `sourcePath` | The store the tile was cut from (for a registered store, the store's own directory) |
| `zarr_array` | The variable, that is the Zarr array, the tile was cut from |
| `sliceDims` | The tile's position along each dimension other than latitude, longitude and the `band_dim`, by position and sorted by name: `level=3,time=12`. Absent when there is no such dimension. The NetCDF reader writes the same form |
| `sliceCoord_<dim>` | The label at that position, for each dimension that has coordinates; a time is ISO text such as `2023-01-01T05:00:00.000000000` |
| `zarr_meta` | JSON: the array's metadata, cut to what decoding needs (data type, chunk and shard layout, codecs, fill value, CF attributes) |
| `zarr_refs` | JSON: for each band of the tile, the storage objects its window needs, each with a file, an offset and a length, taken from the manifest at the pinned version. Empty for a plain store, which has no manifest |
| `zarr_root` | The directory the files are read from: the store for a plain store, the store's root for a managed one, the overlay root for a writable registration |
| `zarr_base_root` | A registered store only: the store's own directory, where its original objects are |
| `zarr_table`, `zarr_version` | The manifest table and the version the read was pinned to. Both are empty for a plain store |
| `zarr_gt`, `zarr_crs` | The geotransform of the whole plane (six comma-separated numbers, north-up) and its CRS |
| `width`, `height` | The size of the whole plane in cells; the tile's `window` is a part of it |
| `count` | The number of bands in the tile |
| `bandDim`, `bandDescriptions`, `bandCoords`, `zarr_band_index` | `band_dim` stacks only: the stacked dimension, a `<dim>=<label>` description of each band, the label of each band (when the dimension has coordinates), and the positions of the bands in the array |

The `crs` field of a virtual Zarr tile is `NULL`: it is the target of a pending reprojection, and the tile's
own CRS is `zarr_crs`. A materialized tile (read with `virtual_tiles=False`) keeps every `zarr_*` key, which is
how a tile is written back to the array it was cut from.
