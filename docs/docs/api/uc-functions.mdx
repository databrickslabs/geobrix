# Unity Catalog functions

Unity Catalog (UC) functions give governed, persistent SQL for SQL warehouses, dashboards, Genie and agent tools. They use the same `gbx_` names as session SQL, called with a three-level name: `<catalog>.<schema>.gbx_*`.

UC carries a slice of GeoBrix, not the whole set. Session SQL and the Python API keep the full range: every CRS form, every tile, aggregates and the select-list generators. The [availability matrix](./availability) shows the surfaces of each function.

## Install

Run `gbx.uc.install` from an env 6 notebook or job. It needs Serverless env 6 or DBR 19. It creates the functions in one schema. The raster functions install the same way, with the same call.

<CodeFromTest code={ucExamples} language="python" functionName="INSTALL_PYTHON" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

The install folder is a Volume folder. Keep these rules for it:

- It holds exactly one env 6 wheel of the same version as the wheel that runs the install.
- It holds one folder per environment. A wheel for another environment in the folder is refused.
- It holds only the current version. Install a new version into a clean folder.

The creator needs `USE CATALOG` on the catalog, `USE SCHEMA` and `CREATE FUNCTION` on the schema, and `READ VOLUME` on the Volume. A caller needs `EXECUTE` on the functions.

The install runs `CREATE OR REPLACE FUNCTION` for each function. Run it again after you update the wheel. Each function carries a COMMENT of the form `geobrix <version>: <summary>`, so the schema records which version made it.

### Packages and start-up time

By default every Python function in the schema declares the same package list. A statement that calls several GeoBrix functions then starts one sandbox and installs the packages once.

This costs time at install. The first create is about 45 s longer, once. The gain comes at query time. On Serverless, a statement with three functions took 33 s with a package list per function and 2.7 s with the shared list. A warehouse measured 28 s against 17 s. A statement with one function runs the same either way.

Pass `deps="per-function"` to give each function only the packages it imports. The install is smaller and faster. A statement that calls several functions with different package lists pays one sandbox start for each list.

## Where UC functions run

UC functions run on:

- Serverless and pro SQL warehouses;
- Serverless env 6 notebooks and jobs;
- dedicated and standard clusters on DBR 19.

They do not run on clusters that use a [Databricks Container Service](../installation/dcs.mdx) image. They do not run on classic SQL warehouses.

A warehouse reads rasters and vector files through the session readers. Ingest the files into a Delta table, then query the table with UC functions. UC has no function that reads a raw file.

### Geometry in, SRID out

A UC function takes a geometry as `GEOMETRY(ANY)` and reads its integer SRID. The grid fixes the SRID it accepts:

- BNG functions take SRID 27700.
- Quadbin and H3 functions take SRID 4326.
- Custom grid functions take the SRID of the grid. A grid made with no SRID takes SRID 0.

A geometry in another SRID is refused with a `Fix:` that names `st_transform`. GeoBrix never reads coordinates as the wrong unit.

A WKB `BINARY` is not a `GEOMETRY`. Build the geometry first.

<CodeFromTest code={ucExamples} language="sql" functionName="UC_WKB_TO_GEOMETRY_SQL" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

The geometry functions `gbx_st_makevalid`, `gbx_st_wrapx`, `gbx_st_legacyaswkb` and the seven cleaners below return a `GEOMETRY` that keeps its SRID. `gbx_bng_aswkb` and `gbx_bng_centroid` return `BINARY`. On UC that value is little-endian EWKB with SRID 27700, and a BNG cell polygon starts at its south-west corner. The bytes are the same whether the install folder holds the JAR or not.

### Grid functions

These rules hold for the BNG, quadbin, H3 and custom grid functions.

- **A cell id that is no cell gives `NULL`.** That covers a text that is no BNG cell and a number that is no cell of the grid.
- **A geometry result is little-endian EWKB with the SRID of the grid.** A custom grid made with no SRID gives plain WKB.
- **A result over 64 MiB is refused with a `Fix:`.** This covers the ring and loop functions, and the BNG and quadbin fills and tessellations. The ring and loop `Fix:` says to lower `k`, split the input, or call the session function. The fill `Fix:` says to use a coarser resolution or split the geometry.
- **A geometry that cannot be read, or has a coordinate that is not finite, gives `NULL`.** A bad `mode`, `coverage`, `k` or resolution raises with a `Fix:` before any row is read.

A custom grid is a struct. Build it once with `gbx_custom_grid` and pass it to the other `gbx_custom_*` functions. `gbx_custom_grid` raises for bounds or sizes that make no grid.

`gbx_quadbin_distance` raises for two cells of different zooms. Compare cells of one zoom, and read a zoom with `gbx_quadbin_resolution`.

`gbx_h3_cell_bbox` takes its CRS as an integer SRID, `EPSG:<n>` or `ESRI:<n>`. UC refuses WKT. `out_crs`, when set, wins over `srid`. A `mode` other than `centroids` or `spatial_envelope` raises, and so does a negative `kring_pad`.

### Functions that run as SQL

`gbx_quadbin_resolution`, `gbx_custom_grid` and `gbx_rst_memsize` run as SQL functions with no Python. They give the same answers as the session functions. `gbx_rst_memsize` returns the length of the tile's pixel bytes and refuses a virtual tile with a `Fix:`.

A UC function takes a CRS argument in three forms:

- an integer SRID, such as `4326`;
- `EPSG:<n>`;

### Numbers as arguments

The SQL engine casts an argument to the parameter type before GeoBrix runs. A string passed as an easting becomes a number there. With ANSI mode off, a string that is no number becomes `NULL` before GeoBrix sees it.

### Raster functions

The raster functions take the arguments of their session functions and give the same answers. These rules apply on UC.

**A tile must be materialized.** A materialized tile carries its pixels. A virtual tile holds a path and no pixels, and UC refuses it. The `Fix:` names the session function.

**A function that reads pixels refuses a tile larger than 64 MiB decoded.** The `Fix:` says to retile first with `gbx_rst_retile`, or to run the session function in a notebook or job. A header accessor reads no pixel, so it answers a tile of any size. `gbx_rst_tryopen` does the same.

### Array and partial forms

A SQL warehouse function cannot be an aggregate. These functions replace the session aggregates.

| Function | How to call it |
|---|---|
| `gbx_h3_cellfill_array`, `gbx_quadbin_cellfill_array`, `gbx_bng_cellfill_array`, `gbx_custom_cellfill_array` | `GROUP BY` the group key, and pass `collect_list(struct(cellid, value))`. |
| `gbx_bng_cellunion_array`, `gbx_bng_cellintersection_array` | `GROUP BY` the cell, and pass `collect_list(struct(cellid, core, chip))`. |
| `gbx_st_coverageisvalid_array`, `gbx_st_coverageinvalidedges_array` | `GROUP BY` the district, and pass `collect_list(st_asewkb(geom))`. |
| `gbx_st_asmvt_array` | `GROUP BY` the tile key, and pass `collect_list(struct(st_asbinary(geom) AS geom, to_json(attrs) AS attrs))`. |
| `gbx_rst_binpoints_partial`, `gbx_rst_binpoints_finalize` | Call `gbx_rst_binpoints_partial(x, y, ...)` for each point, then `GROUP BY` the `(col, row)` key and reduce `z` with `max`, `min`, `avg`, `median` or `percentile`. Pass `collect_list(struct(col, row, value))` to `gbx_rst_binpoints_finalize`. |
| `gbx_rst_h3_rastertogrid_partial` | Call it once for each tile, then `GROUP BY` the band and cell. See [Raster to grid](#raster-to-grid). |

An array form takes the whole group in one call, and a UC function limits an array to 64 MiB. A larger array is refused with a `Fix:`. The binpoints pair has no such limit on the number of points, because the points never reach Python. The finalize input has one entry for each occupied pixel. The [binpoints page](./raster-functions#rst_binpoints_partial) has the full statement.

### Raster to grid

A table function such as `gbx_rst_h3_rastertogridavg(tile, 7)` gives one statistic for each cell of one tile. It reads the pixels again for each statistic you ask for.
Seven H3 statistics are table functions on UC: `avg`, `count`, `max`, `min`, `stddev`, `sum` and `variance`. The median runs in a session.
All seven read the state that `gbx_rst_h3_rastertogrid_partial` gives, so one Python call serves any of them.

To get a statistic across many tiles, call the partial once for each tile and merge the rows with `GROUP BY`. The average of the per-tile averages is not the average of the cell.
Sum `count` and `sum` instead. The variance also needs the squared distance of each tile's mean from the merged mean.

<CodeFromTest code={ucExamples} language="sql" functionName="UC_RASTER_TO_GRID_SQL" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

The statement gives the statistics of the whole raster when you cut it into tiles. A cell on the seam of two tiles holds pixels of both, and the merge counts each pixel once.
Tiles must not overlap. A pixel in two tiles counts twice, as it does in the output of `gbx_rst_tooverlappingtiles`.

The partial has default arguments, so its public name is a SQL function. UC refuses a SQL function inside a generator, so call the partial in a subquery and explode the column, as the statement does.
A partial over 64 MiB is refused with a `Fix:` that says to use a coarser resolution or to retile first. A virtual tile is refused.

### Cutting a tile into tiles

Four table functions cut one tile into many: `gbx_rst_retile`, `gbx_rst_maketiles`, `gbx_rst_tooverlappingtiles` and `gbx_rst_separatebands`.
They give the columns of the session functions and the same sub-tiles in the same order. Call them in `FROM` with `LATERAL`, one row for each sub-tile.

<CodeFromTest code={ucExamples} language="sql" functionName="UC_RASTER_RETILE_SQL" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

Each sub-tile records the pixel window it was cut from in `window`. A band tile from `gbx_rst_separatebands` records its band number in `metadata['band']`.

<CodeFromTest code={ucExamples} language="sql" functionName="UC_RASTER_BANDS_SQL" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

Three limits keep the work inside the memory of a UC function:

- **The input tile is refused over 64 MiB decoded.** A session reads a tile by window, so cut a tile that large there and store the pieces in a table.
- **The result is sized before any window is cut.** The estimate is the decoded size of all the tiles, plus 1 percent for the codec and a header for each tile. It is never under the real size, so it can refuse a result that would have fitted.
- **Each tile made, and the total so far, is checked again.** Nothing is truncated. Over 64 MiB, the `Fix:` says to use larger tiles, a smaller overlap, or the session function.

A tile that cannot be read gives no rows, and so does a NULL size. The session gives one error tile for each. An error tile goes out as itself. A virtual tile is refused.
A window below one pixel, or an overlap outside 0 to below 100, raises with a `Fix:`, also for a tile with nothing to read.

## Cost

Measured on an X-Small pro serverless warehouse. Treat the figures as orders of magnitude.

| Measure | Result |
|---|---|
| A `SELECT 1` statement | 0.53 to 0.63 s |
| A UC Python function over 1M rows | about 10 to 11 s per statement |
| BNG point to cell over 1M rows, Python handler | about 15.4 s |
| BNG point to cell over 1M rows, Scala handler | 10.7 to 11.6 s |

The per-statement cost is high next to a session function, and UC functions suit BI and governed use. For bulk transforms use session SQL or the Python API.

A UC Python function holds about 10 tiles of 512 by 512 pixels, at 4.2 MB each. A function that received 50 tiles ran out of memory. UC has no aggregate over tiles, so use a session aggregate for that work.

## Errors on UC

A UC function has no error tile. It follows one rule for each kind of problem:

- **Corrupt data gives `NULL`.** An unreadable geometry, a text that is no cell id and a point that is not finite give `NULL`.
- **Input the function cannot serve gives an error with a `Fix:`.** A geometry in the wrong SRID, a CRS form UC does not take and a virtual tile fall here. The `Fix:` names the session function.
- **A wrong parameter raises with a `Fix:`.** A bad resolution, mode, coverage, zoom or `k` is checked before any row is read.

## Procedures

Procedures run a whole ETL step inside Unity Catalog. Each one reads a table, calls GeoBrix functions and merges the result into another table. A procedure adds flow only: it computes nothing itself and writes no file.

Install them with the functions. A procedure is created after the functions it calls, and `SQL SECURITY INVOKER` runs it with the privileges of the caller. With `only=`, a procedure is created only when every function it calls is installed. Install prints one line for each procedure it skips.

<CodeFromTest code={ucExamples} language="python" functionName="INSTALL_PROCEDURES_PYTHON" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

A caller needs `EXECUTE` on the procedure and `SELECT` and `MODIFY` on the tables it names. Table names are parameters, as `catalog.schema.table`. Each procedure reads fixed column names, listed in its comment. A procedure creates the target table when it is missing and merges into it on later calls.

| Procedure | Reads | Writes |
|---|---|---|
| `gbx_polygons_to_bng` | `id`, `geom` in SRID 27700 | `id`, `cellid`, `core`, `chip` |
| `gbx_clean_geometries` | `id`, `geom` | the valid geometries, and a rejects table with the reason |
| `gbx_migrate_mosaic_geometry` | `id`, a legacy Mosaic `geom` of one SRID | the same table with a `GEOMETRY` column of that SRID |
| `gbx_points_to_h3_surface` | `longitude`, `latitude`, `value` | one GeoTIFF surface per name, with the empty cells filled |
| `gbx_features_to_mvt` | `geom` in EPSG:4326, `attrs` as a struct | `z`, `x`, `y`, `mvt` |
| `gbx_mosaic_by_key` | `tile_key`, `tile` | one merged tile per key |
| `gbx_combine_by_key` | `tile_key`, `tile`, and an `op` | one tile per key, each pixel the `avg`, `sum`, `count`, `min`, `max` or `stddev` of the key's tiles |
| `gbx_zonal_stats` | zones with `zone_id`, `geom`; tiles with `tile_id`, `tile`, `bbox` | `zone_id`, `tile_id`, `summary` |
| `gbx_zarr_tag_version`, `gbx_zarr_untag_version`, `gbx_zarr_version_history` | a Zarr store's manifest table | a tag, its removal, or the list of commits |

Most procedures upsert. A row already in the target that the source no longer has stays there, so a procedure never deletes stale rows. Delete them yourself when the source drops a feature.

The `id` of the source must be unique for `gbx_polygons_to_bng`, `gbx_clean_geometries` and `gbx_migrate_mosaic_geometry`. A repeated `id` makes the merge fail. In `gbx_zonal_stats`, each `zone_id` must be unique in the zones and each `tile_id` in the tiles.

`gbx_clean_geometries` keeps each `id` in one table per call. A geometry that is valid now is merged into the target and removed from the rejects. One that is invalid now goes to the rejects and is removed from the target. A row whose `id` is NULL is matched like any other. The four writes are not one transaction. They hold when the call succeeds. If it fails part-way, run it again to repair the tables.

`gbx_points_to_h3_surface` adds the cells within `fill_rings` of a point's cell, with no value, before it fills. A cell no point fell in then takes the mean of the neighbours that have a value. So `fill_rings` fills gaps, not only the cells you gave with no value.

<CodeFromTest code={ucExamples} language="sql" functionName="CALL_POLYGONS_TO_BNG_SQL" source="docs/tests/python/api/uc_functions_examples.py" testFile="docs/tests/python/api/test_uc_functions_examples.py" />

`gbx_mosaic_by_key` and `gbx_combine_by_key` take any number of tiles per key. A call to a UC function holds a bounded number of tiles. The limit is eight to merge and six to combine, because the partial tiles of a combine are Float64. So each procedure works in levels. It merges or combines the tiles of a key in groups of that size into a scratch table beside the target. It repeats on the results until a key has one tile. The scratch table is dropped when the call ends, also when it fails. A key with one tile goes to the target as it is.

Tiles of a key should not overlap in `gbx_mosaic_by_key`: which of two overlapping tiles shows is not defined. The tiles of a key in `gbx_combine_by_key` must be aligned (same size, extent and CRS), as for the `gbx_rst_combine*` functions. Pixels with no data are left out of the statistic. `avg` and `stddev` return Float32 tiles, and `stddev` is the population standard deviation. The `median` op is refused with a `Fix:`: it does not split into partial tiles, so combine at most 10 tiles per key with `gbx_rst_combinemedian`. Any other unknown `op` is refused too.

A merged or combined tile over 64 MiB is refused, because a UC function returns no more. The `Fix:` of `gbx_mosaic_by_key` names `mint_vrt` for a mosaic that large (see [VRT & Mosaics](./vrt-mosaic)). The `Fix:` of `gbx_combine_by_key` says to combine that key with the session aggregate, or to split the key. A key that needs more than 10 levels of 8 tiles is refused: split the key. The H3 surface and vector tile procedures refuse an array over 64 MiB and name the session function.

The vector tile procedure writes tiles to a table. A `.pmtiles` archive is built outside Unity Catalog.
