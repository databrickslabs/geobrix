# Zarr Stores: transactional, versioned, in place

_Since:_ **v0.6.0** · _(lightweight tier only; no JAR)_

[Zarr](https://zarr.dev) stores N-dimensional arrays as many small objects in object storage, which
makes it the format of choice for large weather, climate and earth-observation cubes. Plain Zarr has
no transactions: two jobs that write to one store can lose each other's updates, and a reader can
see a half-written store.

GeoBrix adds the missing layer. It reads and samples Zarr stores of any origin, registers an existing
store **in place** without copying it, and lets you **write to a store transactionally**: every write
is all-or-nothing, concurrent writers do not corrupt each other, and every version of the store stays
readable for the store's `retain` period (7 days by default), and for as long as you like if you tag it.

This page explains how the model works and what it guarantees. The examples run against a small
sample cube, and every block of code on this page is run by the documentation tests.

## Why Zarr

| | **Zarr** | **GeoTIFF / COG** | **NetCDF / HDF5** | **GRIB2** | **Delta table, one row per cell** |
|---|---|---|---|---|---|
| Shape | Any number of dimensions | Bands of a 2-D grid | Any number of dimensions | A sequence of 2-D fields | Rows and columns; the grid is lost |
| Layout | One object per chunk, or per shard of chunks | One file; a COG is tiled inside | One file, chunked inside | One file of messages | Parquet files |
| Reading a slice from object storage | Fetches only the chunks the slice touches | A COG fetches the tiles it needs | Possible with range-read tooling; many readers copy the whole file | Needs an index of the messages | Scans and filters rows |
| Several writers at once | Safe only for different chunks, and only if none changes the metadata | One file, one writer | One file, one writer | One file, one writer | Yes (Delta transactions) |
| All-or-nothing writes | No | No | No | No | Yes |
| Versions and time travel | No | No | No | No | Yes |
| Best for | Cubes read and written at scale | Imagery and single surfaces | Files from data providers | Weather model output | Tabular analytics on cells |

Zarr's strength is the layout: a job reads only the chunks it needs, and many jobs read different
chunks at once. Its weakness is that the layout has no commit. GeoBrix keeps the layout and adds the
commit, so a store gets the guarantees of the last column without turning an array into rows.

**What GeoBrix adds**

- **Register in place.** Point a table at an existing store; nothing is copied.
- **Three ways to read.** N-dimensional blocks, a long table with a column per dimension, or
  [GeoBrix raster tiles](../api/virtual-tiles), so every `rst_*` function works on a cube without
  converting it to GeoTIFF. Select by label or by position. See the [Zarr Reader](../readers/zarr).
- **Sample.** Read the time series at points, with the same geometry inputs as `rst_sample`
  ([sampling at points](../readers/zarr#sampling-at-points)).
- **Write back transactionally.** Create, append, update and overwrite, with history, time travel,
  tags, restore, export and lifecycle management. See the [Zarr Writer](../writers/zarr).
- **Concurrent writers.** Writers that touch different chunks both land; writers that only change the
  store's shape or coordinates are rebased automatically; writers that meet on one chunk get a clear error.

## Store kinds

A Zarr store GeoBrix works with is one of four kinds. They differ in where the bytes live, whether a
manifest table exists, and who may write.

| Kind | Created by | Where the bytes live | Versions and transactions | Who may write |
|---|---|---|---|---|
| **Plain store** | Anyone: xarray, a vendor, any Zarr tool | The store's own objects | None. GeoBrix reads the current bytes. | Not GeoBrix |
| **Registered, read-only** | `gbx_zarr_register(spark, path, table)` | The store's own objects, **not copied** | Yes, in the manifest table | Nobody through GeoBrix |
| **Registered, writable** | `gbx_zarr_register(spark, path, table, writable=True, overlay_root=...)` | The store's own objects, plus an **overlay** of new pack files | Yes | Anyone with `MODIFY` on the table and write access to the overlay root's Volume; the store itself is never written |
| **Managed** | `gbx_zarr_write(..., mode="create")` | Pack files GeoBrix wrote under the store's root | Yes | Anyone with `MODIFY` on the table and write access to the root's Volume |

![The four kinds of Zarr store side by side: a plain store with only its own objects and no manifest table; a read-only registered store whose Delta manifest table points at the store's objects without copying them; a writable registered store whose manifest points at the store's objects and at an overlay root of immutable pack files, with the store's objects locked against writes; and a managed store whose manifest points at pack files under a data root. A banner explains that many registrations of one store are independent branches and that every root has exactly one owner.](../../../resources/images/diagrams/zarr/store-kinds.png)

### How a store is made of files and rows

Every byte GeoBrix writes goes into a new **pack file** that is never modified again, under
`data/<array>/<write_id>/part-*.zpack` in the store's root. A **manifest** is a Delta table with one
row per chunk or shard (and per array and group document) that says which file, offset and length hold
it, plus one `commit` row for every write. A version of the store **is** a version of that Delta table,
and one Delta transaction is one store transaction.

Because files are immutable and rows are versioned, a reader that pins a version sees a consistent
snapshot no matter what writers do meanwhile.

### Outside changes: drift, sync and publish

GeoBrix cannot make other tools' writes to a registered store transactional, but it detects them. Every
read checks the identity of the objects it touches (their modification time and size on a Volume). If
another tool changed one, the read stops and says so, instead of returning bytes the manifest never
saw. `gbx_zarr_sync` lists the store again, records what changed, appeared or disappeared as one new
version, and lists any keys that both the store and the overlay changed (the overlay still wins).
The store's shape becomes the larger of the store's and the overlay's, so days a data provider appended
show up. A change to the array's data type, chunk grid or codecs cannot be synced; register the store
again.

(The progress lines GeoBrix prints while it syncs are left out above.)

**Publish** writes a writable registration's overlay into the store itself, so that every Zarr reader
sees it. It needs write access to the store, takes a lock so two publishes cannot interleave, and
refuses if the store changed since the last sync. Publish is **not atomic for plain readers**: it
writes the chunks first and the metadata last, so a plain reader that opens the store while it runs
can see some chunks of the new version. Other registrations of that store see drift on their next
read, and older versions that pointed at objects the publish overwrote can no longer be read.
GeoBrix records the identity of each published object only after the Volume has settled its
modification time (a Volume moves it to the next whole second a moment after the write), so a read
right after a publish does not report drift.

### One owner per root

Every root GeoBrix writes to, a managed store's root or a writable registration's overlay root, has
exactly one owner. The owner is decided by a Delta transaction, not by the file system: a small Delta
table inside the root, `_gbx_owner`, records the owner through a compare-and-swap, so when two tables
claim a root at the same moment exactly one wins, on every kind of compute. A marker file,
`_gbx_store.json`, names the owner as well; it is advisory, and a run that changes the store (not a
dry run) restores it from the ledger if it goes missing.

## File modes

`file_mode` decides how the manifest refers to a store's files, and so who deletes superseded files.
It matches the `file_mode` of `gbx_file_write`.

| `file_mode` | The manifest's `file` column | Who deletes superseded files | Where it runs |
|---|---|---|---|
| `fuse` (default) | Path strings, relative to the store's root | GeoBrix `gbx_zarr_vacuum` | Everywhere, Serverless included |
| `external` | `FILE EXTERNAL` references, governed with the table | GeoBrix `gbx_zarr_vacuum` | Compute that supports `FILE` values, in a workspace with the File type preview (**preview**) |
| `managed` | `FILE MANAGED` values | The table | **Not available in this release** |
| `auto` | `external` on compute that supports `FILE` values (Serverless included, in a workspace with the File type preview), otherwise `fuse`; it never fails | | |

The default is `fuse`, so a store made on `FILE`-capable compute still reads on every compute; pass
`file_mode="auto"` or `"external"` to keep `FILE` references.

`managed` is not available because Delta's `VACUUM` does not reclaim the bytes of a managed file, so a
managed store would only grow. A registered store is never `managed`: managed ingest would copy the
store.

**A `FILE` store needs `FILE`-capable compute.** A store whose files are `FILE` values (`external`) must
be written, maintained and read on compute that supports them. Other compute refuses up front with a
`Fix:` that tells you what to do: use a Databricks Runtime 19 dedicated cluster (single user, with
`fileReferenceCreationMode=MANAGED`) in a workspace with the preview; or copy the data out with
`gbx_zarr_export(method="copy")` and register the copy with `file_mode="fuse"`; or create stores that
other compute also uses with `file_mode="fuse"`. Reads of a store return the same cells in every mode.

## Transactions

A write happens in two phases, and only the second one is visible.

![A write in two phases. Phase one, distributed and invisible: the driver plans against a base version of the manifest and picks a write_id; executor tasks encode the chunks, fully covered chunks fresh and partly covered ones by read-modify-write at the base version; each task writes one immutable pack file for each array it holds to the Volume and returns small manifest rows to the driver. Phase two, atomic: the driver commits one Delta MERGE with a compare-and-swap on each replaced key, the changed array and coordinate rows and a commit row keyed by the write_id, and the manifest moves to the next version, visible whole. A failure before the MERGE leaves only unreferenced packs for vacuum; running a write again with the same write_id returns the version it already committed.](../../../resources/images/diagrams/zarr/write-commit.png)

1. **Files.** The input is grouped by the shard it belongs to. Each task encodes the chunks it owns and
   writes **one pack file for each array it holds**, each in a single sequential write. A chunk the input covers completely is
   encoded fresh; a chunk it only partly covers is read at the base version, patched and re-encoded.
   Each task hands back a small manifest row for every chunk it wrote.
2. **Commit.** The driver collects the rows and runs **one Delta MERGE**. It writes the chunk rows with
   a compare-and-swap (CAS) on every key it replaces (the `write_id` the key had in the base version, or
   "still absent" for a new key), the changed array and coordinate rows, and a `commit` row keyed by
   the write's `write_id`.

Until the MERGE commits nothing is visible. If anything fails before it, the version has not moved and
the packs are unreferenced files that a later vacuum removes. After it commits, the whole write is
visible at once.

The four modes are `create`, `append` (extend one dimension, by default the first time dimension),
`update` (write into the existing extent) and `overwrite` (replace whole variables; older versions
stay readable until vacuumed). Writing a variable the store lacks creates it on the store's dimensions.
Appends label the new steps: they must come after the store's last, and on a regular axis they land
at their step, so appends may arrive out of order.

### Concurrent writers

![What happens when two writers meet, in three panels. When two writers touch different chunks, both MERGEs land without a retry because Delta applies them at row level. When two appends change shared metadata, the array shape and a shared coordinate chunk, the second writer rebases: it re-reads the latest version, checks that none of its own data keys moved, recomputes the shape and the shared chunk, and retries, up to twenty attempts, without rewriting its data files. When two writes change the same chunk, the second fails its compare-and-swap and raises ZarrWriteConflict, naming the keys and the winning write, and nothing of it becomes visible.](../../../resources/images/diagrams/zarr/concurrent-writers.png)

The manifest decides, row by row.

- **Different data.** Writers that touch different chunks touch different rows, so Delta lands both
  without a retry.
- **Shared metadata.** Two appenders both change the array's shape, and often a shared coordinate
  chunk. When a writer finds that another has committed those rows first, it **rebases**: it re-reads
  the latest version, checks that none of the data keys it replaces has changed since its base (the
  CAS), recomputes the shape (the maximum extent) and redoes the coordinate chunk, and retries the
  MERGE. Its data files are never rewritten. A rebase retries up to 20 times with a jittered wait.
  Every lost round means another writer landed, so the last of N simultaneous appenders needs about
  N attempts; in GeoBrix's checks, 8 appenders to one array at the same moment all landed.
- **The same chunk.** If another writer committed a change to a chunk this write also touches, after
  this write's base version, the write raises `ZarrWriteConflict`. That includes two partial writes to
  different cells of one chunk, because each is a read-modify-write of the whole chunk.

## Lifecycle and retention

Immutable files mean old files pile up: every update, overwrite and failed write leaves packs that no
current row needs. `gbx_zarr_vacuum` deletes the files that no readable version needs.

![The timeline of a vacuum. Versions v1 to v8 run left to right, with the retain window, seven days by default, shaded at the right and the horizon, the later of the last vacuum's and the moment retain ago, where it starts; v4, the version live at the horizon, stays readable, and versions older than it raise ZarrVersionUnavailable. A pack replaced before the horizon is superseded and deleted; a pack replaced inside the window is retained because a readable version, v4, still uses it; packs that live rows point at are live; a pack that a tag row points at is tagged and kept until the tag is removed; the pack of a write that never committed is uncommitted and is kept for the retain period and then deleted; a pack younger than one hour is recent and always kept. Below, the manifest table's own retention properties keep Delta history at least as long as the store's retain, and predictive optimization may vacuum the table itself.](../../../resources/images/diagrams/zarr/retention-timeline.png)

A file is kept while **any** of these is true:

- **live**: a current row points at it;
- **tagged**: a tag row points at it;
- **retained**: a version within `retain` points at it (`retain` is `"7 days"` unless you set it when
  you created or registered the store);
- **recent**: it is under one hour old, because the write that made it may still be running. The files of
  a write that never committed are kept for the store's `retain`, too.

Everything else is **superseded** (it was replaced by a newer version, and only versions older than
`retain` used it) or **uncommitted** (its write failed, was retried or lost a conflict). `dry_run=True`
lists what would go and changes nothing. A `retain` under one hour is refused unless `force=True`,
and a `retain` longer than the store's is refused too, since versions older than the store's own
`retain` are not readable anyway.

Time travel needs two things: the files, and the manifest's own Delta history. When a store is created or
registered, GeoBrix sets the manifest table's `delta.deletedFileRetentionDuration` to at least the
store's `retain` and `delta.logRetentionDuration` to the larger of 30 days and `retain`, and vacuum keeps
them aligned; it never lowers a value you raised.

`ZarrVersionUnavailable` with a `Fix:`, even if no vacuum has ever run, because Delta's own maintenance
may already have removed the files. The latest version and every tagged version are always readable.

## Chunk rows and shard rows

Zarr v3 groups many small **inner chunks** into one **shard** object. The manifest has a row for each
of two things:

- a **shard row** points at a whole shard in one object: that is how a registered store of shards begins;
- a **chunk row** points at one inner chunk inside a pack file.

![Chunk rows over a shard row, in three stages. First, a store of shards has one shard row pointing at one shard object that holds eight inner chunks. After appends and updates, the shard row is still there but chunk rows laid over it point at replacement chunks in small packs, and one chunk is a deleted tombstone; a read lays the chunk rows over the shard's bytes. After optimize, a single shard row points at a new pack that holds all eight inner chunks again, and the chunk rows and the deleted chunk are folded away.](../../../resources/images/diagrams/zarr/chunk-vs-shard-rows.png)

A write adds chunk rows, one for each chunk it changes, in packs it has just written. That keeps
a small append or update cheap, because nothing already written is rewritten, and a new managed store is
chunk rows only. The price is on the read side: a shard is now spread over many small objects, and on a
Volume every object costs a round trip.

## Performance

What a store costs to read and write depends on its layout and on the compute. The figures below were
measured on Databricks to show the shape of the trade-offs; they are not a guarantee.

- **Data.** The ERA5 reanalysis for January 2023: 2-metre temperature, 744 hourly steps on the
  0.25-degree global grid (721 x 1440), float32. As Zarr, a v3 store with inner chunks of 24 x 90 x 90
  cells in shards of 168 x 360 x 360, compressed with zstd. For comparison, the same values as one tiled
  GeoTIFF per hour (512 x 512 tiles, ZSTD), read with the [Raster Reader](../readers/raster).
- **Compute.** The reads ran on Databricks Runtime 19 with one 4-core worker (`m5d.xlarge`), the writes
  on Databricks Runtime 19 with two 4-core workers (`m6gd.xlarge`, on demand), both with dedicated
  access; and both on Serverless environment 6.
- **Method.** Each figure is the median of three runs, the first of the three cold, except the 1 GB
  create: its figures are the median of five warm runs after a cold one, with the two Runtime 19 legs
  (through the Volume, direct to storage) taking turns.

### Reads

| Workload | Read with | Runtime 19 | Serverless |
|---|---|---|---|
| One hour of the whole globe | `gbx_zarr_read` | 3.2 s | 3.0 s |
| | GeoTIFF: `raster_gbx` and `rst_avg` | 1.9 s | 3.3 s |
| 1,000 points, every hour (744,000 values) | `gbx_zarr_sample` | 24 s | 16.5 s |
| 30 days over Europe (35-72 N, 10 W-40 E) | `gbx_zarr_read` | 4.8 s | 4.4 s |
| | GeoTIFF: 720 windows, `raster_gbx` and `rst_avg` | 232 s | 83 s |

- **A single map** is quick either way, but this store keeps 24 hours in each inner chunk, so one hour
  reads 24 hours of chunks. A store that is read mostly as maps should be written with `chunks="maps"`.
- **A time series at points** reads each chunk once for all the points in it, whatever the number of
  hours.
- **A box over many hours** reads only the chunks the box touches, in a few large reads; the GeoTIFFs
  need one file per hour.

### Writes

| Write | With | Runtime 19, through the Volume | Runtime 19, direct to storage | Serverless |
|---|---|---|---|---|
| Create a 1 GB cube (240 x 721 x 1440, float32, from 10 tasks) | `gbx_zarr_write` | 19 s | 22 s | 20 s |
| | of which writing the data files | 8.4 s (119 MB/s) | 12.4 s (80 MB/s) | 8.1 s (122 MB/s) |
| | plain `xarray.to_zarr`, no transaction | 5.4 s (184 MB/s) | | 6.1 s (163 MB/s) |
| Eight appends of one day each (100 MB) | `gbx_zarr_write`, all at once | 166 s | | 132 s |
| | `gbx_zarr_write`, one after another | 147 s | | 150 s |

Where the time of a create goes, as the median of each step over the warm runs on Serverless (19.5 s a
create): 2.5 s for the first pass over the block positions, 2.1 s claiming its root in the ownership
ledger, 1.8 s creating the manifest table, 8.1 s writing the data files, and 4.6 s for the commit (3.0 s
of it the MERGE into the manifest). On Runtime 19 through the Volume (19.3 s) the same steps took 1.7 s,
2.3 s, 1.8 s, 8.4 s and 4.9 s. Direct to storage, writing the data files varied most from run to run on
one cluster, from 7.2 s to 25.5 s; measured again on a second cluster, beside plain object-store puts of
the same size on the same nodes, it took a median 6.7 s (149 MB/s), from 5.3 s to 29.7 s. Its slow runs
spent their time in the executors' JVM garbage collection, while Spark handed each 100 MB block from the
step that computed it to the step that writes it; the writes themselves took 0.6-2.6 s each, and the
plain puts, which never cross that step, 0.5-4.9 s.

- **Blocks that are whole shards are written where they are made.** Each block of this cube is one
  shard (24 hours of the whole globe), so the task that makes a block encodes it and writes its data
  file, and nothing is shuffled. Blocks that cut across chunks or shards are regrouped first, which
  costs more; see the [Zarr Writer](../writers/zarr#blocks-on-the-stores-grid).
- **A create has a fixed cost**: claiming its root, creating the manifest table and the commit (the checks
  before them take another 0.1-0.6 s). In the warm runs its median was 9.0 s through the Volume, 8.0 s
  direct to storage and 8.4 s on Serverless (7.4-10.5 s in all); the first create on new compute, which
  ran cold, took 20.8-38.3 s, and the direct leg's first create (the cluster's second) 21.0 s. Through the Volume the commit's coordinate files cost 0.5-0.8 s against
  0.1-0.2 s direct. A write that is not a create pays the commit part of it, so write a store in a few
  large writes rather than many small ones.
- **A plain `xarray.to_zarr` is faster and gives none of the guarantees**: no versions, no all-or-nothing
  commit, no safe concurrent writers.
- **An input that is expensive to compute** is evaluated twice by a create or an append (once for its
  positions). This cube is computed in the tasks, so its first pass took 1.5-8.1 s in the warm runs and
  14-31 s in the first create on new compute. Write such an input to a table first; see the [Zarr Writer](../writers/zarr).
- **Concurrent appenders** land one per round, each rebasing on the others after a jittered wait that
  doubles with every lost round (up to 16 s). The last of eight needed
  seven or eight attempts. On Serverless eight at once took 132 s against 150 s one after another; on
  Runtime 19 with two 4-core workers they took 166 s against 147 s, the eight sharing eight cores as well
  as waiting between attempts.

## Limits

- **Runtimes.** Databricks Runtime 19 and Serverless environment 6 (Python 3.12), lightweight tier only. The
  heavyweight tier reads Zarr data only as materialized GeoBrix tiles.
- **Data types.** Numeric types and CF times. Strings and objects are not supported: an array GeoBrix
  cannot decode is left out of reads and registered without being readable, and a complex array can
  only be read as blocks (a table has no column for complex numbers, and tiles do not hold them yet).
- **Tiles.** `output="tiles"` needs the coordinates to form a regular grid.
  A tile of a registered store does not check its files for changes. A file changed in place reads as its new bytes, or fails.
  Materialize the tiles you keep.
- **Chunk grid.** Only a regular chunk grid is supported. An array with a rectilinear grid is left out of reads
  and registered without being readable.
- **Inner chunks per shard.** A shard that `gbx_zarr_write` creates holds at most 4,096 inner chunks.
  Every read of a shard fetches or builds its index, 16 bytes per inner chunk, so a shard of many tiny
  chunks makes every read slow: on a Volume, reading one chunk of a shard of 93,312 chunks took a median
  of 0.87-1.41 s, against 0.10-0.15 s at 4,096 (ten runs on two runtimes). The computed layout stays
  within the limit, and a `shards=` that goes beyond it raises `ValueError` with a `Fix:`. A registered
  store's shards are read as they are.
- **Codecs.** The codecs that zarr-python, numcodecs and zarrs can decode. Writes use `zstd` and `crc32c`
  unless you pass `codecs`. A Zarr v3 array that has any codec beside `sharding_indexed` in its own codec
  list (a transpose before it, a compressor after it) is not supported: registering the store records it as
  an array GeoBrix cannot decode, a default read leaves it out with a warning, and naming it in `variables`
  raises `ZarrUnsupported`. Rewrite the array so that `sharding_indexed` is its only outer codec, with
  compression and other codecs inside it. zarr-python does not write that layout.
- **Reading with GDAL.** A GDAL before 3.13 cannot read sharded Zarr v3 stores, or ones that use the
  `crc32c` codec, which `gbx_zarr_write` writes by default; see [the Raster Reader](../readers/raster).
- **File modes.** `external` is a preview that needs a workspace with the File type preview and compute
  that supports `FILE` values; `managed` is not available (see [File modes](#file-modes)).
- **Outside writers.** GeoBrix detects writes that other tools make to a registered store; it cannot make
  them transactional. On a Volume the identity of an object is its modification time and size, which is
  weaker than a content hash. A publish is not atomic for plain readers.
- **Many simultaneous appenders.** A rebase retries up to 20 times, and the last of N simultaneous
  appenders needs about N attempts. A burst of more than about twenty writers
  appending to one array at the same instant can exhaust that, and the last of them fails with
  `ZarrWriteConflict` and a `Fix:`; run it again.
- **Direct storage access.** `access="auto"` reads and writes cloud storage directly where Unity Catalog
  can issue temporary credentials (dedicated compute), and through the Volume mount elsewhere, including
  Serverless. Direct access sends short-lived, Volume-scoped credentials (at most one hour) to the
  executors, and under memory pressure Spark may spill task data, those credentials included, to local disk:
  turn on local-disk encryption on clusters that use it, or pass `access="fuse"`, which sends none. Direct
  access has been measured on AWS only; Azure and Google Cloud storage are not measured yet, and
  `access="fuse"` reads and writes through the Volume mount there.
- **Incomplete uploads.** A pack upload that is refused or fails part way can leave an incomplete multipart
  upload in the bucket. GeoBrix does not clean it up: add a bucket lifecycle rule that aborts incomplete
  multipart uploads (`AbortIncompleteMultipartUpload`) to the bucket of the Volume.
- **Branches.** Registrations of one store do not merge.
- **Version history is bounded by `retain`.** Tag a version to keep it indefinitely.
