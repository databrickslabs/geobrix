# Auto Loader ingestion

_Since:_ **v0.6.0** · _(light-only — no heavyweight tier)_

`declare_ingest` declares a complete ingestion flow in a Lakeflow pipeline: Auto Loader watches a
Volume folder, each new or changed file is read with the GeoBrix reader you name, and the rows land
in a table. `on_change` decides what happens when a file is overwritten: keep every version
(`scd2`, the default), keep only the latest content (`replace`), or append every delivery
(`append`). Data that cannot be read is set aside in a bad-records table, and the rest is written
(`on_error`).

Set up the pipeline first (channel, GeoBrix extra, Serverless notes): see
[Lakeflow SDP](./lakeflow-sdp).

![declare_ingest flow — Auto Loader (cloudFiles, binaryFile) watches the source_dir landing folder, where glob picks the files, and delivers an overwritten file again. Under scd2 and replace, each delivery becomes a row of the file-events table with its SHA-256 \_source_hash; a foreach_batch_sink skips content already stored and reads the newest delivery of each file with read_paths into the target rows table, where scd2 appends each new version and replace swaps a file’s rows with an atomic replaceWhere. Under scd2, AUTO CDC SCD type 2 builds the file-versions table from the file events, with history on \_source_hash, and the current view joins it with the rows to show each file’s latest readable version. With on_error set to quarantine, each micro-batch is read once into a staging folder under scratch_dir and what cannot be read is appended to the bad-records table before the rows. :::tip Key considerations
- **`scd2` is the default and keeps every version.** The rows table grows with each content
  change of a file. Use `on_change="replace"` when only the latest content matters.
- **Stage one file before the first update.** The schema is read from `schema_path` (by default
  the first matching file in `source_dir`) when the pipeline is declared, at each update.
- **Unity Catalog Volume paths only.** `source_dir` and `schema_path` are `/Volumes/...` paths; to
  ingest from cloud storage, create an external volume over it. See [Paths](./read-paths#paths).
- **Each format has a default file pattern**, with lower- and upper-case extensions. GeoJSON is
  matched by `.geojson` only (pass `glob="*.{geojson,json}"` for `.json` files), a File
  Geodatabase is delivered as a `.gdb.zip` file, and `pmtiles_gbx` needs its `source` option. See
  [Default file patterns](./read-paths#default-file-patterns).
- **Set `num_partitions` on Serverless.** Without it a large raster or PMTiles archive is read by
  a single task. See [Parallelism](./read-paths#parallelism).
- **Use a channel that has the pipeline APIs.** `declare_ingest` needs `pyspark.pipelines` with
  `foreach_batch_sink` and `create_auto_cdc_flow` (the `CURRENT` channel has them), and the
  GeoBrix extra for that channel's runtime. See [Environment](./lakeflow-sdp#environment).
- **Overwrite files without preserving their modification time.** A copy made with `cp -p` or
  `rsync -t` can give new content an older time than the version it replaces (see
  [Query the latest content](#query-the-latest-content-and-past-content)).
- **Bad data is set aside, not fatal.** By default (`on_error="quarantine"`) a file, a feature, a
  raster window or a run of LiDAR points that cannot be read goes to `<t>_bad_records`, and the
  rest of the micro-batch is written. Each micro-batch is staged in a hidden folder under
  `scratch_dir` (default `source_dir`), so the pipeline must be able to write there; landing folders
  are often read-only to the pipeline, so set `scratch_dir` to a Volume folder it can write. See
  [Unreadable data](#unreadable-data).
:::

## `declare_ingest` parameters

```python
declare_ingest(target, source_dir, format, options=None, *,
               on_change="scd2", glob=None, num_partitions=None, schema_path=None,
               on_error="quarantine", scratch_dir=None)
```

| Parameter | Default | Description |
|-----------|---------|-------------|
| `target` | _required_ | Rows table, a fully qualified `catalog.schema.table` name. The other objects are created in the same catalog and schema. |
| `source_dir` | _required_ | Volume folder Auto Loader watches (see [Paths](./read-paths#paths)). |
| `format` | _required_ | Reader name from the [formats table](./read-paths#supported-formats). |
| `options` | `None` | Reader options, exactly as on that reader's page. |
| `on_change` | `"scd2"` | What to do when a file is overwritten: `"scd2"`, `"replace"` or `"append"`. See [Choosing `on_change`](#choosing-on_change). |
| `glob` | `None` | File-name filter for the folder, in Spark `pathGlobFilter` syntax, such as `"zones_*.gpkg"`. By default, the format's [default file pattern](./read-paths#default-file-patterns); a `glob` replaces that pattern. |
| `num_partitions` | `None` | Spread the reads across this many tasks. See [Parallelism](./read-paths#parallelism). |
| `schema_path` | `source_dir` | File or folder that defines the table schema; a folder's first file matching `glob` is used. It is read once when the pipeline is declared (at each update), not for every micro-batch. |
| `on_error` | `"quarantine"` | What to do with data that cannot be read: `"quarantine"` sets it aside in `<t>_bad_records` and writes the rest; `"fail"` fails the update. See [Unreadable data](#unreadable-data). |
| `scratch_dir` | `source_dir` | Volume folder (`/Volumes/...`, shared by every node) where `on_error="quarantine"` stages each micro-batch, in a hidden `.gbx_scratch` folder that is removed when the micro-batch ends. The pipeline must be able to write it. Set it when the landing folder is read-only to the pipeline. |

Auto Loader delivers every file under `source_dir` on its own, so the file pattern must leave out
the other files of a multi-file dataset: a shapefile's sidecars, or the files inside an unzipped
`.gdb` folder. The format's default pattern does; a `glob` you set replaces it, so for shapefiles
end it in `.shp`. See [Default file patterns](./read-paths#default-file-patterns).

## Choosing `on_change`

Auto Loader runs with `cloudFiles.allowOverwrites` on in every mode, so a file that is overwritten in
place is delivered again. `on_change` decides what the table does with that second delivery.

| | `scd2` (default) | `replace` | `append` |
|---|---|---|---|
| **Rows table** | Append-only: one copy of a file's rows for each distinct content version | Latest content of each file only | Every delivery of every file |
| **Re-delivery, content unchanged** | Writes nothing | Writes nothing | Duplicates the rows |
| **File modified** | New rows are added; the earlier version's rows stay | That file's rows are replaced, one atomic `replaceWhere` per micro-batch | New rows are added; the earlier rows stay |
| **History** | `<t>_file_versions` records when each version was current | None | None |
| **Rows have `_source_hash`** | Yes | Yes | No |
| **Use when** | You need the latest content and a record of what it used to be | Only the latest content matters | You want a log of every delivery |

Here `<t>` is the last part of `target`. `scd2` and `replace` compare a SHA-256 hash of the file's
bytes (`_source_hash`) with what is already stored, so a file that is re-delivered without a content
change is recognized and skipped. `append` does not hash anything.

Each mode declares these objects in the catalog and schema of `target`:

| Object | `scd2` | `replace` | `append` |
|--------|:------:|:---------:|:--------:|
| `target`: the rows | yes | yes | yes (streaming table) |
| `<t>_file_events`: one row per delivery with `_source_path`, `_source_mtime`, `_source_hash`, `_source_size` | yes | yes | no |
| `<t>_file_versions`: one row per content version of a file, with `__START_AT` and `__END_AT` | yes | no | no |
| `<target>_current`: a view of the rows for each file's latest version | yes | no | no |
| `<t>_bad_records`: one row per bad record, created when the first one is found | yes | yes | no |

In `scd2` and `replace` the rows table is written by the pipeline's batch sink: it is a regular
Delta table, created on the first update and clustered by `_source_path`, not a dataset the
pipeline manages.

## Query the latest content and past content

`<target>_current` returns the rows of each file's latest readable version: the newest version
whose content has rows in the table. It is a plain view that scans the rows table, so filter it by
`_source_path` to look up one file quickly. A delivery that could not be read is still recorded as the
file's newest version in `<t>_file_versions`, but it does not hide the content that was read before
it (see [Unreadable data](#unreadable-data)). To read what was current at an earlier time, join the
rows to the versions table on both `_source_path` and `_source_hash`, and keep the version whose
interval contains the time:

`__START_AT` and `__END_AT` are the file's modification times, so the time you ask for is when the
file's content was written, not when the pipeline ingested it. `__END_AT` is `NULL` for the
current version, and an interval includes its start and excludes its end. For a time when the
file's content could not be read, the query returns no rows for that file.

"Current" means the version with the newest modification time. A copy that keeps or backdates the
source's modification time (`cp -p`, `rsync -t`) can give an overwrite an older time than the
version it replaces; that content is then recorded as history and does not become current. Copy
without preserving times when you overwrite a file.

## Unreadable data

`on_error` decides what a micro-batch does with data its reader cannot read:

| `on_error` | What happens |
|---|---|
| `"quarantine"` (default) | Each file is read on its own, and what cannot be read is a **bad record**: it is written to `<t>_bad_records`, then the rest of the micro-batch is written to the rows table. The update succeeds. |
| `"fail"` | The first error fails the update, with an error that names the file. |

A bad record is the smallest part of a file its reader can set aside: a whole file that cannot be
opened, or whose columns differ from the table schema; a feature whose geometry bytes are not
readable, or whose text is not valid UTF-8; a GeoJSONSeq line that is not JSON; a raster tile
window; a run of LiDAR points; a PMTiles tile; a NetCDF variable or slice. Rows read from a file
before an error stay in the table. The [Unreadable files](./read-paths#unreadable-files) reference
lists what each format sets aside, and the damage no reader can detect.

A NULL or empty geometry is data, not a bad record: a feature without a location
(`"geometry": null` in GeoJSON) or a `POINT EMPTY` is written like any other row. GDAL also returns
NULL for a geometry it cannot decode (an unknown geometry type, unreadable coordinates, a damaged
GeoPackage or shapefile record), so those rows are written too. To watch for them, query the
geometry column with `IS NULL` (it is `geom_0` for GeoJSON) and `ST_IsEmpty`. Curves and
surfaces (`CircularString`, `CompoundCurve`, `CurvePolygon`, `MultiCurve`, `MultiSurface`,
`PolyhedralSurface`, `TIN`, `Triangle`) are data too.

Errors of the environment are not bad data either. Out of memory, a missing module (such as a LAZ
decompression backend), an I/O error of the Volume (retried first), and an image too large to read
whole in `exif_gbx` `qc` mode fail the micro-batch, so Spark retries the task or the update fails
with that error, and no bad record is written for them.

:::caution Damaged LAZ point data can stop the worker
A LAZ file whose chunk table or LASzip record is implausible or cannot be decoded is set aside
before it is decoded. Other damage, inside the compressed points (a region of `0xFF` bytes, for
example) or in a chunk table that is wrong but plausible, still reaches the native LAZ decoder
(`lazrs`), and can crash it and end the worker process. A crash cannot be
caught, so the file is not set aside: the task fails, Spark retries it, and then the update fails.
Remove the file or replace it with a readable copy to continue.
:::

| `raw` | `STRING` | What can be recovered, as JSON of at most 4096 characters (longer is cut and marked `"truncated": true`): a feature's other columns (text that is not UTF-8 is escaped, a binary value is shown as `<binary, N bytes>`), a GeoJSONSeq line, or a LiDAR point's `x`, `y` and `z`. | `quarantined_at` | `TIMESTAMP` | When the micro-batch set it aside |

| `error_class` | Set aside because |
|---------------|-------------------|
| `UnreadableGeometry` | The geometry bytes are not valid WKB (for example a polygon ring that is not closed) |
| `InvalidText` | A text value is not valid UTF-8 |
| `RecordsNotRead` | The file declares features, points or lines its reader did not return (a dropped `.dbf` record, an unreadable GeoPackage page, a truncated LAS file, a GeoJSONSeq line that is not JSON) |
| `PointOutOfBounds` | LiDAR points outside the bounds the file's header declares, widened on every side by their largest extent (garbled point records, or garbage that damaged LAZ data decodes to); off with the `lidar_gbx` option `checkHeaderBounds="false"` |
| `ShortTile` | A PMTiles tile is shorter than its directory entry declares (a truncated archive) |
| `NotJpeg` | A `.jpg` / `.jpeg` file has no JPEG start marker, or header segments that do not lead to a frame header (nothing is decoded, so a very large image is still a JPEG; a missing end marker only gives a warning: a truncated scan, or a Motion Photo's video after the image) |
| `UnreadableFile` | An empty file, or a LAS file whose point record length does not fit its data |
| `NothingReadable` | No row of the delivery could be read: every record of it was set aside. One per delivery (`record_index` is `NULL`), next to the records that say why |

### How bad records interact with the tables

- **A file with bad records still has its version.** Under `scd2` the delivery is recorded in
  `<t>_file_versions` like any other. When part of a file's new content was set aside, the rows
  that were read are written under the new hash, and that version is current. When all of it was
  set aside, the version has no rows, so `<target>_current` keeps showing the file's last readable
  content, and `<t>_bad_records` explains the empty version. Removing the bad file keeps it that
  way. The same holds for a file overwritten with content that has no rows (an emptied file):
  `<target>_current` keeps showing its previous rows, while `replace` removes them.
- **`replace` keeps the last readable rows too.** A delivery that is partly readable replaces the
  file's earlier rows with the rows that were read. A delivery set aside entirely (a
  `NothingReadable` record) leaves the file's earlier rows in place.
- **The same bad bytes are not read twice.** A re-delivery with the same content is skipped when it
  has rows in the table, or when it was set aside entirely: it would be set aside again. A
  re-delivery with new content is read.
- **Each micro-batch is staged in `scratch_dir`.** The files are read once: the rows go to a
  hidden `.gbx_scratch` folder under `scratch_dir` (default `source_dir`), in a subfolder of its own
  for each target table, while the bad records are collected there. Then the bad records are
  appended to `<t>_bad_records`, then the rows to the table, and the folder is removed. A bad record
  already in the table is not appended again, so a micro-batch that fails between the two writes
  and is retried neither loses nor repeats one. A staging folder left by a killed micro-batch is
  removed a day later, by the next micro-batch of the same table; pipelines that share a
  `scratch_dir` never touch each other's folders. When the pipeline cannot write to
  `scratch_dir`, the micro-batch fails with an error that says so.
- **To read a file that was set aside again**, for example after fixing a reader option, delete
  its `NothingReadable` rows from `<t>_bad_records` (`DELETE FROM ... WHERE _source_path = '...'
  AND error_class = 'NothingReadable'`), then touch the file or deliver it again. Until then an
  identical delivery is skipped. A delivery that was partly read has rows under its
  `_source_hash`, so the same bytes delivered again are skipped as stored: to read it again,
  delete its rows for that hash from the table (`DELETE FROM ... WHERE _source_path = '...' AND
  _source_hash = '...'`) before you touch or deliver it, or deliver changed content.
- **`append` has no bad-records table.** Its rows table is a plain streaming table, so bad records
  are skipped with a warning in the executor logs, and nothing is staged. Use `scd2` or `replace` to
  keep them.

### With `on_error="fail"`

The update fails with the reader's error, which names the file. Nothing from that micro-batch is
written to the rows table, and the flow's progress is not saved, so the next update reads the same
files again and fails the same way until the file is dealt with. To recover, remove the file or
replace it with a readable copy, then start an update. A file deleted before it is read is skipped
with a warning (see [Files deleted before they are read](./read-paths#files-deleted-before-they-are-read));
a replacement is delivered again and handled like any overwritten file (see
[Choosing `on_change`](#choosing-on_change)). The [Lakeflow connector](./lakeflow-connector)
always reads this way.

## What a pipeline update does

- **The newest delivery of each file wins** (`scd2` and `replace`). When one micro-batch holds
  several deliveries of the same file, only the newest is read, because the bytes on disk are the
  newest content. Under `scd2` the older deliveries still appear in `<t>_file_versions`, but have
  no rows in the table.
- **A file modified after it was hashed is skipped** (`scd2` and `replace`) until its newer delivery
  arrives, so a row's `_source_hash` describes the content it was read from. Before reading, each
  file must still have its delivered size and a modification time within one second of the
  delivered one. A file overwritten in the instant between that check and the read, or rewritten
  with the same size within that second, can still be stored under the earlier hash; its next
  delivery is written as usual (and under `scd2` recorded as the current version).
- **A file deleted before it is read is skipped** with a warning (all modes), and Auto Loader counts
  it as processed. Deleting a file does not remove rows that were already written, with one rare
  exception: under `replace`, a file deleted in the instant between that check and the read is
  still part of the micro-batch's `replaceWhere`, so its earlier rows are removed and no new rows
  are written for it.
