# Installation

GeoBrix has two [execution tiers](./api/execution-tiers.mdx) — the pure-Python **lightweight** tier
and the JVM + native GDAL **heavyweight** tier — and three ways to install them. Pick the path that
matches the tier you need and the compute you run on.

## Choose an install path {#choose-an-install-path}

![Three ways to install GeoBrix — the question of which tier you need, and on which compute, branches three ways: lightweight tier only leads to path a, WHL-only (Lightweight), recommended, installed with the light_env6 extra or another runtime-pinned extra, running on Serverless, standard access mode, Lakeflow pipelines, classic clusters and ARM, with one wheel from a Volume or the GitHub release and no JAR, init script or native GDAL bundle, giving the lightweight tier; heavyweight on Graviton (arm64) leads to path b, Databricks Container Service, preferred for the heavyweight tier, a GeoBrix container image on a dedicated Graviton (arm64) DBR 19 cluster carrying native GDAL and the wheel, plus the JAR as a cluster library, giving both the lightweight and heavyweight tiers, with x86 (amd64) and DBR 17.3 / 18 not yet covered; heavyweight on classic x86 leads to path c, Init Script (Legacy), geobrix-gdal-init.sh on a classic x86 cluster running DBR 17.3, 18 or 19, with the init script, GDAL tarball and .sha256 sidecar on a Volume and the wheel as a cluster library, still supported where the DCS image does not reach yet, giving the heavyweight tier](../../resources/images/diagrams/installation/installation-paths.png)

| Path | Tiers | Compute | What you install |
|---|---|---|---|
| **(a) [WHL-only (Lightweight)](#whl-only)** — recommended | Lightweight | Serverless, standard access mode, Lakeflow declarative pipelines, classic clusters, ARM | One wheel with a runtime-pinned extra — no JAR, no init script |
| **(b) [Databricks Container Service](./installation/dcs.mdx)** — preferred for heavyweight | Lightweight + Heavyweight | Dedicated cluster, Graviton (arm64), DBR 19 | A GeoBrix container image (native GDAL + the wheel) and the JAR as a cluster library |
| **(c) [Init Script (Legacy)](./installation/init-script.mdx)** | Heavyweight | Classic x86 cluster, DBR 17.3 / 18 / 19 | The GDAL init script, its tarball + `.sha256` sidecar on a Volume, and the wheel as a cluster library |

**(a) WHL-only (Lightweight)** is the default: if you don't specifically need the JVM tier, install
the wheel and stop there. The full install steps are [below](#whl-only).

**(b) Databricks Container Service** is the **preferred packaging for the heavyweight tier**. A
dedicated cluster starts from a GeoBrix container image that already carries native GDAL with its
Java bindings and the GeoBrix wheel, so there is no init script and nothing to install at cluster
start; attach the GeoBrix JAR as a cluster library for the heavyweight tier. Verified today on
dedicated Graviton (arm64) clusters with DBR 19; x86 (amd64) and DBR 17.3 / 18 are not yet covered.
See [Databricks Container Service](./installation/dcs.mdx).

**(c) Init Script (Legacy)** is the older heavyweight route, still supported for compute the DCS
image doesn't cover yet — today, classic x86 clusters on DBR 17.3, 18, or 19. A versioned init
script installs native GDAL at cluster start from a hash-verified tarball staged in an isolated Unity
Catalog Volume folder, and puts the JAR in place. See
[Init Script (Legacy)](./installation/init-script.mdx).

## Supported Databricks Runtimes

GeoBrix supports the following Databricks Runtime releases:

| DBR | Ubuntu | Spark | Python | Scala | Java | GeoBrix |
|---|---|---|---|---|---|---|
| **17.3** | 24.04 | 4.0.0 | 3.12.3 | 2.13.16 | 17 | ✅ Supported |
| **18** | 24.04 | 4.1.0 | 3.12.3 | 2.13.16 | 21 | ✅ Supported |
| **19** | 24.04 | 4.2.0 | 3.12.3 | 2.13.18 | 21 | ✅ Supported |

A **single wheel + single JAR** runs on 17.3, 18, and 19: Scala 2.13 minor versions are binary-compatible, the JAR is compiled to Java-17 bytecode so it loads on all three JVMs, and Spark is a `provided` dependency.

GeoBrix Light uses **explicit, runtime-pinned extras** — there is no bare `[light]`. On Serverless, use `geobrix[light_env6]` (environment v6, recommended) or `geobrix[light_env5]` (environment v5). On classic clusters, use `geobrix[light_dbr17]`, `geobrix[light_dbr18]`, or `geobrix[light_dbr19]` to match your runtime. See the extras table under [WHL-only (Lightweight)](#whl-only) below.

:::note PySpark comes from the runtime
On Databricks, GeoBrix uses the PySpark that the runtime provides — installing GeoBrix never downloads PySpark. Outside Databricks (for example a local Spark session), install `pyspark>=4.0.0` alongside GeoBrix.
:::

## WHL-only (Lightweight) {#whl-only}

The lightweight tier is a single Python wheel installed with a runtime-pinned light extra (`light_env6` on Serverless, `light_dbrN` on classic) — **no init script, no JAR, no native GDAL bundle** (rasterio's bundled GDAL does the work). It runs on serverless compute, standard (shared) clusters, Lakeflow declarative pipelines, and ARM. One wheel covers the whole lightweight tier: RasterX (the full `rst_*` set, via `databricks.labs.gbx.pyrx`), VectorX (via `databricks.labs.gbx.pyvx`), and GridX quadbin (via `databricks.labs.gbx.pygx`).

:::note Choose an extra for your runtime
GeoBrix Light uses **explicit, runtime-pinned extras** — every install picks a named, runtime-pinned extra. Pick the one that matches your compute:

| Runtime | Install command | Full feature set |
|---|---|---|
| Serverless env 6 (recommended) | `%pip install "geobrix[light_env6] @ file:///Volumes/…"` | `geobrix[light_env6_all]` |
| Serverless env 5 | `%pip install "geobrix[light_env5] @ file:///Volumes/…"` | `geobrix[light_env5_all]` |
| Classic DBR 17.3 | `%pip install "geobrix[light_dbr17] @ file:///Volumes/…"` | `geobrix[light_dbr17_all]` |
| Classic DBR 18 | `%pip install "geobrix[light_dbr18] @ file:///Volumes/…"` | `geobrix[light_dbr18_all]` |
| Classic DBR 19 | `%pip install "geobrix[light_dbr19] @ file:///Volumes/…"` | `geobrix[light_dbr19_all]` |

*(Full feature set (`_all`) = `[light_envN/_dbrN]` + `[stac]` + `[vizx]` in one install. `[databricks]` is added separately if needed.)*

*`[earthdata]` and `[overture]` are source-specific downloaders kept **outside `_all`** (they change preinstalled base packages on install). Add either alongside your runtime extra — e.g. `geobrix[light_env6,overture]` — or, to use one with the full feature set, install it as a **separate step after** `_all` (not combined in one command). See **[NASA Earthdata / EMIT](./sample-data/emit-downloader)** and **[Overture Maps](./sample-data/overture-downloader)** for details.*

The `file:///Volumes/…` path is a placeholder for the wheel on your Unity Catalog Volume — see
the install steps below for the exact pattern including the PEP 508 `package @ file://` quoting
required on Serverless.
:::

:::note Upgrading from GeoBrix 0.4.x?
**GeoBrix 0.4.x** used a single unversioned extra: `geobrix[light]` (basic) or `geobrix[light,stac,vizx]` (with feature extras). In **0.5.0+** those bare extras are removed — every install names the target runtime explicitly. Replace `[light]` with the matching runtime extra from the table above (e.g. `[light_env6]` on Serverless, `[light_dbr19]` on classic DBR 19). Feature extras (`stac`, `vizx`, `overture`, `earthdata`) are still available and combine with the runtime extra; `[overture]` and `[earthdata]` are opt-in downloaders not included in `_all` — see the note above.
:::

:::tip On Serverless, use `geobrix[light_env6]`
**Environment v6 is recommended for Serverless.** Install `geobrix[light_env6]` and set the environment version to **6** — in the Environment side panel, or `environment_version: "6"` on a job. For an env 5 Serverless cluster, use `geobrix[light_env5]` instead.

**Force-reload on Serverless without touching dependencies.** To swap in fresh wheel bytes during an interactive session, run this in a cell towards the top of your notebook:

```python
%pip install --force-reinstall --no-deps "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>-py3-none-any.whl"
%pip install "geobrix[light_env6] @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>-py3-none-any.whl"
dbutils.library.restartPython()
```

Keep `--no-deps` alongside `--force-reinstall` — without it, pip force-reinstalls dependencies that are already preinstalled and Serverless fails the cell. The second, plain install then restores any dependencies the first (deps-skipped) step left out.
:::

The wheel ships as a **GitHub release artifact** for GeoBrix 0.4.0+ — it is **not** published to PyPI. Install it from a Unity Catalog Volume so the same path works on both Serverless and Classic compute:

1. **Download** `geobrix-<version>-py3-none-any.whl` from the [GeoBrix releases](https://github.com/databrickslabs/geobrix/releases) (0.4.0 or later).
2. **Stage** it in a Unity Catalog Volume your compute can read, e.g. `/Volumes/<catalog>/<schema>/<volume>/geobrix/`.
3. **Install** it — either notebook-scoped with the `%pip` magic (installs across the whole cluster for the notebook session; plain `pip` installs only on the driver), or as a [cluster-scoped library](https://docs.databricks.com/aws/en/libraries/notebooks-python-libraries#manage-libraries-with-pip-commands) pointing at the same Volume path (works on Serverless and Classic):

```python
%pip install "geobrix[light_env6] @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>-py3-none-any.whl"
```

:::warning Serverless install form
**Use the quoted `geobrix[light_env6] @ file://…` form.** Install with the **PEP 508
named form above**, wrapped in quotes as a single argument. Do **not** put the
extra on the path (`'/Volumes/…/geobrix-<version>-py3-none-any.whl[light_env6]'`): on
**Serverless**, `%pip` writes the requirement to a file *including the
surrounding quotes*, so pip reads `[light_env6]` as part of the filename and fails
with *"Expected package name at the start of dependency specifier."* The named
form installs cleanly on **Serverless**, standard/shared, and ARM.
:::

**Or install straight from the GitHub release.** When your compute can reach github.com, skip the
download-and-stage steps and point pip at the release asset. Keep the same quoted PEP 508 named
form, with the extra for your runtime:

```python
%pip install "geobrix[light_env6] @ https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>-py3-none-any.whl"
dbutils.library.restartPython()
```

On a classic cluster, use your runtime's extra instead (for example `geobrix[light_dbr19]`). For a
Serverless job, add the requirement as a dependency line of the job's environment, written
**without spaces around `@`**, with the extra for its environment version (`light_env5` for
version 5, `light_env6` for version 6):

```text
geobrix[light_env6]@https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>-py3-none-any.whl
```

Environment dependencies are installed with an unquoted `%pip install`, so spaces around `@` split
the requirement and the install fails. A Lakeflow pipeline's dependency lines follow the same rule,
but the pipeline runs on the Databricks Runtime of its channel, not on a Serverless environment
version, so it takes the extra for that runtime, not a `light_env` one. See
[Lakeflow SDP](./ingestion/lakeflow-sdp#environment).

Workspaces that restrict outbound network access (for example, Serverless egress controls) can
block GitHub — install from a Unity Catalog Volume, as above, in that case.

Then import the package(s) you need and (optionally) register their SQL functions. Each light package exposes the same `functions` / `register(spark)` pattern:

```python
from databricks.labs.gbx.pyrx import functions as rx  # RasterX (rst_*)
# from databricks.labs.gbx.pyvx import functions as vx  # VectorX (st_*)
# from databricks.labs.gbx.pygx import functions as gx  # GridX quadbin (quadbin_*)

# optional — only needed to call the SQL functions:
rx.register(spark)

# Light DataSource readers (raster_gbx, gtiff_gbx, etc.) are Python DataSource
# V2 and aren't auto-discovered — register them explicitly when you need them:
# from databricks.labs.gbx.ds import register
# register.register(spark)
```

### Verify the lightweight tier

Confirm the wheel imports, rasterio's bundled GDAL is present, and a function runs end to end (no JAR, no init script). The check below exercises RasterX (`rst_*`); VectorX (`pyvx`, `st_*`) and GridX quadbin (`pygx`, `quadbin_*`) ship in the same wheel and register and run the same way:

```python
import rasterio
from databricks.labs.gbx.pyrx import functions as rx

print("rasterio", rasterio.__version__, "| bundled GDAL", rasterio.__gdal_version__)

# Functional check: load a GeoTIFF and read its properties through pyrx.
tiles = (
    spark.read.format("binaryFile")
    .load("/Volumes/<catalog>/<schema>/<volume>/path/to/*.tif")
    .select(rx.rst_fromcontent("content", "GTiff").alias("tile"))
)
tiles.select(
    rx.rst_width("tile").alias("width"),
    rx.rst_height("tile").alias("height"),
    rx.rst_srid("tile").alias("srid"),
).show()
```

If the import succeeds and the query returns raster dimensions, the lightweight tier is ready. For the heavyweight tier, continue with [Databricks Container Service](./installation/dcs.mdx) or [Init Script (Legacy)](./installation/init-script.mdx).
