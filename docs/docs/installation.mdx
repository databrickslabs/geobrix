# Installation

GeoBrix has two [execution tiers](./api/execution-tiers.mdx) — the pure-Python **lightweight** tier
and the JVM + native GDAL **heavyweight** tier — and three ways to install them. Pick the path that
matches the tier you need and the compute you run on.

## Choose an install path {#choose-an-install-path}

![Three ways to install GeoBrix — the question of which tier you need, and on which compute, branches three ways: lightweight tier only leads to path a, WHL-only (Lightweight), recommended, installed as the env wheel for the runtime (env5 or env6), running on Serverless, standard access mode, Lakeflow pipelines, classic clusters and ARM, with one wheel from a Volume or the GitHub release that carries its own GDAL, PROJ and GEOS, giving the lightweight tier; heavyweight on a dedicated cluster leads to path b, Cluster libraries, the env wheel and the GeoBrix JAR both installed as cluster libraries from a Volume, running on a dedicated cluster with x86 on DBR 17.3, 18 or 19 or Graviton on DBR 19, where the wheel's own GDAL serves the JVM, giving both the lightweight and heavyweight tiers; heavyweight on arm64 or x86 with DBR 19 leads to path c, Databricks Container Service, a GeoBrix container image with the env6 wheel, its native GDAL and the JAR, run on a dedicated Graviton (arm64) or x86 (amd64) DBR 19 cluster with no library to attach, giving both the lightweight and heavyweight tiers](../../resources/images/diagrams/installation/installation-paths.png)

| Path | Tiers | Compute | What you install |
|---|---|---|---|
| **(a) [WHL-only (Lightweight)](#whl-only)** — recommended | Lightweight | Serverless, standard access mode, Lakeflow declarative pipelines, classic clusters, ARM | The env wheel for the runtime (`+env5` or `+env6`) |
| **(b) [Cluster libraries (Heavyweight)](#heavyweight)** | Lightweight + Heavyweight | Dedicated cluster, x86 on DBR 17.3 / 18 / 19, Graviton (arm64) on DBR 19 | The env wheel and the GeoBrix JAR, both as cluster libraries |
| **(c) [Databricks Container Service](./installation/dcs.mdx)** | Lightweight + Heavyweight | Dedicated cluster, Graviton (arm64) or x86 (amd64), DBR 19 | A GeoBrix container image (the env6 wheel, its native GDAL and the JAR) — no library to attach |

**(a) WHL-only (Lightweight)** is the default: if you don't specifically need the JVM tier, install
the wheel and stop there. The full install steps are [below](#whl-only).

**(b) Cluster libraries (Heavyweight)** adds the JVM tier. A dedicated cluster installs the env wheel
and the GeoBrix JAR as cluster libraries. The wheel carries the native GDAL, PROJ and GEOS, and the JVM
loads them from the wheel, so nothing else is installed. Verified on dedicated
clusters with x86 on DBR 17.3, 18 and 19, and Graviton (arm64) on DBR 19. See [below](#heavyweight).

**(c) Databricks Container Service** starts a dedicated DBR 19 cluster from a GeoBrix container image.
The image already holds the env6 wheel with its native GDAL, and the GeoBrix JAR, so there is no library
to attach. It runs on both Graviton (arm64) and x86 (amd64) instance types, each with its own image tag.
See [Databricks Container Service](./installation/dcs.mdx).

The **heavyweight tier needs dedicated compute** (a dedicated access mode cluster), through (b) or
(c). On standard access mode and Serverless, use **(a)**: the lightweight tier runs there in full.

## Supported Databricks Runtimes

GeoBrix supports the following Databricks Runtime releases:

| DBR | Ubuntu | Spark | Python | Scala | Java | GeoBrix |
|---|---|---|---|---|---|---|
| **17.3** | 24.04 | 4.0.0 | 3.12.3 | 2.13.16 | 17 | ✅ Supported |
| **18** | 24.04 | 4.1.0 | 3.12.3 | 2.13.16 | 21 | ✅ Supported |
| **19** | 24.04 | 4.2.0 | 3.12.3 | 2.13.18 | 21 | ✅ Supported |

A **single JAR** runs on 17.3, 18, and 19: Scala 2.13 minor versions are binary-compatible, the JAR is compiled to Java-17 bytecode so it loads on all three JVMs, and Spark is a `provided` dependency.

On Databricks, GeoBrix installs as the **env wheel** for the runtime's family. There is one wheel per
family, and no light extra to pick:

| Runtime | Wheel |
|---|---|
| Serverless environment 6 (recommended), DBR 19, DBR 19 ML, SQL warehouses and UC functions | `geobrix-<version>+env6-py3-none-any.whl` |
| Serverless environment 5, DBR 17.3, DBR 18, Lakeflow declarative pipelines | `geobrix-<version>+env5-py3-none-any.whl` |

See [WHL-only (Lightweight)](#whl-only) below for the install steps.

:::note PySpark comes from the runtime
On Databricks, GeoBrix uses the PySpark that the runtime provides — installing GeoBrix never downloads PySpark. Outside Databricks (for example a local Spark session), install `pyspark>=4.0.0` alongside GeoBrix.
:::

## WHL-only (Lightweight) {#whl-only}

The lightweight tier is a single Python wheel, the **env wheel** for your runtime — **no separate JAR and no native GDAL bundle**. The env wheel carries its own GDAL, PROJ and GEOS. It also carries `rasterio`, `pyogrio`, `pyproj`, `shapely`, `netCDF4` and GDAL's own `osgeo`, built against them. A process runs one GDAL. It holds the runtime's preinstalled packages instead of replacing them. It runs on serverless compute, standard (shared) clusters, Lakeflow declarative pipelines, and ARM. One wheel covers the whole lightweight tier: RasterX (the full `rst_*` set, via `databricks.labs.gbx.pyrx`), VectorX (via `databricks.labs.gbx.pyvx`), and GridX quadbin (via `databricks.labs.gbx.pygx`).

:::note Choose the wheel for your runtime
| Runtime | Install command |
|---|---|
| Serverless environment 6 (recommended), DBR 19, DBR 19 ML | `%pip install "geobrix @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"` |
| Serverless environment 5, DBR 17.3, DBR 18 | `%pip install "geobrix @ file:///Volumes/…/geobrix-<version>+env5-py3-none-any.whl"` |

**Feature extras.** Add them in brackets, on the same line: `"geobrix[stac,vizx] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"`.

| Extra | What it adds | Wheels |
|---|---|---|
| `[stac]` | The STAC client (`pystac-client`, `planetary-computer`) | env5, env6 |
| `[vizx]` | Visualization (`matplotlib`, `mapclassify`, `anywidget`, `tippecanoe`, `imageio`; the wheel carries `geopandas` and `contextily`) | env5, env6 |
| `[zarr]` | Zarr transactional stores (`zarr`, `numcodecs`, `zarrs`, `tensorstore`, `obstore`) | env6 |
| `[databricks]` | The Databricks SDK, for the sample-data uploads | env5, env6 |

*What an install changes on the runtime. The env wheel and its extras keep the runtime's preinstalled packages, with these exceptions. Every install upgrades `idna` (the runtime ships 3.7 or 3.11) and installs `httpx2` and `httpcore2`, which `rio-tiler` uses to read remote rasters and which need `idna` 3.18 or later. On Serverless environment 5 and DBR 17.3 / 18 it also upgrades `anyio` and `typing_extensions` (`rio-tiler` 9 needs 4.13 or later), on DBR 17.3 `h11` (to 0.16, the fix for CVE-2025-43859) and `httpcore` (from 1.0.2, which does not accept that `h11`, to 1.0.9), and on DBR 19 ML and Serverless environment 6 ML `lazy_loader`. On those env5 runtimes `[stac]` and `[vizx]` also raise `requests` from 2.32.3 to the latest 2.32 release, which fixes CVE-2024-47081. Databricks may show a one-time "a core package changed" notice; it is harmless, and the restart that follows the install picks up the new versions.*

*`[overture]` and `[earthdata]` are not extras of the env wheels: each changes further preinstalled packages. Install their packages as a **separate step** after the wheel, if you need them, and accept the changes: `%pip install "overturemaps>=1.0.2,<2"` (the Overture CLI, the fast path of [Overture Maps](./sample-data/overture-downloader); it raises `click` to 8.5 and `tqdm` to 4.70 or later, and installs PyPI's `shapely`, which a GeoBrix process does not use) and `%pip install "earthaccess>=0.11,<1" "botocore<1.44.0"` ([NASA Earthdata / EMIT](./sample-data/emit-downloader); it raises `fsspec` from 2023.5.0 to a current release). The Overture downloader works without the CLI, through the STAC catalog.*

The `file:///Volumes/…` path is a placeholder for the wheel on your Unity Catalog Volume — see
the install steps below for the exact pattern including the PEP 508 `package @ file://` quoting
required on Serverless.
:::

:::warning Install the env wheel for the runtime's family
The env wheel of the other family refuses to import, naming the file to install. The **plain wheel**,
`geobrix-<version>-py3-none-any.whl`, is for use **off Databricks** (a laptop, a non-Linux machine,
another Python, a GDAL you bring yourself): `pip install geobrix` gives a working lightweight tier
with PyPI's `rasterio`, `pyogrio`, `pyproj` and `shapely`, and the plain wheel keeps the feature
extras (`stac`, `vizx`, `zarr_dbr19`, `overture`, `earthdata`, …). On Databricks it would put a
second GDAL stack beside the runtime's packages.
:::

:::note Upgrading from GeoBrix 0.5.x?
**GeoBrix 0.5.x** installed the plain wheel with a runtime extra: `geobrix[light_env6]`, `[light_env5]`, `[light_dbr17]`, `[light_dbr18]` or `[light_dbr19]`, or their `_all` forms. In **0.6.0** those extras are gone: install the env wheel for the runtime instead, with no light extra. Replace `"geobrix[light_env6,vizx] @ file:///Volumes/…/geobrix-<version>-py3-none-any.whl"` with `"geobrix[vizx] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"` (`+env5` for `light_env5` and `light_dbr17` / `light_dbr18`). An `_all` form becomes `[stac,vizx]`, and `[stac,vizx,zarr]` on the env6 wheel. An old install line fails at resolution (pip: `ResolutionImpossible`), naming the env wheel to install, rather than installing something else.
:::

:::tip On Serverless, use environment 6
**Environment v6 is recommended for Serverless.** Install the `+env6` wheel and set the environment version to **6** — in the Environment side panel, or `environment_version: "6"` on a job. For an env 5 Serverless cluster, use the `+env5` wheel instead.

**Force-reload on Serverless without touching dependencies.** To swap in fresh wheel bytes during an interactive session, run this in a cell towards the top of your notebook:

```python
%pip install --force-reinstall --no-deps "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
%pip install "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

Keep `--no-deps` alongside `--force-reinstall` — without it, pip force-reinstalls dependencies that are already preinstalled and Serverless fails the cell. The second, plain install then restores any dependencies the first (deps-skipped) step left out; add your feature extras on that line.
:::

The wheels ship as **GitHub release artifacts** — they are **not** published to PyPI. Install from a Unity Catalog Volume so the same path works on both Serverless and Classic compute:

1. **Download** the env wheel for your runtime, `geobrix-<version>+env6-py3-none-any.whl` or `geobrix-<version>+env5-py3-none-any.whl`, from the [GeoBrix releases](https://github.com/databrickslabs/geobrix/releases).
2. **Stage** it in a Unity Catalog Volume your compute can read, e.g. `/Volumes/<catalog>/<schema>/<volume>/geobrix/`.
3. **Install** it — either notebook-scoped with the `%pip` magic (installs across the whole cluster for the notebook session; plain `pip` installs only on the driver), or as a [cluster-scoped library](https://docs.databricks.com/aws/en/libraries/notebooks-python-libraries#manage-libraries-with-pip-commands) pointing at the same Volume path (works on Serverless and Classic):

```python
%pip install "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
```

:::warning Serverless install form
**Use the quoted `geobrix[<extras>] @ file://…` form.** Install with the **PEP 508
named form above**, wrapped in quotes as a single argument. Do **not** put an
extra on the path (`'/Volumes/…/geobrix-<version>+env6-py3-none-any.whl[vizx]'`): on
**Serverless**, `%pip` writes the requirement to a file *including the
surrounding quotes*, so pip reads `[vizx]` as part of the filename and fails
with *"Expected package name at the start of dependency specifier."* The named
form installs cleanly on **Serverless**, standard/shared, and ARM.
:::

**Or install straight from the GitHub release.** When your compute can reach github.com, skip the
download-and-stage steps and point pip at the release asset. Keep the same quoted PEP 508 named
form, with the wheel for your runtime:

```python
%pip install "geobrix @ https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

On DBR 17.3 or 18, use the `+env5` wheel instead. For a Serverless job, add the requirement as a
dependency line of the job's environment, written **without spaces around `@`**, with the wheel for
its environment version (`+env5` for version 5, `+env6` for version 6):

```text
geobrix@https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl
```

Environment dependencies are installed with an unquoted `%pip install`, so spaces around `@` split
the requirement and the install fails. A Lakeflow pipeline's dependency lines follow the same rule,
but the pipeline runs on the Databricks Runtime of its channel, not on a Serverless environment
version, so it takes the wheel for that runtime (`+env5` for DBR 18, `+env6` for DBR 19). See
[Lakeflow SDP](./ingestion/lakeflow-sdp#environment).

Workspaces that restrict outbound network access (for example, Serverless egress controls) can
block GitHub — install from a Unity Catalog Volume, as above, in that case.

Then import the package(s) you need and (optionally) register their SQL functions. Each light package exposes the same `functions` / `register(spark)` pattern:

```python
from databricks.labs.gbx.pyrx import functions as rx  # RasterX (rst_*)
# from databricks.labs.gbx.pyvx import functions as vx  # VectorX (st_*)
# from databricks.labs.gbx.pygx import functions as gx  # GridX quadbin (quadbin_*)

# optional — only needed to call the SQL functions:
rx.register(spark)

# Light DataSource readers (raster_gbx, gtiff_gbx, etc.) are Python DataSource
# V2 and aren't auto-discovered — register them explicitly when you need them:
# from databricks.labs.gbx.ds import register
# register.register(spark)
```

### Verify the lightweight tier

Confirm the wheel imports, the env wheel's GDAL is the one rasterio runs, and a function runs end to end. The check below exercises RasterX (`rst_*`); VectorX (`pyvx`, `st_*`) and GridX quadbin (`pygx`, `quadbin_*`) ship in the same wheel and register and run the same way:

```python
import rasterio
from databricks.labs.gbx.pyrx import functions as rx

print("rasterio", rasterio.__version__, "| GDAL", rasterio.__gdal_version__)

# Functional check: load a GeoTIFF and read its properties through pyrx.
tiles = (
    spark.read.format("binaryFile")
    .load("/Volumes/<catalog>/<schema>/<volume>/path/to/*.tif")
    .select(rx.rst_fromcontent("content", "GTiff").alias("tile"))
)
tiles.select(
    rx.rst_width("tile").alias("width"),
    rx.rst_height("tile").alias("height"),
    rx.rst_srid("tile").alias("srid"),
).show()
```

If the import succeeds and the query returns raster dimensions, the lightweight tier is ready. For the heavyweight tier, continue with [Cluster libraries](#heavyweight) or [Databricks Container Service](./installation/dcs.mdx).

## Cluster libraries (Heavyweight) {#heavyweight}

The heavyweight tier runs on a dedicated cluster with two cluster libraries: the env wheel and the GeoBrix JAR. The wheel carries the native GDAL, PROJ and GEOS. The JVM loads them from the wheel.

1. Stage the env wheel for the runtime in a Unity Catalog Volume: `+env5` on DBR 17.3 and 18, `+env6` on DBR 19.
2. Download `geobrix-<version>-jar-with-dependencies.jar` from the [GeoBrix releases](https://github.com/databrickslabs/geobrix/releases). Stage it in a Volume.
3. Create a cluster with **Dedicated** access mode on DBR 17.3, 18 or 19. Use an x86 instance type on any of them, or Graviton (arm64) on DBR 19.
4. Under **Libraries**, install the wheel (Python whl) and the JAR (JAR) from their Volume paths.
5. Start the cluster, and attach a notebook.

A cluster loads one GeoBrix JAR, so install only one. On DBR 19 you can also install the wheel from a notebook with `%pip` and keep the JAR as a cluster library.

Standard access mode refuses the heavyweight functions. Use the lightweight tier there.

:::warning Upgrading from GeoBrix 0.5.x
GeoBrix 0.5.x installed native GDAL with a cluster init script. **Remove that init script from the cluster** and do not install the GDAL bundle. A system GDAL beside a 0.6.0 wheel puts two GDAL stacks in one cluster. See [Release Notes: 0.6.x](./release-notes-0-6#init-script).
:::

Two optional settings apply to the heavyweight tier:

- **netCDF-4 filters.** Reading zstd, blosc or bzip2 netCDF-4 needs `HDF5_PLUGIN_PATH` in the cluster's environment variables. Without it the result is a silent NULL. The variable also reaches other HDF5 libraries on the cluster. See [Compressed netCDF-4 variables](./readers/netcdf#compressed-netcdf-4-variables-zstd-blosc-bzip2).
- **HTTP.** Leave `GDAL_HTTP_VERSION` unset. See [Remote reads](./readers/raster#remote-reads-over-https).
