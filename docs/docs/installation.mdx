# Installation

GeoBrix installs as one Python wheel per runtime family, the **env wheel**. The env wheel runs every GeoBrix
function, and carries its own GDAL, PROJ and GEOS. For most users, the env wheel is the whole install.

:::tip The env wheel includes the JAR
Every env wheel ships the GeoBrix JAR inside it, so you do not need to download the JAR on its own. (The release
also attaches it as `geobrix-<version>-jar-with-dependencies.jar`, the same file.)

GeoBrix does not load the JAR by itself. The JAR is used only in two cases:

- You install it as a **cluster library** on a **dedicated** cluster ([install 2](#env-wheel-and-jar)). Some functions
  then run faster at the JVM level.
- You place it in the **Unity Catalog install folder** ([install 3](#uc-functions)). Three BNG functions then run as
  Scala functions.

The wheel carries the JAR so that `gbx.stage_jar` can copy the matching JAR to a Volume for you. It also lets
`gbx.register(spark)` check that a cluster's JAR is that same build.
:::

## How GeoBrix registers its functions

GeoBrix functions reach you in one of two ways. You can use both.

| | Session registration | Unity Catalog functions |
|---|---|---|
| **How** | `gbx.register(spark)`, once in each session | `gbx.uc.install(...)`, once, by a schema owner |
| **Where the functions live** | The Spark session: SQL (`gbx_*`), the Python API and the `*_gbx` readers and writers | A Unity Catalog schema: `<catalog>.<schema>.gbx_*` |
| **Who can call them** | Code in that session | Anyone granted access, on any compute that reads Unity Catalog, including SQL warehouses |
| **Which functions** | All of them | A subset (see [Unity Catalog functions](./api/uc-functions)) |
| **What runs them** | The Python level. With the JAR as a cluster library on a dedicated cluster, also the JVM level where it is faster | Python, or SQL where that is faster. Three BNG functions run as Scala when the JAR is in the install folder |

## Choose an install {#choose-an-install-path}

| Install | Runs on | You install | Then |
|---|---|---|---|
| **[1. Session: the env wheel](#env-wheel)** (most common) | Serverless, standard and dedicated clusters, Lakeflow declarative pipelines | The env wheel | `gbx.register(spark)` |
| **[2. Session: the env wheel and the JAR](#env-wheel-and-jar)** | Clusters in **dedicated** access mode only | The env wheel and the JAR, as cluster libraries (or a GeoBrix container image) | `gbx.register(spark)` |
| **[3. Unity Catalog functions](#uc-functions)** | SQL warehouses, and any compute that reads Unity Catalog | Nothing, for callers. A schema owner runs `gbx.uc.install` once | Call `<catalog>.<schema>.gbx_*` |

**Start with install 1.** Your code is the same with or without the JAR: `gbx.register(spark)` picks the faster
level the compute offers. Only a dedicated cluster can load the JAR. Serverless and standard access mode run Spark
Connect, which gives GeoBrix no JVM, so install 1 is the complete install there.

These docs call the Python level **lightweight** and the JVM level **heavyweight**. See
[Surfaces & Levels](./api/execution-tiers.mdx#the-levels).

### Pick the env wheel for your runtime

| Runtime | Env wheel |
|---|---|
| Serverless environment 6 (recommended), DBR 19, DBR 19 ML, Lakeflow declarative pipelines on the `PREVIEW` channel | `geobrix-<version>+env6-py3-none-any.whl` |
| Serverless environment 5, DBR 17.3, DBR 18, Lakeflow declarative pipelines on the `CURRENT` channel | `geobrix-<version>+env5-py3-none-any.whl` |

The wheel of the other family refuses to import and names the file to install. The wheels are assets of the
[GitHub releases](https://github.com/databrickslabs/geobrix/releases), not PyPI packages.

## 1. Install for a session: the env wheel {#env-wheel}

**Runs on:** Serverless, clusters in standard or dedicated access mode, and Lakeflow declarative pipelines, on
x86 and ARM.

1. **Download** the env wheel for your runtime from the [GeoBrix releases](https://github.com/databrickslabs/geobrix/releases).
2. **Stage** it on a Volume your compute can read, for example `/Volumes/<catalog>/<schema>/<volume>/geobrix/`.
3. **Install** it in a notebook cell, then restart Python:

```python
%pip install "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

4. <Link id="register"></Link>**Register** the functions, once per session:

  language="python"
  functionName="REGISTER_PYTHON_INSTALLATION"
  title="Register GeoBrix"
  source="docs/tests/python/installation/verify_installation.py"
  testFile="docs/tests/python/installation/test_verify_installation.py"
/>

5. <Link id="verify-the-install"></Link>**Verify** that the wheel imports, that rasterio runs the wheel's GDAL, and
   that a function runs end to end:

```python
import rasterio
from databricks.labs.gbx.rasterx import functions as rx

print("rasterio", rasterio.__version__, "| GDAL", rasterio.__gdal_version__)

# Functional check: load a GeoTIFF and read its properties.
tiles = (
    spark.read.format("binaryFile")
    .load("/Volumes/<catalog>/<schema>/<volume>/path/to/*.tif")
    .select(rx.rst_fromcontent("content", "GTiff").alias("tile"))
)
tiles.select(
    rx.rst_width("tile").alias("width"),
    rx.rst_height("tile").alias("height"),
    rx.rst_srid("tile").alias("srid"),
).show()
```

If the query returns the raster dimensions, the install is complete. `gbx.register(spark)` registered every `gbx_*`
SQL function and every `*_gbx` reader and writer for this session. A `%sql` cell in the same notebook can call them.

Use the `+env5` file on Serverless environment 5, DBR 17.3 and DBR 18. To install for every notebook on a cluster,
add the same Volume path as a [cluster-scoped library](https://docs.databricks.com/aws/en/libraries/notebooks-python-libraries#manage-libraries-with-pip-commands)
instead of `%pip`.

:::warning Use the quoted named form
Write the requirement as `"geobrix @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"`, in quotes, as one
argument. To add an extra, put it after the name: `"geobrix[vizx] @ file:///…"`. Do **not** append it to the path
(`'/Volumes/…/geobrix-<version>+env6-py3-none-any.whl[vizx]'`). On Serverless, `%pip` keeps the quotes in its
requirements file, and pip then reads `[vizx]` as part of the file name. The error is *"Expected package name at
the start of dependency specifier."*
:::

For extras, jobs, pipelines and installs straight from GitHub, see [Install options](#install-options).

## 2. Install for a session: the env wheel and the JAR {#env-wheel-and-jar}

**Runs on:** clusters in **dedicated** access mode only: x86 on DBR 17.3, 18 or 19, or Graviton (arm64) on DBR 19.

**Why:** some functions run faster at the JVM level. Your code does not change, and every other function still runs
in Python. The JVM uses the wheel's GDAL, PROJ and GEOS, so nothing else is installed.

1. **Stage the env wheel** on a Volume: `+env5` for DBR 17.3 and 18, `+env6` for DBR 19.

for each function that falls back to Python, with the reason.

What `gbx.stage_jar` does:

- It copies the JAR to the folder and writes a `.sha256` file beside it.
- It checks that the JAR matches the wheel's version and the hash in the wheel's `RECORD`.
- It refuses a folder that already holds another GeoBrix JAR, because a cluster must load only one.
- It prints the next step and returns the staged path. Pass `overwrite=True` to copy the JAR again.

Keep these rules in mind:

- One JAR runs on DBR 17.3, 18 and 19. Install only one GeoBrix JAR on a cluster.
- A running cluster cannot load a JAR. Restart the cluster after you add or change the JAR library.
- `gbx.register(spark)` checks that the JAR and the wheel are the same build. A mismatched JAR is not used.
- On DBR 19 you can install the wheel with `%pip` in the notebook and keep only the JAR as a cluster library.

**Or use a container image.** A GeoBrix image for [Databricks Container Service](./installation/dcs.mdx) starts a
dedicated DBR 19 cluster with the env6 wheel and the JAR already in place, so steps 1 to 3 are not needed. There is
one image tag for Graviton (arm64) and one for x86 (amd64).

## Install options {#install-options}

### Supported Databricks Runtimes {#supported-databricks-runtimes}

| DBR | Ubuntu | Spark | Python | Scala | Java |
|---|---|---|---|---|---|
| **17.3** | 24.04 | 4.0.0 | 3.12.3 | 2.13.16 | 17 |
| **18** | 24.04 | 4.1.0 | 3.12.3 | 2.13.16 | 21 |
| **19** | 24.04 | 4.2.0 | 3.12.3 | 2.13.18 | 21 |

On Serverless, use **environment 6**: set the environment version to **6** in the Environment side panel, or
`environment_version: "6"` on a job. GeoBrix uses the PySpark that the runtime provides. Installing GeoBrix never
downloads PySpark.

### Feature extras

Add extras in brackets after the name, on the same line:
`"geobrix[stac,vizx] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"`.

| Extra | What it adds | Wheels |
|---|---|---|
| `[stac]` | The STAC client (`pystac-client`, `planetary-computer`) | env5, env6 |
| `[vizx]` | Visualization (`matplotlib`, `mapclassify`, `anywidget`, `tippecanoe`, `imageio`; the wheel carries `geopandas` and `contextily`) | env5, env6 |
| `[zarr]` | Zarr transactional stores (`zarr`, `numcodecs`, `zarrs`, `tensorstore`, `obstore`) | env6 |
| `[databricks]` | The Databricks SDK, for the sample-data uploads | env5, env6 |

Overture and NASA Earthdata are not extras. Install their packages as a separate step after the wheel, only if you
use them:

- Overture CLI, the fast path of [Overture Maps](./sample-data/overture-downloader): `%pip install "overturemaps>=1.0.2,<2"`.
  It raises `click` to 8.5 and `tqdm` to 4.70 or later, and installs PyPI's `shapely`, which GeoBrix does not use.
  The Overture downloader also works without the CLI, through the STAC catalog.
- Earthdata ([NASA Earthdata / EMIT](./sample-data/emit-downloader)): `%pip install "earthaccess>=0.11,<1" "botocore<1.44.0"`.
  It raises `fsspec` from 2023.5.0 to a current release.

### Install from the GitHub release

When your compute can reach github.com, you can skip the download and the Volume. Point pip at the release asset,
in the same quoted named form:

```python
%pip install "geobrix @ https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

A workspace that restricts outbound network access (for example, Serverless egress controls) can block GitHub.
Install from a Volume in that case.

### Serverless jobs and Lakeflow pipelines

Add the wheel as a dependency line of the job's environment. Write it **without spaces around `@`**:

```text
geobrix@https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl
```

The environment installs its dependencies with an unquoted `%pip install`, so a space around `@` splits the
requirement and the install fails. Use the wheel of the job's environment version: `+env5` for 5, `+env6` for 6.

A Lakeflow pipeline's dependency lines follow the same rule. A pipeline runs on the Databricks Runtime of its
channel, not on a Serverless environment version. Use `+env5` on the `CURRENT` channel (DBR 18) and `+env6` on
`PREVIEW` (DBR 19). See [Lakeflow SDP](./ingestion/lakeflow-sdp#environment).

### Register only some functions

Registering every function takes about 45 seconds on Serverless. To register only the functions you call, pass
their names: `gbx.register(spark, only=["rst_avg", "bng_cellarea"])`. Names may be SQL names or short names. The
Python API also registers a function on its first call.

### Reinstall the same version on Serverless

To load fresh wheel bytes of the same version during a session, run this near the top of the notebook:

```python
%pip install --force-reinstall --no-deps "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
%pip install "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

Keep `--no-deps` with `--force-reinstall`. Without it, pip reinstalls the runtime's preinstalled packages and
Serverless fails the cell. The second, plain install adds back any dependency the first one skipped. Put your
extras on that second line.

### What the install changes on the runtime

The env wheel keeps the runtime's preinstalled packages, with these exceptions:

- Every install upgrades `idna` (the runtime ships 3.7 or 3.11) and adds `httpx2` and `httpcore2`. `rio-tiler`
  uses them to read remote rasters, and they need `idna` 3.18 or later.
- On Serverless environment 5 and DBR 17.3 / 18, it also upgrades `anyio` and `typing_extensions` (`rio-tiler` 9
  needs 4.13 or later).
- On DBR 17.3, it also upgrades `h11` to 0.16 (the fix for CVE-2025-43859), and `httpcore` from 1.0.2 to 1.0.9,
  because 1.0.2 does not accept that `h11`.
- On those env5 runtimes, `[stac]` and `[vizx]` also raise `requests` from 2.32.3 to the latest 2.32 release, which
  fixes CVE-2024-47081.

Databricks may show a one-time "a core package changed" notice. It is harmless: the Python restart after the
install picks up the new versions.

The wheel also carries `rasterio`, `pyogrio`, `pyproj`, `shapely`, `netCDF4`, GDAL's own `osgeo` and the GeoBrix
[Rust module](./api/execution-tiers.mdx#rust-kernels), all built against its GDAL. A process runs one GDAL. One
wheel covers the whole library: RasterX (`databricks.labs.gbx.rasterx`), GridX (`databricks.labs.gbx.gridx.<grid>`),
VectorX (`databricks.labs.gbx.vectorx`) and `pmtiles`.

### JVM settings for install 2

- **netCDF-4 filters.** Reading zstd, blosc or bzip2 netCDF-4 needs `HDF5_PLUGIN_PATH` in the cluster's environment
  variables. Without it the result is a silent NULL. The variable also reaches other HDF5 libraries on the cluster.
  See [Compressed netCDF-4 variables](./readers/netcdf#compressed-netcdf-4-variables-zstd-blosc-bzip2).
- **HTTP.** Leave `GDAL_HTTP_VERSION` unset. See [Remote reads](./readers/raster#remote-reads-over-https).
- **Native copy location.** On first use, each node copies the wheel's native libraries to local disk, about 130 MB
  per GeoBrix build. The JVM loads that copy, so a finished notebook's Python environment cannot remove them. The
  copy goes to `/local_disk0/geobrix/native` when no other user owns `/local_disk0`, else to `/tmp/geobrix/native`.
  Each candidate needs three times the copy's size free. To use one folder only, set
  `spark.databricks.labs.gbx.native.copy.dir` in the cluster's Spark config. An existing folder must belong to the
  JVM's user, with no access for group or others (mode 0700). Set it to `off` to load from the wheel.

## Install without PyPI access {#offline-install}

Some workspaces cannot reach PyPI, and on some the Unity Catalog sandbox cannot either. An install that needs PyPI
then fails. The env wheel lists every wheel it needs, pinned and hashed, for each architecture. Download those wheels
once, stage them on a Volume, then install from the Volume.

### Download the wheels

Run the download on any machine with PyPI access and Python 3.12. It needs the env wheel installed, and no GeoBrix
checkout:

The command does this:

- It downloads binary wheels only, for x86_64 and aarch64, into `<out>/x86_64/` and `<out>/aarch64/`.
- It checks each wheel against the sha256 its list pins.
- It proves for each architecture that the folder covers the install offline (`pip install --dry-run --no-index`).
- It copies the env wheel into the folder and writes `wheels.txt`, the sha256 of each file.

The folder leaves out the packages the runtime already has, such as numpy, pandas, pyarrow and scipy. Options:

- `--arch x86_64` or `--arch aarch64` downloads one architecture. The default is both.
- `--extras zarr,vizx` adds the wheels of those extras.
- `--uc` also checks the Unity Catalog pins, `h3` and `quadbin`.

The same steps run from Python, in `databricks.labs.gbx.stage`:

- `download_deps(out, arches=None, extras=(), uc=False, wheel=None)` downloads and checks the wheels. It returns the path of `wheels.txt`.
- `check_offline(folder, arch, targets, base)` checks that `targets` install from `folder` alone. It returns the `name==version` lines pip would install.
- `dep_pins(arch, extras=())` returns each wheel an install needs on `arch`, beyond the runtime's own packages. Each maps a name to its version and sha256.
- `uc_pins()` returns the pins of the Unity Catalog function environments, `h3` and `quadbin`.
- `read_wheels_txt(folder)` returns the sha256 and relative path of each file in `wheels.txt`.
- `install_lines(vol_dir, wheel, arches, extras=())` returns the install lines `gbx.stage_deps` prints for a staged folder.

## Call GeoBrix from Scala or Java {#jvm-sql}

Most users can skip this section. It is for code on the JVM, in Scala or Java, that calls GeoBrix functions.

`gbx.register(spark)` registers the SQL functions from Python, in one Spark session. JVM code on the same session
calls them by SQL name. The JAR adds faster implementations for many functions, but it registers no SQL names.

Choose the route by where the code runs:

| Route | Compute | Functions |
|---|---|---|
| [Python entry point, Scala body](#jvm-python-entry) | A job task on a dedicated cluster | All of them. A table function cannot go in a select list, as described below. |
| [A notebook that mixes languages](#jvm-notebook) | A notebook on dedicated compute | All of them |
| [Unity Catalog functions](#jvm-uc) | Any compute that reads Unity Catalog, including Serverless JAR tasks | The Unity Catalog subset |

Unity Catalog route there.

### A notebook that mixes languages {#jvm-notebook}

On dedicated compute, run `gbx.register(spark)` in a Python cell. Cells in other languages use the same Spark
session, so a `%sql` or `%scala` cell calls the functions by name.

Serverless notebooks have no Scala cells.

### Unity Catalog functions {#jvm-uc}

## Upgrading from GeoBrix 0.5.x {#upgrade-from-0-5}

- **Install lines.** 0.5.x installed with a runtime extra: `geobrix[light_env6]`, `[light_env5]`, `[light_dbr17]`,
  `[light_dbr18]` or `[light_dbr19]`, or their `_all` forms. In 0.6.0 those extras are gone: install the env wheel
  for the runtime, with no runtime extra.
  - Replace `"geobrix[light_env6,vizx] @ file:///Volumes/…/geobrix-<version>-py3-none-any.whl"` with
    `"geobrix[vizx] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"`.
  - Use `+env5` in place of `light_env5`, `light_dbr17` and `light_dbr18`.
  - An `_all` form becomes `[stac,vizx]`, or `[stac,vizx,zarr]` on the env6 wheel.
  - An old install line fails at resolution (pip: `ResolutionImpossible`) and names the env wheel to install. It
    never installs something else.
- **GPU extras.** The 0.5.x extras `photogrammetry_gpu_env5`, `models_gpu_env5` and `gpu_env5_all` map to the `+env6`
  wheel, because the UDF workers of the Serverless GPU runtime run environment 6. A driver-only GPU step, such as
  dense MVS with `pycolmap-cuda12`, can stay on the `+env5` wheel with no extra. Install the GPU packages as a
  separate step after the wheel.
- **Init script.** 0.5.x installed native GDAL with a cluster init script. **Remove that init script from the
  cluster**, and do not install the GDAL bundle. A system GDAL beside a 0.6.0 wheel puts two GDAL stacks in one
  cluster. See [Breaking changes in 0.6.0](./release-notes/0-6/breaking.mdx#init-script).
- **The JAR.** In 0.5.x the JAR was only a separate release asset. In 0.6.0 it also ships inside the env wheel:
  stage it with `gbx.stage_jar` ([install 2](#env-wheel-and-jar)), which checks that it matches the wheel.
- **Registration.** The per-package `register()` functions are removed. `gbx.register(spark)` replaces them.

See the [migration guide](./migration-0-6) for every change.

To stay on 0.5.x, use the assets of the [v0.5.2 release](https://github.com/databrickslabs/geobrix/releases/tag/v0.5.2).
They include the init script, the GDAL bundle and `geobrix-docs-0.5.2.zip`, the docs for that release.
