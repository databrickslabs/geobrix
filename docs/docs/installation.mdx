# Installation

GeoBrix installs as one **env wheel** for your runtime. The wheel runs every function in Python, the
**lightweight** implementation. A dedicated cluster can add the GeoBrix JAR for the JVM,
**heavyweight**, implementation of some functions. You never choose between them in code:
`gbx.register(spark)` picks the faster one the compute offers. See [Surfaces and levels](./api/execution-tiers.mdx).
Pick the install path that matches your compute.

## Choose an install path {#choose-an-install-path}

![Three ways to install GeoBrix — the question of which tier you need, and on which compute, branches three ways: lightweight tier only leads to path a, WHL-only (Lightweight), recommended, installed as the env wheel for the runtime (env5 or env6), running on Serverless, standard access mode, Lakeflow pipelines, classic clusters and ARM, with one wheel from a Volume or the GitHub release that carries its own GDAL, PROJ and GEOS, giving the lightweight tier; heavyweight on a dedicated cluster leads to path b, Cluster libraries, the env wheel and the GeoBrix JAR both installed as cluster libraries from a Volume, running on a dedicated cluster with x86 on DBR 17.3, 18 or 19 or Graviton on DBR 19, where the wheel's own GDAL serves the JVM, giving both the lightweight and heavyweight tiers; heavyweight on arm64 or x86 with DBR 19 leads to path c, Databricks Container Service, a GeoBrix container image with the env6 wheel, its native GDAL and the JAR, run on a dedicated Graviton (arm64) or x86 (amd64) DBR 19 cluster with no library to attach, giving both the lightweight and heavyweight tiers](../../resources/images/diagrams/installation/installation-paths.png)

| Path | Runs | Compute | What you install |
|---|---|---|---|
| **(a) [Env wheel](#whl-only)** — recommended | Every function, in Python | Serverless, standard access mode, Lakeflow declarative pipelines, classic clusters, ARM | The env wheel for the runtime (`+env5` or `+env6`) |
| **(b) [Env wheel and JAR](#heavyweight)** | Every function, plus the JVM engine where it is faster | Dedicated cluster, x86 on DBR 17.3 / 18 / 19, Graviton (arm64) on DBR 19 | The env wheel and the GeoBrix JAR, both as cluster libraries |
| **(c) [Databricks Container Service](./installation/dcs.mdx)** | Every function, plus the JVM engine where it is faster | Dedicated cluster, Graviton (arm64) or x86 (amd64), DBR 19 | A GeoBrix container image (the env6 wheel, its native GDAL and the JAR) — no library to attach |

**(a) Env wheel** is the default: if you don't specifically need the JVM engine, install
the wheel and stop there. The full install steps are [below](#whl-only).

**(b) Env wheel and JAR** adds the JVM engine. A dedicated cluster installs the env wheel
and the GeoBrix JAR as cluster libraries. `gbx.stage_jar` puts the JAR on a Volume for you. The wheel carries the native GDAL, PROJ and GEOS, and the JVM
loads them from the wheel, so nothing else is installed. Verified on dedicated
clusters with x86 on DBR 17.3, 18 and 19, and Graviton (arm64) on DBR 19. See [below](#heavyweight).

**(c) Databricks Container Service** starts a dedicated DBR 19 cluster from a GeoBrix container image.
The image already holds the env6 wheel with its native GDAL, and the GeoBrix JAR, so there is no library
to attach. It runs on both Graviton (arm64) and x86 (amd64) instance types, each with its own image tag.
See [Databricks Container Service](./installation/dcs.mdx).

The **JVM engine needs dedicated compute** (a dedicated access mode cluster), through (b) or
(c). On standard access mode and Serverless, use **(a)**: every function runs there in Python.

**SQL warehouses** run no wheel. An owner installs the [Unity Catalog functions](#uc-functions) once, and users call them by their three-part names.

## Supported Databricks Runtimes

GeoBrix supports the following Databricks Runtime releases:

| DBR | Ubuntu | Spark | Python | Scala | Java | GeoBrix |
|---|---|---|---|---|---|---|
| **17.3** | 24.04 | 4.0.0 | 3.12.3 | 2.13.16 | 17 | ✅ Supported |
| **18** | 24.04 | 4.1.0 | 3.12.3 | 2.13.16 | 21 | ✅ Supported |
| **19** | 24.04 | 4.2.0 | 3.12.3 | 2.13.18 | 21 | ✅ Supported |

A **single JAR** runs on 17.3, 18, and 19. Scala 2.13 minor versions are binary-compatible. The JAR is compiled to Java-17 bytecode so it loads on all three JVMs, and Spark is a `provided` dependency.

On Databricks, GeoBrix installs as the **env wheel** for the runtime's family. There is one wheel per
family, and no light extra to pick:

| Runtime | Wheel |
|---|---|
| Serverless environment 6 (recommended), DBR 19, DBR 19 ML, SQL warehouses and UC functions | `geobrix-<version>+env6-py3-none-any.whl` |
| Serverless environment 5, DBR 17.3, DBR 18, Lakeflow declarative pipelines | `geobrix-<version>+env5-py3-none-any.whl` |

See [Env wheel](#whl-only) below for the install steps.

:::note PySpark comes from the runtime
On Databricks, GeoBrix uses the PySpark that the runtime provides — installing GeoBrix never downloads PySpark.
:::

## Env wheel {#whl-only}

The env wheel is a single Python wheel for your runtime — **no separate JAR and no native GDAL bundle**. The env wheel carries its own GDAL, PROJ and GEOS. It also carries `rasterio`, `pyogrio`, `pyproj`, `shapely`, `netCDF4` and GDAL's own `osgeo`, built against them. A process runs one GDAL. It holds the runtime's preinstalled packages instead of replacing them. It runs on serverless compute, standard (shared) clusters, Lakeflow declarative pipelines, and ARM. One wheel covers the whole library: RasterX (`databricks.labs.gbx.rasterx`), GridX (`databricks.labs.gbx.gridx.<grid>`), VectorX (`databricks.labs.gbx.vectorx`) and `pmtiles`.

:::note Choose the wheel for your runtime
| Runtime | Install command |
|---|---|
| Serverless environment 6 (recommended), DBR 19, DBR 19 ML | `%pip install "geobrix @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"` |
| Serverless environment 5, DBR 17.3, DBR 18 | `%pip install "geobrix @ file:///Volumes/…/geobrix-<version>+env5-py3-none-any.whl"` |

**Feature extras.** Add them in brackets, on the same line: `"geobrix[stac,vizx] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"`.

| Extra | What it adds | Wheels |
|---|---|---|
| `[stac]` | The STAC client (`pystac-client`, `planetary-computer`) | env5, env6 |
| `[vizx]` | Visualization (`matplotlib`, `mapclassify`, `anywidget`, `tippecanoe`, `imageio`; the wheel carries `geopandas` and `contextily`) | env5, env6 |
| `[zarr]` | Zarr transactional stores (`zarr`, `numcodecs`, `zarrs`, `tensorstore`, `obstore`) | env6 |
| `[databricks]` | The Databricks SDK, for the sample-data uploads | env5, env6 |

*What an install changes on the runtime. The env wheel and its extras keep the runtime's preinstalled packages, with these exceptions. Every install upgrades `idna` (the runtime ships 3.7 or 3.11) and installs `httpx2` and `httpcore2`, which `rio-tiler` uses to read remote rasters and which need `idna` 3.18 or later. On Serverless environment 5 and DBR 17.3 / 18 it also upgrades `anyio` and `typing_extensions` (`rio-tiler` 9 needs 4.13 or later). On DBR 17.3 it also upgrades `h11` (to 0.16, the fix for CVE-2025-43859) and `httpcore` (from 1.0.2, which does not accept that `h11`, to 1.0.9). On DBR 19 ML and Serverless environment 6 ML it also upgrades `lazy_loader`. On those env5 runtimes `[stac]` and `[vizx]` also raise `requests` from 2.32.3 to the latest 2.32 release, which fixes CVE-2024-47081. Databricks may show a one-time "a core package changed" notice; it is harmless, and the restart that follows the install picks up the new versions.*

*`[overture]` and `[earthdata]` are not extras of the env wheels: each changes further preinstalled packages. Install their packages as a **separate step** after the wheel, if you need them, and accept the changes. For Overture, run `%pip install "overturemaps>=1.0.2,<2"` (the Overture CLI, the fast path of [Overture Maps](./sample-data/overture-downloader)). It raises `click` to 8.5 and `tqdm` to 4.70 or later, and installs PyPI's `shapely`, which a GeoBrix process does not use. For Earthdata, run `%pip install "earthaccess>=0.11,<1" "botocore<1.44.0"` ([NASA Earthdata / EMIT](./sample-data/emit-downloader)). It raises `fsspec` from 2023.5.0 to a current release. The Overture downloader works without the CLI, through the STAC catalog.*

The `file:///Volumes/…` path is a placeholder for the wheel on your Unity Catalog Volume. See
the install steps below for the exact pattern, including the PEP 508 `package @ file://` quoting
required on Serverless.
:::

:::warning Install the env wheel for the runtime's family
The env wheel of the other family refuses to import, naming the file to install. Install the `+env6`
wheel on Serverless environment 6 and DBR 19, and the `+env5` wheel on Serverless environment 5, DBR 17.3 and DBR 18.
:::

:::note Upgrading from GeoBrix 0.5.x?
**GeoBrix 0.5.x** installed with a runtime extra: `geobrix[light_env6]`, `[light_env5]`, `[light_dbr17]`, `[light_dbr18]` or `[light_dbr19]`, or their `_all` forms. In **0.6.0** those extras are gone: install the env wheel for the runtime instead, with no light extra. Replace `"geobrix[light_env6,vizx] @ file:///Volumes/…/geobrix-<version>-py3-none-any.whl"` with `"geobrix[vizx] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"` (`+env5` for `light_env5` and `light_dbr17` / `light_dbr18`). An `_all` form becomes `[stac,vizx]`, and `[stac,vizx,zarr]` on the env6 wheel. An old install line fails at resolution (pip: `ResolutionImpossible`), naming the env wheel to install, rather than installing something else.
:::

:::tip On Serverless, use environment 6
**Environment v6 is recommended for Serverless.** Install the `+env6` wheel and set the environment version to **6** — in the Environment side panel, or `environment_version: "6"` on a job. For an env 5 Serverless cluster, use the `+env5` wheel instead.

**Force-reload on Serverless without touching dependencies.** To swap in fresh wheel bytes during an interactive session, run this in a cell towards the top of your notebook:

```python
%pip install --force-reinstall --no-deps "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
%pip install "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

Keep `--no-deps` alongside `--force-reinstall` — without it, pip force-reinstalls dependencies that are already preinstalled and Serverless fails the cell. The second, plain install then restores any dependencies the first (deps-skipped) step left out; add your feature extras on that line.
:::

The wheels ship as **GitHub release artifacts** — they are **not** published to PyPI. Install from a Unity Catalog Volume so the same path works on both Serverless and Classic compute:

1. **Download** the env wheel for your runtime, `geobrix-<version>+env6-py3-none-any.whl` or `geobrix-<version>+env5-py3-none-any.whl`, from the [GeoBrix releases](https://github.com/databrickslabs/geobrix/releases).
2. **Stage** it in a Unity Catalog Volume your compute can read, e.g. `/Volumes/<catalog>/<schema>/<volume>/geobrix/`.
3. **Install** it in one of two ways. Notebook-scoped, use the `%pip` magic (it installs across the whole cluster for the notebook session; plain `pip` installs only on the driver). Or add a [cluster-scoped library](https://docs.databricks.com/aws/en/libraries/notebooks-python-libraries#manage-libraries-with-pip-commands) pointing at the same Volume path (works on Serverless and Classic):

```python
%pip install "geobrix @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"
```

:::warning Serverless install form
**Use the quoted `geobrix[<extras>] @ file://…` form.** Install with the **PEP 508
named form above**, wrapped in quotes as a single argument. Do **not** put an
extra on the path (`'/Volumes/…/geobrix-<version>+env6-py3-none-any.whl[vizx]'`). On
**Serverless**, `%pip` writes the requirement to a file *including the
surrounding quotes*. Pip then reads `[vizx]` as part of the filename and fails.
The error is *"Expected package name at the start of dependency specifier."* The named
form installs cleanly on **Serverless**, standard/shared, and ARM.
:::

**Or install straight from the GitHub release.** When your compute can reach github.com, skip the
download-and-stage steps and point pip at the release asset. Keep the same quoted PEP 508 named
form, with the wheel for your runtime:

```python
%pip install "geobrix @ https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

On DBR 17.3 or 18, use the `+env5` wheel instead. For a Serverless job, add the requirement as a
dependency line of the job's environment, written **without spaces around `@`**. Use the wheel for
its environment version (`+env5` for version 5, `+env6` for version 6):

```text
geobrix@https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl
```

Environment dependencies are installed with an unquoted `%pip install`, so spaces around `@` split
the requirement and the install fails. A Lakeflow pipeline's dependency lines follow the same rule.
The pipeline runs on the Databricks Runtime of its channel, not on a Serverless environment
version. It therefore takes the wheel for that runtime (`+env5` for DBR 18, `+env6` for DBR 19). See
[Lakeflow SDP](./ingestion/lakeflow-sdp#environment).

Workspaces that restrict outbound network access (for example, Serverless egress controls) can
block GitHub — install from a Unity Catalog Volume, as above, in that case.

### Verify the install

Confirm the wheel imports, the env wheel's GDAL is the one rasterio runs, and a function runs end to end. The check below exercises RasterX (`rst_*`); VectorX (`st_*`) and GridX ship in the same wheel and run the same way:

```python
import rasterio
from databricks.labs.gbx.rasterx import functions as rx

print("rasterio", rasterio.__version__, "| GDAL", rasterio.__gdal_version__)

# Functional check: load a GeoTIFF and read its properties.
tiles = (
    spark.read.format("binaryFile")
    .load("/Volumes/<catalog>/<schema>/<volume>/path/to/*.tif")
    .select(rx.rst_fromcontent("content", "GTiff").alias("tile"))
)
tiles.select(
    rx.rst_width("tile").alias("width"),
    rx.rst_height("tile").alias("height"),
    rx.rst_srid("tile").alias("srid"),
).show()
```

If the import succeeds and the query returns raster dimensions, the install is ready. To add the JVM engine, continue with [Env wheel and JAR](#heavyweight) or [Databricks Container Service](./installation/dcs.mdx).

## Env wheel and JAR {#heavyweight}

The JVM engine runs on a dedicated cluster with two cluster libraries: the env wheel and the GeoBrix JAR. The wheel carries the native GDAL, PROJ and GEOS. The JVM loads them from the wheel.

1. Stage the env wheel for the runtime in a Unity Catalog Volume: `+env5` on DBR 17.3 and 18, `+env6` on DBR 19.
2. Stage the JAR with `gbx.stage_jar`, as described [below](#stage-jar).
3. Create a cluster with **Dedicated** access mode on DBR 17.3, 18 or 19. Use an x86 instance type on any of them, or Graviton (arm64) on DBR 19.
4. Under **Libraries**, install the wheel (Python whl) and the JAR (JAR) from their Volume paths.
5. Start the cluster, attach a notebook and [register](#register).

A cluster loads one GeoBrix JAR, so install only one. On DBR 19 you can also install the wheel from a notebook with `%pip` and keep the JAR as a cluster library.

Standard access mode refuses the JVM functions. Every function still runs in Python there.

The env wheel carries the JAR that matches its version. `gbx.stage_jar` copies it to a Volume folder, so you need no separate download:

The call does this:

- It copies the JAR to the folder and writes a `.sha256` file beside it.
- It checks that the JAR matches the wheel's version and the hash in the wheel's `RECORD`.
- It refuses a folder that already holds another GeoBrix JAR. A cluster must load one.
- It prints the next step and returns the staged path.

Pass `overwrite=True` to copy the JAR again. Then add the printed path as a cluster library and **restart the cluster**: a running cluster cannot load a JAR.

On standard access mode, a metastore admin must first add the Volume path to the artifact allowlist. Dedicated clusters need no allowlist entry.

Then install the same env wheel on the cluster. `gbx.register(spark)` checks that the JAR and the wheel are the same version.

:::warning Upgrading from GeoBrix 0.5.x
GeoBrix 0.5.x installed native GDAL with a cluster init script. **Remove that init script from the cluster** and do not install the GDAL bundle. A system GDAL beside a 0.6.0 wheel puts two GDAL stacks in one cluster. See [Release Notes: 0.6.x](./release-notes-0-6#init-script) and the [migration guide](./migration-0-6).
:::

:::note Staying on GeoBrix 0.5.x
These pages describe 0.6.x. To install 0.5.x with its init script, use the assets of the [v0.5.2 release](https://github.com/databrickslabs/geobrix/releases/tag/v0.5.2). They include the init script, the GDAL bundle and `geobrix-docs-0.5.2.zip`, the docs for that release.
:::

Two optional settings apply to the JVM engine:

- **netCDF-4 filters.** Reading zstd, blosc or bzip2 netCDF-4 needs `HDF5_PLUGIN_PATH` in the cluster's environment variables. Without it the result is a silent NULL. The variable also reaches other HDF5 libraries on the cluster. See [Compressed netCDF-4 variables](./readers/netcdf#compressed-netcdf-4-variables-zstd-blosc-bzip2).
- **HTTP.** Leave `GDAL_HTTP_VERSION` unset. See [Remote reads](./readers/raster#remote-reads-over-https).

## SQL from a JVM job {#jvm-sql}

GeoBrix registers its SQL functions from Python with `gbx.register(spark)`. The registration lives in one Spark session. JVM code on the same session, in Scala or Java, calls the functions by SQL name. The JAR adds faster implementations for many functions. It registers no SQL names.

Choose the route by where the code runs:

| Route | Compute | Functions |
|---|---|---|
| [Python entry point, Scala body](#jvm-python-entry) | A job task on a dedicated cluster | All of them. A table function cannot go in a select list, as described below. |
| [A notebook that mixes languages](#jvm-notebook) | A notebook on dedicated compute | All of them |
| [Unity Catalog functions](#jvm-uc) | Any compute that reads Unity Catalog, including Serverless JAR tasks | The Unity Catalog slice |

What the Scala code can call, checked on a dedicated cluster on DBR 17.3:

- A scalar function, with `spark.sql`, `functions.expr` or `call_function`.
- An aggregate function, in a `GROUP BY`.
- A table function, in `SELECT * FROM gbx_x(...)` and in `FROM t, LATERAL gbx_x(...)`.
- A lightweight data source, such as `spark.read.format("raster_gbx")`.

A lightweight table function does not resolve in a select list: `SELECT gbx_x(...)` and `call_function("gbx_x", ...)` fail with `UNRESOLVED_ROUTINE`. Use the `FROM` or `LATERAL` form. See [Surfaces and levels](./api/execution-tiers.mdx).

`spark._jvm` and `spark._jsparkSession` exist only where Python and the JVM share a process. That is a dedicated cluster. Standard access mode and Serverless run Spark Connect, which gives Python no access to the JVM. Use the Unity Catalog route there.
:::

### A notebook that mixes languages {#jvm-notebook}

On dedicated compute, run `gbx.register(spark)` in a Python cell. Cells in other languages use the same Spark session, so a `%sql` or `%scala` cell calls the functions by name.

Serverless notebooks have no Scala cells.

### Tasks of a job do not share a session

Each task of a job has its own session. Functions registered in a Python task are not visible to a later JAR task. Put the Scala call in the same Python task, as above.
