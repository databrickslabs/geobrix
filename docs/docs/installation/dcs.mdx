# Databricks Container Service

[Databricks Container Service](https://docs.databricks.com/aws/en/compute/custom-containers) (DCS)
starts a cluster from a custom Docker image. A GeoBrix image carries native GDAL with its Java (JNI)
bindings, the GeoBrix wheel and the GeoBrix JAR, so a **dedicated** cluster started from it runs
**both tiers** — heavyweight readers included — with no init script and no cluster library.

DCS is the **preferred packaging for the heavyweight tier**: GeoBrix is moving away from the
[init script](./init-script.mdx) toward it. The GeoBrix image is built on the **DCS vNext**
environment images (`databricksruntime/environment:v6-standard` and its `-arm` variant), which
support Graviton through the ARM base image. Today's verified scope is a dedicated Graviton (arm64)
cluster on DBR 19 with the env 6 ARM image below; x86 (amd64) and DBR 17.3 / 18 images are not yet
available. On classic x86 clusters (DBR 17.3, 18, or 19), the
[Init Script (Legacy)](./init-script.mdx) route is still supported.

**x86 (amd64) and DBR 17.3 / 18 images are not yet available.** On that compute, use
[Init Script (Legacy)](./init-script.mdx) for the heavyweight tier on classic x86 clusters.

The heavyweight tier needs dedicated compute. On standard access mode and Serverless, use
[WHL-only (Lightweight)](../installation.mdx#whl-only).

## The image

The image is published as:

- **`mjohns797/geobrix:<version>-env6-arm`** — pinned to a GeoBrix release (for example
  `mjohns797/geobrix:0.5.3-env6-arm`). Use this one so the image, wheel and JAR stay on the version
  you tested.
- **`mjohns797/geobrix:env6-arm`** — moves to the newest release.

It contains:

- **Base:** `databricksruntime/environment:v6-standard-arm`, the DCS vNext environment 6 image
  for Graviton (arm64); its x86 counterpart is `v6-standard` — see the
  [Databricks base image list](https://docs.databricks.com/aws/en/compute/custom-containers-standard).
- **Native GDAL 3.11.4**, built from source with its Java (JNI) bindings — the native library the
  heavyweight JAR loads.
- **The GeoBrix wheel**, installed with the `[light_env6,vizx]` extras (the core lightweight tier
  plus visualization) into the image's Python, so the lightweight tier needs no `%pip` step.
- **The GeoBrix JAR**, the only GeoBrix JAR on the image, in `/databricks/jars` — the directory a
  dedicated cluster loads JARs from.

STAC search is not in the image. Add it in a notebook with `%pip install "geobrix[stac]"`; on env 6
this upgrades `requests` from the image's 2.32.5 to 2.34.2 or later. The sample-data downloaders and the
other opt-in extras (`[overture]`, `[earthdata]`, `[photogrammetry]` and `[models]`) are not in the image
either and install the same way, for example `%pip install "geobrix[earthdata]"`.

The Dockerfile that builds each release's image is attached to the
[GitHub release](https://github.com/databrickslabs/geobrix/releases) as
`geobrix-<version>-dcs.Dockerfile`.

## Set up a dedicated cluster

1. **Enable DCS for the workspace.** A workspace admin enables Container Service (the `enableDcs`
   workspace setting) — see
   [Databricks Container Services for dedicated compute](https://docs.databricks.com/aws/en/compute/custom-containers).
2. **Create the cluster** with **Dedicated** access mode, **Databricks Runtime 19**, and a
   **Graviton (arm64)** instance type.
3. **Point it at the image.** Under **Advanced**, open the **Docker** tab, select **Use your own
   Docker container**, and enter the image in **Docker Image URL**.
4. **Enable Unity Catalog Volumes.** Add this line to the cluster's **Spark config** — without it,
   `/Volumes` paths are not available on the cluster:

   ```text
   spark.databricks.unityCatalog.volumes.enabled true
   ```

5. **Start the cluster.** The first start pulls the image (about 7 GB), which takes several
   minutes — about 9 minutes in testing.

There is **no init script** and **no library to attach**. In particular, do **not** attach the
GeoBrix JAR as a cluster library: the image already carries it, and a cluster should have only one
GeoBrix JAR.

## Reading `/Volumes` data with the heavyweight tier {#volumes-heavyweight}

On the image, the heavyweight readers read `/Volumes` paths directly: the raster `gdal` reader and
the vector `*_ogr` readers (`ogr`, `geojson_ogr`, `gpkg_ogr`, `shapefile_ogr`, …) take the same
`/Volumes/<catalog>/<schema>/<volume>/…` path you would give a lightweight reader, including for
schema inference. Pass the bare `/Volumes/…` path, not a `file:` URI. There is no need to read with
a `*_gbx` reader first and hand the result to heavyweight functions. See the
[Readers overview](../readers/overview.mdx) for each reader's options.
