# Databricks Container Service

[Databricks Container Service](https://docs.databricks.com/aws/en/compute/custom-containers) (DCS)
starts a cluster from a custom Docker image. A GeoBrix image carries native GDAL with its Java (JNI)
bindings and the GeoBrix wheel, so a **dedicated** cluster started from it runs **both tiers**
without an init script: the lightweight tier straight from the image's Python, and the heavyweight
tier once the GeoBrix JAR is attached as a cluster library.

DCS is the **preferred packaging for the heavyweight tier**: GeoBrix is moving away from the
[init script](./init-script.mdx) toward it. The GeoBrix image is built on the **DCS vNext**
environment images (`databricksruntime/environment:v6-standard` and its `-arm` variant), which
support Graviton through the ARM base image. Today's verified scope is a dedicated Graviton (arm64)
cluster on DBR 19 with the env 6 ARM image below; x86 (amd64) and DBR 17.3 / 18 images are not yet
available. On classic x86 clusters (DBR 17.3, 18, or 19), the
[Init Script (Legacy)](./init-script.mdx) route is still supported.

## The image

The verified image is **`mjohns797/geobrix:0.5.3-env6-arm`** (GeoBrix 0.5.3). It contains:

- **Base:** `databricksruntime/environment:v6-standard-arm`, the DCS vNext environment 6 image
  for Graviton (arm64); its x86 counterpart is `v6-standard` — see
  [DCS for standard compute](https://docs.databricks.com/aws/en/compute/custom-containers-standard)
  for the base image list.
- **Native GDAL 3.11.4**, built from source with its Java (JNI) bindings — the native library the
  heavyweight JAR loads.
- **The GeoBrix wheel**, installed with the `[light_env6]` extra into the image's Python, so the
  lightweight tier needs no `%pip` step.

Dedicated compute does **not** load JARs from the image's `/scala-jars/user` directory (the
location the Databricks standard-compute DCS page describes), so the heavyweight tier needs the
GeoBrix JAR attached as a cluster library — step 5 below.

## Set up a dedicated cluster

1. **Enable DCS for the workspace.** A workspace admin enables Container Service (the `enableDcs`
   workspace setting) — see
   [Databricks Container Services for dedicated compute](https://docs.databricks.com/aws/en/compute/custom-containers).
2. **Create the cluster** with **Dedicated** access mode, **Databricks Runtime 19**, and a
   **Graviton (arm64)** instance type.
3. **Point it at the image.** Under **Advanced**, open the **Docker** tab, select **Use your own
   Docker container**, and enter the image in **Docker Image URL**.
4. **Enable Unity Catalog Volumes.** Add this line to the cluster's **Spark config** — without it,
   `/Volumes` paths are not available on the cluster:

   ```text
   spark.databricks.unityCatalog.volumes.enabled true
   ```

5. **Attach the JAR** (heavyweight tier only). Download
   `geobrix-<version>-jar-with-dependencies.jar` from the
   [GeoBrix releases](https://github.com/databrickslabs/geobrix/releases) — the same version as the
   image's wheel — stage it in a Unity Catalog Volume, and install it on the cluster as a
   [compute-scoped library](https://docs.databricks.com/aws/en/libraries/cluster-libraries).
6. **Start the cluster.**

## Reading `/Volumes` data with the heavyweight tier {#volumes-heavyweight}

On this setup the JVM cannot read `/Volumes` paths directly. Native GDAL, Python, and Spark query
paths (such as the `binaryFile` reader) read them fine, but the heavyweight OGR readers
(`geojson_ogr`, `gpkg_ogr`, …) fail at schema inference on a `/Volumes` path. Read with the
lightweight readers, then apply heavyweight functions — the
[light→heavy bridge](../api/execution-tiers.mdx#light-heavy-bridge):

- **Vector:** read with a `*_gbx` reader (for example `geojson_gbx` or `gpkg_gbx`) and pass the
  geometry column to heavyweight `gbx_st_*` functions.
- **Raster:** list the files with [`file_gbx`](../readers/file.mdx), build tiles with the
  lightweight `rst_fromfile(..., materialize=True)`, then call heavyweight `gbx_rst_*` functions —
  the heavyweight tier accepts only materialized tiles.

Heavyweight [`gbx_st_transformcrs`](../api/vectorx-functions.mdx#st_transformcrs) returns **EWKB**
(the SRID travels with the geometry). To turn its output into a product geometry, use
`st_geomfromewkb`, not `st_geomfromwkb`.

## Standard access mode (Beta)

[DCS for standard compute](https://docs.databricks.com/aws/en/compute/custom-containers-standard)
is in Beta. With a GeoBrix image on standard access mode today:

- The lightweight **UDF functions** (`pyrx`, `pyvx`, `pygx`, and their `gbx_*` SQL registrations)
  work.
- The lightweight **Python DataSource readers** (`*_gbx`) are not available yet: they fail with a
  `ModuleNotFoundError` for `databricks.labs` when the data source is created.
- The **heavyweight tier is not available yet**.

Support for the readers and the heavyweight tier on standard access mode is being worked on.

For lightweight work on standard access mode, use
[WHL-only (Lightweight)](../installation.mdx#whl-only) on standard compute without a custom
container — the full lightweight tier runs there, readers included.

## Serverless

DCS is not available on Serverless compute yet. On Serverless, use
[WHL-only (Lightweight)](../installation.mdx#whl-only).
