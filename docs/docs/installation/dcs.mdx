# Databricks Container Service

[Databricks Container Service](https://docs.databricks.com/aws/en/compute/custom-containers) (DCS)
starts a cluster from a custom Docker image. A GeoBrix image carries the env6 wheel with its native GDAL
and Java (JNI) bindings, and the GeoBrix JAR. A **dedicated** cluster started from it runs **both tiers**,
heavyweight readers included, with no library to attach.

The image bakes in the same natives that the env wheel installs on a stock cluster. On DBR 17.3, 18 or 19
you can skip the image and install the wheel and the JAR as
[cluster libraries](../installation.mdx#heavyweight). Use the image to start every node with them in place.

The GeoBrix image is built on the **DCS vNext** environment images
(`databricksruntime/environment:v6-standard` for x86 and its `-arm` variant for Graviton). The image
targets a dedicated cluster on DBR 19, on a Graviton (arm64) or an x86 (amd64) instance type.

## Status

| Compute | Image |
|---|---|
| **Dedicated** access mode, Graviton (arm64), DBR 19 | Built, and its in-image checks pass |
| **Dedicated** access mode, x86 (amd64), DBR 19 | Built, and its in-image checks pass |
| DBR 17.3 / 18 | No image; use [cluster libraries](../installation.mdx#heavyweight) |

The in-image checks cover the GDAL stack, the JNI link, the plugin link and the locked packages.
GeoBrix has not yet run the current image on a cluster. The env wheel and JAR route is the one
verified on clusters, on DBR 17.3, 18 and 19.

There is no DBR 17.3 / 18 image. On that compute, install the env5 wheel and the GeoBrix JAR as
[cluster libraries](../installation.mdx#heavyweight).

The heavyweight tier needs dedicated compute. On standard access mode and Serverless, use
[WHL-only (Lightweight)](../installation.mdx#whl-only).

## The image

The image is published for each instance architecture, with a pinned tag per GeoBrix release and a
tag that moves to the newest release:

| Instance architecture | Pinned to a release | Newest release |
|---|---|---|
| Graviton (arm64) | `mjohns797/geobrix:<version>-env6-arm` | `mjohns797/geobrix:env6-arm` |
| x86 (amd64) | `mjohns797/geobrix:<version>-env6-x86` | `mjohns797/geobrix:env6-x86` |

Use the pinned tag (for example `mjohns797/geobrix:0.6.0-env6-x86`) so the image, wheel and JAR stay
on the version you tested. The two architectures carry the same contents:

- **Base:** `databricksruntime/environment:v6-standard-arm` for Graviton (arm64) or
  `databricksruntime/environment:v6-standard` for x86 (amd64), the DCS vNext environment 6 images —
  see the
  [Databricks base image list](https://docs.databricks.com/aws/en/compute/custom-containers-standard).
- **Native GDAL 3.13.3, PROJ 9.9.0 and GEOS 3.15.0** from the env6 wheel, with GDAL's Java (JNI) bindings.
  The image links the JNI library into `/usr/lib`, where the heavyweight JAR loads it.
- **The GeoBrix env6 wheel**, installed with the `[vizx]` extra (the core lightweight tier plus
  visualization) into the image's Python, so the lightweight tier needs no `%pip` step. The image
  holds the wheel's dependencies from a hashed lock. The lock changes one base package, `idna`, which moves to 3.20.
- **The GeoBrix JAR**, the only GeoBrix JAR on the image, in `/databricks/jars` — the directory a
  dedicated cluster loads JARs from.

STAC search is not in the image. Add it in a notebook from the env6 wheel at the image's version,
the `<version>` in the image tag. Use the same install form as the
[Installation](../installation.mdx#whl-only) page:

```python
%pip install "geobrix[stac] @ https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl"
dbutils.library.restartPython()
```

If the workspace restricts outbound network access, install from a Unity Catalog Volume instead:
`%pip install "geobrix[stac] @ file:///Volumes/<catalog>/<schema>/<volume>/geobrix/geobrix-<version>+env6-py3-none-any.whl"`.
In a job or pipeline environment, write the dependency line without spaces around `@`, the form
that works there:
`geobrix[stac]@https://github.com/databrickslabs/geobrix/releases/download/v<version>/geobrix-<version>+env6-py3-none-any.whl`.

On env 6 the STAC extra upgrades `requests` from the image's 2.32.5 to 2.34.2 or later. The
sample-data downloaders and the other opt-in extras (`[overture]`, `[earthdata]`,
`[photogrammetry]` and `[models]`) are not in the image either and install the same way, with the
extra's name in place of `stac`.

The Dockerfile that builds each release's image is attached to the
[GitHub release](https://github.com/databrickslabs/geobrix/releases) as
`geobrix-<version>-dcs.Dockerfile`.

### Build your own image

To build the image yourself, for example into a registry only your workspace can pull from, use the
Dockerfile attached to the release. The build installs binary wheels and compiles nothing. Every build
step runs with no network, and no package index is needed.

1. Put these in one empty directory:
   - `geobrix-<version>-dcs.Dockerfile`, from the release.
   - `geobrix-wheel/`, holding the env6 wheel `geobrix-<version>+env6-py3-none-any.whl`.
   - `geobrix-<version>-jar-with-dependencies.jar`, the JAR from the release.
   - `dcs.lock`, the hashed lock for the instance architecture: `python/geobrix/envs/env6/dcs-<arch>.lock` in the source tree of the release tag.
   - `wheelhouse/`, holding the locked wheels that the base image lacks (about 55), including GeoBrix's own `rasterio` build, which the lock pins by hash.
2. Build from that directory. The Dockerfile needs BuildKit, the default in Docker 23 and later
   (older versions: set `DOCKER_BUILDKIT=1`):

   ```bash
   docker build \
     -f geobrix-<version>-dcs.Dockerfile \
     --build-arg GEOBRIX_VERSION=<version> \
     --build-arg GBX_ARCH=aarch64 \
     -t <your-repo>:<tag> .
   ```

   The default base image is the arm64 (Graviton) one. For an x86 image, use
   `--build-arg GBX_ARCH=x86_64 --build-arg BASE_IMAGE=databricksruntime/environment:v6-standard --platform linux/amd64`.
3. Push the image to a registry your workspace can pull from, and enter it as the cluster's
   **Docker Image URL** in the steps below.

The release does not attach the lock or the wheelhouse. Build the image from a source checkout of the
release tag, where `gbx:dcs:build` stages these inputs, builds the image and checks it:

1. Build the env6 wheel with `gbx:build:wheel --env 6`.
2. Build GeoBrix's `rasterio` for the architecture with `gbx:build:native`. The lock pins its hash.
3. Run `gbx:dcs:build --arch arm64` or `--arch amd64`.

To make a new lock, for example after a base image update, add `--relock`. It needs `uv` and Docker,
and it runs `scripts/docker/dcs/dcs_lock.py relock`. The command fetches the wheelhouse from the lock.

The build takes about a minute natively and a few minutes under emulation. The wheel install leaves the
base image's package versions as they are, except `idna`. The build fails rather than change any other.

## Set up a dedicated cluster

1. **Enable DCS for the workspace.** A workspace admin enables Container Service (the `enableDcs`
   workspace setting) — see
   [Databricks Container Services for dedicated compute](https://docs.databricks.com/aws/en/compute/custom-containers).
2. **Create the cluster** with **Dedicated** access mode, **Databricks Runtime 19**, and a
   **Graviton (arm64)** or **x86 (amd64)** instance type.
3. **Point it at the image.** Under **Advanced**, open the **Docker** tab, select **Use your own
   Docker container**, and enter the image in **Docker Image URL**. Pick the tag that matches the
   cluster's instance architecture: `-arm` on a Graviton instance type, `-x86` on an x86 one.
4. **Enable Unity Catalog Volumes.** Add this line to the cluster's **Spark config** — without it,
   `/Volumes` paths are not available on the cluster:

   ```text
   spark.databricks.unityCatalog.volumes.enabled true
   ```

5. **Start the cluster.** The first start pulls the image, about 7 GB, which takes several
   minutes. An earlier image took about 9 minutes in testing.

There is **no library to attach**. Do **not** attach the GeoBrix JAR as a cluster library.
The image already carries it, and a cluster should have only one GeoBrix JAR.

## Reading `/Volumes` data with the heavyweight tier {#volumes-heavyweight}

On the image, the heavyweight readers read `/Volumes` paths directly: the raster `gdal` reader and
the vector `*_ogr` readers (`ogr`, `geojson_ogr`, `gpkg_ogr`, `shapefile_ogr`, …) take the same
`/Volumes/<catalog>/<schema>/<volume>/…` path you would give a lightweight reader, including for
schema inference. Pass the bare `/Volumes/…` path, not a `file:` URI. There is no need to read with
a `*_gbx` reader first and hand the result to heavyweight functions. See the
[Readers overview](../readers/overview.mdx) for each reader's options.

## netCDF-4 filters and h5py {#netcdf-filters}

The image links `/usr/local/hdf5/lib/plugin` to the wheel's HDF5 filter plugins. By design, the
heavyweight tier then reads zstd, blosc and bzip2 netCDF-4 with no `HDF5_PLUGIN_PATH` setting.
GeoBrix has checked the link in the image, but has not run such a read on a cluster.

h5py's own `libhdf5` searches that directory too. An h5py write that uses `hdf5plugin`, blosc
especially, can fail on a DCS cluster, because the wheel's plugin loads into a different `libhdf5`.
GeoBrix measured this failure on DBR 19 ML with `HDF5_PLUGIN_PATH` set to the same directory. It has
not measured it on a DCS cluster. See
[Compressed netCDF-4 variables](../readers/netcdf.mdx#compressed-netcdf-4-variables-zstd-blosc-bzip2).
