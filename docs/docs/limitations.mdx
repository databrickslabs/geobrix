## Coordinate Reference Systems (PROJ version skew)

GeoBrix's GDAL stack and DBR's built-in spatial functions each carry
their own PROJ runtime — they coexist on the cluster but are not the
same library, and the two PROJ versions can diverge slightly:

- **GeoBrix's GDAL** comes from the env wheel: GDAL 3.13.3, PROJ 9.9.0 and GEOS 3.15.0, in the
  wheel's own directory. The lightweight and the heavyweight tier both use that PROJ and its data.
- **DBR 17.3 LTS's built-in `ST_*` functions** link to PROJ 9.7.1,
  bundled with the runtime under `/databricks/native/` (with
  `PROJ_DATA=/databricks/native/proj-data`). Not registered with
  `ldconfig` and not installed via apt — fully isolated from
  `/usr/lib`.

The two run side-by-side in the same JVM/Python process without
conflict, because they're loaded from distinct paths. The cost is
**CRS-catalog skew at the edges**: any EPSG code added or refined
between PROJ 9.7.1 and 9.9.0 (newly-added projections, updated
grid-shift definitions, transformation pipeline changes) may be
interpreted slightly differently by a GeoBrix function vs. a DBR
built-in operating on the same geometry.

For the common EPSG codes you're most likely to use day-to-day —
`EPSG:4326`, `EPSG:3857`, `EPSG:27700`, the UTM zones — this is
invisible. For freshly-added projections or very precise datum
transformations, it may surface.

If you run into a CRS-related discrepancy between a GeoBrix function
and a DBR `ST_*` built-in on the same input, please
[file an issue](https://github.com/databrickslabs/geobrix/issues) with
the EPSG code and a minimal repro — that's the signal we'd use to
decide whether GeoBrix should follow DBR's PROJ version.

## Compute Requirements

The compute requirements below apply to the **heavyweight** tier (Scala JAR + native GDAL). The **lightweight** tier (the env wheel for the runtime, e.g. `geobrix-<version>+env6`, with its own GDAL) has none of them — it runs on Serverless compute (environment v6), standard (shared) clusters, Lakeflow declarative pipelines, and ARM. See [Choosing an Execution Tier](./api/execution-tiers).

The heavyweight tier runs on **dedicated clusters**. Install the env wheel and the GeoBrix JAR as cluster libraries, or use the GeoBrix [DCS image](./installation/dcs.mdx). See [Choose an install path](./installation.mdx#choose-an-install-path).
- **Not** compatible with Serverless compute (use the lightweight tier there)
- Not available on standard (shared) access mode, with or without a DCS image (use the lightweight tier there)
- Requires native GDAL libraries, which the env wheel carries (and the DCS image, from the same wheel)
- Runs on x86 for DBR 17.3 / 18 / 19, and on Graviton (arm64) for DBR 19
- **Band math with `gdal_calc`.** Heavyweight `rst_mapalgebra` failed on every cluster GeoBrix tested that has only the env wheel. The JVM cannot find `gdal_calc.py` on its `PATH`. `rst_ndvi` and `rst_chm` run the same code path, so expect the same failure. The DCS image is untested for it. Use the lightweight functions.

Databricks Runtime:
- **Minimum**: DBR 17.1 (recommended/tested: DBR 17.3 LTS or 18 LTS)
- GeoBrix is designed to work with Databricks product spatial functions (available DBR 17.1+)

### Serverless Spark configuration

On Serverless compute most Spark properties are locked to platform defaults and cannot be
overridden (for example, adaptive-query-execution toggles are ignored). Serverless does, however,
accept a **limited set** of Spark configs — including **`spark.sql.files.maxPartitionBytes`**, which
you can tune down (e.g. `"32m"`) to reduce the rows/bytes per partition on file and Delta scans. This
is a useful lever for controlling memory per task in decode-heavy pipelines (each partition holds
fewer files/rows, so each task decodes less at once). See the Databricks docs on
[configuring Spark properties for Serverless](https://docs.databricks.com/aws/en/spark/conf) for the
full allowlist.

## Zarr Stores

GeoBrix reads, registers and writes [Zarr stores](./formats/zarr) within these limits. The
[Limits](./formats/zarr#limits) section of that page repeats them beside the rest of the transactional model.

- **Runtimes.** Databricks Runtime 19 and Serverless environment 6 (Python 3.12), in the lightweight tier only.
  Databricks Runtime 17.3 and 18 and Serverless environment 5 are not supported. The heavyweight tier reads
  Zarr data only as materialized GeoBrix tiles.
- **Data types.** Numeric types and CF times. Strings and objects are not supported: an array GeoBrix cannot
  decode is left out of reads, and a complex array cannot be read as a table (a table has no column for
  complex numbers; read it as blocks).
- **Tiles.** `output="tiles"` needs the coordinates to form a regular grid. Read an irregular or curvilinear
  grid as blocks or a table.
- **Codecs.** The codecs that zarr-python, numcodecs and zarrs can decode. Writes use `zstd` and `crc32c`
  unless you pass `codecs`. A Zarr v3 array that has any codec beside `sharding_indexed` in its own codec list
  (a transpose before it, a compressor after it) is not supported: registering the store records the array as
  one GeoBrix cannot decode, a default read leaves it out with a warning, and naming it in `variables` raises
  `ZarrUnsupported`. Rewrite the array so that `sharding_indexed` is its only outer codec, with compression and
  other codecs inside it. zarr-python does not write that layout.
- **Reading with GDAL.** A GDAL before 3.13 cannot read sharded Zarr v3 stores, or ones that use the `crc32c`
  codec, which `gbx_zarr_write` writes by default. See [Zarr in the Raster Reader](./readers/raster).
- **File modes.** `file_mode="external"` is a preview that needs a workspace with the File type preview and
  compute that supports `FILE` values; the default, `"fuse"`, keeps path strings and works everywhere.
  `file_mode="managed"` is not available.
- **Cloud storage.** Direct storage access (`access="direct"`) has been measured on AWS only. Azure and
  Google Cloud storage are not measured yet: pass `access="fuse"` to read and write through the Volume mount,
  which sends no credentials.
