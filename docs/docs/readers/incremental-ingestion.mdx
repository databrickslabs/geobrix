# Incremental ingestion with Auto Loader

_Since:_ lightweight `read_paths` and `declare_ingest` **v0.5.3** · _(light-only — no heavyweight tier)_

[Auto Loader](https://docs.databricks.com/aws/en/ingestion/cloud-object-storage/auto-loader/) finds
new and changed files in a Volume folder and remembers which ones it has already delivered. The
GeoBrix `*_gbx` readers parse those files. Two functions join them, so a folder of vector files,
LiDAR point clouds, EXIF photos, rasters, NetCDF files or PMTiles archives becomes a table that
keeps up with the folder:

- **`read_paths`** takes a DataFrame of file paths — a batch listing or an Auto Loader stream — and
  reads every file with the reader you name.
- **`declare_ingest`** declares a complete Lakeflow pipeline flow on top of it: it watches a folder,
  writes the rows to a table, and decides what happens when a file is overwritten (`scd2`,
  `replace` or `append`).

Both are pure Python: no JAR and no init script, and neither needs `register(spark)` (they call the
reader classes directly). They run on Serverless, standard (shared) and classic compute.

## Supported formats

`read_paths` and `declare_ingest` take the name of a lightweight reader. The `_gbx` suffix is
optional and the name is case-insensitive.

| `format` | Reader | One input file becomes |
|----------|--------|------------------------|
| `vector_gbx` | [Vector](./vector) | Features (generic OGR reader) |
| `shapefile_gbx` | [Shapefile](./shapefile) | Features |
| `geojson_gbx` | [GeoJSON](./geojson) | Features |
| `geojsonl_gbx` | [GeoJSONL](../writers/geojsonl) | Features |
| `gpkg_gbx` | [GeoPackage](./geopackage) | Features |
| `file_gdb_gbx` | [File Geodatabase](./filegdb) | Features |
| `lidar_gbx` | [LiDAR](./lidar) | Points |
| `exif_gbx` | [EXIF/GPS](./exif) | Image metadata |
| `raster_gbx`, `gtiff_gbx` | [Raster](./raster), [GeoTIFF](./geotiff) | Raster tiles |
| `cog_gbx` | [COG](./cog) | Raster tiles, split into tile windows the same way as `raster_gbx` (see [Rasters](#rasters)). The Lakeflow connector maps a `.tif` file to `gtiff_gbx`; set `format: cog` there to use the COG reader. |
| `netcdf_gbx` | [NetCDF](./netcdf) | Set by the `mode` option: `"raster"` (default) gives one `(source, tile)` GeoTIFF tile per grid variable (and per slice with `fanout`); `"vector"` gives one point feature per observation or grid cell. |
| `pmtiles_gbx` | [PMTiles](./pmtiles) | Set by the `source` option, which is **required** here: `"archive"` gives one `(z, x, y, bytes)` row per tile stored in a `.pmtiles` file; `"raster"` renders `(z, x, y, bytes)` XYZ tiles from a GeoTIFF. Each file is rendered on its own, so a tile that covers two files appears once for each. |

Two kinds of reader are not supported. `file_gbx` only lists files, and the `binaryFile` or Auto
Loader listing that feeds `read_paths` already gives each file's path, size and modification time.
The heavyweight readers (`gdal`, `gtiff_gdal`, `*_ogr`) run in the JVM, and these two functions are
lightweight-tier only.

Each row carries the columns that reader normally returns, plus two lineage columns:

| Column | Type | Meaning |
|--------|------|---------|
| `_source_path` | `STRING` | Bare `/Volumes/...` path of the file the row came from |
| `_source_mtime` | `TIMESTAMP` | That file's modification time |

| Parameter | Default | Description |
|-----------|---------|-------------|
| `df` | _required_ | DataFrame with one row per file. Batch or streaming. |
| `format` | _required_ | Reader name from the table above. |
| `options` | `None` | Dict of reader options, exactly as on that reader's page (for example `layerName`, `chunkSize` or `tileSize`). |
| `path_col` | `"path"` | Column holding the file path, a Unity Catalog Volume path (see [Paths](#paths)). `dbfs:` and `file:` prefixes are accepted. |
| `mtime_col` | `"modificationTime"` | Column copied to `_source_mtime`. Pass `None` to leave `_source_mtime` NULL. |
| `schema_path` | `None` | The file whose columns define the output schema, or a folder: then only its first file (in path order) matching the format's [default file pattern](#default-file-patterns) is opened. For a batch DataFrame the default is the first path in `df`. **Required for a streaming DataFrame.** |
| `num_partitions` | `None` | Spread the work across this many tasks. See [Parallelism](#parallelism). |
| `lineage` | `True` | Set `False` to leave out `_source_path` and `_source_mtime`. |

### Rasters

Raster files (`raster_gbx`, `gtiff_gbx` and `cog_gbx`) are planned into their tile windows first.
The windows are read as separate tasks **only when `num_partitions` is set**; without it, a large
raster is read by a single task. Set `num_partitions` (on Serverless, always) and use the raster
reader's `tileSize` option to choose the window size:

By default each raster file is a single whole-file tile; `tileSize` cuts it into a grid of windows
(see the [Raster Reader](./raster) for its options). The raster `manifest` and `tilesTable` options
are rejected by `read_paths`: each input row already names one file, and a manifest would be read
again for every row. Read those with `spark.read.format("gtiff_gbx")` instead. A `.vrt` source
reports the `.vrt` file itself as its `_source_path`.

PMTiles inputs are planned the same way, in groups of `tilesPerPartition` tiles, for an archive
(`source="archive"`) and for a GeoTIFF it renders (`source="raster"`). A NetCDF file is read whole
by one task in both modes, because the reader reads all of a file's variables and slices in one
pass.

`declare_ingest` needs a Lakeflow pipeline whose runtime provides `pyspark.pipelines` with
`foreach_batch_sink` and `create_auto_cdc_flow`; the `CURRENT` channel does. Install the GeoBrix
light wheel in the pipeline's environment with the extra that matches the channel's Databricks
Runtime: `geobrix[light_dbr18]` for a DBR 18 channel, `geobrix[light_dbr19]` for DBR 19 (see
[Installation](../installation)).

```python
declare_ingest(target, source_dir, format, options=None, *,
               on_change="scd2", glob=None, num_partitions=None, schema_path=None)
```

| Parameter | Default | Description |
|-----------|---------|-------------|
| `target` | _required_ | Rows table, a fully qualified `catalog.schema.table` name. The other objects are created in the same catalog and schema. |
| `source_dir` | _required_ | Volume folder Auto Loader watches (see [Paths](#paths)). |
| `format` | _required_ | Reader name from the [formats table](#supported-formats). |
| `options` | `None` | Reader options, as for `read_paths`. |
| `on_change` | `"scd2"` | What to do when a file is overwritten: `"scd2"`, `"replace"` or `"append"`. |
| `glob` | `None` | File-name filter for the folder, in Spark `pathGlobFilter` syntax, such as `"zones_*.gpkg"`. By default, the format's [default file pattern](#default-file-patterns); a `glob` replaces that pattern. |
| `num_partitions` | `None` | As for `read_paths`. |
| `schema_path` | `source_dir` | File or folder that defines the table schema; a folder's first file matching `glob` is used. It is read once when the pipeline is declared (at each update), not for every micro-batch. Stage at least one file there before the first update. |

### Default file patterns

Auto Loader delivers every file under `source_dir` separately, so the parts of a multi-file
dataset (a shapefile's `.shx`, `.dbf` and `.prj` sidecars, or the files inside a `.gdb` folder)
would otherwise be read as inputs of their own. When `glob` is not set, `declare_ingest` passes the
format's pattern to Auto Loader. The same pattern picks the schema file from a folder
`schema_path`, in `read_paths` too.

| `format` | Default `glob` |
|----------|----------------|
| `vector_gbx` | `*.{gpkg,geojson,geojsonl,geojsons,shp,shz,shp.zip,gdb.zip,GPKG,GEOJSON,GEOJSONL,GEOJSONS,SHP,SHZ,SHP.ZIP,GDB.ZIP}` |
| `shapefile_gbx` | `*.{shp,shz,shp.zip,SHP,SHZ,SHP.ZIP}` |
| `geojson_gbx` | `*.{geojson,GEOJSON}` |
| `geojsonl_gbx` | `*.{geojsonl,geojsons,GEOJSONL,GEOJSONS}` |
| `gpkg_gbx` | `*.{gpkg,GPKG}` |
| `file_gdb_gbx` | `*.{gdb.zip,GDB.ZIP}` |
| `lidar_gbx` | `*.{las,laz,LAS,LAZ}` |
| `exif_gbx` | `*.{jpg,jpeg,JPG,JPEG}` |
| `raster_gbx`, `gtiff_gbx`, `cog_gbx` | `*.{tif,tiff,TIF,TIFF}` |
| `netcdf_gbx` | `*.{nc,NC}` |
| `pmtiles_gbx` with `source="archive"` | `*.{pmtiles,PMTILES}` |
| `pmtiles_gbx` with `source="raster"` | `*.tif` |

The patterns match the file name as written, so they cover lower- and upper-case extensions
(`photo.jpg` and `PHOTO.JPG`) but not mixed case such as `.Jpg`. Set `glob` for other names, for
example `glob="*.jp2"` for another raster format or `glob="*.{nc,nc4}"` for NetCDF-4 files named
`.nc4`. Deliver a File Geodatabase as a zipped `.gdb.zip` file. The `pmtiles_gbx` raster pattern is
`*.tif` only because that reader's `filterRegex` option keeps `.tif` files by default; to render
other files, set both `filterRegex` and `glob`.

GeoJSON is matched strictly by its `.geojson` extension, because many `.json` files are not
GeoJSON. For GeoJSON files named `.json`, pass `glob="*.{geojson,json}"`.

A `glob` you set replaces the default pattern rather than narrowing it, so it must still leave out
the other files of a multi-file dataset. For shapefiles, end it in the data file's extension:
`glob="zones_*.shp"` delivers only the `.shp` files, while `glob="zones_*"` also delivers each
shapefile's `.dbf`, `.shx` and `.prj` sidecars as inputs of their own. A backslash escapes a
pattern character (`\*` matches a literal `*`), as in Spark.

### Choosing `on_change`

Auto Loader runs with `cloudFiles.allowOverwrites` on in every mode, so a file that is overwritten in
place is delivered again. `on_change` decides what the table does with that second delivery.

| | `scd2` (default) | `replace` | `append` |
|---|---|---|---|
| **Rows table** | Append-only: one copy of a file's rows for each distinct content version | Latest content of each file only | Every delivery of every file |
| **Re-delivery, content unchanged** | Writes nothing | Writes nothing | Duplicates the rows |
| **File modified** | New rows are added; the earlier version's rows stay | That file's rows are replaced, one atomic `replaceWhere` per micro-batch | New rows are added; the earlier rows stay |
| **History** | `<t>_file_versions` records when each version was current | None | None |
| **Rows have `_source_hash`** | Yes | Yes | No |
| **Use when** | You need the latest content and a record of what it used to be | Only the latest content matters | You want a log of every delivery |

Here `<t>` is the last part of `target`. `scd2` and `replace` compare a SHA-256 hash of the file's
bytes (`_source_hash`) with what is already stored, so a file that is re-delivered without a content
change is recognized and skipped. `append` does not hash anything.

Each mode declares these objects in the catalog and schema of `target`:

| Object | `scd2` | `replace` | `append` |
|--------|:------:|:---------:|:--------:|
| `target`: the rows | yes | yes | yes (streaming table) |
| `<t>_file_events`: one row per delivery with `_source_path`, `_source_mtime`, `_source_hash`, `_source_size` | yes | yes | no |
| `<t>_file_versions`: one row per content version of a file, with `__START_AT` and `__END_AT` | yes | no | no |
| `<target>_current`: a view of the rows for each file's latest version | yes | no | no |

In `scd2` and `replace` the rows table is written by the pipeline's batch sink: it is a regular
Delta table, created on the first update and clustered by `_source_path`, not a dataset the
pipeline manages.

`<target>_current` returns each file's latest rows. To read what was current at an earlier time,

`__START_AT` and `__END_AT` are the file's modification times, so the time you ask for is when the
file's content was written, not when the pipeline ingested it. `__END_AT` is `NULL` for the
current version, and an interval includes its start and excludes its end.

"Current" means the version with the newest modification time. A copy that keeps or backdates the
source's modification time (`cp -p`, `rsync -t`) can give an overwrite an older time than the
version it replaces; that content is then recorded as history and does not become current. Copy
without preserving times when you overwrite a file.

### What a pipeline update does

- **The newest delivery of each file wins** (`scd2` and `replace`). When one micro-batch holds
  several deliveries of the same file, only the newest is read, because the bytes on disk are the
  newest content. Under `scd2` the older deliveries still appear in `<t>_file_versions`, but have
  no rows in the table.
- **A file modified after it was hashed is skipped** (`scd2` and `replace`) until its newer delivery
  arrives, so a row's `_source_hash` describes the content it was read from. Before reading, each
  file must still have its delivered size and a modification time within one second of the
  delivered one. A file overwritten in the instant between that check and the read, or rewritten
  with the same size within that second, can still be stored under the earlier hash; its next
  delivery is written as usual (and under `scd2` recorded as the current version).
- **A file deleted before it is read is skipped** with a warning (all modes), and Auto Loader counts
  it as processed. Deleting a file does not remove rows that were already written, with one rare
  exception: under `replace`, a file deleted in the instant between that check and the read is
  still part of the micro-batch's `replaceWhere`, so its earlier rows are removed and no new rows
  are written for it.

## Behavior

### Schema

The table schema comes from one file: `schema_path`, or for a folder its first file matching the
format's [default file pattern](#default-file-patterns) (or `glob`). Files and folders whose names
start with `_` or `.` are skipped, as Spark's file sources skip them. For `file_gdb_gbx` and
`vector_gbx`, an unzipped `.gdb` folder inside that folder counts as one file. No other file is
opened to resolve it, so a folder that already holds files with other columns still resolves.
Every file that is read must have the same columns with the same types: a file that differs by
column name or type fails with an error that names the file. A file whose columns are in a
different order is realigned by name. A file with no features adds no rows.

### Paths

Paths are Unity Catalog Volume paths: `/Volumes/...`, or `dbfs:/Volumes/...` as Auto Loader and
`binaryFile` report them. The readers open each file through the Volume's file system, so an
object-store URI (`s3://`, `abfss://`, `gs://`) or a GDAL virtual path (`/vsis3/...`,
`/vsizip/...`, `/vsimem/...`) fails with an error that names it, rather than being skipped as
missing. To ingest from cloud storage, create an external volume over the location and use its
`/Volumes` path.

### Files deleted before they are read

A file that is deleted after it was listed but before it is read is skipped with a warning, not
treated as an error. In a stream, Auto Loader counts such a file as processed.

### Parallelism

- **Vector, LiDAR, EXIF and NetCDF files are each read whole by a single task.** `num_partitions`
  repartitions the files across that many tasks.
- **Raster files are planned into tile windows, and PMTiles inputs into groups of tiles; these are
  spread across tasks only when `num_partitions` is set.** Without it a large raster or archive is
  read by a single task. On Serverless, set `num_partitions`.

## Compared with the Lakeflow connector

GeoBrix also ships a Lakeflow Connect community connector (`sourceName` `geobrix`). It is the
route for the **Add data** page and managed ingestion pipelines, and it is governed through a Unity
Catalog connection: its `root_path` option confines every table to a Volume prefix, and `USE
CONNECTION` controls who can build pipelines on it.

It reads the same formats with the same code as `read_paths`, so its rows carry the same columns
and the same `_source_path` and `_source_mtime` lineage columns. The reader comes from the file
extension, or from the `format` table option, which takes the same reader names as `read_paths`
(the `_gbx` suffix is optional, so `gpkg` and `gpkg_gbx` are the same reader); a folder that mixes
formats needs `format`. By extension a `.tif` file is read with `gtiff_gbx` (set `format: cog` for
the COG reader), a `.nc` file with `netcdf_gbx` and a `.pmtiles` file with `pmtiles_gbx`, which
reads the tiles stored in the archive (`source="archive"`). A `.json` file is not taken for
GeoJSON: set `format: geojson` and a `file_glob` such as `*.{geojson,json}`.

The table options `layer`, `where`, `bbox` and `chunk_size` apply to the vector readers and `mode`
to `lidar`, `exif` and `netcdf`; set for another reader, an option fails with an error that names
it. The `file_glob` option uses the same pattern syntax as `declare_ingest`'s `glob` (Spark
`pathGlobFilter`: case-sensitive, with `{a,b}` groups and `\` escapes). With `format` set it alone
picks a folder's files, as `glob` does; without `format` it narrows the files with a recognized
extension. Folders and files whose names start with `_` or `.` are ignored, so use `_archive/` or
`_staging/` to keep files out of a table. The connector is **append only**, with the file
modification time as its cursor.

| | Lakeflow connector | `declare_ingest` |
|---|---|---|
| Where you set it up | Add data, or a managed ingestion pipeline | A pipeline source file |
| Access control | Unity Catalog connection (`root_path`, `USE CONNECTION`), plus Volume grants | Volume grants |
| Overwritten files | Re-read and appended | `scd2`, `replace` or `append` |
| File version history | No | Yes, with `scd2` |

Use the connector when you want the managed Add data experience and append is enough. Use
`declare_ingest` when a folder is large or grows quickly (Auto Loader keeps track of the files it
has delivered), or when a file can be overwritten and you need its latest content, or its history.
