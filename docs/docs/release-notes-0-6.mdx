## Python API and registration {#python-api}

### One Python API; the old modules are internal (breaking) {#one-python-api}

- **The Python API is `rasterx`, `gridx.<grid>`, `vectorx` and `pmtiles`.** The same import path serves every compute. `<grid>` is `bng`, `quadbin`, `custom` or `h3`.
- **The `pyrx`, `pygx` and `pyvx` packages are internal.** They export nothing. Their public functions and their `register()` are removed.
  - An old import path raises an error that gives a `Fix:` with the new path.
  - Every function keeps its name. `pyrx.functions.rst_width` is `rasterx.functions.rst_width`. `pygx.functions.bng_tessellate` is `gridx.bng.functions.bng_tessellate`. `pyvx.functions.st_makevalid` is `vectorx.functions.st_makevalid`.
  - The function names GeoBrix moved are every `rst_*`, `bng_*`, `quadbin_*`, `custom_*`, `h3_*` and `st_*` name the old modules defined.
- **Python-only helpers moved to `helpers` modules.**
  - `databricks.labs.gbx.rasterx.helpers`: `rst_viewshed_towers`, the `*_grouped` functions, `bin_points_tiled`, `rst_h3_gridspec`, `tile_range`, `mint_vrt`, `tile_to_numpy` and `rst_apply`.
  - `databricks.labs.gbx.vectorx.helpers`: `coverage_simplify`.
  - `databricks.labs.gbx.gridx.helpers`: `h3_los_visible` and `h3_viewshed_towers`.
- **Python-only modules moved.** `pyrx.checkpoint`, `mvs`, `ortho`, `sfm`, `imagery` and `file_table` are now `rasterx.<same name>`. `pyvx.file_read` and `pyvx.file_write` are now `vectorx.<same name>`. `Manifest`, `checkpoint_skip` and `input_signature` live in `rasterx.checkpoint`. The `dense_*` functions, `gpu_infra` and `recommend_dense_allocation` live in `rasterx.mvs`.
- **`gridx.h3.functions.h3_geomkring` and `h3_geomkloop` replace `geomkring` and `geomkloop`.** They take an optional `coverage` argument. `mode` stays.
- **`gridx.h3.functions.h3_cell_bbox(cellid, srid, mode, kring_pad, out_crs)` replaces `gbx_h3_cell_bbox` in the old modules.** The lightweight function called its `srid` argument `out_srid`. The v0.5.2 Scala function had no `out_crs`.
- **`vectorx.functions.st_setcrs` and `st_transformcrs` read a bare string as a CRS.** `vectorx.jts.legacy.functions.st_legacyaswkb` is gone. Use `vectorx.functions.st_legacyaswkb`.

See the [migration guide](./migration-0-6) for the old and new import for each entry point.

### One registrar: `gbx.register(spark)` (breaking) {#one-registrar}

- **One call registers the functions and the readers.** Call `from databricks.labs import gbx`, then `gbx.register(spark)`. It picks the best level for each function on the compute. It also registers the `*_gbx` data sources.
  - `gbx.register(spark, only=["gbx_rst_width"])` limits the functions. A name no function matches raises a `ValueError`.
  - The Python API also registers a function on its first call. In a Lakeflow pipeline it registers on the first call in each flow. See [Lakeflow SDP](./ingestion/lakeflow-sdp#register-geobrix-in-each-dataset-function).
- **The per-package registrars are removed.** The old `register()` functions of the generated modules (`rasterx`, `gridx.<grid>`, `vectorx`) raise an `AttributeError`. So do those of the `pyrx`, `pygx` and `pyvx` modules, of `databricks.labs.gbx.ds.register` and of `vectorx.jts.legacy`. The message gives the fix.
- **`databricks.labs.gbx.vectorx.jts.legacy` no longer exists.** The legacy decode is `vectorx.functions.st_legacyaswkb`.
- **Importing `databricks.labs.gbx.ds` no longer registers the readers.** The Scala data source that registered them is gone.
- **`register` prints a short reminder that links the [migration guide](./migration-0-6).** It prints the reason once when a function falls back to another level.
- **`gbx.register(spark, catalog="main", schema="geobrix")` says once when that schema holds functions from another version.** See [Unity Catalog functions](#unity-catalog-functions).

### Scala no longer registers SQL (breaking) {#scala-registration}

- **The `register` function of every Scala package is removed.** No Scala code registers SQL. Register once from Python or SQL with `databricks.labs.gbx.register(spark)`, then call the SQL names from Scala.
- **Scala keeps the per-name wrappers of the functions whose JVM implementation stays.** Those wrappers call the registered SQL names. For every other function, call `call_function("gbx_<name>", ...)` or `expr(...)`.
- **These Scala wrappers and classes are removed.**
  - Raster: `rst_retile`, `rst_polygonize`, `rst_rasterize`, `rst_viewshed`, `rst_clip`, `rst_histogram`, `rst_median`, `rst_metadata`, `rst_hillshade`, `rst_ndvi`, `rst_ndwi`, `rst_nbr`, `rst_evi`, `rst_savi`, `rst_index`, `rst_threshold`, `rst_chm`, `rst_align_to`, `rst_binpoints`, `rst_cog_convert`, `rst_transformcrs`, `rst_gridfrompoints`, `rst_combineavg`, `rst_combinecount`, `rst_combinemax`, `rst_combinemedian`, `rst_combinemin`, `rst_combinestddev`, `rst_combinesum`, `rst_bng_tessellate`, and the 96 `rst_{h3,quadbin,bng,custom}_rastertogrid{stat}` overloads.
  - Vector: `st_asmvt`, `st_asmvt_pyramid`.
  - Grid: `bng_eastnorthasbng`.
  - The `com.databricks.labs.gbx.gridx.quadbin` package. Call `call_function("gbx_quadbin_<name>", ...)`.
  - The expression classes behind these functions, and `BNG_CellUnionAgg`, `BNG_CellIntersectionAgg`, `RST_MergeAgg`, `RST_DTMFromGeoms`, `RST_DTMFromGeomsAgg` and `RST_GridFromPointsAgg`. The SQL names run on the lightweight level.
- **The JAR no longer holds the Scala expressions `RST_AlignTo`, `RST_CogConvert`, `RST_TransformCrs` and `ST_AsMvt`, or the `RstTransformCrsBytesUdf` Java UDF.** Their JVM forms measured slower than the lightweight forms at every scale tried on a dedicated cluster. GeoBrix keeps JVM code only where it is faster. `gbx_rst_binpoints` and `gbx_rst_cog_convert` ran the JVM form by default with the JAR. They now run the lightweight form. From Scala, call these functions with `call_function("gbx_<name>", ...)`.
- **16 more functions run the JVM form by default with the JAR.** On a dedicated cluster, each JVM form was at least 1.2x faster than the best lightweight form at 4x rows. The decoded output is the same. Without the JAR they run the lightweight form, as before.
  - The BNG `gbx_bng_geomkring`, `gbx_bng_geomkloop`, `gbx_bng_kloop` and `gbx_bng_polyfill`.
  - The custom-grid `gbx_custom_kring`, `gbx_custom_kloop`, `gbx_custom_geomkring`, `gbx_custom_geomkloop`, `gbx_custom_polyfill`, `gbx_custom_geomkringexplode`, `gbx_custom_geomkloopexplode` and `gbx_custom_cellfill`.
  - The cell rasterizers `gbx_rst_custom_rasterize_agg`, `gbx_rst_quadbin_rasterize_agg` and `gbx_rst_h3_rasterize_agg`.
  - `gbx_st_legacyaswkb`.
  - The gains ran from 1.7x (`gbx_bng_kloop`) to 9.8x (`gbx_custom_polyfill`) at 4x rows. See [Performance](./api/performance).
- **`gbx_rst_tilexyz` runs the JVM form by default with the JAR.** On a dedicated cluster the JVM form was 1.25x faster at 4x tiles and 1.22x faster at 16x tiles. The lightweight form it was timed against moves tiles in Arrow batches. The decoded output is the same. A virtual, NULL or error tile goes to the lightweight form.
- **`gbx_bng_kring`, `gbx_bng_cellfill` and `gbx_rst_bng_rasterize_agg` run the JVM form by default with the JAR.** On a dedicated cluster the JVM form was 1.2x to 2.5x faster than the lightweight form at 4x or 16x rows. The decoded output is the same. Without the JAR they run the lightweight form, as before.
- **Two raster accessors that return one value run the JVM form first with the JAR.** They are `gbx_rst_boundingbox` and `gbx_rst_worldtorastercoordy`. On a dedicated cluster they were timed against the lightweight form that moves tiles in Arrow batches. The JVM `gbx_rst_boundingbox` was 1.27x faster at 4x rows, and `gbx_rst_worldtorastercoordy` 1.22x faster at 16x rows. The decoded output is the same. A virtual tile goes to the lightweight form and a materialized tile to the JVM form, through a SQL function that routes the two. The accessors that return an `ARRAY<...>`, `MAP<...>` or `STRUCT<...>` stay on the lightweight form, because that routing function cannot sit under `explode` or `inline`.
- **The JAR no longer holds the 12 accessors and statistics that return an `ARRAY<...>`, `MAP<...>` or `STRUCT<...>`.** They are `RST_Avg`, `RST_Min`, `RST_Max`, `RST_PixelCount`, `RST_Sample`, `RST_GetNoData`, `RST_Type`, `RST_GeoReference`, `RST_BandMetaData`, `RST_Subdatasets`, `RST_RasterToWorldCoord` and `RST_WorldToRasterCoord`. Such a function can sit under `explode` or `inline`. There, Spark refuses the SQL function that routes a virtual tile to the lightweight form. So the JVM form could not be the default. On a dedicated cluster, `gbx_rst_avg` took 0.59x and 0.65x the lightweight time at 4x and 16x rows. That did not justify keeping it. These functions ran the lightweight form by default and still do. From Scala, call them with `call_function("gbx_<name>", ...)`.
- **The JAR no longer holds `RST_GridFromPoints`.** On a dedicated cluster the JVM form took 1.78x and 1.91x the time of the lightweight form at 4x and 16x rows. The decoded output was the same. `gbx_rst_gridfrompoints` ran the JVM form by default with the JAR. It now runs the lightweight form. From Scala, call it with `call_function("gbx_rst_gridfrompoints", ...)`.
- **The JAR no longer holds `RST_Slope`.** On a dedicated cluster, the JVM form took 0.97x and 1.05x the time of the lightweight form at 4x and 16x rows. So it is no faster. `gbx_rst_slope` runs the lightweight form, which runs GDAL's own slope algorithm. From Scala, call it with `call_function("gbx_rst_slope", ...)`. `gbx_rst_mapalgebra` and `gbx_rst_transformcrs` have no JVM form either. The JVM form of map algebra took 1.05x and 1.15x the time. The JVM form of `gbx_rst_transformcrs` returned NULL tiles for some of 4000 tiles under load. The lightweight forms returned none.
- **The JAR no longer holds `RST_Aspect`, `RST_TPI`, `RST_Roughness` or `RST_ColorRelief`.** On a dedicated cluster at 16x rows, the JVM forms of aspect, TPI and roughness were 1.17x, 1.14x and 1.05x faster. The comparison is the best lightweight form. That is under the 1.2x bar to keep a JVM form. The JVM color relief could not read a color table on a Volume. From Scala, call the four culled functions with `call_function("gbx_rst_<x>", ...)`.
- **The JAR no longer holds `RST_Transform`, `RST_Resample`, `RST_ResampleToRes`, `RST_ResampleToSize`, `RST_ToWebMercator`, `RST_FillNodata`, `RST_Proximity` or `RST_Summary`.** On a dedicated cluster, none of the JVM forms ran 1.2x faster than the best lightweight form. `gbx_rst_transform` ran at 0.71x the speed at 4x rows. `gbx_rst_resample` ran at 1.18x and 0.84x, and `gbx_rst_resample_to_res` at 1.10x and 1.01x, at 4x and 16x rows. `gbx_rst_to_webmercator` and `gbx_rst_resample_to_size` ran at 0.98x at 4x rows. `gbx_rst_fillnodata` ran at 0.32x and 0.18x. `gbx_rst_proximity` ran at 1.0x and 1.16x. The JVM summary wrote no band statistics, so its output differed from the lightweight one. These eight functions ran the lightweight form by default and still do. The JAR also no longer holds the JVM forms of 15 more raster functions. They are the aggregates `gbx_rst_binpoints_agg`, `gbx_rst_combineavg_agg`, `gbx_rst_derivedband_agg`, `gbx_rst_frombands_agg` and `gbx_rst_rasterize_agg`. They are the table functions `gbx_rst_h3_tessellate`, `gbx_rst_quadbin_tessellate`, `gbx_rst_custom_tessellate`, `gbx_rst_maketiles`, `gbx_rst_separatebands` and `gbx_rst_tooverlappingtiles`. They are also `gbx_rst_isempty`, `gbx_rst_tryopen`, `gbx_rst_isoband` and `gbx_rst_merge`. These functions run on the Python level, as before. From Scala, call them all with `call_function("gbx_rst_<x>", ...)`. The JAR also no longer holds the JVM forms of `gbx_rst_xyzpyramid` and `gbx_rst_derivedband`. The JVM table function of `gbx_rst_xyzpyramid` returned one `tile` column. That column held `z`, `x`, `y` and `bytes`, where the session function returns four columns. The JVM form of `gbx_rst_derivedband` kept the data type of the source, where the session function returns `Float64`. Both functions run on the Python level, as before. From Scala, call them with `call_function("gbx_rst_<x>", ...)`.
- **The JAR no longer holds the JVM forms of nine more functions.** They are `gbx_st_crs`, `gbx_st_setcrs`, `gbx_h3_cell_bbox`, `gbx_rst_frombands`, `gbx_rst_asformat`, `gbx_rst_convolve`, `gbx_rst_initnodata`, `gbx_rst_updatetype` and `gbx_pmtiles_agg`. On a dedicated cluster, none ran 1.2x faster than the best lightweight form at 4x or 16x rows. The decoded output was the same. The JVM `gbx_st_crs` ran at 0.59x the speed at 4x rows, and `gbx_rst_convolve` at 0.34x and 0.52x at 4x and 16x rows. `gbx_st_setcrs`, `gbx_st_crs`, `gbx_h3_cell_bbox` and `gbx_rst_frombands` ran the JVM form by default with the JAR. All nine now run the lightweight form. From Scala, call them with `call_function("gbx_<name>", ...)`. The `com.databricks.labs.gbx.pmtiles` package is gone with `gbx_pmtiles_agg`.
- **The JAR no longer holds the JVM forms of five more functions.** They are `gbx_rst_band`, `gbx_rst_setsrid`, `gbx_rst_setcrs`, `gbx_rst_getsubdataset` and `gbx_rst_tri`. On a dedicated cluster, none ran 1.2x faster than the best lightweight form at 4x or 16x rows. The decoded output was the same. The JVM `gbx_rst_setsrid` ran at 0.39x and 0.28x the speed at 4x and 16x rows, and `gbx_rst_setcrs` at 0.38x and 0.37x. The JVM `gbx_rst_band` ran at 0.43x and 0.46x, and `gbx_rst_getsubdataset` at 0.53x and 0.45x. `gbx_rst_tri` ran at 1.10x and 1.16x, and ran the JVM form by default with the JAR. All five now run the lightweight form. From Scala, call them with `call_function("gbx_<name>", ...)`.
- **The JAR no longer holds the JVM forms of 19 raster accessors.** They are `gbx_rst_crs`, `gbx_rst_format`, `gbx_rst_height`, `gbx_rst_memsize`, `gbx_rst_numbands`, `gbx_rst_pixelheight`, `gbx_rst_pixelwidth`, `gbx_rst_rotation`, `gbx_rst_scalex`, `gbx_rst_scaley`, `gbx_rst_skewx`, `gbx_rst_skewy`, `gbx_rst_srid`, `gbx_rst_upperleftx`, `gbx_rst_upperlefty`, `gbx_rst_width`, `gbx_rst_rastertoworldcoordx`, `gbx_rst_rastertoworldcoordy` and `gbx_rst_worldtorastercoordx`. They were timed on a dedicated cluster against the lightweight form that moves tiles in Arrow batches. Both forms spend most of the time reading the tile. Each JVM form was between 1.05x and 1.2x faster at 4x and 16x rows, under the 1.2x bar. The decoded output was the same. All 19 ran the JVM form by default with the JAR. They now run the lightweight form. From Scala, call them with `call_function("gbx_<name>", ...)`.
- **The JAR no longer holds `RST_Clip`.** It was never registered, so `gbx_rst_clip` always ran the lightweight form and no call changes. That form stays on rasterio, because GDAL's `raster clip` has no all-touched option. From Scala, call it with `call_function("gbx_rst_clip", ...)`.
- **The spectral indices, `rst_index` and `rst_threshold` run GDAL's `raster calc`.** The pixels equal the earlier results, with a few differences.
  - A pixel is NoData where an input band is NoData, a value is NaN or infinite, or a denominator is 0.
  - A source with no declared NoData value now treats the pixels equal to -9999 as NoData.
  - `rst_chm` subtracts with the same `raster calc`, so it needs the env wheel's GDAL. It raises the reason where GDAL is absent.
- **The warp functions run GDAL's `raster reproject`.** They are `rst_transform`, `rst_transformcrs`, `rst_to_webmercator`, `rst_resample`, `rst_resample_to_size` and `rst_resample_to_res`. They used rasterio before. The pixels equal the earlier results, with a few differences.
  - `rst_resample_to_res` gives pixels of exactly the resolution you ask for. When the resolution does not divide the extent, the extent changes by less than one pixel.
  - `bilinear` and `cubic` can differ from the earlier pixels beside NoData. `near`, `average` and every reprojection give the same pixels.
  - A call whose input and result together pass the compute's decoded size gives an error tile with a `Fix:`. Before, only the input counted.
  - A reprojection of a tile with no NoData value masks the pixels outside its footprint, with the tile's own mask band. Before, they were valid zeros. The band count stays.
  - `rst_resample` reads a virtual tile at the target size when the factor is below 1. A file with overviews serves the shrink from them.
  - A size from a factor that ends in .5 pixels rounds to the even size. Before, it rounded up.
- **`gbx_rst_contour` runs GDAL's `raster contour`.** It traced the lines with scikit-image before. The lines cross the same levels, and each level's lines lie within one pixel of the earlier ones.
  - The return type is the same: `ARRAY<STRUCT<geom_wkb: BINARY, value: DOUBLE>>`. `attr_field` is still accepted and still ignored.
  - A line now runs to the tile's edge, half a pixel past the outermost pixel centres. It can split differently at a NoData cell.
  - A pixel equal to -9999 is NoData in a tile that declares no NoData value. Before, the lines traced it as data.
  - `levels` may come in any order. Repeated and NULL elements are dropped.
  - An infinite level raises and names the value. Before, it gave no lines.
  - Empty `levels` with an `interval` that is not above 0 and finite raises, and so does a blank `attr_field`.
  - A NULL, error or corrupt tile gives NULL, and a tile with no line to trace gives an empty array.
- **`gbx_rst_polygonize` runs GDAL's `raster polygonize`.** It traced the regions with rasterio before. It takes the same arguments and gives the same two columns.
  - A float band is grouped by its exact value. Before, each pixel was rounded to a whole number first, so 1.2 and 1.4 joined one region and `value` was the rounded number, 1.
  - A NoData pixel, a transparent pixel and a pixel hidden by the tile's own mask band still give no polygon. So does a NaN or infinite pixel in a tile with no NoData value.
  - The regions of a tile stream through a temporary file on the worker's local disk. Memory grows by about 30 bytes for each region.
  - A read of that file that fails once it has opened fails the task, and Spark retries it. The result is never partial.
  - A `band` outside the tile raises and names the band. A `connectedness` other than 4 or 8 raises and names the value.
  - The JAR no longer holds `RST_Polygonize`. It had no SQL form, so no call changes.
- **`gbx_rst_fillnodata` runs GDAL's `raster fill-nodata`.** It used rasterio before. The filled pixels equal the earlier results, with a few differences.
  - GDAL fills one band for each run. The function runs it once for each band and keeps the tile's other properties, so every band is still filled by its own mask.
  - `max_search_dist` and `smoothing_iter` must be whole numbers from 0 to 2147483647. A fraction or a negative number raises and names the value. Before, `max_search_dist` took a fraction.
  - A pixel with no valid pixel within `max_search_dist` stays NoData. The function adds no value beyond GDAL's interpolation.
  - A NULL number gives NULL. A tile that declares no NoData value and has no mask band comes back as it is.
  - A tile whose validity is its own mask band keeps it. One example is a reprojection of a tile with no NoData value. The filled pixels become valid, and the pixels the search did not reach stay masked. Before, the mask was dropped and every pixel read as valid.
- **A virtual tile whose file is missing is retried, then raises with a `Fix:`. It is never a silent NULL.** This holds for every function that runs GDAL's own algorithm, such as slope, aspect, color relief, `raster calc` and contour. A Volume path can lag a write, so the read retries about 10 times. If the file is still missing, the error names the path. Check that it exists and is readable from the workers. A corrupt file still gives an error tile or NULL.
- **The JAR no longer holds the seven `RST_Combine*` expressions or `RST_BNG_Tessellate`.** On a dedicated cluster, the JVM `gbx_rst_combineavg` took 1.08x and 1.49x the time of the best lightweight SQL form at 4x and 16x rows. The times were 131.56 s against 122.16 s, and 576.44 s against 387.95 s. The DataFrame helper `combine_by_key` took 261.07 s at 16x rows. The raster `gbx_rst_bng_tessellate` took 0.97x and 1.03x the time of the lightweight form, a tie. These eight functions ran the JVM form by default with the JAR. They now run the lightweight form. From Scala, call them with `call_function("gbx_<name>", ...)`. The grid `gbx_bng_tessellate` keeps its JVM form.
- **The JAR no longer holds `RST_BuildOverviews`.** On a dedicated cluster the lightweight `gbx_rst_buildoverviews` was 2.2x faster than the JVM form. The function already ran the lightweight form by default and still does. The JVM form wrote the overviews in a sidecar file that the tile bytes did not carry. From Scala, call it with `call_function("gbx_rst_buildoverviews", ...)`.
- **The JAR no longer holds `RST_PercentileStretch`.** Its JVM form took the nearest-rank percentile and rounded the rescale, where the lightweight `gbx_rst_percentile_stretch` interpolates the percentile and truncates. On an 8-bit test tile the two differed by up to 1.24 levels. The function already ran the lightweight form by default and still does. From Scala, call it with `call_function("gbx_rst_percentile_stretch", ...)`.
- **The JAR no longer holds `RST_Filter`.** Its JVM mean filter of a gray + alpha tile left a different NoData mask than the lightweight `gbx_rst_filter` at a window with no valid pixel. The JVM form was never timed against it. The function already ran the lightweight form by default and still does. From Scala, call it with `call_function("gbx_rst_filter", ...)`.
- **The JAR no longer holds the band-math, canopy-height and contour expressions.** They are `RST_NDVI`, `RST_NDWI`, `RST_NBR`, `RST_EVI`, `RST_SAVI`, `RST_Index`, `RST_Threshold`, `RST_MapAlgebra`, `RST_Chm` and `RST_Contour`. The band-math and canopy-height functions run GDAL's `raster calc` in the worker. The JVM form ran `gdal_calc.py` for each row and is not needed. `gbx_rst_contour` returns an array. Spark refuses the SQL function that routes a virtual tile to the lightweight form under `explode`, so the JVM form could not be the default. From Scala, call them with `call_function("gbx_rst_<name>", ...)`. The Scala `rst_mapalgebra` and `rst_contour` Column functions are gone.
- **The JAR no longer holds `BNG_EastNorthAsBNG` or its Java UDFs `BngEastNorthAsBngUdf` and `BngEastNorthAsBngConnectUdf`.** On a dedicated cluster the JVM form took 1.17x and 1.35x the time of the lightweight batch form at 4 and 16 million rows. On a standard cluster the Java UDF was also slower (3.24 s against 1.70 s at 4 million rows). `gbx_bng_eastnorthasbng` now runs as a SQL function that needs no JAR, and falls back to the lightweight form.
- **Scala wrappers gained or renamed arguments.**
  - `rst_transform` takes `srid`, not `targetSrid`.
  - `rst_rastertoworldcoord*` and `rst_worldtorastercoord*` take `x` and `y`.
  - `rst_derivedband` names its second argument `pythonFunc`. `rst_maketiles` names its size `sizeInMb`.
  - `bng_kringexplode` and `bng_kloopexplode` name their parameter `cellid`. `quadbin_distance(cellid1, cellid2)` and `custom_distance(cellid1, grid, cellid2)` take the new names.
  - `st_triangulate` and `st_interpolateelevationbbox` gain Column wrappers. `st_legacyaswkb` gains a Scala wrapper.
- **`rst_viewshed` is lightweight only.** Its Scala wrappers and the Scala tab of its example are gone.

### Renamed and reordered arguments (breaking) {#signature-changes}

These changes affect callers that pass keywords or named arguments.

- **`rst_mapalgebra`: `json_spec` is now `expression`.** The expression uses GDAL's `muparser` grammar.
  - It replaces NumExpr. NumPy spellings such as `numpy.where` raise. Write a condition as `A > 0 ? A : 0`.
  - The envelope takes `calc` and the `A_index` and `A_band` style keys only.
  - A `dialect` or `extra_options` key raises and names itself.
- **`rst_transformcrs`: `crs` is now `target_crs`.**
- **`rst_align_to(tile, reference_tile)`** replaces `(tile, reference)`.
- **`rst_color_relief(tile, color_table)`** replaces `(tile, color_table_path)`. Pass the color table's text, not a file path. A path now raises, and so does any text that is not a color table. The error names the first bad line and carries a `Fix:`. To use a table file, read its text first and pass that.
- **`rst_land_cover(tile, method, n_clusters, smooth)`** replaces the keyword-only form. The `classes` argument always raised and is gone.
- **`rst_bng_rasterize_agg` takes twelve required arguments:** `cellid, value, out_srid, pixel_size, xmin, ymin, xmax, ymax, width, height, mode, kring_pad`. `out_crs` is an optional last argument.
- **`rst_custom_rasterize_agg(cellid, value, grid, ...)`** replaces `(cellid, grid, value, ...)`.
- **`custom_pointascell` takes `point` as its first argument** (it was `geom`). `custom_distance` takes `cellid1` and `cellid2`.
- **`pmtiles_agg(bytes, z, x, y, metadata_json=None)`** replaces `bytes_col`.
- **`rst_tilexyz` reads `rescale` as `'auto'`, `'none'` or the text `'min,max'`.** A tuple is no longer accepted.
- **`rst_histogram` takes an integer literal or a column for `n_buckets`.** `rst_sample` takes a literal for `crs`.
- **`rst_fillnodata` uses the SQL defaults:** 100.0 and 0.
- **`rst_hillshade` takes optional `xscale` and `yscale` in SQL.** `rst_slope` and `rst_hillshade` refuse one without the other, with a `Fix:`.
- **String arguments are literals.** These names read a string as its value, not as a column name: `format`, `resampling`, `rescale`, `compression`, `overview_resampling`, `color_table`, `crs`, `metadata_json`, `new_format`, `operation`, `python_func`, `func_name`, `subset_name`, `new_type`, `method`, `driver`, `coverage`, `assignment`, `layer_name`, `out_crs`, `attr_field`, `statistic`, `mode`, and the BNG `resolution` and the TIN `split_point_finder` and `grid_origin`.
  - A column can no longer supply those arguments row by row.
- **`rst_derivedband` and `rst_derivedband_agg` take the pixel function as a Python string only.** A `Column`, including `F.lit(...)`, raises a `TypeError` with a `Fix:`. SQL is unchanged.
- **The `rst_fromfile` Python default is a virtual tile.** Pass `materialize=True` for a materialized tile. The SQL function `gbx_rst_fromfile` materializes.
- **`rst_merge_agg(tile, materialize=False)` returns the unforced BINARY form.** Only `materialize=True` or a directory and prefix force a tile.
- **`rst_rasterize`, `rst_gridfrompoints` and `rst_dtmfromgeoms` take an optional `out_srid` and a trailing `out_crs`.** `out_crs` is `EPSG:n`, `ESRI:n` or WKT. Setting both raises. A NULL `out_srid` with no `out_crs` leaves the output without a CRS.

### Generators and aggregates change shape (breaking) {#shape-changes}

- **Generators are DataFrame calls in Python.** `rst_retile`, `rst_polygonize`, `rst_xyzpyramid`, `rst_maketiles`, `rst_h3_rastertogridavg` and the other tessellation, TIN and explode functions take the input DataFrame and return it joined with the generated rows.
  - `gridx.bng.functions.bng_kringexplode(df, "cell", 1)`, `vectorx.functions.st_triangulate(df, ...)` and `rasterx.functions.rst_retile(df, "tile", 512, 512)` are examples.
  - The retile rows carry the tile's fields (`cellid`, `raster`, `path`), not one `tile` column. Rename an input column that has a generated column's name first.
  - A string argument in these calls names a column. `bng_tessellateexplode(df, "geom", "res")` reads the size from a column.
  - `rst_polygonize` is a table-function call. It no longer returns an array Column.
  - `rst_contour(tile, levels, interval, base, attr_field)` and `rst_isoband(tile, breaks)` are Columns.
- **The `rst_*_rastertogrid*` reducers return rows.** In SQL, write `FROM t, LATERAL gbx_rst_h3_rastertogridavg(tile, 5) t`. The old `posexplode(...)` and `LATERAL VIEW inline(...)` forms on the `ARRAY` no longer apply.
- **Aggregates return `BINARY` everywhere.** `rst_combineavg_agg`, `rst_frombands_agg`, `rst_derivedband_agg`, `rst_rasterize_agg`, `rst_gridfrompoints_agg`, `rst_binpoints_agg`, `rst_dtmfromgeoms_agg`, the cell rasterize aggregates, `rst_merge_agg` and `rst_bng_rasterize_agg` return GeoTIFF bytes.
  - This holds in SQL on every compute and in the Python call. Wrap the result with `rst_fromcontent(col, "GTiff")` for a tile.
  - Heavyweight SQL callers that read tile fields from a rasterize aggregate must wrap it.
  - Their optional arguments are positional. The rasterize aggregates take 12 or 13 arguments.
  - `rst_rasterize_agg` takes WKB only.
- **`gbx_rst_summary` returns GDAL's own JSON.** The function runs GDAL's `raster info` with statistics, in the worker. It returns the text of `gdalinfo -json`. The earlier lightweight shape is gone, so a query that reads its keys must change.
  - `bands[].min` and `bands[].max` are now `bands[].minimum` and `bands[].maximum`. `mean`, `stdDev`, `type` and `noDataValue` keep their names.
  - `coordinateSystem.epsg` and `coordinateSystem.crs` are now `coordinateSystem.wkt`. The EPSG code is `stac."proj:epsg"`.
  - GDAL rounds `minimum`, `maximum`, `mean` and `stdDev` to three decimals. The band's `metadata` holds `STATISTICS_*` strings with more digits.
  - The JSON adds `description`, `files`, `cornerCoordinates`, `wgs84Extent`, `stac` and, for each band, `block`, `colorInterpretation` and `metadata`. The input is shown as `<input>`.
  - A band with no valid pixel has no statistics. A tile held as bytes in another driver, such as PNG or netCDF, reports its own driver. A tile with no band held that way, such as a netCDF container, has an empty `bands` list. A virtual tile is read into a GeoTIFF of its window first, so it reports `GTiff`. A virtual tile of a container with no band gives NULL.
- **The four cell-fill aggregates return the `BINARY` payload,** not `ARRAY<STRUCT<cellid, value>>`.
- **`gbx_rst_merge_agg` has no JVM level.** It runs in Python on every compute.
- **`gbx_st_asmvt_pyramid` takes `layer_name` and `extent` as optional arguments.**

## Installation and runtime {#installation}

### One env wheel per runtime family, no light extra (breaking) {#env-wheels}

- **Install the env wheel for the runtime, with no light extra.**
  - `geobrix-<version>+env6-py3-none-any.whl`: Serverless environment 6, DBR 19, DBR 19 ML, SQL warehouses and UC functions.
  - `geobrix-<version>+env5-py3-none-any.whl`: Serverless environment 5, DBR 17.3, DBR 18 and Lakeflow pipelines on the `CURRENT` channel.
  - Each wheel carries its own GDAL, PROJ and GEOS. It also carries `rasterio`, `pyogrio`, `pyproj`, `shapely`, `netCDF4` and GDAL's `osgeo`, built against them. A process runs one GDAL.
  - The wheel of the other family refuses to import and names the file to install.
- **The Lakeflow examples run on DBR 19.**
  - As of 0.6.0, Lakeflow Spark Declarative Pipelines run DBR 19 on the `PREVIEW` channel; the examples use it with the env6 wheel.
  - Set the bundle variable `pipeline_channel` to `CURRENT`, with the env5 wheel, to fall back to DBR 18.
- **Migration.** Replace `"geobrix[light_env6,<extras>] @ file:///Volumes/…/geobrix-<version>-py3-none-any.whl"` with `"geobrix[<extras>] @ file:///Volumes/…/geobrix-<version>+env6-py3-none-any.whl"`.
  - Use `+env5` where you used `light_env5`, `light_dbr17` or `light_dbr18`.
  - The env wheels' extras are `stac`, `vizx`, `databricks`, and `zarr` on env6.
  - An `_all` form becomes `[stac,vizx]`, plus `[zarr]` on env6.
  - For GPU, replace `photogrammetry_gpu_env5`, `models_gpu_env5` and `gpu_env5_all` with the env wheel of the GPU runtime. Then follow the GPU install step below.
- **GPU install.** GPU stays on CUDA 12. The UDF workers of the Serverless GPU AI Runtime run environment 6, even when the driver runs environment 5. An env wheel refuses to import on the other environment. For a notebook that runs UDFs (GeoSAM, land cover), select environment 6 and install the env6 wheel. A driver-only GPU step such as dense MVS (`pycolmap-cuda12`) can stay on the env5 wheel. Then install the GPU packages as a separate step:
  - Photogrammetry: `pycolmap-cuda12==4.2.1`.
  - Models (GeoSAM): `torch==2.9.0`, `torchvision==0.24.0`, `segment-geospatial` and `opencv-python-headless==4.11.0.86`.
  - See [GeoSAM](./models/geosam).
- **Old install lines stop.** These 0.5.x extras fail at resolution (pip: `ResolutionImpossible`) and name the env wheel to install:
  - The light extras `light_env5`, `light_env6`, `light_dbr17`, `light_dbr18`, `light_dbr19` and their `_all` forms.
  - The GPU extras `photogrammetry_gpu_env5`, `models_gpu_env5` and `gpu_env5_all`.
  - See [Installation](./installation#whl-only).
- **`[models]`, `[photogrammetry]`, `[overture]` and `[earthdata]` are not extras in 0.6.0.** Install their packages as a separate step after the env wheel. See [Installation](./installation#whl-only).
  - `overturemaps` (raises `click` and `tqdm`).
  - `earthaccess` (raises `fsspec`).
  - `pycolmap`, or `pycolmap-cuda12` on the GPU runtime.
  - `torch`, `torchvision`, `segment-geospatial` and `opencv-python-headless` for GeoSAM.
- **`[vizx]` no longer installs a second GDAL.** It no longer installs PyPI's `rasterio`, `pyogrio`, `pyproj` and `shapely` (about 265 MB). It no longer moves `click` (Graviton, DBR 19) or `psutil` (DBR 17.3 / 18, environment 5).
- **`requests` on Serverless environment 5 and DBR 17.3 / 18.** These runtimes ship `requests` 2.32.3, which can send `~/.netrc` credentials to another host (CVE-2024-47081).
  - The env5 wheel's `[stac]` and `[vizx]` require 2.32.4 or later, below 2.33. Installing either upgrades `requests`.
  - Environment 6 and DBR 19 ship 2.32.5.
- **The env wheels are about 90 to 115 MB.** The 0.5.x wheel was 1.1 MB. Each env wheel carries GDAL, PROJ, GEOS and the GeoBrix JAR.

### The init-script install is removed (breaking) {#init-script}

- **GeoBrix 0.6.0 has no GDAL init script.** The heavyweight tier takes its GDAL, PROJ and GEOS from the env wheel.
  - Install the env wheel for the runtime and the GeoBrix JAR as cluster libraries on a dedicated cluster. The wheel is `+env5` on DBR 17.3 and 18, and `+env6` on DBR 19.
  - GeoBrix verified this on x86 for DBR 17.3, 18 and 19, and on Graviton (arm64) for DBR 19.
  - See [Cluster libraries](./installation#heavyweight).
- **Migration.** Remove the init script and the GDAL bundle from the cluster, then install the wheel and the JAR as libraries.
  - A 0.6.0 wheel beside the init script's system GDAL puts two GDAL stacks in one cluster.
- **GeoBrix no longer publishes the init script or the GDAL bundle tarball.** The 0.6.0 release attaches neither.
- **Heavyweight netCDF-4 with zstd, blosc or bzip2 filters returns NULL, with no error, unless `HDF5_PLUGIN_PATH` is set.** The lightweight tier reads these files without it.
  - Setting `HDF5_PLUGIN_PATH` cluster-wide breaks an h5py write with `hdf5plugin` blosc on a Databricks ML runtime.
  - See [Compressed netCDF-4 variables](./readers/netcdf#compressed-netcdf-4-variables-zstd-blosc-bzip2).
- **Band math runs GDAL's `raster calc` on every compute.** `rst_mapalgebra`, the spectral indices, `rst_threshold` and `rst_chm` need no `gdal_calc.py`, which the env wheel does not carry.
- **Leave `GDAL_HTTP_VERSION` unset.** See [Remote reads over HTTPS](./readers/raster#remote-reads-over-https).

### The JAR travels inside the env wheel; `gbx.stage_jar` stages it (new) {#stage-jar}

- **Each env wheel carries the GeoBrix JAR of its version.** The env wheels are about 90 to 115 MB, where the 0.5.x wheel was 1.1 MB, because they carry GDAL, PROJ, GEOS and the JAR.
- **`gbx.stage_jar(vol_dir)` copies the JAR to a Volume folder.** It writes a `.sha256` file beside it and checks the JAR against the wheel's version and its `RECORD` hash.
  - It refuses a folder that already holds another GeoBrix JAR. A cluster loads one.
  - It prints the next step: add the path as a cluster library on a dedicated cluster, and restart the cluster.
  - On standard access mode, a metastore admin must first allowlist the Volume path.
- **`register` refuses a JAR whose version differs from the wheel's.**
- **You no longer download the JAR from the release page.** See [Env wheel and JAR](./installation#heavyweight).

### A reminder prints on the first `register` (new) {#register-reminder}

- **`register` prints one line at the start of a session.** It names the env wheel, the registrar and the Python API, and links the [migration guide](./migration-0-6).
- **Importing a wheel built for another environment fails** and names the file to install.

### The native stack is GDAL 3.13.3, PROJ 9.9.0 and GEOS 3.15.0 (behavior change) {#native-stack}

- **One stack serves both tiers.** The env wheel carries it. The DCS image used GDAL 3.11.4 before. The images now take the wheel's stack.
- **What the build adds.**
  - JPEG XL: the `JPEGXL` driver and the GeoTIFF `JXL` codec read JPEG XL data. GeoBrix's writers do not offer `JXL`.
  - `raster calc` accepts the `muparser` dialect.
  - `REGEXP` works in GDAL's SQLite dialect (PCRE2).
  - libcurl 8.23 with HTTP/2, and JPEG decoding with SIMD.
  - Three PROJ grids (OSTN15, OSGM15 and EGM96) and the `projsync` grid downloader.
- **Drivers to know.** GDAL's PMTiles driver is vector only, and LIBERTIFF is an opt-in, read-only GeoTIFF reader. GeoBrix uses its own PMTiles code and does not enable LIBERTIFF.
- See [GeoBrix's GDAL build](./readers/raster#gdal-build) and [PROJ version skew](./limitations#coordinate-reference-systems-proj-version-skew).

### GeoBrix no longer installs PySpark (breaking for local installs) {#pyspark}

- Databricks provides PySpark. For a local Spark session, install `pyspark>=4.0.0` alongside GeoBrix. See [Installation](./installation).

### GDAL driver policy (behavior change) {#driver-policy}

- **The raster driver policy is on for the whole process.** From GeoBrix's import, these drivers are unavailable:
  - Drivers that run stored pipelines.
  - Drivers that index other rasters.
  - Drivers that reach a network API.
  - Drivers that act on what a file names (`KMLSUPEROVERLAY`, `ESRIC`, `MRF`).

  GeoBrix opens every raster with the allowed drivers only. With the env wheel, it also identifies a raster before opening it.
- **Turn it off** with `GBX_GDAL_DRIVER_POLICY=off`, or `spark.databricks.labs.gbx.gdal.driver_policy=off` in the cluster's Spark config. Set it before the first GDAL use. See [Security § 7](./security#7-raster-data-other-principals-can-write) for the install paths that get the full defence.
- **The lightweight tier refuses tile bytes that hold a VRT or another format that names other files.** Examples are `VRT`, `DERIVED`, the label formats (`PDS`, `ISIS3`, `VICAR`, `ENVI`) and the product directories. The error gives a fix: store the tile as a GeoTIFF, or pass the VRT as a virtual tile (a path). netCDF, HDF5, HFA, JP2 and GPKG bytes still open. `rst_asformat` no longer offers these formats. See [Security § 7](./security#7-raster-data-other-principals-can-write).
- **`spark.gdal.GDAL_SKIP` adds to the refused drivers** and can no longer re-enable one. `spark.gdal.*` cannot turn the VRT raw-band or Python settings back on.

### PROJ data, registered grids and OSTN15 (behavior change, fix) {#proj-data}

- **Lightweight CRS lookups work on the driver of a standard-access cluster (fix).** On DBR 19, functions that resolve a CRS on the driver, such as `gbx_zarr_sample`, failed with `Cannot find proj.db`. GeoBrix now uses its bundled PROJ data when the `PROJ_DATA` that is set holds no readable `proj.db`.
- **Raster CRS transforms work after `register_proj_grids` (fix).** GeoBrix points `PROJ_DATA` at one directory that combines the PROJ data and the registered grids. See [Registering custom grid files](./api/coordinate-reference-systems#registering-custom-grid-files).
- **The JVM engine takes a `PROJ_DATA` of several directories (fix).** GDAL read a colon-separated `spark.gdal.PROJ_DATA` as one directory, so EPSG codes did not resolve. Grids registered while queries ran could also make `gbx_rst_srid` NULL on some rows.
- **British National Grid transforms use OSTN15 (behavior change).** The env wheels ship Ordnance Survey's OSTN15 grid. Transforms between EPSG:27700 and WGS 84 or ETRS89 use it instead of PROJ's Helmert approximation.
  - Results are within millimetres of Ordnance Survey's test points.
  - Results differ from earlier values by about 1.7 m in central London and up to about 5 m elsewhere in Great Britain.
  - See [Grids that ship with GeoBrix](./api/coordinate-reference-systems#grids-that-ship-with-geobrix).
- **The JVM engine loads GDAL from a node-local copy (new).** On first use, each node copies the native libraries to `/local_disk0/geobrix/native`, or to `/tmp/geobrix/native` when another user owns `/local_disk0`. The JVM then loads them from that copy, not from a notebook's Python environment. Set `spark.databricks.labs.gbx.native.copy.dir` to use one folder only, or to `off` to load from the wheel. See [Env wheel and JAR](./installation#heavyweight).
- **`projsync` needs a local target directory.** Syncing straight into a Volume leaves `cache.db` at 0 bytes with a `disk I/O error`. Sync to local disk, then copy to the Volume. See [Fetch grids with projsync](./api/coordinate-reference-systems#fetch-grids-from-the-proj-cdn-with-projsync).

## Unity Catalog {#unity-catalog}

### Unity Catalog functions (new) {#unity-catalog-functions}

- **`gbx.uc.install(catalog, schema, volume_dir)` creates GeoBrix functions in Unity Catalog.** Run it from a Serverless environment 6 or DBR 19 notebook. SQL warehouses, dashboards and Genie then call `<catalog>.<schema>.gbx_*`.
- **Twelve SQL files of [Unity Catalog SQL examples](./examples/uc-functions) let you try the functions.** Install them into a schema, then run the queries in the SQL editor. The files cover every function by category, and `gbx:examples:uc-sql` runs them and imports them into your workspace.
- **The install covers these functions.**
  - BNG: `gbx_bng_pointascell`, `gbx_bng_eastnorthasbng`, `gbx_bng_polyfill`, `gbx_bng_tessellate`, `gbx_bng_kring`, `gbx_bng_geomkring`, `gbx_bng_cellarea`, `gbx_bng_aswkb` and `gbx_bng_centroid`.
  - Quadbin and H3: `gbx_quadbin_pointascell`, `gbx_quadbin_polyfill` and `gbx_h3_geomkring`.
  - Vector: `gbx_st_explainvalidity`, `gbx_st_makevalid`, `gbx_st_wrapx` and `gbx_st_legacyaswkb`.
  - Raster: `gbx_rst_transformcrs`.
  - Table functions: `gbx_bng_kringexplode`, `gbx_bng_geomkringexplode`, `gbx_bng_tessellateexplode` and `gbx_h3_geomkringexplode`.
- **A geometry goes in as a `GEOMETRY` with an integer SRID.** BNG functions need SRID 27700. Quadbin and H3 functions need 4326. Another SRID is refused with a `Fix:`, never read as the wrong unit.
  - A WKB `BINARY` is not a `GEOMETRY`. Build it with `st_geomfromwkb(wkb, srid)`.
  - `gbx_st_wrapx` and `gbx_st_legacyaswkb` return a `GEOMETRY`.
- **UC functions take a CRS as an integer SRID, `EPSG:<n>` or `ESRI:<n>`.** WKT, PROJJSON and PROJ strings are refused with a `Fix:`.
- **UC returns NULL where the session function raises for data it cannot serve.** One example is a text that is no cell id, or a quadbin polyfill of too many cells. A wrong parameter (mode, coverage, resolution, zoom or `k`) still raises a `Fix:` error.
- **Some BNG functions run as Scala functions when the install folder holds the JAR.** These are `gbx_bng_kring`, `gbx_bng_aswkb` and `gbx_bng_centroid`. Without the JAR they run as Python functions and give the same answers.
  - `gbx.uc.install` takes only `geobrix-<version>-jar-with-dependencies.jar` of the wheel's version. It refuses a folder without it, and an explicit `jar=` must be a Volume path that ends in `.jar`.
  - Stage the JAR with [`gbx.stage_jar`](#stage-jar) to use the Scala form.
- **The SQL engine casts an argument to the parameter type before GeoBrix runs.** A string passed as an easting becomes a number there. With ANSI mode off, a string that is no number becomes NULL.
- **`gbx_bng_cellarea` and `gbx_bng_eastnorthasbng` run as SQL functions on Unity Catalog and in the session.** They need no JAR and no Python. Over 1M rows on a local session, `gbx_bng_eastnorthasbng` took 0.28 s against 2.43 s for the Python form. A session without the JAR now uses the SQL form. `gbx_quadbin_distance`, `gbx_quadbin_kring` and `gbx_quadbin_kloop` also run as SQL functions, 1.7x to 4.3x faster than the Python form over 1M rows. `gbx_bng_cellarea` raises for a cell finer than 1 m, and `gbx_bng_eastnorthasbng` trims all white space from a resolution text.
- **`gbx.uc.install` gives every Python function the same package list by default (`deps="shared"`).** A statement that calls several GeoBrix functions then starts one sandbox. Three functions in one statement ran in 2.7 s instead of 33 s on Serverless. The first create takes about 45 s longer, once. Pass `deps="per-function"` for the old behavior.
- **Each function's COMMENT is `geobrix <version>: <summary>`.** `gbx.register(spark, catalog=..., schema=...)` says once when that schema was made by another version.
- **`gbx_bng_geomkring` and `gbx_h3_geomkring` raise a `Fix:` for a `k` below 0 or not whole.** They gave NULL. An empty `coverage` reads as the default, as an empty `mode` does.

See [Unity Catalog functions](./api/uc-functions) and [Installation](./installation#uc-functions).

### Unity Catalog forms that need no session (new) {#uc-no-session-forms}

- **Cell fills and BNG chips have `_array` forms.** These are `gbx_h3_cellfill_array`, `gbx_quadbin_cellfill_array`, `gbx_bng_cellfill_array`, `gbx_custom_cellfill_array`, `gbx_bng_cellintersection_array` and `gbx_bng_cellunion_array`. Call each with `GROUP BY` and `collect_list`.
- **`gbx_rst_bng_rasterize`, `gbx_rst_quadbin_rasterize` and `gbx_rst_custom_rasterize` run on Unity Catalog, as `gbx_rst_h3_rasterize` does.** Pass `collect_list(struct(cellid, value))`. For a large group, take `max(value)` for each cell first.
- **`gbx_rst_binpoints_partial` and `gbx_rst_binpoints_finalize` bin points in two steps.** Run the partial step, then `GROUP BY`, then the finalize step.
- **`gbx_rst_stats_partial` returns the state of each band of one tile.** It holds `count`, `sum`, `m2`, `min` and `max`. Merge the state across tiles with `GROUP BY` to get the statistics of their union.
- **`gbx_rst_h3_rastertogrid_partial` returns the H3 cell state of one tile.** Merge the state across tiles with `GROUP BY`.
- **On Unity Catalog, each raster-to-grid table function computes only its own statistic.** This covers H3, quadbin, BNG and custom grids, and the median is a table function there too. A sum or a count takes about half the time it took when every statistic read the full state. `gbx_rst_quadbin_rastertogrid_partial`, `gbx_rst_bng_rastertogrid_partial` and `gbx_rst_custom_rastertogrid_partial` join the H3 partial, and serve several statistics in one pass.
- **`gbx_rst_retile`, `gbx_rst_maketiles`, `gbx_rst_tooverlappingtiles` and `gbx_rst_separatebands` are table functions.** Call each with `LATERAL`. `gbx_rst_retile`, `gbx_rst_maketiles` and `gbx_rst_tooverlappingtiles` read a tile one window at a time and take one up to 256 MiB decoded. `gbx_rst_separatebands` keeps 64 MiB. A tile over its limit, or a result that could not fit, is refused with a `Fix:`.
- **The four `gbx_rst_<grid>_tessellate` functions, `gbx_rst_xyzpyramid`, `gbx_st_triangulate` and the two `gbx_st_interpolateelevation*` functions are table functions on Unity Catalog.** They give the session's cells, tiles, triangles and elevation points. A tessellation and the pyramid take a tile up to 64 MiB decoded, and the TIN functions take `ARRAY<GEOMETRY(ANY)>` points that keep their Z. A result over 64 MiB is refused with a `Fix:`. An elevation function also refuses a surface whose triangles, at most two for each point, pass 64 MiB, before it builds them.
- **On Unity Catalog, `gbx_rst_dtmfromgeoms` and `gbx_rst_gridfrompoints` take `ARRAY<GEOMETRY(ANY)>` points.** The Z of each point is kept, and so are the break lines of the terrain function. The session functions still take WKB or WKT arrays. Collect `GEOMETRY` values, not `BINARY`, in a UC statement.
- **`gbx_st_asmvt_array`, `gbx_st_coverageisvalid_array` and `gbx_st_coverageinvalidedges_array` take a collected array.** Call each with `GROUP BY` and `collect_list`. They answer as the aggregates `gbx_st_asmvt`, `gbx_st_coverageisvalid` and `gbx_st_coverageinvalidedges` do. The attributes of a feature are JSON text.
- **Seven vector functions and two raster file functions run on Unity Catalog.** They are `gbx_st_node`, `gbx_st_snap`, `gbx_st_split`, `gbx_st_simplifypreservetopology`, `gbx_st_reduceprecision`, `gbx_st_removerepeatedpoints`, `gbx_st_shiftlongitude`, `gbx_rst_buildoverviews` and `gbx_rst_cog_convert`. A geometry result keeps the SRID of the first argument. Two geometries in different SRIDs are refused with a `Fix:`.
- **The GDAL raster functions give on Unity Catalog the answer they give in a session.** These are the terrain functions, the spectral indices, `gbx_rst_index`, `gbx_rst_threshold`, `gbx_rst_mapalgebra`, the warp and resample functions, `gbx_rst_fillnodata`, `gbx_rst_summary` and `gbx_rst_contour`. Each UC function runs the same GDAL call as its session function, so it gives the same tile, lines or JSON.
  - The input and the result of one call together must fit 64 MiB decoded. Over that, the call is refused with a `Fix:`.
  - A tile with no CRS, given to a function that reprojects, gives NULL, as a corrupt tile does. A session gives an error tile for both.
- **`gbx_rst_viewshed`, `gbx_rst_color_relief` and `gbx_rst_polygonize` run on Unity Catalog.** The viewshed observer is a `GEOMETRY`. `gbx_rst_polygonize` is a table function, called with `LATERAL`, and refuses a result over 64 MiB with a `Fix:`.
- **`gbx.uc.install(..., stubs=True)` creates a raising function for each session-only scalar.** The scalars are `gbx_st_crs`, `gbx_st_setcrs`, `gbx_st_transformcrs`, `gbx_rst_fromfile` and `gbx_rst_derivedband`. The error names the route on Unity Catalog. Stubs are off by default. The [Unity Catalog page](./api/uc-functions#session-functions-on-uc) lists the route for every session function without a Unity Catalog twin. It also gives recipes, measured costs and size limits.

## Ingestion {#ingestion}

### Incremental ingestion: `read_paths` and `declare_ingest` (new) {#read-paths}

- **`read_paths` reads a DataFrame of file paths with any lightweight reader.** Give it a batch listing or an Auto Loader stream, and a reader name. The readers are `vector_gbx`, `shapefile_gbx`, `geojson_gbx`, `geojsonl_gbx`, `gpkg_gbx`, `file_gdb_gbx`, `lidar_gbx`, `exif_gbx`, `raster_gbx`, `gtiff_gbx`, `cog_gbx`, `netcdf_gbx` and `pmtiles_gbx`.
  - Rows carry the reader's columns plus `_source_path` and `_source_mtime`.
  - Raster, COG and PMTiles files spread across tasks when `num_partitions` is set. One task reads a NetCDF file.
  - See [`read_paths`](./ingestion/read-paths).
- **`pmtiles_gbx` needs the `source` option.** `"archive"` reads the tiles stored in `.pmtiles` files. `"raster"` renders tiles from GeoTIFF files, each on its own.
- **`declare_ingest` declares an Auto Loader flow in a Lakeflow pipeline.** `on_change` sets what happens when a file is overwritten:
  - `scd2` (default): append-only rows, with a versions table and a `_current` view.
  - `replace`: latest content only.
  - `append`: every delivery.

  See [Auto Loader ingestion](./ingestion/auto-loader).
- **GeoJSON is matched by its `.geojson` extension only.** The default pattern for `geojson_gbx` and `vector_gbx` excludes `.json`. For `.json` GeoJSON files, pass `glob="*.{geojson,json}"`.

### Bad data in ingestion: `on_error` (new) {#on-error}

- **`declare_ingest` sets bad records aside.**
  - `on_error="quarantine"` (default): each file is read on its own. What cannot be read goes to `<table>_bad_records`, created when the first one is found. The rest goes to the table, including rows read before an error in the same file.
  - `on_error="fail"`: the update fails on the first error and names the file.
  - With `on_change="append"` there is no bad-records table. Bad records are skipped with a warning in the executor logs.

  See [Unreadable data](./ingestion/auto-loader#unreadable-data).
- **`<table>_bad_records` has one row per bad record.** The columns are `_source_path`, `_source_mtime`, `_source_hash`, `_source_size`, `record_index` (`NULL` for the whole file), `error_class`, `error_message`, `raw` and `quarantined_at`. `raw` is the recovered content as JSON, at most 4096 characters. See [Query the bad records](./ingestion/auto-loader#query-the-bad-records).
- **A bad record is the smallest part of a file its reader can set aside.** It is one of these, or the whole file:
  - A vector feature, or a GeoJSONSeq line.
  - A GeoPackage feature on a corrupt page (by `fid`).
  - A raster tile window, or a run of LiDAR points.
  - A PMTiles tile.
  - A NetCDF variable or slice.
  - A `.jpg` that is not a JPEG.

  See [Unreadable files](./ingestion/read-paths#unreadable-files) for each format.
- **LiDAR.** When `on_error` is `skip` or `quarantine`:
  - A LAZ file with a corrupt chunk keeps the points around it. A truncated LAS file keeps its complete points.
  - GeoBrix sets the rest of a file aside as one record. It does so only after `max(3 × chunkSize, 250,000)` points in a row cannot be read.
  - A point outside the header's bounds is a `PointOutOfBounds` record. The bounds are widened on every side by their largest extent. Turn this off with the `lidar_gbx` option `checkHeaderBounds="false"`. See the [LiDAR reader](./readers/lidar#options).
  - GeoBrix sets aside a LAZ file before decoding if it has any of these. Otherwise the `lazrs` decoder would kill the worker.
    - An implausible chunk table or LASzip record.
    - More chunks than the header's point count needs.
    - A run of `0xFF` bytes in the point data. This scan adds about 5 to 10 percent to decode time.
  - A header that declares more points than the chunk table holds is read up to the table's points.
  - Without `skip` or `quarantine`, these files give a warning and a skip. The LiDAR downloader and the point-cloud layer of `plot_static` raise a `ValueError` that names the file.
  - `lazrs` must be 0.8.2 or later. GeoBrix requires it.
- **Other damage to a LAZ file can still stop the worker.** Damage inside the compressed points, a wrong but plausible chunk table, or a crafted file can crash the native decoder until `lazrs` fixes it.
  - A crash cannot be caught, so the file is not set aside. Spark retries the task and the update fails.
  - Remove the file or replace it with a readable copy.
- **A NULL or empty geometry is data, not a bad record.** A feature without a location, a `POINT EMPTY`, and a curve or surface are written like any other row. With `asWKB="false"`, curves and surfaces are set aside, because WKT cannot hold them. GDAL returns NULL for a geometry it cannot decode. Query the geometry column with `IS NULL` and `ST_IsEmpty` to watch for them.
- **Errors of the environment fail the update.** No bad record is written for these, because they are not about the data:
  - Out of memory.
  - A missing module, such as a LAZ decompression backend.
  - A Volume I/O error (retried first).
  - An image too large for `exif_gbx` `qc` mode.
- **A delivery set aside entirely is not read again.** It gets one `NothingReadable` bad record, and an identical re-delivery is skipped.
  - To read it again, for example after you fix a reader option, delete the file's `NothingReadable` rows from `<table>_bad_records`. Then touch the file or deliver it again.
  - A partly read delivery is skipped as stored. Delete its rows for that `_source_hash` from the table first, or deliver changed content.
- **`scratch_dir` sets where a micro-batch is staged.** Quarantine stages the micro-batch in a hidden `.gbx_scratch` folder under `scratch_dir` (a `/Volumes` folder; default `source_dir`).
  - The pipeline must be able to write there. A read-only landing folder needs a writable `scratch_dir` (or `on_error="fail"`).
  - GeoBrix removes the folder when the micro-batch ends. It removes one left by a killed micro-batch after 24 hours.
- **`<target>_current` shows each file's newest readable version.** If a file's latest delivery cannot be read, the view keeps the rows of its last readable version, also under `on_change="replace"`. A partly readable delivery replaces them with the rows that were read.
- **`read_paths(on_error="skip")` skips what cannot be read** and logs a warning in the executor logs. The default, `on_error="fail"`, fails the read and names the file. The [Lakeflow connector](./ingestion/lakeflow-connector) always fails the read on an unreadable file.

### Lakeflow connector: one multi-format connector (new) {#lakeflow-connector}

- **The `geobrix` connector reads vector, LiDAR, EXIF, GeoTIFF, COG, NetCDF and PMTiles files** with the same code as `read_paths`. A folder that mixes file kinds needs the `format` table option.
- **Defaults by extension.**
  - A `.tif` file is GeoTIFF. Set `format: cog` for the COG reader.
  - A `.nc` file is NetCDF.
  - A `.pmtiles` file reads the tiles stored in the archive.
  - A `.json` file is not taken for GeoJSON. Set `format: geojson` and a `file_glob` such as `*.{geojson,json}`.
- **`format` takes a reader name, as `read_paths` does.** The `_gbx` suffix is optional and case is ignored (`gpkg`, `GPKG` and `gpkg_gbx` are one reader). The File Geodatabase reader is `file_gdb`.
- **Table options apply only to the readers that take them.** `layer`, `where`, `bbox` and `chunk_size` apply to the vector readers. `mode` applies to `lidar`, `exif` and `netcdf`. An option set on a table read with another reader fails with an error that names it.
- **`file_glob` uses the same Hadoop glob syntax as `glob`** (case-sensitive, with `{a,b}` groups and `\` escapes). Folders and files whose names start with `_` or `.` are ignored. Use `_archive/` or `_staging/` to keep files out of a table.

See the [Lakeflow connector](./ingestion/lakeflow-connector) page for setup, table options and formats.

## Readers {#readers}

### The Scala readers and writers are retired (breaking) {#readers-retired}

- **The Scala readers are retired.** The lightweight `*_gbx` readers replace them. They run on every compute, and the Scala `gdal` reader was slower than the lightweight path at 4000 and 10000 tiles on a dedicated cluster.

| Retired format | Reader that replaces it |
|---|---|
| `gdal` | `raster_gbx` |
| `gtiff_gdal` | `gtiff_gbx` |
| `netcdf_gdal` | `netcdf_gbx` |
| `ogr` | `vector_gbx` |
| `shapefile_ogr` | `shapefile_gbx` |
| `geojson_ogr` | `geojson_gbx` |
| `gpkg_ogr` | `gpkg_gbx` |
| `file_gdb_ogr` | `file_gdb_gbx` |
| `netcdf_ogr` | `netcdf_gbx` with `mode="vector"` |
| `geojsonl_ogr` (write) | `geojsonl_gbx` |
| `pmtiles` (write) | `pmtiles_gbx` |

- **The JAR registers no data source.** A read with a retired format name gives "data source not found". `gbx.register(spark)` registers the `*_gbx` readers.
- **The Scala writers are retired.** A write with the `gdal` or `gtiff_gdal` format fails with a `Fix:`. Write with `raster_gbx`, `gtiff_gbx` or `cog_gbx` after `register(spark)`. See [Raster Writer](./writers/raster).
- **A Python data source cannot be queried by path in SQL.** Create a view instead: `CREATE VIEW v USING raster_gbx OPTIONS (path '...')`.
- **`netcdf_gbx` vector mode reads CF discrete sampling geometries (new).** A profile file gave no rows, and a trajectory file lost its `time` column. Now each observation is a point.
  - A profile's altitude is the point's Z. Its id and time repeat on each observation. Indexed and contiguous ragged arrays are supported.
  - A trajectory or profile file whose latitude and longitude sit on the observation dimension keeps its instance variables (id, time, platform) on each observation.
  - The file's `time` is a `TIMESTAMP`, its CRS is EPSG:4326, and its coordinate variables on the observation dimension are columns.
  - A depth (`positive = "down"` or `standard_name = "depth"`) is the point's Z with its stored sign.
  - A ragged file whose index is missing, negative or past the profiles, or whose counts do not add up, is refused with a `Fix:`. Before, it read the wrong values.
- **Raster readers with `virtualTiles=false` read several whole files per task.** Without `tileSize`, `windows`, `clipPolygons` or `sizeInMB`, a task returns batches of at most 64 MiB. Set `sizeInMB` or retile a file over the compute's read cap (64 MiB on Serverless, 256 MiB classic). That read now fails with a retile `Fix:`. Before, it read up to 1.8 GiB.
- **The read cap is enforced on Serverless even where the read is planned without a session.**
- **`read_paths(..., on_error="skip")` and `"quarantine"` keep the other files of a batched read.** A file that cannot be read is recorded under its own path. With `"fail"` the read still fails and names that file. A missing-file error on a Volume while a header is read is retried.


### Materialized reads keep sidecar files (fix) {#materialized-sidecars}

- **A materialized read keeps the CRS and NoData that sidecar files hold.** A tile holds the bytes of one file. `raster_gbx` with `virtualTiles=false`, `gbx_rst_fromfile` and `rst_fromfile(materialize=True)` dropped the other files.
  - A GeoTIFF lost the NoData or CRS from its `.aux.xml` file.
  - An EHdr, ENVI or SAGA raster (`.hdr`, `.prj`, `.sgrd`) failed with `not recognized as being in a supported file format`, or returned `NULL`.
- **The staged copy now carries the sidecars.** A GeoTIFF whose sidecar changes its CRS, NoData, geotransform, scale or offset is written from the open dataset. Any other GeoTIFF still passes through as its own bytes.
- **A sidecar is looked up by name,** with no folder listing. A file that the reader found to have no sidecar skips the look-up.

### Reader staging cache (fix) {#staging-cache}

- **Lightweight readers bound their staged copies (fix).** They copy GeoPackage, FileGDB and (for windowed decodes) raster sources to worker-local disk. The copies used to fill it.
  - GeoBrix now removes the least recently used idle copies. The cap is half the available local disk, or `GBX_STAGE_CACHE_MB`.
  - GeoBrix also removes copies left by exited workers.
  - See [Serverless and Memory](./serverless-and-memory).
- **The readers re-read a file replaced at the same path (fix).** They reuse a copy only while the source's size and modification time are unchanged.

### PMTiles reader (behavior change, fix) {#pmtiles-reader}

- **`pmtiles_gbx` no longer reads the whole archive once per partition.**
  - With `source="archive"`, planning reads only the header and directories. Each worker stages the archive once.
  - With `source="raster"`, each source raster is staged once per worker.
  - See [PMTiles Reader](./readers/pmtiles).
- **A damaged PMTiles header cannot crash a worker.** An archive whose header declares a length beyond the end of the file fails with an error.
- **`pmtiles_gbx`, `pmtiles_info` and the `gbx.vizx` PMTiles viewers read archives with uncompressed directories (fix).** Archives written with uncompressed directories failed with `Not a gzipped file`. These readers now decode directories by the compression the header declares. They read none and gzip.
  - `pmtiles_gbx` fails on any other compression with an error that names it.
  - `pmtiles_info` fails with `internal compression ... is not supported` on unknown, brotli or zstd. This includes an archive that declares unknown but stores gzip.
  - The viewers treat such an archive as unreadable.
  - `pmtiles_info` no longer imports PySpark or rasterio.

### NetCDF reader (fix) {#netcdf-reader}

- **`dimIndex` and `bandDim` are honored in `spark.read` (fix).** The reader ignored them and read the first slice of each extra dimension (also in v0.5.1 and v0.5.2). `fanout` was not affected.
- **`group` is honored when a variable is read without decoding (fix).** xarray cannot always apply a variable's CF masks, for example for integer data with an integer `scale_factor`. In that case `netcdf_gbx` read raw values from the root group, not your `group`.
  - A variable of the same name in the root returned wrong data without an error (also in v0.5.2).
  - A variable only in the group failed with `No variable named …`.
- **`netcdf_gbx` vector mode reads times, dates and flags as such.** These came back as a `STRING` of epoch nanoseconds and a float. Now:
  - A CF time variable is a `TIMESTAMP` (UTC).
  - An integer count of whole days is a `DATE`. This needs `days since …` from a midnight base, with no `scale_factor` or `add_offset`.
  - A variable that flags `0` and `1` as `false true` is a `BOOLEAN`.
  - A `NULL` stays `NULL`.
  - A fractional, scaled or clock-time day count stays a `TIMESTAMP`.
- **A fill-value cell keeps its fill value in the tile (fix).** xarray decodes the fill value to `NaN`, but the tile's NoData stayed the fill value, so no cell matched it. The cells now hold the fill value, as GDAL reads the file.

### Raster readers: read a tile index with `read_tiles_table` (fix, new) {#read-tiles-table}

- **`read_tiles_table(spark, table, options)` reads a `tilesTable`.** `spark.read.format("raster_gbx").option("tilesTable", ...)` failed, because Spark plans the read in a worker with no Spark session. That read now fails with an error that names `read_tiles_table`.
  - `read_tiles_table` returns the same `(source, tile)` DataFrame as the reader.
  - It takes the reader options (in any case), `format="gtiff_gbx"` or `"cog_gbx"`, and `num_partitions` (default: two tasks per index row, up to 256).
  - See [Raster Reader](./readers/raster#read-tiles-table).
- **A Parquet `manifest` reads through `spark.read` (fix),** from a Parquet file or from the directory Spark writes.
- **`versionAsOf` and `timestampAsOf` read a tile index as it was (new).** Pass either option to `read_tiles_table` to plan from that Delta version. A pipeline can then re-run against the exact version it used.
  - The table must be a Delta table. A version or time outside its history fails the read.
  - Setting both options raises an error. Setting either for a manifest or a directory read raises an error.
  - See [Raster Reader](./readers/raster#tiles-table-time-travel).

### Raster windows: edge pixels of unaligned rasters (fix) {#raster-windows}

- **A window cut around an area keeps the pixels at both edges.** The window used to start up to a pixel late and end up to two pixels early. That lost 2 to 3 percent of the pixels on a raster whose pixels do not line up with the area (typically in another CRS).
  - This applies to the `clipPolygons` option of the raster readers and to the bounding-box download of STAC assets.
  - An aligned raster is cut as before.

### GDAL driver listing: `gbx_drivers` (new) {#gbx-drivers}

- **`gbx_drivers()` lists the GDAL drivers that the current environment can run.** In Python, call `drivers()` from `databricks.labs.gbx.drivers.functions`. Pass `'raster'` or `'vector'` to keep one kind.
  - Each row says whether the driver is raster or vector, reads, writes and is allowed by GeoBrix.
  - It also says whether a raster can be held as tile bytes, whether the driver works as shipped, and what it `requires`.
  - It runs on Serverless and standard clusters. It needs the env wheel's GDAL bindings, and raises an error that names the env wheel without them.
- **The rows reflect the environment as it runs now.** Adding or removing packages changes them. The `shipped` column marks the drivers of the env wheel's own build, which [GDAL drivers as provided](./gdal-drivers) lists.
- **`tested` and `tested_with` follow the kind you ask for.** `gbx_drivers('raster')` reports a driver tested only as a vector driver, such as `OpenFileGDB`, as not tested. The `guidance` notes start with one of a few fixed phrases.
- **`tile_bytes` is false for BAG, GTX, SRTMHGT and raster MBTiles (fix).** Their bytes do not load as a tile, because GDAL identifies them by file name or extension. Read them by path with `raster_gbx` or `gbx_rst_fromfile`. The bytes of a BAG file are refused with a Fix.
- **CAD (DWG) is tested for reading.** `vector_gbx` with `driverName` set to `CAD` reads AutoCAD R2000 drawings. GeoBrix does not write DWG.
- See the [General Function Reference](./api/general-functions#drivers).

## Vector {#vector}

### Lightweight vector readers: large layers and coded-value domains {#vector-large-layers}

- **Lightweight vector readers stream large layers (fix).** `vector_gbx`, `file_gdb_gbx`, `gpkg_gbx`, `shapefile_gbx`, `geojson_gbx` and `geojsonl_gbx` read a layer in batches of `chunkSize` features. They split any batch that nears Arrow's 2 GiB per-column limit.
  - Layers with more than 2 GiB of geometry now read. They failed with `ArrowInvalid: offset overflow while concatenating arrays`.
  - Memory per task scales with `chunkSize`.
  - One value too large for any Spark row fails with an error that names the layer, column and feature.
  - `vector_file_read` streams its sources the same way.
  - See [Vector Readers](./readers/vector#options).
- **Coded-value domain fields read correctly (fix).** FileGDB and GeoPackage fields bound to a coded-value domain failed with `Cannot call the method "getInt"`. They now return the stored code in the field's declared type.
  - The new lightweight-only `codedDomains` option returns the domain descriptions as strings. Its values are `"code"` (default) and `"description"`.
  - See [FileGDB Reader](./readers/filegdb#options) and [GeoPackage Reader](./readers/geopackage#options).

### Vector readers: `driverName` is honored (behavior change) {#driver-name}

- **A requested driver is no longer silently ignored.** `vector_gbx` with a `driverName`, and the named readers (`geojson_gbx`, `gpkg_gbx`, `shapefile_gbx`, `file_gdb_gbx`), used to let GDAL pick any driver. `driverName` is now case-insensitive.
  - GDAL's equivalent drivers are accepted: the GeoJSON family (GeoJSON, GeoJSONSeq, ESRIJSON, TopoJSON, JSON-FG), KML and LIBKML, OpenFileGDB and FileGDB, and GPKG and SQLite.
- **Forced and refused drivers.**
  - GDAL can force the driver for the GeoJSON family, GPKG and CSV, also when GDAL recognizes nothing. The file is read with the requested driver.
  - Any other family with a misnamed file fails with an error. The error names the file, the detected driver and the reader to use.
  - A `driverName` GDAL does not know fails with the closest matches.
  - With your own `.schema(...)`, a file with an extension GDAL reads by itself is not checked. pyogrio does not expose the driver when it reads.
  - See [Vector Readers](./readers/vector#options).

### Vector writers (new, behavior change, fix) {#vector-writers}

- **`file_gdb_gbx` writes File Geodatabases with the lightweight tier alone (behavior change).** It no longer needs native GDAL (`osgeo`), or classic x86 clusters. It encodes the `.gdb` through pyogrio's bundled OpenFileGDB driver. It runs on Serverless, standard and dedicated clusters, on x86 and ARM. The output layout, `zip=true`, the shared schema and the other options are unchanged.
- **Column types follow the DataFrame types.**
  - An `int` column stays a 32-bit integer, and a `smallint` a 16-bit integer. Both were doubles.
  - A column named `shape` (any case) is refused with an error, because the layer's geometry field is `SHAPE`.
  - An empty `geometryType` counts as not given and takes the type of the first geometry.
  - `unknown` in any case is refused with the same message as `'Unknown'`.
- **New option `targetArcGisVersion`** (`auto`, `ALL` or `ARCGIS_PRO_3_2_OR_LATER`) decides which Esri clients can open the layer.
  - With `auto` (default), a DataFrame with a long (64-bit integer), date or timestamp column targets ArcGIS Pro 3.2 or later. Those columns keep their exact types. Before, they were rounded to a double or written as a date-time with no offset. An older Esri client may refuse to open the layer.
  - A DataFrame without such a column is written for every client. `ALL` forces that.
  - GeoBrix's readers and any reader built on GDAL 3.11 or later open a Pro 3.2 layer.
  - See [GeoDatabase Writer](./writers/filegdb).
- **Timestamp columns work in the lightweight vector readers and writers on Serverless (fix).** They failed with `AssertionError`. Timestamps are read and written as UTC. A written timestamp is exact on a worker whose time zone is not UTC.
- **`netcdf_gbx` writes timestamp, date, string and boolean attributes (fix).** A vector write with such a column failed. Now:
  - A timestamp is a CF time variable: seconds since 1970-01-01 00:00:00 UTC, with `units` and `calendar` attributes. A timestamp without a time zone is read as UTC.
  - A date is a CF time variable in days.
  - A string is a text variable (a null is an empty string).
  - A boolean is an int8 0 or 1 with `flag_values` and `flag_meanings`.
  - A null timestamp, date or boolean is the fill value.
  - `merge` keeps the attributes.
  - See [NetCDF Writer](./writers/netcdf).

- **`vector_gbx` writes KML, GML and DXF from a DataFrame with any number of partitions (fix).** The writer appended each partition to the file. GDAL cannot reopen those formats to append, so a second partition failed. They now write in one pass, as GeoJSON does.
- **`vector_gbx` writes CSV with a WKT column (fix).** The CSV driver needs the layer option `GEOMETRY=AS_WKT`, and the writer set none. For CSV input, use Databricks' own reader.
- **A GPX column named like a GPX field is refused with a Fix (fix).** GPX makes `name`, `ele`, `time` and `desc` itself. The error says to rename or drop the column.
- **`vector_gbx`, `gpkg_gbx`, `geojson_gbx` and `shapefile_gbx` write a DataFrame of mixed geometry types as a layer of any geometry (fix).** The layer took the type of the first geometry. GML then read a polygon back as a line string when a line string came first, and FlatGeobuf refused the write. A layer of one geometry type keeps that type. A FileGDB layer still takes the type of the first geometry, and GDAL refuses the others. Polygons mixed with multipolygons are a layer of any geometry too; each geometry is written as it is, not promoted to a multi type.
- **The vector writers declare a layer 3D when its geometries carry Z (fix).** A 2D layer type made a Shapefile drop the heights and FlatGeobuf refuse the write. A GeoPackage layer that mixes 2D and 3D geometries is declared 3D and keeps each geometry as it is. A Shapefile, FlatGeobuf or FileGDB layer holds one dimension. The writer refuses a mix of 2D and 3D there with a `Fix:`: write one dimension, or set `geometryType` (for example `'Polygon Z'`). A layer of any geometry is not declared 3D.

### Vector function arguments (behavior change) {#vector-arguments}

- **A negative or non-finite tolerance raises and names the value.** This covers `st_simplifypreservetopology`, `st_removerepeatedpoints` and `st_snap`, and the grid size of `st_reduceprecision`. They returned garbage or a bare GEOS error. NULL still gives NULL. A NULL `st_removerepeatedpoints` tolerance is the default 0.
- **Geometry text that mixes 2D and 3D keeps the Z values it has, on both levels.** `LINESTRING Z (15 51 5, 16 52)` has a Z on one vertex only. The Z that exists is kept and the missing one is `NaN`, never `0`. Before, the JVM `gbx_st_transformcrs` gave NULL. The lightweight `st_transformcrs` dropped every Z of such a geometry, and so of any geometry with a Z on some vertices only. Now `st_transformcrs` reprojects X and Y of every vertex and keeps the Z of each vertex that has one. A `st_setcrs` then `st_transformcrs` chain no longer loses its elevations. The other `gbx_st_*` functions that take geometry text read it the same way.
- **Geometry text whose dimension tag contradicts its coordinates is refused, not read as 3D.** `POINT Z (1 2)` has a Z tag and two ordinates. Both levels now raise the parse error instead of reading a `NaN` Z. Only text that mixes 2D and 3D coordinates is repaired.
- **`st_transformcrs` takes X, Y and Z of a vertex that has a Z from the 3D transform.** A target that moves the height, such as a geocentric CRS, changes X and Y with Z. A vertex of a partial-Z geometry now gets the result the same vertex gets alone. Both levels agree.
- **The lightweight H3 geometry functions refuse a geometry whose SRID is not 4326.** EWKT with `SRID=27700` was read as longitude and latitude. The error names the SRID and says to reproject with `st_transformcrs`. SRID 0 still reads as 4326.
- **`gbx_st_legacyaswkb` returns a 2D geometry for 2D input.** The JVM function had a NaN Z.
- **`st_transformcrs` runs on the JVM level first when the JAR is present.** `st_crs` and `st_setcrs` run on the lightweight level.
- **A CRS argument is judged by its kind.** A PROJJSON, with its `"$schema"` URL, and a WKT2 with an ID URI bind to their EPSG code on both levels. A URL, a file name and any grid or init file named by path stay refused. Before, a PROJJSON target was refused.
- **Contour and isoband run on the lightweight level.**
- **`gbx_rst_isoband` raises for breaks that do not rise,** and for a NULL element in `breaks`. `gbx_rst_contour` and `gbx_rst_isoband` give NULL for an unreadable tile.

### TIN functions: snapping, and the conforming mode on every level (breaking, new, fix) {#tin}

These changes cover `st_triangulate`, `st_interpolateelevationbbox` and `st_interpolateelevationgeom`.

- **`snap_tolerance` places points onto break lines before triangulating (breaking).** Output vertices and triangles can differ from 0.5.x when it is above 0.
  - A point within `snap_tolerance` of a break line moves onto the nearest one, takes its Z there and becomes a vertex of the line. On a tie, the first line wins.
  - A point that lands within `merge_tolerance` of a line vertex merges into it.
  - Before, the JVM level moved vertices onto a line after triangulating, which could leave zero-area triangles. It also missed points beside a horizontal or vertical line.
  - Before, the Python level changed only the Z of a vertex and kept its X and Y.
- **The `conforming` mode runs on every level (new).** It runs on Serverless, on standard access mode and in Unity Catalog functions. The Python level gives the same vertices and triangles as the JVM level.
- **`split_point_finder` takes effect on the JVM level (fix).** The JVM level ignored it, so every conforming call placed its points as `'NONENCROACHING'` does. `'MIDPOINT'` now splits segments in half.
- **An extra point of the `conforming` mode takes the Z of its break line (fix).** Before, a midpoint had no Z, and a projected point took the Z of the point that caused it.
- **A coordinate without Z has Z 0 in both modes (fix).** In the `conforming` mode, the JVM level gave a 2D break line a NaN Z. A 2D mass point had a NaN Z on the JVM level in both modes.
- **The `conforming` mode raises with a `Fix:` where it cannot fit the break lines (behavior change).** Crossing break lines are the usual cause. The JVM level raised JTS's own exception.
- **Any `split_point_finder` other than `'NONENCROACHING'` or `'MIDPOINT'` raises on the Python level too (behavior change).** The JVM level already raised, in both modes.
- **The `mode` word is taken in any case on every level (fix).** The JVM level raised for `'CONFORMING'`, which the Python level ran.
- **A multi-line break line adds each of its lines, and a polygon adds its rings (behavior change).** Any other geometry in `breaklines_array` is ignored. Before, the Python level raised for a multi-line string, and a point added a site. The JVM `st_interpolateelevationbbox` raised for anything but a line string.
- **`merge_tolerance` merges each point into the nearest one kept before it (breaking).** Output can differ from 0.5.x when `merge_tolerance` is above 0.
  - The break line vertices come first, so a mass point near a vertex merges into it. The vertex keeps its Z.
  - The merge runs once, whether or not `snap_tolerance` is above 0, the same way in both modes.
  - Before, the `constrained` mode merged the points in one grid cell of `merge_tolerance`. Points closer than it could stay apart, and a snapped point could be lost.
- **The `constrained` mode makes every break line segment a triangle edge (fix).** Before, it often left a segment that crossed more than one edge without that edge, and gave no error. A point exactly on a break line now splits it there.
- **The `constrained` mode raises with a `Fix:` where break lines cross (behavior change).** Before, one of the crossing segments was not an edge, and it gave no error.
- **The `constrained` mode gives the same triangles on every level (fix).** Where four or more points lie on one circle, as in a grid, the Python level and Unity Catalog now pick the JVM level's triangles. Before, they could pick other, equally valid triangles.
- **The `constrained` mode raises with a `Fix:` where JTS cannot locate a point (behavior change).** Sites very close together are the cause. The JVM level raised JTS's own exception.
- **The TIN functions run up to 80x faster on the Python level (performance).** The env wheel triangulates with a Rust port of JTS, with the JVM level's triangles. A 250,000-point grid takes about 2 seconds, down from about 150. [Performance](./api/performance#the-rust-kernel-for-tin-triangulation) has the numbers.
- **The elevation functions sample Z in batches (performance).** Before, the Python level tested each grid cell against every triangle. 400 cells on a 40,000-point surface took 28 seconds, and now take under 1 second.
- **The `conforming` mode names a point it cannot locate, as the JVM level does (fix).** With crossing break lines, the Python level could report the 99-pass limit instead.
- **Each triangle ring starts at its lowest vertex, on every level (behavior change).** A ring runs counter-clockwise from the vertex with the least X, then the least Y. Every level now writes the same WKB bytes for a triangle.
- **A NULL `mode` gives no rows on every level (fix).** Before, the Python level and Unity Catalog ran the `constrained` mode, and the JVM level raised.
- **`merge_tolerance` 0 merges only points with the same X and Y (fix).** Before, points under 1e-12 apart merged too. A coordinate above about 9.2 million then overflowed the merge key, so distant points could merge.
- **The JAR no longer holds `ST_InterpolateElevationGeom`.** `gbx_st_interpolateelevationgeom` ran its Python level by default and still does. Its Scala Column wrapper is gone. From Scala, call it with `call_function("gbx_st_interpolateelevationgeom", ...)`.

## Writers {#writers}

### Raster writers (fix) {#raster-writers}

- **The lightweight COG writers write `raw` and `none` uncompressed.** This covers `raster_gbx` with `cog=true`, `cog_gbx` and `rst_cog_convert`. `rst_cog_convert` now takes `'NONE'` as well as `'RAW'`. They used to get LZW from the COG driver. A COG written from a tile whose `compression` metadata says `raw` or `none` kept the source's codec.
- **`cog_gbx` writes sources with a non-byte-aligned bit depth.** A band tagged with an `NBITS` such as 15 (common for Sentinel-2 `uint16` products) failed with `PREDICTOR=2 is only supported with 8/16/32/64 bit samples`. The writer promotes such samples to the full width of the data type. This is lossless.
- **`cog_gbx` names the parts of one source apart.** With no `nameCol`:
  - A tile that is only part of its source is written as `<source name>_<key>.tif`. This covers a window or clip, and one band from `rst_separatebands`.
  - A tile with no path or source is written as `<cellid>_<key>.tif`. It was `<cellid>.tif`.
  - A tile read whole from a file keeps the plain source name.
  - The key derives from the tile, so a re-run writes the same names.

  `rst_retile`, `rst_tooverlappingtiles` and `rst_maketiles` record each tile's pixel window in `tile.window`. `rst_separatebands` records the 1-based band in `tile.metadata['band']`. Set `nameCol` when you write one source both as a materialized split and as a whole file into one directory.

## Raster functions {#raster-functions}

### `rst_asformat` and `rst_cog_convert` (fix) {#asformat-cog}

- **The lightweight `rst_asformat(tile, 'COG')` writes a Cloud Optimized GeoTIFF.** It failed with `driver 'COG' is not available in this GDAL build`. The tile has the COG layout, as `rst_cog_convert` writes it:
  - `LAYOUT=COG` and 512-pixel blocks.
  - Size-adaptive ZSTD.
  - Overviews when the tile is larger than 512 pixels.

- **The lightweight `rst_asformat` takes a driver name in any case,** and the Surfer grid formats (`GS7BG`, `GSAG`, `GSBG`) are available.
- **The tile of `rst_asformat(tile, 'COG')` records `metadata['driver'] = 'GTiff'`** (it was `'COG'`). That is the driver its bytes open as, and the one `rst_cog_convert` records. A writer passes those bytes through and keeps the layout and codec you asked for.
- **`rst_asformat(tile, 'JP2OpenJPEG')` keeps the CRS (fix).** The in-memory writer dropped it. A driver that cannot encode a tile through that writer now raises one `ValueError` that names the driver and gives a Fix. It used to raise a raw `SystemError` or `TypeError`.
- **Other fixes.**
  - `rst_cog_convert`, `rst_asformat(..., 'COG')` and the lightweight functions that rewrite a striped GeoTIFF no longer log a GDAL warning per tile. Those functions are `rst_asformat`, `rst_merge` and the STAC windowed download.
  - The STAC windowed download and the vizx tile-simplify raster path read a JPEG/YCbCr source. They failed on `PHOTOMETRIC=YCBCR`.
  - The lightweight `rst_cog_convert` keeps the red, green and blue labels of RGB tiles.

### Heavyweight tile size (fix) {#l1-parity}

- **Heavyweight rasterize tiles are compressed.** They were raw bytes. They now use the heavyweight default (DEFLATE with the dtype's predictor). Pixels are unchanged.

### `rst_sample` on virtual tiles (fix) {#rst-sample}

- **The lightweight `rst_sample` on a virtual tile reads only the block that holds its point.** The points of one file in a task share one open. Each call used to open the file twice and decode and re-encode the tile's whole window. That took about a second of task time per point on a Volume.
  - The values are unchanged.
  - Clipped or reprojected virtual tiles, Zarr-backed and materialized tiles, and files with their own mask band are read as before.
  - Releases v0.5.0 to v0.5.2 are affected.

### Lightweight raster opens: no folder listing (behavior change) {#raster-opens}

- **The lightweight tier lists each folder once per worker, not at every open.** GDAL lists a raster's folder at every open to look for sidecar files. That took 0.3 s to 10 s per open on a Volume on Serverless. GeoBrix now lists a folder once per Python worker, when the worker opens a second, different file of it. It tells GDAL where to look.
  - A GeoTIFF, PNG, JPEG, JPEG 2000, netCDF, HDF or GRIB file with no sidecar opens with no sidecar look-up. It no longer pays the per-open folder listing.
  - A file with sidecars (external overviews, masks, `.aux.xml`, world files) still finds them. So do the files a VRT or another multi-file dataset opens.
  - Sidecars are checked by name before a folder is listed, and in a folder of more than 100,000 files.
  - A folder of up to 100,000 files is listed once per worker. A file with no sidecar in a folder of 10,000 files then opens with no sidecar look-up.
  - Tiles read from a folder of more than 100,000 files with `raster_gbx` carry the reader's file count in `path_folder_files` and skip the listing.
  - A sidecar added after a worker listed the folder is not seen until the worker lists it again or restarts. A missing file triggers a new listing, at most every 10 seconds.

  See [Sidecar files and folder listings](./api/performance#sidecar-files-and-folder-listings).
- **Importing `databricks.labs.gbx.pyrx` (or anything that imports `databricks.labs.gbx.core.crs`) sets `GDAL_DISABLE_READDIR_ON_OPEN=TRUE` for the whole Python process,** unless it is set already. Your own rasterio, GDAL or Fiona code in that process then checks sidecars by name. So do programs it starts (`gdalinfo`, `tippecanoe`). A sidecar whose name mixes case (`x.Tfw`) is found only with `NO`.
  - Set `GDAL_DISABLE_READDIR_ON_OPEN=NO` to keep GDAL's listing. Set `YES` for checks by name without GeoBrix's per-file choice.
  - Set it in the environment of the Python workers (a cluster or job environment variable) before GeoBrix is imported there. A notebook's `os.environ` does not reach the workers.
  - A value you set before the import, or in a `rasterio.Env` around your reads, is used for every open.
  - When the outermost `rasterio.Env` that names the option exits, rasterio keeps the value it found on entry as a GDAL option for the process. A later change of the environment variable then has no effect.
- **A local copy of a Volume file is removed from disk as soon as it is opened (fix).** The copy that `rst_sample` keeps open for a task leaves the disk at once, even when the Python worker ends without cleanup.

### Lightweight tile functions move rows in Arrow batches (fix) {#arrow-tile-rows}

- **On every DBR 19 and Serverless compute the lightweight tile functions move their rows to Python in Arrow batches.** Before, Spark pickled up to 100 tiles into one buffer on the executor heap. With large tiles, 16 times the rows spent up to half of each task in garbage collection, and executors were lost.
  - This covers the tile operations, accessors, statistics, constructors, the array and pair functions, and the rasterizers. It also covers `rst_apply`, the GDAL spec engine's row form and the vector array functions.
  - It also covers the table functions over tiles: `rst_retile`, `rst_tooverlappingtiles`, `rst_separatebands`, `rst_maketiles`, `rst_xyzpyramid`, the `rst_*_tessellate` functions and the `rst_*_rastertogrid*` reducers. `st_triangulate`, `st_interpolateelevation*` and `st_asmvt_pyramid` are covered too.
  - Dedicated and standard DBR 19 clusters need no Spark config for this. Integer arguments, BIGINT cell ids and NULLs arrive exactly.
  - GeoBrix turns a batch into Python values a slice of rows at a time. A large batch never holds a second copy of all its tiles.
  - DBR 17.3 and 18 (Spark 4.0) keep the pickled rows. Spark 4.0 can round a large BIGINT cell id in an Arrow batch.
  - The `gbx_rst_combine*` array functions use Arrow batches on DBR 17.3 and 18 too.
  - Set the `GBX_CAP_ARROW_TILE_TRANSPORT=0` environment variable on the cluster to keep the pickled rows of the row functions anywhere. `GBX_CAP_ARROW_TILE_UDTF_TRANSPORT=0` does the same for the table functions.
  - A tile table written in large Parquet row groups still costs memory per batch. See [Tile tables with large row groups](./serverless-and-memory#tile-table-row-groups).
- **A NULL coordinate gives NULL (fix).** `rst_worldtorastercoord` and `rst_rastertoworldcoord` raised a `TypeError` for a NULL `x` or `y`. They now return NULL, as their `x` and `y` forms do.

### Raster tiling functions (behavior change, fix) {#raster-tiling}

- **Call a generator with `FROM t, LATERAL f(...)`.** This works on every compute for `rst_retile`, `rst_tooverlappingtiles`, `rst_separatebands`, `rst_maketiles`, `rst_custom_tessellate`, `rst_xyzpyramid`, the `rst_*_tessellate` functions and the `rst_*_rastertogrid*` reducers.
  - These functions have no JVM form, so they have no select-list or `LATERAL VIEW` form.
  - The `rst_*_rastertogrid*` reducers no longer return an `ARRAY`. See [Generators and aggregates change shape](#shape-changes).
- **Bad arguments raise their own message.**
  - An unknown `format`, `resampling` or `rescale` raises.
  - A `size` outside (0, 4096], a `max_z` above the cap, or a tile count above the limit raises.
  - Heavyweight `rst_tilexyz` now raises for them too, as `rst_xyzpyramid` and the lightweight tier do. It returned a transparent PNG.
  - A tile that cannot be read or rendered still returns a transparent PNG, never NULL.
- **A tile that cannot be read gives one error row (fix).** This holds for `rst_retile`, `rst_separatebands`, `rst_tooverlappingtiles`, `rst_maketiles` and the four `rst_*_tessellate` functions. The row's `tile` holds the error tile (NULL raster, error in `metadata.last_error`), as [Error handling](./api/error-handling#generators) describes. The lightweight forms used to fail with `UDTF_RETURN_SCHEMA_MISMATCH`.
  - `rst_maketiles` with a size of 0 or less returns the tile unchanged as one readable row.

### `rst_gdal` runs an allowlisted GDAL `raster` command (new) {#rst-gdal}

- **`gbx_rst_gdal(tile, command)` runs one GDAL `raster` step or a pipeline on a tile.** `command` is what follows `gdal raster`, such as `'slope --unit=percent'` or `'reproject --output-crs=EPSG:3857 ! slope ! hillshade --zfactor=2'`.
  - It is available in session SQL and Python on every compute. It has no Unity Catalog form and no JVM form.
  - GeoBrix adds the read and write steps. The result is a GeoTIFF tile.
- **Only listed steps and arguments run.** The steps are `aspect`, `clip`, `fill-nodata`, `hillshade`, `neighbors`, `nodata-to-alpha`, `proximity`, `reclassify`, `reproject`, `resize`, `roughness`, `scale`, `select`, `set-type`, `sieve`, `slope`, `tpi`, `tri`, `unscale` and `viewshed`.
  - Any other step, a short flag, an unlisted argument or a `--config` option raises. So does an input or output override.
  - A value is never a file, a URL, an `@file` or a `/vsi` name. A CRS value goes through the CRS resolver, and `clip --geometry` takes a WKT polygon.
  - GDAL's `calc` step does not run inside a pipeline. Use `gbx_rst_mapalgebra`.
- **The tile in a file is read by its path.** A virtual tile that is a whole file is read block by block.
  - A pipeline that GDAL cannot run on a tile gives an error tile with GDAL's reason.
  - A source with no declared NoData keeps its footprint as a mask after `reproject`. The decoded size of each step is checked against the compute's cap.

### Raster viewshed: GDAL's `raster viewshed` (behavior change) {#viewshed}

- **`rst_viewshed` runs GDAL's `raster viewshed` in the worker,** in the edge line-of-sight mode with a curvature coefficient of 0.85714. Small DEMs used xarray-spatial, and large DEMs another line-of-sight mode.
  - A mask changes by a fraction of a percent on smooth terrain to a few percent on rough terrain.
  - xarray-spatial and `numba` are no longer needed.
  - There is no first-call compile delay.
- **One rule places the observer.** A POINT in WKB, EWKB, WKT or EWKT is moved into the DEM's CRS. Its own CRS is its SRID, else the `crs` argument, else the DEM's CRS. A bad `crs` raises.
  - `observer_height` is optional and defaults to 0. A NULL height is 0.
  - A NULL `target_height` gives NULL. It used the default of 1.6.
  - A POINT EMPTY, and text that is no geometry, raise.
- **An observer outside the DEM gets GDAL's own result.** It got an all-invisible raster.
  - GDAL assumes nothing blocks the view between the observer and the DEM, and takes the observer's height from elevation 0.
  - A `max_distance` that leaves no part of the DEM gives an error tile with GDAL's message.
  - An observer within half a pixel of the DEM's edge gets a viewshed, as before.
- **A virtual tile that is a whole file is read by GDAL from the file,** block by block, as the earlier code read it. A tile with bytes, or a window of a file, is read whole under the compute's read cap. Over the cap it gives an error tile that says to retile it first.
  - A block GDAL cannot read gives an error tile that names the file. It is never a mask built on zeros.
- **`rst_viewshed` with a `max_distance` returns the window around the observer (fix).** In v0.5.2 the lightweight tier was wrong on a DEM above its small-DEM size limit (about 366 × 366 pixels by default). The visible area came out several times too large and in the wrong place. The `rst_viewshed_towers` counts (`visible_px`, `total_px`) were inflated.
  - The result is the window: the observer's pixel plus `max_distance` each way, clipped to the DEM. It is aligned to the DEM's pixel grid.
  - Without a `max_distance` it returns the whole DEM.
  - Pixels beyond the distance but inside the window are 0, as before.
- **Smaller changes.**
  - `rst_viewshed_towers` gives no row for a tower in a grid cell with no DSM tile.

### Raster tessellation and tiling: large rasters (behavior change) {#tessellation-parity}

- **Centroid tiles are cropped to their cell.** With `assignment='centroid'` (default), `rst_h3_tessellate`, `rst_quadbin_tessellate`, `rst_bng_tessellate` and `rst_custom_tessellate` crop each tile to the window of the pixels assigned to its cell. Pixel values and positions are unchanged.
  - A tile's width, height and geotransform are now its own, not the source's.
  - Code that assumes every tile has the source extent must change. An example is stacking tiles as same-shape arrays.
  - Tiles are about 5 times smaller on an 11k × 11k pixel scene.
- **Empty cells.** With `coverage='complete'`, a covered cell that received no pixel is a 1×1 all-NoData tile at the cell's centroid pixel. In v0.5.2 it was a source-sized tile.
- **Scene-sized tiles no longer time out.** Tiles are built from their own window. Pixels are assigned to cells a strip of about one million pixels at a time. Memory grows with the pixel count, at about 23 bytes per pixel.
  - For very large scenes, run `gbx_rst_retile` first to spread the work across tasks.
  - A cell on a seam between tiles then appears once per tile it overlaps.
  - See [Grid Raster Tessellation](./api/grid-raster-tessellation#large-rasters).
- **Covered cells follow the raster footprint.** `coverage='complete'` and `assignment='covering'` keep a cell when it overlaps the raster footprint.
  - The footprint is the raster's edges, reprojected to the grid's CRS with points along each edge. It follows the curved edges of a projected scene, for example UTM.
  - `rst_h3_tessellate` and `rst_quadbin_tessellate` raise an error when the footprint crosses the antimeridian or encloses a pole. Reproject the raster first (for example to EPSG:4326), or split it.
- **Tiling keeps all-NoData windows.** The v0.5.2 heavyweight forms dropped them, so a retile-then-merge round trip could lose part of a scene's edge. These functions now emit every window:
  - `rst_retile`, `rst_tooverlappingtiles` and `rst_maketiles` (with `size_in_mb > 0`).

  To drop the all-NoData windows, filter with `WHERE NOT gbx_rst_isempty(tile)` or write with `pruneEmpty`.
- **Retile tiles carry the parent's `cellid`** (0 when the parent has none). This covers `rst_retile`, `rst_tooverlappingtiles`, `rst_maketiles` and `rst_separatebands`. They used to be numbered 0, 1, 2, ….
- **Quadbin cells are decided exactly.** A latitude within 1e-6 of a whole web-mercator row is decided exactly. In `rst_quadbin_rastertogrid*`:
  - A pixel centre at longitude 180 lands in the easternmost tile instead of tile 0.
  - A pixel on a tile edge falls in the same cell as in `rst_quadbin_tessellate`.

### NoData, alpha and mask bands (behavior change) {#nodata-alpha-mask}

GeoBrix applies one rule for which pixels are valid.

- **One NoData fallback for sources without NoData.** Source pixels equal to the fallback become NoData. The fallback by type:
  - `uint8`: 0.
  - `uint16`: 65535.
  - `int16`: −32768.
  - `uint32`: 4294967294.
  - `int32`: −2147483648.
  - `float32` and `float64`: the type's minimum.

  Further changes:
  - In v0.5.2, centroid tessellation used 0 for every integer type. Real zero pixels of `uint16`, `int16`, `uint32` and `int32` sources now stay valid. Float tiles carry the type's minimum, not NaN.
  - `covering` tiles carry this NoData, so pixels outside each cell read as NoData.
  - The lightweight `rst_initnodata` and `rst_threshold` use the same table.
  - The lightweight `rst_filter` min, max and median of a `uint8` source blank a window with no valid pixel with 0.
  - In the [EO series](./notebooks/eo-series) notebooks 03 and 04, `uint16` bands that pass through `rst_initnodata` carry NoData 65535.
- **A source's own mask band is kept.** This is a mask band that is not an alpha band, as JPEG-compressed aerial imagery often carries. Masked pixels used to read as valid data in these places:
  - `rst_initnodata`.
  - The warps of `rst_bng_tessellate` and the raster-to-grid reducers.
  - `assignment='covering'`.
  - Lightweight `gbx_rst_transform` and `gbx_rst_transformcrs`.
  - The `raster_gbx` encoder and re-encode.
  - `cog_gbx` mosaic windows.
  - Lightweight virtual tiles, which `rst_fromfile` returns by default.

- **`rst_clip` fills with NoData.** The pixels outside the cutline, and the ones the source masks, are NoData. They take the tile's own NoData, else the fallback of its type, which the output declares.
  - They were valid zeros when the source declared no NoData.
  - A tile with an alpha band gets alpha 0 there and declares no NoData.
  - A cutline smaller than one pixel keeps the pixel it touches. It kept only NoData.
  - Virtual tiles with a `clip_polygon`, `rst_clip_grouped` and the Unity Catalog `rst_clip` follow the same rule.
  - If a source pixel inside the cutline equals the fallback of its type, such as 0 in a `uint8` tile, it is NoData too. This follows the [NoData fallback](#nodata-alpha-mask) rule.
- **The warp fill is NoData.** `rst_bng_tessellate` and the `rst_h3_rastertogrid*`, `rst_quadbin_rastertogrid*` and `rst_bng_rastertogrid*` reducers first warp a source that is not in the grid's CRS.
  - For a source with no NoData and no alpha band, the pixels outside the footprint were valid zeros. Edge-cell tiles carried them, and the reducers counted them as data.
  - They are now NoData with the fallback value. Source pixels equal to it are NoData too.
  - A source's own NoData is kept. An alpha band marks the fill of a source that has one.
- **Tiles of a source with an alpha band keep it.** The alpha band is the last band, when it is labelled alpha, as gdalwarp reads a source.
  - A band labelled alpha anywhere else is ordinary data. The fourth band of a `uint8` source without alpha (red, green, blue, near-infrared) stays ordinary.
  - Tiles declare no NoData. A pixel with alpha 0 is NoData, and so is the part of a tile outside its cell. An opaque pixel whose colour bands are 0 stays valid.
  - Tiles and clips also copy the colour interpretation of every band.
- **A transparent pixel belongs to no cell and counts for no band, at every band count.** A pixel is valid when its alpha is above 0 and a data band is valid by its NoData or mask. GDAL derives a mask from an alpha band only for two- and four-band rasters, so other band counts used to read as entirely valid.
  - `rst_*_tessellate` with `coverage='sparse'` no longer emits cells that hold only transparent pixels (`centroid`). It no longer keeps fully transparent tiles (`covering`).
  - These functions judge each band this way:
    - The raster-to-grid reducers: `rst_h3_rastertogrid*`, `rst_quadbin_rastertogrid*`, `rst_bng_rastertogrid*` and the custom-grid variants.
    - `gbx_rst_pixelcount`, `gbx_rst_avg`, `gbx_rst_min`, `gbx_rst_max` and `gbx_rst_histogram`.
    - The percentiles of `gbx_rst_percentile_stretch`.
    - The neighbours of `gbx_rst_filter` and `gbx_rst_convolve`.
    - The pixels that `gbx_rst_polygonize` and `gbx_rst_isoband` vectorise.
  - `gbx_rst_isempty` is true for a raster with no valid pixel.
  - The lightweight `gbx_rst_summary` takes its statistics over the valid pixels.
  - `gbx_rst_derivedband` of one raster is invalid where its input is.
- **Lightweight functions label a band alpha exactly where their source does.** GDAL labels band 4 of every four-band `uint8` GeoTIFF alpha when it creates one. It drops the alpha band of a 16-bit RGBA or gray-plus-alpha raster. The lightweight functions that write a raster from another one used to do the same. This covers:
  - `gbx_rst_updatetype`, `gbx_rst_initnodata`, `gbx_rst_threshold`, `gbx_rst_setsrid` and `gbx_rst_setcrs`.
  - `gbx_rst_filter`, `gbx_rst_convolve`, `gbx_rst_fillnodata` and `gbx_rst_percentile_stretch`.
  - `gbx_rst_resample` and its variants, and `gbx_rst_buildoverviews`.
  - `gbx_rst_asformat` to GeoTIFF, `gbx_rst_cog_convert` and `gbx_rst_getsubdataset`.
  - `gbx_rst_fromfile` with `materialize`.
  - The merge family: `gbx_rst_merge`, `gbx_rst_merge_agg`, `gbx_rst_align_to` and the `gbx_rst_combine*` functions.
  - The retile family: `gbx_rst_retile`, `gbx_rst_tooverlappingtiles` and `gbx_rst_maketiles`.
  - The reads of a lazily read tile.
  - The tile encoders of the `raster_gbx` and `cog_gbx` writers.
- **A band selection writes the alpha band as data, unless it is selected last with a data band.** `gbx_rst_band` and `gbx_rst_separatebands` extract a band for its values. The alpha band of an RGBA raster comes out as an ordinary band. A multi-band selection keeps the alpha label only when the source's alpha band is selected last with at least one other band.
- **A raster with an alpha band and its own mask band keeps both.** This holds in the encoders, writers and reprojections, in the warp behind covering and in the raster-to-grid reducers. A pixel is valid when a data band is valid, its alpha is above 0 and the mask says so.
  - The remaining lightweight writers also keep the alpha label and the mask:
    - `cog_gbx` quadbin, h3 and BNG cells, and its `pruneEmpty` check. A window or cell with no valid pixel is not written.
    - The COG re-encode of the `raster_gbx` writer.
    - `gbx_rst_frombands`.
    - `gbx_rst_merge` and the streamed merge of large groups.
    - The `pmtiles_gbx` reader's RGB sibling of an RGBA source.
    - The `netcdf_gbx` `bandDim` stack.
  - The h3 cells of a source with an alpha band and no NoData carry their hexagon as a mask band.

### Raster merge, reprojection and grouped functions (fix) {#raster-merge-fixes}

- **Lightweight merge and mosaic crashes are fixed.**
  - A quadbin, h3 or BNG `cog_gbx` cell that a source barely touches no longer fails with `Invalid dataset dimensions`.
  - `gbx_rst_merge` of tiles in two coordinate systems takes its size and pixel size from the reference system, whichever tile sorts first. It reprojects the other tile onto the reference tile's pixel grid, in memory and streamed alike. That tile can grow by up to a pixel on each side.
- **A lightweight merge no longer overwrites valid pixels with zeros** when a tile is reprojected. The reprojected tile carries its warp footprint as a mask. The mosaic has a mask band, and a pixel no tile covers is invalid.
- **A streamed lightweight merge reads each tile by its own NoData,** as the in-memory merge does. The `cog_gbx` mosaic index masks a multi-band tile only where every band is NoData. The layout still differs: the streamed result is a Cloud Optimized GeoTIFF (tiled, with overviews), and the in-memory one a striped GeoTIFF.
- **Focal defects are fixed.**
  - `gbx_rst_filter` of a raster with no declared NoData no longer returns NaN for every window.
  - `gbx_rst_convolve` no longer writes each block's result shifted.
  - A focal window adds only the neighbours on the raster. v0.5.2 replicated the edge.
- **`gbx_rst_merge_agg` refuses an oversize group on Serverless.** A Serverless task holds the whole group before any merge. A group of tiles that add up (decoded) to more than the task's memory cap used to end the query with a memory-limit error. It is now refused first, with a `Fix:` that names `merge_by_key(method="vrt")`. The SQL call raises, and the Python call returns the group's error tile.
- **`gbx_rst_merge` runs on the lightweight level, also on a cluster with the JAR.** The merge streams a group over the memory budget and returns the mosaic. In v0.5.2 a hot key of a skewed table came back with no raster.
- **A merge of virtual tiles skips the sidecar look-up for files the reader marked sidecar-free.** Tiles from `raster_gbx` carry `path_sidecar_free`. The merge now honors it for the member headers and for the streamed read. It no longer lists a large folder once per worker for them.
- **Grouped functions apply a virtual tile's clip.** On runtimes with the FILE type, the lightweight `*_grouped` functions skipped the `clipPolygons` polygon of a `raster_gbx` or `cog_gbx` virtual tile. These include `rst_clip_grouped`, `rst_memsize_grouped` and `rst_resample_grouped`.
  - They now read the tile clipped, and reproject a tile whose `crs` differs from its source's.
  - A tile written with `virtualize_dir` from a clipped or reprojected tile no longer applies that clip and CRS twice when read.
- **A file written with `virtualize_dir` ends in a random id.** The name held only the cell and the size. Two results of one size in one directory wrote the same file, the second over the first. This held for a mosaic, `rst_combineavg`, `rst_frombands` and tiles of one cell.
- **Grouped functions apply `rst_initnodata`, `rst_band`, `rst_setsrid` and `rst_setcrs` to a whole-file virtual tile.** After one of those functions, a `*_grouped` function that reads pixels returned NULL without an error on a cluster without the FILE type. Examples are `rst_resample_grouped` and `rst_slope_grouped`. On a cluster with the FILE type, it ignored the instruction.
- **Raster output encoding.**
  - Lightweight raster functions write ZSTD with the predictor that suits the data type, instead of the source file's codec. JPEG (YCbCr) sources no longer make writes fail.
  - An explicit JPEG request keeps YCbCr.
  - Heavyweight tiles whose metadata names no `compression` are DEFLATE in every path, as documented. Some paths wrote ZSTD.
  - `rst_cog_convert` still defaults to ZSTD.

### Grid rasterizers: repeated cell ids burn the largest value (fix) {#grid-rasterizers}

- **The lightweight cell rasterizers keep the largest value when a cell repeats, like the heavyweight tier.** `rst_h3_rasterize_agg`, `rst_quadbin_rasterize_agg`, `rst_bng_rasterize_agg` and `rst_custom_rasterize_agg` burned the row that arrived last. The same data could give a different raster on each run.
  - A cell that appears once, or whose rows all carry the same value, burns as before.
  - Two spellings of one BNG cell, such as `TQ3080` and `TQ 3080`, are one cell.
- **`gbx_rst_custom_rasterize_agg` and `gbx_rst_custom_rasterize` derive their canvas from the grid's cell edges.** With NULL canvas arguments, a grid whose bounds are not a multiple of the pixel size gave a tile of NoData.
  - The canvas snapped to multiples of the pixel size from 0, so every pixel centre fell on a cell edge. It now snaps from the grid's `bound_x_min` and `bound_y_min`.
  - The padding of `kring_pad` holds the cells that exist, so a canvas at the grid edge no longer grows past the grid.
  - The JVM form gives NoData for a pixel outside the grid, as the lightweight form does. It raised an error.
  - The JVM and Python forms give the same canvas. A canvas in another CRS than the grid's still snaps from 0.
- **In the lightweight rasterizers a null value never wins.** A null or `NaN` is ignored whenever the cell has a number, so values `0.5` and `NULL` burn `0.5`.
  - A cell whose values are all null burns `NaN`, also when the whole `value` column is null.
  - Only an omitted `value` (or an untyped `NULL`) is the presence mask and burns `1.0`.
  - The heavyweight tier still counts a null value as `1.0`.
- **The lightweight `*_cellfill` aggregates give the same fill whatever order rows arrive in.** `h3_cellfill`, `quadbin_cellfill`, `bng_cellfill` and `custom_cellfill` used the last row for a repeated cell id. They use the cell's largest non-null value. A cell stays `NULL` only when all its values are null. The heavyweight tier still keeps the last row it receives.

### Cell rasterizers: scalar forms and table functions (new) {#cell-rasterizer-forms}

- **`gbx_rst_h3_rasterize`, `gbx_rst_quadbin_rasterize`, `gbx_rst_bng_rasterize` and `gbx_rst_custom_rasterize` burn an array of cells into a raster tile.** Pass `collect_list(struct(cellid, value))` and get the bytes of one GeoTIFF without a `GROUP BY`.
- **`gbx_rst_bng_rasterize_tvf` burns BNG cells into one raster per key without holding a whole group in memory.** Call it with `TABLE(...) PARTITION BY (key)` and an explicit canvas.
- **`gbx_rst_merge_tvf` merges each key's tiles into one raster, reading them a row at a time.** Use it instead of `gbx_rst_merge_agg` for large groups.

## Results and errors {#results-errors}

### Errors, NULLs and wrong arguments follow one contract (behavior change) {#error-contract}

Every raster function follows the same order of checks on both implementations.

- **A NULL tile or a NULL required argument gives NULL.** An error tile in comes out as itself.
- **A tile that cannot be read gives an error tile.** This covers an unreadable tile, a tile the driver policy refuses and a tile over the compute's read cap. The tile has a NULL raster and the reason in `metadata.last_error`, beside `error_message`. `rst_tryopen` is false for it.
  - A tile whose file cannot be reached now fails the task, so Spark retries it. Examples are a Volume path that has not caught up and a missing file after the retries. Before, the row became an error tile that stayed.
  - A tile that opens but cannot be read (truncated or corrupt pixels) is the tile's error tile with GDAL's reason. Before, the task failed.
- **A wrong argument raises and names the value.** These are wrong arguments:
  - A factor or size of 0, an unknown resampling word, or a data type, driver or operation GeoBrix does not know.
  - A kernel that is not rectangular with odd sides, or percentiles outside 0 to 100.
  - A method other than `spectral`, `kmeans` or `hybrid`, a subdataset the tile lacks, or a band past the last band.
  - An `out_srid` that is not a positive EPSG or ESRI code.
  - `gbx_rst_slope` raises for a unit other than `degrees` or `percent`; it used to treat any other value as degrees.
  - The Python Column API raises the same errors as SQL.
  - A function that gave an error tile for a wrong argument now fails the call.
- **An aggregate of only error tiles gives the first error tile.** `rst_combine*` and `rst_frombands` skip a NULL element, an error tile or a tile that cannot be opened, and combine the others.
  - They give NULL for a NULL or empty array.
  - Tiles of different shape raise. `rst_combineavg` no longer resamples.
- **`rst_isempty` is true only for an error tile,** or a raster with no valid pixel. A tile with neither raster nor path and no reason is NULL.
- **`rst_setsrid(tile, 0)` clears the CRS.** A raster georeferenced by ground control points counts as having a CRS.
- **A merge too big to build is that group's error tile** with a `Fix:`. The aggregate raises.
- **A duplicate cell's maximum ignores NaN.** A NaN never beats a number in the rasterize aggregates and the cell fills.
- **`gbx_rst_binpoints` and its aggregate skip points with a NaN or infinite coordinate.** On some platforms such a point used to land in the first column.
- **`out_srid` and `out_crs` together raise,** in every rasterizer: `Fix: set one`. This includes the H3 and quadbin rasterizers, where `out_crs` used to win.
- **`rst_fromfile(vrt, materialize=True)` gives a GeoTIFF tile,** or an error tile with the reason, instead of NULL. A file the driver policy refuses is an error tile. A missing path stays NULL.
- **Remote paths need a switch.** `gbx_rst_fromfile('https://...')` reads the URL through GDAL's `/vsicurl/` when you set `GBX_ALLOW_REMOTE_PATHS=true` before `register()`. The same size cap applies as for a local file. A URL that cannot be opened gives NULL. With the switch off the call raises with the location and a `Fix:`. A VRT served at a URL is refused, whatever its name.
- **The `driver` of `rst_fromcontent` and `rst_fromfile` must be a raster driver.** A vector-only driver such as `GeoJSON` raises. The driver is stored as GDAL spells it.
- **`gbx_rst_fromcontent` gives an error tile with a `Fix:` for bytes GDAL cannot open,** or a format that can name other files (VRT).

### Tile reads honor the compute's memory cap (behavior change) {#read-caps}

- **A tile held in a column is refused when its decoded size passes the cap.** The cap is 64 MiB on Serverless and 1536 MiB on classic and dedicated compute. The lightweight functions used to process such a tile on Serverless. The refusal text is the same on both implementations.
  - Reading a file over the cap fails the call with a retile `Fix:`. The same holds for `gbx_rst_fromfile`, `rst_fromfile(materialize=True)` and `raster_gbx` with `virtualTiles=false`.
  - `rst_align_to` reads only the header of the reference tile, so a large reference no longer turns every aligned tile into an error tile.
- **A virtual tile is refused when the window it reads passes the cap.** Before, only a tile that carried bytes was judged, so a large window could run a Serverless task out of memory. The refusal text and `Fix:` are the same as for a tile with bytes.
  - The size is the window's width and height, times the bands it reads, times the size of the type. A small window of a large file is read.
  - `rst_maketiles`, `rst_retile` and `rst_tooverlappingtiles` stream huge virtual tiles. They cut the tile window by window from its file, so they need the memory of one piece.
  - This holds when the tile is clipped, reprojected or read from a file with its own mask band. A piece keeps that mask band.
  - `rst_maketiles` sizes a tile over the cap from its header, as its decoded size. A tile under the cap is split as before.
  - A reprojected piece of a huge tile may take another source pixel than the whole tile would, at a few borderline pixels.
  - Reads that decode no window are not judged: the plain-window warp, a merge by reference and the block-streaming write.
- **Heavyweight and lightweight functions take the same tile drivers and refuse the same oversized tiles.** The JVM reads tile bytes of netCDF, HDF, HFA, JP2 and GPKG as a GeoTIFF. Subdatasets and extra metadata domains are not kept. These reads failed before 0.6.0.
  - `gbx_rst_subdatasets` and `gbx_rst_getsubdataset` read a netCDF or HDF tile as its own dataset, so they keep working.
  - A netCDF or HDF container with several variables and no band answers `rst_width`, `rst_height`, `rst_numbands`, `rst_subdatasets` and `rst_metadata`. It was an error tile. `rst_metadata` includes the file's own metadata domains.
  - Heavyweight netCDF and HDF reads run one at a time per executor. This avoids a native crash in GDAL 3.13's netCDF metadata path. Throughput of concurrent netCDF reads in one executor is lower.
- **A merge or combine over the memory budget no longer fails or returns NULL.** `gbx_rst_merge_agg` and `gbx_rst_combineavg_agg` stream the work, and `gbx_rst_combinesum`, `count`, `median` and `stddev` fold in windows.
  - The streamed mosaic is a Cloud Optimized GeoTIFF with the same pixels as the in-memory one.
  - A mosaic past 10 GiB decoded raises a `Fix:`. It says to keep the tiles as files on a Volume, then build the mosaic with `databricks.labs.gbx.rasterx.helpers.mint_vrt(paths, out="/Volumes/...")` or the `cog_gbx` writer with `vrtMosaic=true`, and read the VRT.
  - Members in different CRSs or pixel sizes get a first step in the `Fix:`: bring them to one CRS and pixel size with `gbx_rst_transform` and `gbx_rst_resample_to_res`.
  - A tile that must be decoded whole and is over the read cap names `merge_by_key(..., method="vrt")`.
  - A virtual tile is merged as a file, with its window as the source rectangle. No member is read into memory first, so a group of virtual tiles merges in the same memory at any size. This covers `gbx_rst_merge_agg`, its Python form with a directory, `gbx_rst_merge`, `gbx_rst_merge_tvf` and `merge_by_key`.
  - Where tiles overlap, the order is now defined: tiles with bytes first, sorted by their bytes, then virtual tiles, sorted by path and window. A group of virtual tiles used to be ordered by their re-encoded bytes.
  - `merge_by_key` keeps no group in memory. It takes windows of files and mixed CRS, and its group has no size cap. Its shuffle has a fixed width (`num_partitions`, else the session's task slots, at least 64).
  - A mosaic written with `virtualize_dir` is copied from scratch to the directory and not read back.
  - A stack too wide for one row names retiling first, then `combine_by_key`. The row is then one raster per sub-tile.
  - `gbx_rst_combineavg_agg`, `gbx_rst_frombands_agg` and `gbx_rst_derivedband_agg` raise a `Fix:` in SQL for a group they cannot fold or a member over the read cap. The Python tile form keeps the group's error tile.
  - See [Performance](./api/performance) and [Error handling](./api/error-handling).
- **`gbx_rst_merge_tvf` and `gbx_rst_bng_rasterize_tvf` are new table functions (new).** Python has `rst_merge_tvf(df)` and `rst_bng_rasterize_tvf(df, xmin, ymin, xmax, ymax, width, height)`. They are the grouped merge and the BNG rasterize as `TABLE(...) PARTITION BY (key)` calls.
  - One mosaic or canvas per key, with the same pixels as the aggregates. A task reads a row at a time and needs about a third of the aggregate's memory on large groups.
  - The table needs the columns `key, tile` or `key, cellid, value`. A key with no readable tile or no cell gives no row.
  - A partition that holds more than one key raises. Call it as `TABLE(SELECT key, ... FROM ...) PARTITION BY (key)`.
  - A `BINARY` `tile` column raises with `Fix: pass gbx_rst_fromcontent(<bytes>, 'GTiff') as tile`. A NULL canvas value raises and names it.
  - The cell rasterize aggregates derive the canvas from the cells when `xmin` to `height` and `kring_pad` are all NULL. A canvas given in part raises.

### WKB is little-endian and cell rings start south-west (behavior change) {#output-formats}

- **WKB from the heavyweight functions is little-endian,** as the lightweight functions, GDAL and `st_asbinary` give. The same call returns the same bytes on every compute.
- **A BNG or custom-grid cell polygon starts at the south-west corner and runs counter-clockwise.** An example is `POLYGON ((530000 180000, 531000 180000, 531000 181000, 530000 181000, 530000 180000))`. The lightweight level started at the south-east corner.
- **`gbx_bng_aswkb` and `gbx_bng_centroid` on Unity Catalog return little-endian EWKB with SRID 27700.** The bytes are the same whether the Volume holds the JAR or not. The session functions return plain WKB without an SRID.

### Raster function results (behavior change) {#raster-results}

- **Light band mean and standard deviation are exact to double.** They were off in the 7th digit for `float32` bands.
- **Heavyweight changes.**
  - `gbx_rst_srid` is NULL when the CRS has no authority code (it was 0).
- **Changes from v0.5.2 for functions that now run on the lightweight level.**
  - `gbx_rst_getnodata` is NULL when no band declares NoData (it was NaN per band).
  - `gbx_rst_sample` raises for a non-point geometry. A longitude/latitude point (EWKT, EWKB or the `crs` argument) lands on the right pixel. It used the authority's axis order and missed the raster.
  - `gbx_rst_convolve` returns `Float64`. The median filter of an even number of valid pixels is the mean of the two middle values.
  - `gbx_rst_initnodata` keeps a NoData value every band declares, NaN included. `gbx_rst_percentile_stretch` declares NoData 0.
  - `gbx_rst_gridfrompoints` with `max_pts` below the number of points weights the nearest `max_pts` points.
  - `gbx_rst_merge` mosaics tiles in different CRSs. The reference CRS is the smallest EPSG code present. GeoBrix reprojects a tile in another CRS onto the pixel size and grid of the first tile in it. That tile can grow by up to a pixel on each side.
- **Lightweight changes.**
  - `gbx_rst_updatetype` rounds a float to the nearest integer and clamps to the type's range. It truncated and wrapped. The type name is read in any case.
  - `gbx_rst_getsubdataset` works on a tile that points to a netCDF or HDF file, and returns a tile labelled driver `GTiff`.
  - `rst_getsubdataset` on a tile with a window, clip or pending edits gives an error tile with a `Fix:`.
  - `rst_filter` with a fractional window such as 3.9 raises. `rst_derivedband` finds a function defined inside `if`, `try`, `with`, `for` or `while`.
  - `gbx_rst_histogram` with a bucket count below 1 raises. `gbx_rst_bandmetadata(tile, NULL)` is NULL.
  - Resampling words match in every function: `near` (or `nearest`), `bilinear`, `cubic`, `cubicspline`, `lanczos`, `average`, `mode`, `max`, `min`, `med`, `q1` and `q3`, in any case. Words such as `gauss`, `sum` and `rms` raise and list the words that work.
  - `gbx_rst_transform` and `gbx_rst_to_webmercator` give an error tile with a `Fix:` for a tile with no CRS.
  - `gbx_rst_proximity` with a NaN or NULL `max_distance` means no cap. It agrees with GDAL to within a pixel's diagonal.
  - `gbx_rst_clip` with a cutline that cannot be read, or a `clip_crs` that names no CRS, gives the tile's error tile.
  - `gbx_rst_aspect(..., trigonometric => true)` is 0 to 360. `gbx_rst_threshold` with an unknown operator raises, and `op` and `value` default to `'>'` and 0.0. Passing pixels keep their value and others become NoData.
  - `rst_tilexyz` of a one-band raster is an RGBA PNG or RGB JPEG. A NULL `z`, `x` or `y` gives NULL.
  - `rst_cog_convert` writes any block size that is a multiple of 16, and `'AUTO'` is ZSTD. `rst_color_relief` writes RGBA when a stop has an alpha column.
  - `gbx_rst_color_relief` takes the color table as text and runs GDAL's own color-map algorithm. NoData pixels take the `nv` color. Without an `nv` line they are transparent in an RGBA result and black in an RGB one.
  - `gbx_rst_polygonize` defaults band 1 and connectedness 4. It raises for another connectedness or a band the tile lacks.
  - `gbx_rst_tooverlappingtiles` raises for a window below one pixel and for an overlap outside 0 to 99 percent.
  - `gbx_rst_viewshed_towers` fails the query when the DSM tile of a tower cannot be read.
- **`gbx_rst_gridfrompoints` and `gbx_rst_binpoints` give NULL for a NULL extent, size or SRID.** With no `out_srid` and no `out_crs`, the output has no CRS.
- **`gbx_rst_rasterize` reprojects an EWKT geometry into the output CRS,** as it did EWKB. A geometry that cannot be read, or an empty string, raises and names it.
- **A rasterize aggregate with the `value` left out burns 1.0 (the presence mask).** A typed NULL burns NaN.
- **A GCP-georeferenced raster is warped from its points** by `gbx_rst_transform` and `gbx_rst_to_webmercator`.
- **A tile's alpha band keeps its label through the band selection of `rst_band`.** See [NoData, alpha and mask bands](#nodata-alpha-mask).
- **The `rst_merge` overlap winner does not depend on the array order.** The bytes that sort last win. The old text said the first tile wins.
- **`gbx_rst_asformat` takes the driver name in any case.** It resolves the name to GDAL's spelling and leaves a tile that is already in that driver unchanged. The `driver` in the result is the driver the bytes open as (`GTiff` for `COG`).
- **The JVM cell rasterizers read `out_crs` as `EPSG:<n>` or a bare integer.** They refuse `ESRI:<n>` and WKT with a `Fix:`. The lightweight level accepts them.
- **`gbx_rst_derivedband` runs your Python (`exec`) in the session.** Use it in session SQL and Python only. `gbx_rst_clip` runs on the lightweight level only.
- **SQL tile functions read a `FILE` column through the same fast path as the Python API.**
- **`SHOW USER FUNCTIONS` works on DBR 17.3 after `gbx.register`.** The SQL tile functions that mint a `FILE` argument (`gbx_rst_avg`, `gbx_rst_width` and 32 more) run a check once per session. The check asks whether the runtime can list a function with `FILE` in its body. Where it cannot, they pass NULL and read the tile by its path.

## Grid functions {#grid-functions}

### Resolutions, NULLs and non-finite input (behavior change) {#grid-contract}

Every grid function follows one contract for its resolution and its input.

- **A BNG resolution is an index or a digit string.** `'3'` works, and so does `'1km'` for a BNG size. A resolution outside the INT range raises and names the value. Before, the JVM narrowed it to INT and could wrap to a valid index.
- **A fractional resolution such as 3.5 raises and names the value** in the quadbin, custom-grid and H3 functions. A whole number written as text (`'3'`) is accepted.
- **A NULL cell gives NULL** in the quadbin and custom-grid cell functions. Before, the lightweight functions raised or gave resolution 0.
- **A non-finite coordinate gives NULL.** An infinite longitude or latitude in `quadbin_pointascell` was a made-up cell. An infinite geometry gives NULL in `geomkring` and `geomkloop` of all three grids. An unreadable geometry gives NULL in `quadbin_polyfill` and `quadbin_tessellate`.
- **The custom-grid functions treat NULL, text and bad modes alike.** A NULL resolution or `k` gives NULL. A text resolution works. An unknown dilation mode raises.
- **The geometry explodes follow the rules of their array functions.** An unknown mode or an undefined resolution raises. A non-finite point or unreadable geometry gives no rows. The BNG and custom explodes raise for an unknown `coverage` before they run, and read a `BIGINT` `k`. A `k` past INT raises.
- **`gbx_rst_bng_tessellate` raises for a resolution BNG does not define.**
- **A bad `coverage` and a negative `k` now raise on the JAR level too.** `gbx_bng_geomkring`, `gbx_bng_geomkloop`, `gbx_custom_geomkring` and `gbx_custom_geomkloop` raise for an unknown `coverage`, and `gbx_custom_kring`, `gbx_custom_kloop` raise for a `k` below 0, each naming the value. Before, the JAR level returned NULL where the lightweight level raised. `gbx_bng_tessellate` also raises for an integer resolution BNG does not define.
- **A bad argument raises in more raster functions.** v0.5.2 returned an error tile, a NULL or a tile that could not be opened.
  - `gbx_rst_h3_tessellate`, `gbx_rst_quadbin_tessellate` and `gbx_rst_custom_tessellate` raise for an `assignment` or `coverage` they do not know, naming the value. A NULL `resolution` gives the row's error tile, not a tessellation at resolution 0.
  - `gbx_rst_tooverlappingtiles` raises for a window below 1 pixel and for an overlap outside 0 to below 100 percent. A NULL window or overlap gives the row's error tile. A NULL size in `gbx_rst_maketiles` does the same.
  - `gbx_rst_asformat` refuses a format whose bytes GeoBrix does not open as a tile, such as `VRT`, with a `Fix:`.
- **The TIN generators and `gbx_st_asmvt_pyramid` give no rows for a NULL required argument.** They failed the query before.

### Exact cell ids (fix) {#exact-cell-ids}

- **The 500 km squares `S`, `T`, `N`, `O`, `H` and `J` are the right squares.** A one-letter name such as `N` read as `S`, and `T` gave a polygon far east of Great Britain. Each name is now the 500 km square from its south-west corner (`T` from 500000, 0; `N` from 0, 500000). A point writes as the square it lies in. The name reads back to the same square. This holds on every level, and for the `500km` resolution.
- **Cell functions that take a `BIGINT` cell no longer return the wrong cell when the batch holds a NULL.** The affected functions are `gbx_quadbin_resolution`, `distance`, `aswkb` and `centroid`, and `gbx_custom_cellaswkb`, `cellaswkt`, `centroid` and `distance`. Pandas rounded ids past 2^53 to a neighbour. They now run row by row.
- **The grouped aggregates raise for a group with a NULL cell id.** The aggregates are `gbx_quadbin_cellunion_agg`, `gbx_h3_cellfill`, `gbx_quadbin_cellfill` and `gbx_custom_cellfill`. Pandas cannot read exact ids, so the message says to filter first: `WHERE cellid IS NOT NULL`. `gbx_rst_*_rasterize_agg` already did this.
- **A BNG chip with NULL bytes is an empty geometry** in `gbx_bng_cellunion`, `gbx_bng_cellintersection` and their aggregates, on both levels. The union is the other chip, and the intersection is empty. `gbx_bng_cellintersection` leaves NULL bytes for an empty intersection.
- **A BIGINT resolution in the custom-grid functions raises an `IllegalArgumentException` that names the value,** where `ArithmeticException: integer overflow` was raised.
- **`gbx_custom_kring` and `gbx_custom_kloop` at the grid edge no longer include cells outside the grid.** A ring at the east edge held a cell of the next row. A ring at the north edge held a cell past the last row. The geometry-aware rings, their explodes and `gbx_custom_cellfill` walk the same neighbours, so they keep to the grid as well. This holds on every level.
- **The JAR level of the custom-grid cell functions takes a cell id given as INT,** such as the literal `180530`. `gbx_custom_kring`, `kloop`, `cellaswkb`, `cellaswkt`, `centroid` and `distance` returned NULL or raised for it, where the lightweight level answered.
- **`gbx_custom_cellfill` and `gbx_rst_custom_rasterize_agg` read the grid from the rows of each group on the JAR level.** A grid held in a table column, not a constant, failed with an internal error. Each group now uses its own grid, as the lightweight level does, and the options of the rasterize aggregate may be columns too.
- **The raster-to-grid functions give no rows for an unreadable tile** and no rows for a NULL resolution or custom grid. A bad resolution, coverage or assignment raises and names the value before the tile is opened. A custom resolution above the grid's maximum raises before the tile is opened.
- **`gbx_rst_*_rastertogrid*` cell functions treat a transparent pixel as no data.** See [NoData, alpha and mask bands](#nodata-alpha-mask).


### `bng_tessellateexplode` columns (behavior change) {#bng-explode}

- **Heavyweight `bng_tessellateexplode` returns `core` and `chip`, like the lightweight tier.** It declared one column and dropped the `core` flag and chip geometry. It now returns `cellid` (STRING), `core` (BOOLEAN) and `chip` (BINARY, WKB). This holds for a WKB or WKT geometry alike, as in the lightweight tier and `bng_tessellate`.
  - A query that named the whole generator output with one alias (`.as("chip")`) needs one name per column, or none.
- **`keep_core_geom` is an optional third argument that defaults to false in every API.** The SQL function takes two or three arguments.
  - The Python wrapper's default changes from true to false.
  - The Scala two-argument wrapper passes false instead of true.
  - A core cell's `chip` is NULL unless you ask for it. Border cells always carry their geometry.
- **Call the BNG, quadbin, custom-grid and H3 explode functions with `FROM t, LATERAL f(...)`.** This form works on every compute.

### `bng_tessellate` core geometry off by default (behavior change) {#bng-tessellate-default}

- **`bng_tessellate` defaults `keep_core_geom` to false in every API,** as `bng_tessellateexplode` does.
  - The two-argument SQL form returned a NULL core chip in the heavyweight tier but the cell geometry in the lightweight tier.
  - The Scala and Python wrappers of both tiers defaulted to true.
  - A core cell's `chip` is NULL unless you pass `keep_core_geom` as true.
  - The Scala wrapper gains overloads that take it. Pass true to keep the old wrapper result.

### `bng_tessellate` keeps cells that clip to a MultiPolygon or a mixed collection (fix) {#bng-tessellate-fix}

- **A polygon no longer loses cells when its clip is a MultiPolygon or a mixed collection.** A valid polygon can clip to a cell as a MultiPolygon. It can also clip as a GeometryCollection that holds polygons plus a point or line along the cell edge.
  - The heavyweight `bng_tessellate` returned NULL for the whole polygon. `bng_tessellateexplode` returned no rows.
  - The lightweight tier returned fewer cells than the polygon covers.
  - Both tiers now keep the polygonal part of every clip and return the same cells and chips.
- **Chip shapes.**
  - A MultiPolygon input returns its Polygon chips, and a polygon's chip can be a MultiPolygon.
  - Points and lines that only touch a cell edge are dropped.
  - Results for polygons that clip to plain Polygon chips do not change.
- **A GeometryCollection that holds a large polygon is tessellated.** It returned NULL in the heavyweight tier and raised an error in the lightweight tier. Both tiers now tessellate the union of the collection's polygons, at any nesting depth. A line or point in the collection can remain in the chip of a cell the polygons also touch. It never yields a cell of its own.

### A NULL resolution in a batch (fix) {#null-resolution}

- **`bng_pointascell` and `bng_eastnorthasbng` answer the rows beside a NULL.** In the lightweight tier, a NULL `resolution` made `bng_pointascell` fail the whole batch (`BNG resolution not supported; found nan`). A NULL resolution, easting or northing now gives a NULL cell, and the other rows are answered.
- **`quadbin_pointascell` and `custom_pointascell` answer the rows beside a NULL too.**
  - `quadbin_pointascell` also answered a NULL longitude or latitude with a made-up cell.
  - A resolution that is not a whole number (3.5) is refused instead of cut to 3.
  - `custom_pointascell` no longer rounds a cell id above 2^53 when its batch holds a NULL.

### Other grid changes (behavior change, new) {#grid-other}

- **`out_crs` on `gbx_rst_bng_rasterize_agg` is refused on both tiers when it is not NULL (behavior change).** BNG output is always EPSG:27700. Both tiers used to accept and ignore the argument. Pass NULL, and reproject the tile with `gbx_rst_transformcrs` for another CRS.

## Zarr {#zarr}

### Transactional, versioned stores (new) {#zarr-stores}

- **The lightweight tier registers, reads and writes Zarr stores transactionally.** [Zarr](https://zarr.dev) keeps N-dimensional arrays as many small objects in object storage, with no commit. Two jobs writing one store can lose each other's updates, and a reader can see a half-written store.
  - In GeoBrix, a store's manifest is a Delta table.
  - A version of the store is a version of that table.
  - One Delta transaction is one store transaction.
- **Requirements.** Zarr runs on Databricks Runtime 19 and Serverless environment 6, with no JAR. Install the env6 wheel with its `[zarr]` extra. See [Dependencies](#dependencies) and [Zarr Stores](./api/zarr-stores).
- **`gbx_zarr_register` registers an existing store in place.** It lists a Zarr v2 or v3 store once and records every object in a manifest table. It does not copy or write to the store.
  - `writable=True` with an `overlay_root` sends writes to new files outside the store.
  - Several tables can register one store. Each is an independent branch with its own history, grants and overlay. Branches do not merge.
- **`gbx_zarr_read`, `gbx_zarr_sample` and the `zarr_gbx` reader read stores.** Select by label (`sel`) or position (`isel`). A read returns one of these:
  - Blocks.
  - A table with a column per dimension and variable (missing data is `NULL`).
  - Virtual GeoBrix tiles, so every `rst_*` function works on a cube.

  `gbx_zarr_sample` reads the time series at the points of a DataFrame. A read of a manifest table pins one version. `zarr_gbx` reads plain stores by path. See [Zarr Reader](./readers/zarr).
- **Zarr reads fill the cores.** A read is split into tasks of about 16 MiB decoded (spread over the session's cores when it is smaller). It is no longer split by the memory limit alone. A 1 GB read on a classic cluster was one task. A chunk counts only the cells inside the array. The `gbx_zarr_sample` function splits a chunk with many time steps into several tasks. A county in one chunk is therefore no longer read on one thread. On a Databricks job cluster the read counts the cluster's workers and cores. A plain store on a Volume is decoded by a larger thread pool. A whole-grid tile of many chunks therefore waits less on the mount. See [Zarr Reader](./readers/zarr).
- **`gbx_zarr_write` creates, appends to, updates and overwrites a store in one transaction.** Nothing is visible until the write commits. Blocks and tiles that were read can be written back. See [Zarr Writer](./writers/zarr). Writers resolve conflicts like this:
  - Writers that touch different chunks both land.
  - Appenders that change the array's shape and a shared coordinate chunk are rebased, up to 20 attempts.
  - Writers that meet on one chunk get a `ZarrWriteConflict`. It names the keys and the write that won.
  - A `write_id` makes a retried write apply once.
- **`gbx_zarr_write` takes a table of cells.** A DataFrame with one row per cell is written as it is. Name its dimension columns in `dim_cols`: no packing into blocks and no staging table. The writer reads the dimension columns for the plan. It then shuffles the cells once by the shard they fall in. Each input partition first gathers its cells into partial blocks, so the shuffle moves blocks, not a row per cell. The writer builds and writes one shard at a time. `coords` fixes a new store's labels, and `coords` for every dimension with `complete=True` plans the write without the scan of the table, so the table is read once. Missing cells read as the fill value, duplicate cells are refused, and `create` and `append` are supported. An append that starts inside a shard now spreads its first stage over the blocks it holds, instead of over the input's partitions. See [Write from a table of cells](./writers/zarr#write-from-a-table-of-cells).
- **`gbx_zarr_write` appends cells without a scan, and Zarr-to-Zarr transforms have a recipe.** An `append` of cells takes `coords` for the append dimension, and `coords` with `complete=True` plans the append with no scan of the table. A table with one row per cell of the grid needs one scan, not two. For a Zarr-to-Zarr compute, read the cells, compute in Spark columns and write them with `coords` and `complete=True`. A blocks recipe stays for block-shaped computes. See [Zarr to Zarr: compute on cells](./writers/zarr#zarr-to-zarr-compute-on-cells).
- **`gbx_zarr_write(..., transactional=False)` writes a plain Zarr store.** `target` is a path. There is no manifest table, ownership ledger or Delta commit, so no versions, no time travel and no guard against a second writer. Metadata is written last, so a write that stops part way leaves no store. It supports `create` and `append`, and returns a summary. The default stays transactional. See [Plain stores](./writers/zarr#plain-stores-opt-in).
- **`gbx_zarr_sync` brings a registered table up to date with other tools' changes.** A read stops with `ZarrStoreDrift` when an object changed (its modification time and size on a Volume). `gbx_zarr_sync` records the change as one new version. `gbx_zarr_export(method="publish")` writes a writable registration's overlay into the store itself. That is not atomic for plain readers.
- **Versions.** Every version stays readable for `retain` (7 days by default), and a tagged version for good.
  - `gbx_zarr_history` lists the commits.
  - Read an older version with `version_as_of` (a number or `"tag:<name>"`) or `timestamp_as_of`. A version older than `retain` raises `ZarrVersionUnavailable`.
  - `gbx_zarr_tag` and `gbx_zarr_untag` name a version so that vacuum keeps its files.
  - `gbx_zarr_restore` makes the store equal an older version again as a new commit.
  - `gbx_zarr_optimize` folds the small chunk rows that appends leave into shards.
  - `gbx_zarr_vacuum` deletes the files no readable version needs (`dry_run=True` lists them).
  - A version that changes no data counts as the version before it. Examples are an `OPTIMIZE`, a property change, or Databricks' auto compaction after each `MERGE`. The version a write returns stays readable until the next data change passes the horizon. A write, optimize or restore with nothing to do returns the last version that changed data.
- **A store's root belongs to exactly one table.** A managed store's data root and a writable registration's overlay root carry an ownership ledger. It is the small Delta table `_gbx_owner`, next to the `_gbx_store.json` marker.
  - A table that claims a root another table owns gets `ZarrOwnershipError`.
  - Leave `_gbx_owner` where it is. Delete it, with the marker, only when no store owns the root.
- **Limits.** Zarr support reads numeric types and CF times. It needs a regular grid to return tiles. It has been measured for direct storage access on AWS only. See [Known Limitations](./limitations#zarr-stores).

### Direct storage access (new) {#zarr-direct}

- **`access="direct"` reads and writes a Zarr store's files straight from the Volume's cloud storage.** `gbx_zarr_read`, `gbx_zarr_sample`, `gbx_zarr_write` and `gbx_zarr_export` take `access="auto"` (default), `"fuse"` or `"direct"`. Direct access reads byte ranges with obstore using temporary Unity Catalog credentials. It is several times faster than the Volume mount for many small ranges.
  - `"auto"` uses direct access where credentials can be had (dedicated compute). It uses the Volume mount everywhere else, Serverless included, without an error. If credentials expire during a long job, it carries on through the mount.
  - An explicit `"direct"` raises `ZarrAccessUnavailable` where credentials cannot be had. It also raises for a plain-path store: register the store with `gbx_zarr_register` to use direct access. It raises when credentials expire.
- **Direct access sends credentials to the executors.** They last at most one hour and cover only the one Volume.
  - Under memory pressure Spark may write task data, credentials included, to local disk. Turn on local-disk encryption on clusters that use direct access.
  - This includes the default, because `access="auto"` is direct access on dedicated compute.
  - `access="fuse"` sends no credentials.
  - `gbx_zarr_export` asks for credentials on the driver only, and writes none to the reference file.
- **A refused or failed pack upload can leave an incomplete multipart upload in the bucket.** The parts stay, and are billed, until removed. Add a lifecycle rule to the bucket that aborts incomplete multipart uploads (`AbortIncompleteMultipartUpload`, after a few days).

### File modes, copy targets and reference files (new) {#zarr-file-modes}

- **The default `file_mode` is `"fuse"`, so a Zarr store reads from every compute.** `gbx_zarr_write` and `gbx_zarr_register` keep path strings in the manifest unless you pass `file_mode="auto"` or `"external"`.
  - Only `create` takes a `file_mode`.
  - A later `gbx_zarr_write` follows the store's own. It raises if you pass a different one.
- **`file_mode="external"` is available where the File type preview is on.** A store made or registered on a DBR 19 dedicated cluster in a workspace with the preview keeps FILE EXTERNAL references in its manifest. The cluster must have `fileReferenceCreationMode=MANAGED` in its config. The references are governed with the table.
  - `file_mode="auto"` picks FILE on any compute that supports FILE values. This includes Serverless where the workspace has the preview.
  - On the Databricks Container Service image, and where the preview is off, `auto` keeps path strings.
  - Spark cannot hash a FILE value. Leave the manifest's `file` column out of a `hash(*)` or a `GROUP BY`.
- **A store made in FILE mode needs FILE-enabled compute to read, write and maintain.** The Databricks Container Service image and compute in a workspace without the preview cannot commit FILE values. `gbx_zarr_read`, `gbx_zarr_write`, `gbx_zarr_sync`, `gbx_zarr_export` and the maintenance functions stop there with a `ZarrUnsupported` before they write anything.
  - To move a FILE store there, copy it with `gbx_zarr_export(method="copy")` on a cluster that has FILE. Register the copy with `file_mode="fuse"`.
  - FILE mode also makes registering about 3 times slower.
- **`file_mode="managed"` is not available in 0.6.0.** Delta `VACUUM`, a deletion-vector delete and `REORG TABLE ... APPLY (PURGE)` never reclaim a managed file's bytes. It raises `ZarrUnsupported`. Use `"fuse"` (default), `"auto"` or `"external"`.
- **A copy export needs a path every node sees.** `gbx_zarr_export(method="copy")` is written by the cluster's tasks. A `to` on the driver's local disk is refused before any task runs (`ValueError`, "export to a /Volumes path"). A single-node session can still copy to a local path.
- **Reading a reference file needs fsspec 2024.12.0 or later.** Databricks runtimes preinstall fsspec 2023.5.0. It cannot open a reference file written by `gbx_zarr_export(method="reference")` (`ReferenceNotReachable`). Upgrade fsspec on the compute that reads the reference. GeoBrix does not pin it, because `s3fs`, `gcsfs` and `adlfs` on the runtime share it.

## File {#file}

### `gbx_file_write` defaults to `fuse` (breaking behavior change) {#file-write}

- **`gbx_file_write` and `open_for_write` default to `file_mode="fuse"`.** The default was `"auto"`. It wrote a FILE column wherever the runtime had one, so other compute could not read or append to a table written on FILE compute. With no `file_mode`, they now write a plain Delta table (a path string and the raster bytes) that reads everywhere.
- **Migration.**
  - Pass `file_mode="auto"` to use FILE where the runtime supports it.
  - Pass `"external"` or `"managed"` to ask for FILE references.
  - Passing `filespace=` with no `file_mode` still asks for FILE MANAGED. It writes managed where the runtime has FILE, and raises an error where it does not.

## Containers (Databricks Container Service) {#dcs}

### A Databricks Container Service image for dedicated clusters (new) {#dcs-image}

- **A GeoBrix image runs every function, and the JVM engine, on a dedicated cluster.** The tags are:
  - Graviton (arm64): `mjohns797/geobrix:<version>-env6-arm` (pinned to a release) and `mjohns797/geobrix:env6-arm` (newest release).
  - x86 (amd64): `mjohns797/geobrix:<version>-env6-x86` and `mjohns797/geobrix:env6-x86`.
- **Contents.** The images are built on the DCS vNext environment 6 images. They carry:
  - The env6 wheel, installed with `[vizx]`. Its GDAL 3.13.3, PROJ 9.9.0 and GEOS 3.15.0 serve both tiers, with GDAL's Java (JNI) bindings.
  - The GeoBrix JAR in `/databricks/jars`.
  - A link from `/usr/local/hdf5/lib/plugin` to the wheel's HDF5 filter plugins. By design, the heavyweight tier then reads zstd, blosc and bzip2 netCDF-4 with no setting. This is untested on a cluster.

  Each release attaches `geobrix-<version>-dcs.Dockerfile` to the GitHub release. The build installs wheels from a hashed lock and compiles no GDAL. See [Build your own image](./installation/dcs#build-your-own-image).
- **Use.**
  - Start a dedicated cluster on DBR 19 from the tag that matches its instance architecture.
  - Set `spark.databricks.unityCatalog.volumes.enabled true`.
  - There is no cluster library to attach.
  - A cluster should have only one GeoBrix JAR, so do not attach it again.
- **Limits.**
  - GeoBrix built the images and ran their in-image checks. It has not yet run them on a cluster.
  - DBR 17.3 / 18 images are not available. Install the env5 wheel and the JAR as cluster libraries.
  - On a DCS cluster, h5py with `hdf5plugin` can see the plugin directory the image links, so a blosc write with h5py may fail. See [netCDF-4 filters and h5py](./installation/dcs#netcdf-filters).
  - The JVM engine needs dedicated compute. On standard access mode and Serverless, every function still runs in Python.

See [Databricks Container Service](./installation/dcs.mdx) and [Choose an install path](./installation.mdx#choose-an-install-path).

The fixed releases of `httpx2` (2.12 or later) and `httpcore2` (2.10 or later) need `idna` 3.18 or later. With `idna` held at the runtime's copy, pip fell back to `httpx2` and `httpcore2` 2.3.0, which have high-severity advisories.

  - See [Installation](./installation).
- **Photogrammetry packages.** `pycolmap` and `pycolmap-cuda12` move to 4.2.1.
- **The env 5 and 6 wheels ship GDAL's own Python bindings.** `xarray-spatial`, `numba` and `rio-cogeo` are no longer installed.

  - GDAL's viewshed and COG driver replace `xarray-spatial` and `rio-cogeo`. `rst_cog_convert` takes the same profile names.
  - GeoBrix now installs `xarray` itself.
- **JAR contents.** The GeoBrix JAR no longer bundles the Scala standard library (Databricks Runtime provides it) or `proj4j` (unused). It bundles `h3` 3.7.3, the version DBR 17.3, 18 and 19 ship. Nothing changes for users.

## Examples {#examples}

- **Wireless Coverage Lakeflow: `wc_lidar_pts` is a streaming table (behavior change; upgrade step).** The silver LiDAR table reads, with `read_paths`, only the `.laz` tiles that reached the `laz_inventory` stream since the last update.
  - **Upgrading a deployment** needs a one-time rebuild. The first update fails with `CANNOT_CHANGE_DATASET_TYPE`, which a full refresh does not fix. Run `DROP MATERIALIZED VIEW <catalog>.<schema>.wc_lidar_pts` once, then run the pipeline.
  - Rows keep the settings of the update that read them.
    - After changing `full_aoi`, `tile_m` or `srid`, run the pipeline with `--full-refresh wc_lidar_pts`.
    - After changing `laz_dir`, use `--full-refresh laz_inventory,wc_lidar_pts`.
    - Tiles deleted from the Volume keep their points until such a reset.

  See [Wireless Coverage](./notebooks/wireless-coverage).
- **The advanced library-integration page no longer shows a PDAL example.** The rasterio and xarray sections are unchanged. GeoBrix reads point clouds itself with the `lidar_gbx` reader. See [Third-party library integration](./advanced/library-integration).
