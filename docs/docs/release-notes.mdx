# Release Notes

:::info Current version: 0.6.0
:::

This page tracks **API and naming changes** across GeoBrix releases — the single place to look up what changed and why.

---

## What's new in v0.6.0

:::note
v0.6.0 is under development and not yet released.
:::

Incremental ingestion of new and changed files with Auto Loader that sets unreadable data aside
instead of failing, a multi-format Lakeflow connector, a Databricks Container Service image that
runs both tiers on dedicated clusters, fixes for very large and domain-coded vector sources and
one field-type mapping shared by both vector reader tiers, and raster tessellation whose
centroid chips match across tiers and scale to scene-sized tiles, with tiling that keeps every
window in both tiers.

### Incremental ingestion — `read_paths` and `declare_ingest` (new)

- **`read_paths` reads a DataFrame of file paths with any lightweight reader.** Give it a batch
  listing or an Auto Loader stream and the name of a reader (`vector_gbx`, `shapefile_gbx`,
  `geojson_gbx`, `geojsonl_gbx`, `gpkg_gbx`, `file_gdb_gbx`, `lidar_gbx`, `exif_gbx`,
  `raster_gbx`, `gtiff_gbx`, `cog_gbx`, `netcdf_gbx` or `pmtiles_gbx`); rows carry the reader's
  columns plus `_source_path` and `_source_mtime`. Raster, COG and PMTiles files are planned into
  tile windows or tile groups that spread across tasks when `num_partitions` is set; a NetCDF
  file is read by one task. `pmtiles_gbx` needs the `source` option: `"archive"` reads the
  tiles stored in `.pmtiles` files and `"raster"` renders tiles from GeoTIFF files, each file on
  its own. See [`read_paths`](./ingestion/read-paths).
- **`declare_ingest` declares an Auto Loader flow in a Lakeflow pipeline**, with `on_change`
  choosing what happens when a file is overwritten: `scd2` (the default; rows are append-only and
  a versions table with a `_current` view records each content version), `replace` (latest content
  only) or `append` (every delivery). See [Auto Loader ingestion](./ingestion/auto-loader).
- **GeoJSON is matched by its `.geojson` extension only.** The default file pattern for
  `geojson_gbx` (and `vector_gbx`) does not include `.json`; for GeoJSON files with that
  extension pass `glob="*.{geojson,json}"`.

### Bad data in ingestion — `on_error` (new)

- **`declare_ingest` sets bad records aside.** With `on_error="quarantine"` (the default), each
  file is read on its own: what cannot be read is written to `<table>_bad_records` (created when
  the first one is found) and the rest goes to the table, including the rows read from a file
  before an error in it. `on_error="fail"` fails the update on the first error, with an error that
  names the file. With `on_change="append"` there is no bad-records table: bad records are skipped
  with a warning in the executor logs. See [Unreadable data](./ingestion/auto-loader#unreadable-data).
- **`<table>_bad_records` says which file, where in it and why.** One row per bad record:
  `_source_path`, `_source_mtime`, `_source_hash`, `_source_size`, `record_index` (`NULL` for the
  whole file), `error_class`, `error_message`, `raw` (what could be recovered, as JSON of at most
  4096 characters) and `quarantined_at`. See
  [Query the bad records](./ingestion/auto-loader#query-the-bad-records).
- **A bad record is the smallest part of a file its reader can set aside:** a vector feature
  whose geometry bytes are not readable or whose text is not valid UTF-8, a GeoJSONSeq line, a
  GeoPackage feature on a corrupt page (by `fid`), a raster tile window, a run of LiDAR points, a
  PMTiles tile, a NetCDF variable or slice, a `.jpg` that is not a JPEG, or the whole file. A LAZ
  file with a corrupt chunk keeps the points around it, a truncated LAS file keeps its complete
  points, and a NetCDF-3 file shorter than its header declares is set aside (CDF-5 files are read
  as they are). See [Unreadable files](./ingestion/read-paths#unreadable-files) for each format.
- **A LiDAR file is given up only after a long run of unreadable points.** When `on_error` is
  `skip` or `quarantine`, the rest of a LAS or LAZ file is set aside (as one record) only after
  `max(3 × chunkSize, 250,000)` points in a row could not be read, so one corrupt LAZ chunk never
  ends the read, whatever `chunkSize` is.
- **LiDAR points far outside the header's bounds are set aside.** When `on_error` is `skip` or
  `quarantine`, a point outside the bounds the file's header declares, widened on every side by
  their largest extent (of x, y and z), is a `PointOutOfBounds` record. Damaged LAZ data can
  decode without an error into points that are not in the file; they land far away, so this check
  catches them, as it does garbled point records. The margin is wide so that a header whose bounds
  were not updated after points were added or moved keeps those points. Turn it off with the
  `lidar_gbx` option `checkHeaderBounds="false"`. See the [LiDAR reader](./readers/lidar#options).
- **An implausible LAZ chunk table is set aside before decoding, and reads take their limit from
  it when `on_error` is `skip` or `quarantine`.** A LAZ file whose chunk table or LASzip record is
  implausible or cannot be decoded is set aside instead of ending the worker (an unreadable-file
  record when `on_error` is `skip` or `quarantine`, a warning and a skip otherwise), and so is one
  whose chunk table has more chunks than its header's point count needs. The LiDAR downloader and
  the point-cloud layer of `plot_static` raise a `ValueError` naming the file. When `on_error` is
  `skip` or `quarantine`, a header that declares more points than the chunk table holds is read up
  to the points the table holds, so a highly compressible file (50,000 identical points) is read
  in full rather than cut short by a guess at the size of a point. The LAZ decoder `lazrs` must be
  0.8.2 or later: the lightweight extras require it, because earlier versions print a Rust panic
  in the executor logs when a file declares more points than its chunks hold.
- **LAZ point data with a run of `0xFF` bytes is set aside before decoding.** The GPS-time decoder
  of `lazrs` (point formats 1 and 3 to 10; formats 0 and 2 are not affected) calls itself without a
  depth limit on such a run, as erased storage or a failed copy leaves, so its stack overflows and
  the whole worker process dies; no `on_error` setting could catch that. `lidar_gbx` now scans the
  compressed points of the chunks a read needs, ahead of the decoder, for 256-byte blocks that are
  at least half `0xFF`, and sets the file aside (an unreadable-file record when `on_error` is
  `skip` or `quarantine`, a warning and a skip otherwise). The LiDAR downloader and the
  point-cloud layer of `plot_static` raise a `ValueError` naming the file. The scan reads the
  compressed points once more, ahead of the decoder; on local storage that adds about 5 percent
  to the time it takes to decode them, up to about 10 percent when the file is not cached.
- **Other damage to a LAZ file can still stop the worker.** A run of `0xFF` bytes in the compressed
  points, and a chunk table or LASzip record that is implausible or cannot be decoded, are set aside
  before the file is decoded, but these checks look for those patterns only. Other damage inside
  the compressed points, a chunk table that is wrong but plausible, or a crafted file reaches the
  native LAZ decoder and can still crash it, until `lazrs` releases a fix for the underlying
  recursion. A crash cannot be caught, so the file is not set aside: the task is retried and then
  the update fails. Remove the file or replace it with a readable copy.
- **A NULL or empty geometry is data, not a bad record.** A feature without a location, a
  `POINT EMPTY`, and a curve or surface (with `asWKB="false"` those are set aside, because WKT
  cannot hold them) are written like any other row. GDAL also returns NULL for a geometry it cannot
  decode, so such a feature is written with a NULL geometry; query the geometry column with
  `IS NULL` and `ST_IsEmpty` to watch for them. A JPEG without an end marker (a truncated scan, a
  Motion Photo) and a very large JPEG are read as well, and the records a `.dbf` marks deleted
  are not counted as features that went unread.
- **Errors of the environment fail the update instead.** Out of memory, a missing module (such as
  a LAZ decompression backend), an I/O error of the Volume (retried first) and an image too large
  for `exif_gbx` `qc` mode are not about the data, so no bad record is written: the task is
  retried, or the update fails with that error.
- **A delivery set aside entirely is not read again.** A delivery none of whose rows could be
  read gets one `NothingReadable` bad record, and an identical re-delivery is skipped. To read it
  again, after fixing a reader option for example, delete the file's `NothingReadable` rows from
  `<table>_bad_records`, then touch the file or deliver it again. A delivery that was partly read
  is skipped as stored: delete its rows for that `_source_hash` from the table first, or deliver
  changed content.
- **`scratch_dir` sets where a micro-batch is staged.** Quarantine reads the files once and stages
  the micro-batch in a hidden `.gbx_scratch` folder under `scratch_dir` (a `/Volumes` folder;
  default `source_dir`), in a subfolder for each target table that is removed when the
  micro-batch ends; one left by a killed micro-batch is removed after 24 hours. The pipeline must
  be able to write there, so a read-only landing folder needs a `scratch_dir` it can write (or
  `on_error="fail"`). Bad records are appended before the rows, skipping those already there, so a
  retried micro-batch neither loses nor repeats them.
- **`<target>_current` shows each file's newest readable version.** A file whose latest delivery
  could not be read keeps showing the rows of its last readable version. An existing `_current`
  view is replaced when its definition differs, the next time a micro-batch writes rows. Under
  `on_change="replace"`, a file keeps its last readable rows when its new delivery cannot be read
  at all; a delivery that is partly readable replaces them with the rows that were read.
- **`read_paths(on_error="skip")` skips what cannot be read** and logs a warning in the executor
  logs; the default, `on_error="fail"`, fails the read with an error that names the file. The
  [Lakeflow connector](./ingestion/lakeflow-connector) always fails the read on an unreadable file.

### Lakeflow connector — one multi-format connector (new)

- **The `geobrix` connector reads vector, LiDAR, EXIF, GeoTIFF, COG, NetCDF and PMTiles files**
  with the same code as `read_paths`. A folder that mixes file kinds needs the `format` table
  option. A `.tif` file is read as GeoTIFF (set `format: cog` for the COG reader), a `.nc` file as
  NetCDF, and a `.pmtiles` file reads the tiles stored in the archive. A `.json` file is not taken
  for GeoJSON: set `format: geojson` and a `file_glob` such as `*.{geojson,json}`.
- **`format` takes a reader name, as `read_paths` does.** The `_gbx` suffix is optional and case
  is ignored (`gpkg`, `GPKG` and `gpkg_gbx` are the same reader). The File Geodatabase reader is
  `file_gdb`.
- **Table options apply only to the readers that take them.** `layer`, `where`, `bbox` and
  `chunk_size` apply to the vector readers and `mode` to `lidar`, `exif` and `netcdf`. Set on a
  table read with another reader, such an option fails with an error that names it.
- **`file_glob` uses the same Hadoop glob syntax as `glob`** (case-sensitive, with `{a,b}`
  groups and `\` escapes). Folders and files whose names start with `_` or `.` are ignored, so
  `_archive/` or `_staging/` keeps files out of a table.

See the [Lakeflow connector](./ingestion/lakeflow-connector) page for setup, table options and
formats.

### Vector readers — large layers and coded-value domains

- **Lightweight vector readers stream large layers.** `vector_gbx`, `file_gdb_gbx`,
  `gpkg_gbx`, `shapefile_gbx`, `geojson_gbx` and `geojsonl_gbx` now read a layer in batches
  of `chunkSize` features instead of loading it whole, and split any batch that would come
  close to Arrow's 2 GiB per-column limit. Layers with more than 2 GiB of geometry — which
  previously failed with `ArrowInvalid: offset overflow while concatenating arrays` after
  parsing the whole layer — now read normally, and memory per task scales with `chunkSize`
  rather than layer size. A single value too large for any Spark row fails with an error
  naming the layer, column, and feature. See [Vector Readers](./readers/vector#options).
- **Coded-value domain fields read correctly.** FileGDB and GeoPackage fields bound to a
  coded-value domain no longer fail with `Cannot call the method "getInt"`; they return the
  stored code in the field's declared type — the same values the heavyweight readers return.
  The new lightweight-only `codedDomains` option (`"code"`, the default, or
  `"description"`) returns the domain's descriptions as strings instead. See
  [FileGDB Reader](./readers/filegdb#options) and
  [GeoPackage Reader](./readers/geopackage#options).
- **`vector_file_read` streams its sources.** The function-layer FILE read now streams each
  source layer in bounded batches as well, so very large layers read without exhausting
  memory or exceeding Arrow's per-column limit.

### Vector readers — `driverName` is honored (behavior change)

- **A requested driver is no longer silently ignored.** `vector_gbx` with a `driverName`, and the
  named readers (`geojson_gbx`, `gpkg_gbx`, `shapefile_gbx`, `file_gdb_gbx`), used to let GDAL pick
  whichever driver it detected. `driverName` is now matched without regard to case, and GDAL's
  equivalent drivers are accepted: the GeoJSON family (GeoJSON, GeoJSONSeq, ESRIJSON, TopoJSON and
  JSON-FG), KML and LIBKML, OpenFileGDB and FileGDB, and GPKG and SQLite. A file GDAL would open
  with a different driver is read with the requested one where GDAL can force it (the GeoJSON
  family, GPKG and CSV, also when GDAL recognizes nothing). Any other family with a misnamed file
  fails with an error that names the file, the driver GDAL detected and the reader to use. A
  `driverName` GDAL does not know fails with the closest matches. See
  [Vector Readers](./readers/vector#options).
- **Limit: a given schema skips the driver check for native extensions.** When you pass your own
  `.schema(...)`, a file with an extension GDAL reads by itself is not checked against the
  requested driver, because pyogrio does not expose the driver when it reads.

### Heavyweight vector readers — declared field types and NULLs (breaking behavior change)

- **Heavyweight vector readers return the declared OGR field types and keep NULLs.** The
  `*_ogr` readers previously inferred each attribute's type from sampled values — OGR
  `Integer` fields came back as `bigint`, and `String` fields holding numeric-looking text
  came back as numbers — and returned unset fields as `0` / `""`. They now use each field's
  declared OGR type (`Integer` → `int`, `Integer64` → `bigint`, `String` → `string`,
  `Real` → `double`, `Integer` with the Boolean subtype → `boolean`) and return `NULL` for
  unset fields, matching the lightweight `*_gbx` readers. Cast explicitly where code relied
  on the old types.
- **OGR `Time` fields read as text in both tiers.** Spark has no time-of-day type, so a
  `Time` field (for example a GeoJSON property such as `"12:34:56"`) now reads as a
  `string` in GDAL's `HH:MM:SS` form (`HH:MM:SS.sss` with milliseconds). The lightweight
  readers previously failed on these fields with `Cannot call the method "getLong"`.

### Heavyweight vector readers — unreadable files fail the read (behavior change)

- **A file the heavyweight vector readers cannot plan now fails the read.** Previously an
  explicit-schema or directory read of an unreadable file, a path that does not exist, or a
  `layerName` / `layerNumber` the file does not have silently returned 0 rows (or dropped that file
  from a directory). The read now fails with an error that names each such file (up to five), the
  driver, and the message GDAL gave.
- **Directory reads skip files that are not datasets of the requested format.** Metadata files next
  to the data (`.shp.xml`, `.aux.xml`, `.txt`, `.md`) are skipped, and so are files of another
  vector format when you use a named reader or `ogr` with a `driverName`, each with a warning in
  the driver log that names them. A folder holding a README or an ArcGIS metadata file next to its
  shapefiles keeps reading, and a `.txt` or `.md` file no longer becomes the schema source of a
  folder. A file you name as the path is never skipped, and a directory in which every file is of
  another format fails the read, naming the files and the reader to use, instead of returning no
  rows. See [Vector Readers](./readers/vector?tier=heavyweight#unreadable-files).
- **Paths with a space or another special character read.** A file or folder such as
  `/Volumes/main/data/my maps/city #1.geojson` failed with the heavyweight vector readers
  (the name reached the copy step URL-encoded, as `my%20maps`). It now reads, and so does a
  `netcdf_gdal` read of such a path. An empty folder with a space or a `%` in its name reads as
  0 rows when you pass a `.schema(...)`; it failed to plan.
- **A folder that cannot be listed fails the read.** When listing a folder for the heavyweight
  readers failed, the folder read as empty and returned 0 rows. The read now fails with an error
  that names the folder and the cause.
- **Fewer empty partitions and no leftover temp folders.** A layer whose feature count is an exact
  multiple of `chunkSize` no longer gets an empty trailing partition, and schema inference no
  longer leaves a staging folder in the driver's temp directory for each read, or keeps the
  inspected dataset open.

### Heavyweight vector readers — `layerNumber` reads the layer it names (fix)

- **`layerNumber` picks the layer the heavyweight vector readers return.** A read with a
  `layerNumber` above 0 and no `layerName` took its schema and row counts from that layer but
  returned the rows of layer 0, so the result was wrong without an error. It now returns the rows
  of the layer at that index. A `layerName` still wins over `layerNumber`, even when the index is
  one the file does not have (that read used to fail), and a `layerNumber` the file does not have
  fails the read and lists the file's layers. The option is `layerNumber` in both tiers: the
  heavyweight reader pages listed it as `layerN`, which was never read, so a read that passed
  `layerN` got layer 0. See [Vector Readers](./readers/vector#options).

### Reader staging cache

- **Staged copies no longer accumulate on worker disks.** The lightweight readers copy
  GeoPackage, FileGDB and (for windowed decodes) raster sources to worker-local disk before
  reading them. Those copies were kept for the life of the worker process and were not
  cleaned up when Spark ended the worker, so long-running clusters could fill local disk.
  The cache is now bounded — least recently used idle copies are removed, capped at half the
  available local disk by default or at `GBX_STAGE_CACHE_MB` — and copies left by exited
  workers are removed. See [Serverless and Memory](./serverless-and-memory).
- **Files replaced at the same path are re-read.** The lightweight readers now stage a new copy
  when a GeoPackage, FileGDB or raster is replaced at the same path. Previously a worker that had
  already staged the old file could keep serving the stale copy.
- **The heavyweight readers delete their staged copies too.** `gdal`, `gtiff_gdal`, `netcdf_gdal` and
  the OGR vector readers (`ogr`, `shapefile_ogr`, `geojson_ogr`, `gpkg_ogr`, `file_gdb_ogr`,
  `netcdf_ogr`) copy a Volume or cloud source to worker-local disk before GDAL opens it. Those copies
  were never deleted. A copy is now deleted once no read is using it, after an idle period that lets
  the next partition of the same file reuse it. For example, the chunks of a large GeoPackage that
  a worker reads share one copy instead of each copying the whole file again. The idle period is 60
  seconds by default. Set it with the Spark conf `spark.databricks.labs.gbx.nodecache.retention.ms`
  as a duration such as `60s` or `500ms` (a bare number is milliseconds); `0` deletes a copy as soon
  as its last read ends.
- **The heavyweight readers re-read a file replaced at the same path.** A copy is reused only while
  the source's size and modification time are unchanged, so a file rewritten in place is copied
  again. Previously a worker could keep reading its earlier copy.
- **The heavyweight `gdal` and `gtiff_gdal` writers replace an output of the same name**: an `append`
  write used to keep an older file of the same size instead of the new tile, and every write of a
  directory format such as Zarr failed while removing its local working copy.

### PMTiles reader

- **`pmtiles_gbx` no longer reads the whole archive once per partition.** With `source="archive"`,
  planning now reads only the archive's header and directories, and each worker process stages the
  archive once and reads just the tile ranges of each partition, so the read cost no longer grows
  with the number of partitions. With `source="raster"`, each source raster is staged once per
  worker process instead of once per partition. See [PMTiles Reader](./readers/pmtiles).
- **A damaged PMTiles header cannot crash a worker.** Range reads stop at the end of the file,
  so an archive whose header declares a length far beyond its end fails with an error instead of
  trying to allocate that many bytes.
- **`pmtiles_gbx` reads archives with uncompressed directories (fix).** The heavyweight `pmtiles`
  writer stores its root directory and metadata uncompressed, as the PMTiles v3 spec allows, but the
  reader always gunzipped directories, so an archive written by the heavyweight writer failed to
  read back with `Not a gzipped file`. The reader now decodes directories by the compression the
  archive header declares: none and gzip are read, and any other compression fails the read with an
  error that names it.
- **`pmtiles_info` and the `gbx.vizx` PMTiles viewers read the same archives (fix).** They failed
  with `Not a gzipped file` on an archive written by the heavyweight `pmtiles` writer, and a
  viewer could show no tiles instead of an error. They now decode directories by the compression
  the archive header declares, as `pmtiles_gbx` does, so none and gzip are read. `pmtiles_info`
  fails with `internal compression ... is not supported` on an archive that declares its directory
  compression as unknown, brotli or zstd, including an archive that declares unknown but stores
  gzip directories, which it used to read; the viewers treat such an archive as unreadable.
  `pmtiles_info` also no longer imports PySpark or rasterio.

### NetCDF reader

- **`group` is honored when a variable is read without decoding (fix).** When xarray cannot apply
  a variable's CF masks (for example, integer data with an integer `scale_factor`), `netcdf_gbx`
  reads the raw values instead. That read opened the file's root group, not the `group` you set:
  a variable of the same name in the root returned the root's values, silently wrong data (this
  also affected v0.5.2), and a variable only in the group failed with `No variable named …`. Both
  now read the group.

### Raster writers

- **The heavyweight `gdal` writer writes Zarr with its default options.** The default compression,
  DEFLATE, is a TIFF codec name the Zarr driver does not have, so a Zarr write failed with
  `Compressor/decompressor for DEFLATE not available` unless the tile's `compression` named a Zarr
  codec. The writer now writes DEFLATE as `ZLIB` (the same zlib stream, with `zlevel` as its level)
  and keeps `ZSTD` (with `zstd_level`); `NONE`, `GZIP` and `LZMA` pass through. Any other codec,
  such as `LZW`, raises an error that names the codecs the Zarr driver of the GDAL build does have.
- **The heavyweight `gdal` and `gtiff_gdal` writers refuse an output name that leaves the target
  directory.** A `nameCol` value with a `..` segment or starting with `/` would have written outside
  the target (an absolute name also left its file behind); the write now raises and names the value.
- **`cog_gbx` writes sources with a non-byte-aligned bit depth.** Rasters whose band is
  tagged with an `NBITS` such as 15 (common for Sentinel-2 `uint16` products) failed to
  convert with `PREDICTOR=2 is only supported with 8/16/32/64 bit samples`. The writer now
  promotes such samples to the data type's full width, a lossless change, and keeps
  predictor-based compression.
- **`cog_gbx` names the parts of one source apart.** Tiles from the retile functions share
  their parent's cellid and source, so with no `nameCol` a tile that is only part of its source
  (a window or clip, or one band from `rst_separatebands`) is now written as
  `<source name>_<key>.tif`, and a tile with no path or source as `<cellid>_<key>.tif` (it was
  `<cellid>.tif`). The key is derived from the tile, so a re-run writes the same names. A tile
  read whole from a file keeps the plain source name: it has a path and its window is its own
  full extent. This relies on tile provenance: the lightweight `rst_retile`,
  `rst_tooverlappingtiles` and `rst_maketiles` now record each tile's pixel window in
  `tile.window`, relative to its immediate input tile, so windows from different parents can
  repeat (the first piece of every parent sits at the origin). A function that returns one tile
  covering its whole input hands that tile the input's own provenance instead. The lightweight
  `rst_separatebands` records the 1-based band in `tile.metadata['band']`, and the retile functions
  keep that marker on the pieces they cut from a band. The heavyweight
  retile-family functions record none of these, so set `nameCol` when you write heavyweight
  parts; pixels are identical across tiers. The first tile of a materialized split read is
  indistinguishable from a whole-file read of the same source, so if you write one source both
  ways into the same directory, set `nameCol`.

### Vector writers — `file_gdb_gbx` on any compute, timestamps on Serverless (behavior change)

- **`file_gdb_gbx` writes File Geodatabases with the lightweight tier alone.** The writer used
  to need native GDAL (`osgeo`) and so ran only on classic x86 clusters with the init script.
  It now encodes the `.gdb` through pyogrio's bundled OpenFileGDB driver, so FileGDB writing
  is lightweight and runs on Serverless, standard and dedicated clusters, on x86 and ARM, with
  no extra install. The output layout, `zip=true`, the shared schema and the other options are
  unchanged, and the driver still assembles the file in one pass.
- **Column types follow the DataFrame types.** An `int` column stays a 32-bit integer and a
  `smallint` a 16-bit integer in the layer; the earlier encoder wrote both as doubles. A
  column named `shape` (any letter case) is refused with a clear error, because the layer's
  geometry field is `SHAPE`.
- **New option `targetArcGisVersion`** (`auto`, `ALL` or `ARCGIS_PRO_3_2_OR_LATER`) decides which
  Esri clients can open the layer. By default (`auto`), a DataFrame with a long (64-bit integer),
  date or timestamp column targets ArcGIS Pro 3.2 or later, so those columns keep their exact
  types (64-bit integer, date-only and timestamp-with-offset fields) instead of being rounded to
  a double or written as a date-time with no offset; the whole layer is then marked as needing a
  3.2 client, and an older Esri client may refuse to open it. A DataFrame without such a column
  is written for every client, and `ALL` forces that. GeoBrix's readers and any reader built on
  GDAL 3.11 or later open a Pro 3.2 layer. See [GeoDatabase Writer](./writers/filegdb).
- **Timestamp columns work in the lightweight vector readers and writers on Serverless.** A
  layer with a date-time field (or a DataFrame with a timestamp column) failed to read or write
  on Serverless compute with `AssertionError`, because those workers have no session time zone
  for PySpark to type the column with. Timestamps are now read and written as UTC, and a
  written timestamp is exact on a worker whose time zone is not UTC.
- **`netcdf_gbx` writes a timestamp attribute as a CF time variable.** A vector write with a
  timestamp column failed (in the task for the default write, when the files were merged for
  `singleFile`). The column is now written as seconds since 1970-01-01 00:00:00 UTC with CF
  `units` and `calendar` attributes, a null timestamp is the fill value, and `merge` keeps the
  units. See [NetCDF Writer](./writers/netcdf).

### Grid explode functions — `bng_tessellateexplode` columns (behavior change)

- **Heavyweight `bng_tessellateexplode` now returns `core` and `chip`, like the lightweight tier.**
  It declared a single column, so the `core` flag and the chip geometry were dropped from every
  result. It now returns `cellid` (STRING), `core` (BOOLEAN) and `chip` (BINARY, WKB), for a WKB or
  a WKT geometry alike, as the lightweight tier and `bng_tessellate` do. `keep_core_geom` is an
  optional third argument that defaults to false in every API (the SQL function takes two or three
  arguments; the Python wrapper's default changes from true to false, and the Scala two-argument
  wrapper now passes false instead of true): a core cell's `chip` is NULL
  unless you ask for it, and border cells always carry their geometry. A query that named the whole
  generator output with one alias (`.as("chip")`) now needs one name per column, or none.
- **Heavyweight Python `bng_kringexplode`, `bng_kloopexplode`, `bng_geomkringexplode` and
  `bng_geomkloopexplode` work.** They wrapped the generator in `explode(...)`, which Spark rejects
  as a generator nested in an expression (`UNSUPPORTED_GENERATOR.NESTED_IN_EXPRESSIONS`), so every
  call failed. They now return the generator Column: select it and it expands to one `cellid` row
  per cell.
- **Explode examples show each tier's form.** `FROM t, LATERAL f(...)` reaches only the
  lightweight table function. The SQL, Python and Scala examples of the heavyweight quadbin and
  custom-grid explode functions now call the generator with `LATERAL VIEW` or in the select list,
  and the H3 explode examples say that H3 geometry-aware functions are lightweight-only.

### Grid functions — `bng_tessellate` core geometry off by default (behavior change)

- **`bng_tessellate` defaults `keep_core_geom` to false in every API.** The two-argument SQL form
  returned a NULL core chip in the heavyweight tier but the cell geometry in the lightweight tier,
  and the Scala and Python wrappers of both tiers defaulted to true. All now default to false, as
  `bng_tessellateexplode` does: a core cell's `chip` is NULL unless you pass `keep_core_geom` as
  true (the Scala wrapper gains overloads that take it). Pass true to keep the old wrapper result.

### Grid functions — `bng_tessellate` keeps cells that clip to a MultiPolygon or a mixed collection (fix)

- **A polygon no longer loses cells when its clip is a MultiPolygon or a mixed collection.** A valid
  polygon can clip to a cell as a MultiPolygon, or as a GeometryCollection that holds polygons plus a
  point or line along the cell edge. The heavyweight `bng_tessellate` returned NULL for the whole
  polygon and `bng_tessellateexplode` returned no rows, because the clip failed on the collection;
  the lightweight tier returned fewer cells than the polygon covers, and dropped every border cell
  of a MultiPolygon input. Both tiers now keep the polygonal part of every clip and return the same cells
  and chips. A MultiPolygon input returns its Polygon chips, and a polygon's chip can be a
  MultiPolygon. Points and lines that only touch a cell edge are still dropped, so a polygon aligned
  to the grid produces no degenerate chips. Results for polygons that clip to plain Polygon chips do
  not change.
- **A GeometryCollection that holds a large polygon is tessellated.** When a collection's polygons
  were big enough to leave core cells after the tessellation shrinks them, the call failed before any
  cell was clipped: the heavyweight `bng_tessellate` returned NULL (and `bng_tessellateexplode` no
  rows), and the lightweight tier raised an error. Both tiers now tessellate the union of the
  collection's polygons, at any nesting depth, so two polygons that share an edge give the same cells
  as the polygon they form. A line or point in the collection can remain in the chip of a cell the
  polygons also touch, but never yields a cell of its own.

### Raster tiling functions

- **Raster generator examples show each tier's form.** The SQL and Python examples of
  `rst_retile`, `rst_tooverlappingtiles`, `rst_separatebands`, `rst_maketiles`,
  `rst_custom_tessellate`, `rst_xyzpyramid`, the `rst_*_tessellate` functions and the
  `rst_*_rastertogrid*` reducers mark each statement as the heavyweight or the lightweight form.
  Heavyweight generators are called in the select list or with `LATERAL VIEW`, and the heavyweight
  reducers return an ARRAY that `posexplode` and `inline` flatten to the same rows the lightweight
  table functions yield. Several heavyweight examples, and `DESCRIBE FUNCTION` for the tiling
  generators, showed `FROM t, LATERAL f(...)`, which reaches only the lightweight table function.
- **Heavyweight tiling and tessellation functions return their error row.** When a tile cannot be
  read, `rst_retile`, `rst_separatebands`, `rst_tooverlappingtiles`, `rst_maketiles` and the four
  `rst_*_tessellate` functions now return one row whose `tile` holds the error tile, as
  [Error handling](./api/error-handling#generators) describes; they failed the query with a
  `ClassCastException` instead. `rst_maketiles` with a size of 0 or less should hand the tile back
  unchanged as one row, but the row was malformed and its `tile` could not be read; it now holds the
  tile. The heavyweight `rst_xyzpyramid` returns one row with a NULL `tile` for a raster it cannot
  read, since its `(z, x, y, bytes)` struct cannot hold an error tile. A bad argument raises its own
  message instead: an unknown `format`, `resampling` or `rescale`, a `size` outside (0, 4096], a
  `max_z` above the cap, or a tile count above the limit.
- **Heavyweight `rst_tilexyz` raises for a bad parameter.** An unknown `format`, `resampling` or
  `rescale`, or a `size` outside (0, 4096], returned a transparent PNG, which hid the typo; it now
  raises its message, as `rst_xyzpyramid` and the lightweight tier do. A tile that cannot be read or
  rendered still returns a transparent PNG, never NULL.
- **Corrupt tiles yield an error row again.** The lightweight `rst_separatebands`,
  `rst_retile` and `rst_tooverlappingtiles` table functions are meant to emit one error tile
  (NULL raster, the error in `metadata.last_error`) for an unreadable input. They instead
  failed the query with `UDTF_RETURN_SCHEMA_MISMATCH`, because the error tile lacked the newer
  tile-struct fields. They now emit the error row as intended.

### Raster tiling and tessellation — tier parity and large rasters (behavior change)

- **Centroid chips are cropped to their cell.** With `assignment='centroid'` (the default),
  `rst_h3_tessellate`, `rst_quadbin_tessellate`, `rst_bng_tessellate` and `rst_custom_tessellate`
  crop each chip to the window of the pixels assigned to its cell, in both tiers. Pixel values and
  positions are unchanged, but a chip's width, height and geotransform are now its own, not the
  source's: code that assumed every chip has the source extent (for example stacking chips as
  same-shape arrays) needs to change. Chips are much smaller, about 5× fewer bytes on an
  11k × 11k pixel scene. Under `coverage='complete'`, a covered cell that received no pixel is a
  1×1 all-NoData chip at the cell's centroid pixel in both tiers; the heavyweight tier emitted a
  source-sized chip. Both tiers now produce the same chip for each cell.
- **Scene-sized tiles no longer time out.** Each centroid chip was built over the whole raster,
  so the work grew with the number of cells times the number of pixels, and tessellating a
  scene-sized tile could run past a task timeout in either tier. Chips are now built from their
  own window, and pixels are assigned to cells a strip of about one million pixels at a time, so
  memory grows with the pixel count, not with cells × pixels (about 23 bytes per pixel in the
  lightweight tier; a 4-byte label per pixel plus one strip in the heavyweight tier). For very
  large scenes, running `gbx_rst_retile` first spreads the work across tasks; a cell on a seam
  between tiles then appears once per tile it overlaps. See
  [Grid Raster Tessellation](./api/grid-raster-tessellation#large-rasters).
- **Both tiers keep the same covered cells.** `coverage='complete'` and `assignment='covering'`
  keep a cell when it overlaps the raster footprint: the raster's edges, reprojected to the grid's
  coordinate system with points along each edge, so the curved edges of a projected (for example
  UTM) scene are followed. The lightweight tier used the scene's longitude/latitude bounding box
  and emitted empty cells outside the raster, and the heavyweight tier joined the reprojected
  corners with straight lines, which could drop a covering cell that holds edge pixels. On a
  110 km UTM scene at H3 resolution 7, both tiers now emit the same 2464 cells, in `covering` and
  in `centroid` with `complete`. `rst_h3_tessellate` and `rst_quadbin_tessellate` now raise an
  error when the footprint crosses the antimeridian or encloses a pole, instead of returning wrong
  cells or failing with a geometry error: reproject (for example to EPSG:4326) or split such a
  raster first.
- **One NoData fallback for sources without NoData.** Where a source declares no NoData, both
  tiers blank with the same value for its data type: 0 for `uint8`, 65535 for `uint16`, −32768
  for `int16`, 4294967294 for `uint32`, −2147483648 for `int32`, and the type's minimum for
  `float32` and `float64`. Source pixels equal to that value become NoData, for example the zeros
  of a `uint8` source. Heavyweight centroid tessellation blanked every integer type with 0, so
  the real zero pixels of a `uint16`, `int16`, `uint32` or `int32` source became NoData; they now
  stay valid (and float chips carry the type's minimum, not NaN). `covering` chips of such a
  source now carry this NoData in both tiers, so the pixels outside each cell read as NoData
  instead of as valid zeros. The lightweight `rst_initnodata` and `rst_threshold` use the same
  table: a `uint16` source gets 65535, as in the heavyweight tier (`rst_threshold` and
  tessellation failed on it, and `rst_initnodata` set nothing), and a `uint8` source now gets 0.
  The lightweight `rst_filter` min, max and median of a `uint8` source blank a window with no valid
  pixel with 0, where they failed on a NoData of -9999 that a `uint8` band cannot hold.
  On an integer band without NoData, heavyweight `rst_initnodata` kept the pixels equal to the
  fallback as valid data with the value moved by one (a `uint8` 0 became 1); it now marks them
  NoData, as the lightweight tier does. A source that carries its own mask band (not an alpha band)
  keeps that mask through `rst_initnodata` in both tiers, also when it declares NoData: its masked
  pixels become NoData. The lightweight tier used to drop the mask, and the heavyweight tier used
  to drop it when the source declared NoData, so the masked pixels read as valid data. In the
  [EO series](./notebooks/eo-series) notebooks 03 and 04, the `uint16` bands that pass through
  `rst_initnodata` now carry NoData 65535.
- **BNG tessellation marks the warp fill as NoData.** `rst_bng_tessellate` first warps a source
  that is not in EPSG:27700 to it. For a source with no NoData and no alpha band, both tiers used
  to fill the pixels outside the source's footprint with valid zeros, which reached the chips of
  the edge cells as data. That fill is now NoData, with the fallback value above, and source
  pixels equal to that value are NoData too. A source's own NoData is kept. A source with an alpha
  band is warped without a NoData, as before: its alpha band marks the fill and the transparent
  pixels, and the chips keep that alpha band (see the next entry). A source's own mask band (not
  an alpha band) is kept, also when the source declares NoData: both tiers used to let the masked
  pixels of a source that declared NoData through the warp as valid data.
- **Chips of a source with an alpha band keep it, in both tiers.** The alpha band of a raster is
  its last band, when that band is labelled alpha, as gdalwarp reads a source; a band labelled
  alpha anywhere else is ordinary data. Tessellating a source with an alpha band and no NoData
  (aerial imagery as RGBA, for example), the lightweight tier declared the NoData fallback (0 for
  `uint8`) on every chip, over the alpha band. That hid the alpha band, so the transparent pixels,
  whose colour bands are not 0, read as valid data in `centroid` chips, and reading the mask of a
  `covering` chip raised a `NodataShadowWarning`. The heavyweight tier did the same in the
  `centroid` chips of a source it does not warp: `rst_h3_tessellate`, `rst_quadbin_tessellate`,
  the custom grid, and `rst_bng_tessellate` of a source already in EPSG:27700. The chips in both
  tiers now keep the alpha band and declare no NoData: a pixel with alpha 0, and the part of a chip
  outside its cell, is NoData, and an opaque pixel whose colour bands are 0 stays valid. A chip is
  labelled alpha exactly where its source is: the fourth band of a `uint8` source without alpha
  (red, green, blue and near-infrared, for example) stays an ordinary band, and the alpha band of
  a 16-bit RGBA source stays alpha, in the heavyweight chips too.
- **A transparent pixel belongs to no cell.** Both tiers gave the pixels with alpha 0 to cells,
  so `rst_*_tessellate` with `assignment='centroid'` and `coverage='sparse'` emitted cells that
  hold only transparent pixels. A pixel is now valid when its alpha is above 0 and some data band
  is valid by its NoData or its mask, at every band count: GDAL derives a mask from an alpha band
  only for two- and four-band rasters, so a three-band gray-plus-extra-plus-alpha raster or a
  six-band one with alpha used to read as entirely valid, and `covering` with `coverage='sparse'`
  kept the chips that were entirely transparent. A pixel that is NoData in the colour bands is
  NoData also under an opaque alpha, when the source declares that NoData. A raster that is only
  an alpha band is judged by its alpha values.
- **Lightweight functions keep the alpha label of their source.** GDAL labels band 4 of every
  four-band `uint8` GeoTIFF alpha when it creates one, and drops the alpha band of a 16-bit RGBA or
  a gray-plus-alpha raster. The lightweight functions that write a raster from another one used to
  label the fourth band of a four-band raster without alpha (red, green, blue and near-infrared,
  for example) as alpha, which made that band a transparency mask, and lost the alpha band of other
  rasters. They now label a band alpha exactly where the raster they read does. This covers
  `gbx_rst_updatetype`, `gbx_rst_initnodata`, `gbx_rst_threshold`, `gbx_rst_setsrid`,
  `gbx_rst_setcrs`, `gbx_rst_filter`, `gbx_rst_convolve`, `gbx_rst_fillnodata`,
  `gbx_rst_percentile_stretch`, `gbx_rst_resample` and its variants, `gbx_rst_buildoverviews`,
  `gbx_rst_asformat` to GeoTIFF, `gbx_rst_cog_convert`, `gbx_rst_getsubdataset`, `gbx_rst_fromfile`
  with `materialize`, the merge family (`gbx_rst_merge`, `gbx_rst_merge_agg`, `gbx_rst_align_to`
  and the `gbx_rst_combine*` functions), the retile family (`gbx_rst_retile`,
  `gbx_rst_tooverlappingtiles`, `gbx_rst_maketiles`), the reads of a lazily read tile, and the tile
  encoders of the `raster_gbx` and `cog_gbx` writers.
- **A band selection writes the alpha band as data, unless it is selected last with a data
  band.** `gbx_rst_band` and `gbx_rst_separatebands` extract a band for its values, so the alpha
  band of an RGBA raster comes out as an ordinary band, valid wherever its own NoData says so, in
  both tiers. They used to keep the alpha label (the heavyweight tier, and the lightweight
  `gbx_rst_band` of a lazily read tile), which made the zero pixels of the extracted band NoData. A selection of
  several bands keeps the alpha label only when the source's alpha band is selected last with at
  least one other band; a band labelled alpha anywhere else in the source is ordinary data.
- **A raster with an alpha band and its own mask band keeps both.** GDAL reports only the own mask
  of a raster that has both, so the writers and warps that look for a mask band skipped every
  raster with an alpha band, and the pixels the mask hides came out valid. The lightweight
  encoders, writers and reprojections, and the heavyweight warp behind covering, `rst_initnodata`
  and the raster-to-grid reducers, now carry the mask beside the alpha band: a pixel is valid when
  a data band is valid, its alpha is above 0 and the mask says so. The heavyweight warp labels the
  alpha band alpha again in its output.
- **The remaining lightweight writers keep the alpha label and the own mask.** The `cog_gbx`
  writer's quadbin, h3 and BNG cells, and its `pruneEmpty` check (a window or cell with no valid
  pixel is not written, whether it is all NoData, all transparent or all masked); the COG
  re-encode of the `raster_gbx` writer; `gbx_rst_frombands` (a stack of four `uint8` tiles no
  longer gets an alpha band from GDAL's default); `gbx_rst_merge` and the streamed merge of large
  groups, whose mosaic carries the union of what each tile says is valid (a pixel is valid when
  any of its data bands is, by NoData or mask band, and, with an alpha band, opaque), so a valid
  pixel that holds 0 stays valid, a pixel with data in one band only stays valid, a tile's NoData
  pixels stay invalid beside a tile that has a mask band, and the result no longer depends on how
  large the group is, and whose index VRT carries the colour interpretation; the `pmtiles_gbx` reader's RGB sibling of an RGBA source;
  and the `netcdf_gbx` `bandDim` stack (four `uint8` steps used to read the fourth as alpha). The
  h3 cells of a source with an alpha band and no NoData of its own declare none over it: their
  pixels outside the hexagon are written transparent, and each cell carries its hexagon as a mask
  band, so the index VRT composites the cells by it (the corners of a cell's bounding box no
  longer overwrite its neighbours). A NoData the source does declare is kept on its cells.
- **Chips copy the colour interpretation of every band.** Tessellation chips and clips used to
  copy only the alpha label, so RGB, and the data bands of a gray-plus-extra-plus-alpha or a
  16-bit RGBA raster, followed GDAL's defaults for a new GeoTIFF. Both tiers now label each band
  as the source does.
- **A transparent pixel counts for no band, whatever the band count.** The raster-to-grid
  reducers (`rst_h3_rastertogrid*`, `rst_quadbin_rastertogrid*`, `rst_bng_rastertogrid*` and the
  custom-grid variants), the band statistics `gbx_rst_pixelcount`, `gbx_rst_avg`, `gbx_rst_min`,
  `gbx_rst_max` and `gbx_rst_histogram`, the percentiles of `gbx_rst_percentile_stretch` (a pixel
  invalid for a band is written 0 in it, in both tiers), the neighbours of `gbx_rst_filter` and
  `gbx_rst_convolve`, and the pixels `gbx_rst_polygonize` and `gbx_rst_isoband` vectorise judge
  each band by its own NoData or mask and its alpha band, in both tiers: GDAL derives a mask from
  an alpha band only for two- and four-band rasters, and the heavyweight statistics ignored even
  that one, so they counted the transparent pixels. A band masked by its own mask band (no alpha
  band) is left out of the heavyweight `gbx_rst_avg` and `gbx_rst_pixelcount` too. The alpha band
  itself is summarised over every pixel. `gbx_rst_isempty` is true for a raster with no valid
  pixel, so an entirely transparent raster is empty. The lightweight `gbx_rst_summary` takes its
  statistics over the valid pixels the same way (the heavyweight one reports none), and
  `gbx_rst_derivedband` of one raster is invalid where its input is, in both tiers: the validity
  is written as the derived band's own mask.
- **Quadbin cells of a point on a tile edge agree between the tiers.** The row of a latitude on a
  web-mercator tile edge came out one apart in the two tiers on some platforms (the last bit of
  `tan`, `cos` and `log` differs). A latitude within 1e-6 of a whole row is decided exactly now,
  identically in both tiers.
- **Two lightweight merge and mosaic crashes, and two heavyweight focal defects, are fixed.** A
  quadbin, h3 or BNG `cog_gbx` cell that a source barely touches no longer fails with
  `Invalid dataset dimensions`; `gbx_rst_merge` of tiles in two coordinate systems no longer
  measures its size or picks its pixel size in the units of whichever tile sorts first (a few
  pixels could be sent to the streamed merge, with 0.5 degrees read as 0.5 metres): the tile in the
  other system is reprojected onto the pixel size of a tile in the reference system, and the
  mosaic has that size, in memory and streamed alike, whichever tile sorts first;
  `gbx_rst_filter` of a raster with no declared NoData no longer returns NaN for every window; and
  `gbx_rst_convolve` writes each block's result where the block is (it wrote it shifted and left
  the rest as the input), and in both tiers adds only the neighbours that are on the raster, so
  the two agree over the whole raster, its edges included (the lightweight one replicated the edge).
- **The lightweight reprojection and the tile encoders keep a source's own mask band.**
  `gbx_rst_transform` and `gbx_rst_transformcrs` dropped the own mask band (not an alpha band) of a
  source, as JPEG-compressed aerial imagery often carries, so its masked pixels read as valid data;
  so did a transform to the CRS the raster is already in, the `raster_gbx` writer's tile encoder
  and its compression re-encode, and the windows of the `cog_gbx` writer's mosaic tiles. The
  masked pixels stay masked now: where the source declares a NoData they take it, and otherwise
  the mask is warped with the pixels and written with the output, as a virtual tile with a target
  CRS does.
- **Heavyweight covering keeps a source's own mask.** Some sources carry their own mask band
  (not an alpha band), as JPEG-compressed aerial imagery often does. With
  `assignment='covering'`, the heavyweight clip of each cell used to let the pixels that mask
  hides through as valid data: for the hexagonal cells of `rst_h3_tessellate`, and for every
  grid when the source also declared NoData. The lightweight tier already left them out. The
  heavyweight clip now keeps the mask, so those pixels are NoData in both tiers, and source pixels
  equal to the chip's NoData are NoData too, as on a source with no NoData and no mask or alpha
  band (on a masked source they used to shift by one and stay valid). `rst_bng_tessellate` clips
  the EPSG:27700 warp of a source in another CRS, which keeps the mask too (see above).
  Heavyweight `rst_clip` now fills the masked pixels like the area outside the geometry, as the
  lightweight tier does: with the source's NoData when it declares one, else with 0. A source with
  an alpha band is clipped as before.
- **Raster-to-grid reducers aggregate only the source's pixels.** The `rst_h3_rastertogrid*`,
  `rst_quadbin_rastertogrid*` and `rst_bng_rastertogrid*` reducers first warp a source in another
  coordinate system to the grid's (EPSG:4326, or EPSG:27700 for BNG). For a source with no
  NoData and no alpha band, both tiers used to fill the pixels outside the source's footprint with
  valid zeros, which the reducers counted and averaged as data. That fill is now NoData, with the
  fallback value above, and source pixels equal to that value are NoData too, so neither is
  aggregated. A source's own mask band (not an alpha band) is kept: its masked pixels used to be
  aggregated as zeros, or with their values when the source also declared NoData. A source with an
  alpha band is warped as before, and a source already in the grid's coordinate system is not
  warped.
- **Lightweight virtual tiles keep a source's own mask band.** `rst_fromfile` returns virtual
  tiles by default, and reading one dropped the source's own mask band (not an alpha band), as
  JPEG-compressed aerial imagery often carries, so every masked pixel read as valid data in every
  lightweight function that started from it: `rst_initnodata`, covering and BNG tessellation, the
  raster-to-grid reducers and the rest. A virtual tile now reads as its bytes would. The mask
  comes with the pixels, also through a band selection, a reprojection or a clip, and a NoData
  that `rst_initnodata` stamps takes the place of the masked pixels, as it does on bytes. Tiles
  made with `materialize=True`, and the tiles the writers stream block by block, carry the mask
  as well, so the heavyweight tier, which reads those bytes, sees the same pixels as the
  lightweight one.
- **Grouped functions apply a virtual tile's clip.** `raster_gbx` and `cog_gbx` emit virtual
  tiles that carry the `clipPolygons` polygon, and the lightweight `*_grouped` functions
  (`rst_clip_grouped`, `rst_memsize_grouped`, `rst_resample_grouped` and the rest) on runtimes
  with the FILE type read such a tile as the whole envelope window of its source file, so the
  polygon was skipped. They now read it clipped, as every other lightweight function does, and a
  tile whose `crs` differs from its source's is reprojected too. A tile written with
  `virtualize_dir` from a clipped or reprojected tile no longer applies that clip and CRS a
  second time when it is read.
- **Grouped functions apply `rst_initnodata`, `rst_band`, `rst_setsrid` and `rst_setcrs` to a
  whole-file virtual tile.** `raster_gbx` emits whole-file virtual tiles by default. After one of those
  functions, a lightweight `*_grouped` function that reads pixels (`rst_resample_grouped`,
  `rst_slope_grouped` and the rest) returned NULL on a cluster without the FILE type, with no
  error, and on one with it ignored the instruction, so the NoData was never applied. They now
  read the tile as every other lightweight function does, and the header-only grouped
  functions see the band count, NoData and CRS the instruction sets.
- **Lightweight raster outputs use one encoding.** Lightweight raster functions write ZSTD with
  the predictor that suits the data type, instead of inheriting the source file's codec. Sources
  compressed as JPEG (YCbCr) no longer make lightweight writes fail; an explicit JPEG request
  keeps YCbCr.
- **Heavyweight tiles default to DEFLATE in every path.** A heavyweight tile whose metadata names
  no `compression` is now always written as DEFLATE with the predictor for its data type, as
  documented (some paths wrote ZSTD), and `rst_cog_convert` still defaults to ZSTD.
- **Tiling keeps all-NoData windows in both tiers.** `rst_retile`, `rst_tooverlappingtiles`,
  `rst_maketiles` (with `size_in_mb > 0`) and the heavyweight tiled raster readers (`gdal`,
  `gtiff_gdal` and `netcdf_gdal` with `sizeInMB > 0`) now emit every window, including windows
  whose pixels are all NoData, as the lightweight tier already did. The heavyweight tier dropped
  them, so row counts differed between tiers and a retile-then-merge round trip could lose part
  of a scene's edge. To drop them, filter with `WHERE NOT gbx_rst_isempty(tile)` or write with
  `pruneEmpty`. Tiles from `rst_retile`, `rst_tooverlappingtiles`, `rst_maketiles` and
  `rst_separatebands` now carry the parent tile's `cellid` in both tiers (0 when the parent has
  none); the lightweight tier numbered them 0, 1, 2, ….
- **Lightweight quadbin raster-to-grid matches the heavyweight cell for edge pixels.** In
  `rst_quadbin_rastertogrid*`, a pixel centre at longitude 180 now lands in the easternmost tile
  instead of tile 0, and one on a tile edge falls in the same cell as in the heavyweight tier and
  in `rst_quadbin_tessellate`.

### Grid rasterizers — repeated cell ids burn the largest value (fix)

- **The lightweight cell rasterizers keep the largest value when a cell repeats, like the
  heavyweight tier, so results no longer depend on row order.** When a group held the same cell id
  more than once with different values, `rst_h3_rasterize_agg`, `rst_quadbin_rasterize_agg`,
  `rst_bng_rasterize_agg` and `rst_custom_rasterize_agg` burned whichever row arrived last in the
  lightweight tier, and the order of the rows inside a group is not fixed, so the same data could
  give a different raster from one run to the next. Both tiers now burn the largest value of the
  cell. A cell that appears once, or whose rows all carry the same value, burns as before. Two
  spellings of one BNG cell, such as `TQ3080` and `TQ 3080`, are one cell.
- **In the lightweight rasterizers a null value never wins.** A null value, or a `NaN`, is ignored
  whenever the cell has a number, so a cell with the values `0.5` and `NULL` burns `0.5`, not
  `1.0`; a cell whose values are all null burns `NaN`. A group with no number at all, as when
  `value` is omitted, is still the presence mask and burns `1.0`. A typed Double column delivers a
  null as `NaN`, so the lightweight tier cannot tell the two apart. The heavyweight tier still
  counts a null value as `1.0`.
- **The lightweight `*_cellfill` aggregates give the same fill whatever order the rows arrive
  in.** When a cell id repeated in a group, `h3_cellfill`, `quadbin_cellfill`, `bng_cellfill` and
  `custom_cellfill` used the row that arrived last. They now use the cell's largest non-null
  value, and a cell stays `NULL` only when every one of its values is null. The heavyweight tier
  still keeps the row it receives last.

### LiDAR reader and writer — `lidar_gbx` (new)

- **New `lidar_gbx` Spark DataSource** reads LAS and LAZ point-cloud files into a

### Point-cloud DSM functions (new)

The four registered functions below ship in **both tiers** — heavyweight RasterX and
lightweight `pyrx` — so they take part in the same heavy-vs-light parity comparison as the
rest of the raster family; `rx.bin_points_tiled` is a lightweight-tier Python helper.

- **`gbx_rst_binpoints`** — bin parallel `ARRAY<DOUBLE>` x/y/z columns into a Float32
  DSM raster. Each pixel carries a configurable statistic (`max`, `min`, `mean`,
  `median`, `count`, or `percentile:<p>`) over all points whose centroid falls in the
  cell. Empty cells carry NoData.

- **`gbx_rst_binpoints_agg`** — streaming aggregator variant: one scalar (x, y, z) point
  per row, binned into a DSM per group. The SQL aggregate returns `BINARY` (raster bytes);
  wrap with `gbx_rst_fromcontent(<agg>, 'GTiff')` to rebuild a tile struct. The Python
  wrapper `rx.rst_binpoints_agg(...)` returns the full tile struct.

- **`rx.bin_points_tiled`** (lightweight Python helper) — bounded tiled point binning built
  on `gbx_rst_binpoints_agg`: peak memory scales with the raster grid (width × height), not
  the point count, so a full-density (`decimate=1`) tile bins without exhausting a worker. It
  returns the same tile struct and matches `groupBy(...).agg(rst_binpoints_agg(...))` for
  `max`/`min`/`mean`/`count`.

- **`gbx_rst_isoband`** — reclassify a raster band into value bins and return one WKB
  polygon per contiguous patch. Returns
  `ARRAY<STRUCT<geom_wkb BINARY, band INT, lower DOUBLE, upper DOUBLE>>`. Useful for
  height-band polygons from a CHM or elevation isobands from a DEM.

- **`gbx_rst_chm`** — compute a Canopy Height Model: warp the DSM onto the DEM grid,
  subtract, and clamp negatives to zero. NoData propagates from either input.

### Contrast stretch — `gbx_rst_percentile_stretch` (new)

- **`gbx_rst_percentile_stretch`** — per-band percentile contrast stretch. For each band,
  clip pixel values to the `[lo_pct, hi_pct]` percentiles over valid (non-NoData) pixels and
  linearly rescale to 8-bit `[0, 255]`; pixels that are NoData in every band are preserved.
  `gbx_rst_percentile_stretch(tile, 2.0, 98.0)` is a common contrast-enhancement and
  display-prep step — for example before a COG or tile export. Available on both the
  heavyweight and lightweight tiers. See [Raster Functions](./api/raster-functions).

### Land-cover classification — `rst_land_cover` (new, Python-only)

- **`rst_land_cover`** classifies an RGB(+NIR) tile into land-cover class ids and returns a
  single-band `Int32` class-mask tile. Three methods: `"spectral"` (fixed excess-green /
  brightness thresholds), `"kmeans"` (a SciPy k-means partition over RGB + excess-green +
  brightness features, labeled by the same spectral thresholds), and `"hybrid"` (default).
  Each pixel is an index into the class scheme — `["vegetation", "bare", "impervious",
  "dark"]` by default — and NoData / unclassified pixels are `-1`. It is a **Python-only**
  lightweight-tier function, called as
  `rx.rst_land_cover(tile, method=..., n_clusters=..., smooth=...)`; a SQL surface is deferred
  to a later release. Because the output is an ordinary tile, class regions trace to vector
  polygons via the registered `gbx_rst_polygonize` streaming UDTF. See
  [Raster Functions](./api/raster-functions).

### Viewshed pipeline — `rst_viewshed_towers` (new, Python-only)

- **`rst_viewshed_towers`** runs a per-tower raster viewshed over a tiled DSM and returns one
  scalar row per tower. For each tower it selects the in-radius DSM tiles via the new
  `tile_range` windowing helper (using an EPSG:3857 grid origin `x0`/`y0` and tile size `tile_m`
  that the `tx`/`ty` indices in `dsm_tiles_df` reference), mints one bytes-free VRT over them,
  runs a single `rst_viewshed` (materialized once, in-memory), and derives coverage counts from
  a histogram. No raster bytes cross a shuffle — each tower row carries a ~100-byte VRT path —
  so there is no FUSE read-back and no whole-AOI merge. Returns one row per tower with
  `visible_px` (long), `total_px` (long), and `frac` (double, visible/total); when `to_crs` is
  set it also emits `visible_px_reproj` and `total_px_reproj` from a reprojected viewshed.
  `observer_height` may be a per-tower column name or a scalar applied to every tower.
  It is a **Python-only** lightweight-tier pipeline function, called as
  `rx.rst_viewshed_towers(towers_df, dsm_tiles_df, radius_m, observer_height, x0=..., y0=..., tile_m=...)`;
  no SQL surface is provided. Powers the Wireless Coverage Part 3b viewshed analysis. See
  [Raster Functions](./api/raster-functions).

### Distributed H3 viewshed — `h3_viewshed_towers` (new, Python-only)

- **`h3_viewshed_towers`** is the H3-native sibling of `rst_viewshed_towers`: it runs a per-tower
  line-of-sight viewshed entirely in H3 cell space and returns one row per `(tower, visible
  cell)`. For each tower it tests the in-buffer H3 cells with the exact `h3_los_visible` line of
  sight — the blocker is the surface map (DSM, or DSM + canopy), the observer sits at the
  tower-top absolute elevation, and each target receiver is the ground (DTM) elevation plus
  `target_height`. The two surface/ground maps are collected once to the driver (bounded at
  `viewshed_res`) and the per-tower work is fanned one-tower-per-task with `mapInPandas` over the
  towers frame repartitioned by `tower_id_col`, so the same code path runs on Databricks
  Serverless and on classic clusters. H3 cell ids flow as `BIGINT` (the integer H3
  representation) in every column. It is a **Python-only** lightweight-tier function, called as
  `h3_viewshed_towers(towers_df, surface_df, ground_df, radius_m=..., viewshed_res=...)`; no SQL
  surface is provided. This is the mechanism that lets the Wireless Coverage tower siting scale
  across Spark. See [GridX Functions](./api/gridx-functions).

### Geom-aware grid functions — GeometryCollection inputs

- **GeometryCollection inputs** to the geom-aware grid functions
  (`gbx_*_geomkring` / `gbx_*_geomkloop` and their explode variants) are now
  processed as the union of their members, matching `MULTI*` behavior — polygon,
  line, and point members all contribute (previously non-polygon members were
  dropped or the result was empty). As with a standalone point or line, point and
  line members contribute only under `coverage = coveras`.

### Geom-aware grid functions — performance improvement for large polygons

- **`gbx_quadbin_geomkring` / `gbx_quadbin_geomkloop`, `gbx_bng_geomkring` /
  `gbx_bng_geomkloop`, and `gbx_custom_geomkring` / `gbx_custom_geomkloop`
  (and their `*explode` variants) now scale with the polygon's boundary length rather
  than its area.** For large polygons, the previous implementation enumerated every
  cell inside the polygon before identifying the boundary band — a cost proportional
  to the polygon's area. The new implementation traces the polygon boundary ring
  directly, classifying only cells near the perimeter. For a polygon that covers tens
  of thousands of cells at the target resolution, large-polygon `boundary-out` calls
  are dramatically faster (10–100× depending on grid and resolution), and
  medium-polygon throughput is 2–10× higher. **The cell sets returned are unchanged**
  — this is a pure performance improvement with no effect on results.

- **Behaviour fix for non-rectangular polygons in the heavyweight tier.** For
  non-rectangular polygons, the geom-aware kring/kloop functions in the heavyweight
  (Scala/Spark) tier previously returned a slightly larger boundary band than the
  lightweight tier due to an over-count in the outer-perimeter seed calculation. The
  heavyweight tier now uses the same boundary-tracing seed as the lightweight tier,
  so the two tiers produce identical cell sets for all polygon shapes.

### CRS authority preserved for ESRI and OGC coordinate systems

Readers, writers, and raster accessors previously dropped the ESRI or OGC
authority from non-EPSG coordinate reference systems.  For example, a raster
with `ESRI:54008` (Sinusoidal projection) would produce `None` from `srid()`,
an authority-less WKT in the `crs` output column, and an incorrectly labeled
`EPSG:54008` tag in a LAS/LAZ header.

These sites are now fixed: the canonical `ESRI:54008` or `OGC:CRS84` string
is preserved end-to-end.  `authority_srid_of` is the correct function to
extract the integer SRID — it returns `None` only for CRSes with no integer
authority code (such as `OGC:CRS84`, whose code `CRS84` is a string).

**Parity contract:** CRS equivalence is semantic, not string equality.
A raster emitted as `ESRI:102008` and one as the equivalent WKT are the same
CRS; `crs_equal(a, b)` is the right comparison.

**Honest limits:**

- **LiDAR writer (`lidar_gbx`):** The LAS/LAZ format can only encode EPSG codes in a LAS header CRS record.  ESRI and OGC CRS are not representable in a LAS header.  They survive in the `lidar_gbx` **reader** `crs` column, but are correctly dropped (not mislabeled) when writing a `.laz` file.  Pass an equivalent EPSG code via the `crs` writer option if the format requires one.
- **NetCDF `spatial_epsg` attribute:** For a non-EPSG CRS the NetCDF writer now stores the ESRI code in the legacy `spatial_epsg` grid-mapping attribute (whose name implies EPSG).  The authoritative CRS is in `crs_canonical` / `crs_wkt` — take the authority from `crs_canonical`, not `spatial_epsg`, for non-EPSG CRS.
- **ESRI-identity reproject:** Raster operations now short-circuit an identity reproject when the source and target CRS are both ESRI-authored and equal.  Output is content-equivalent, but callers that depended on receiving byte-identical output from an ESRI-identity `rst_transform` call may observe a different bytes path (ZSTD re-encode vs. warp pipeline) for that specific case.

### Light-tier ZSTD compression: horizontal-differencing predictor now applied

Light-tier COG and GTiff re-encodes that use ZSTD compression now apply the
horizontal-differencing predictor consistent with the heavyweight tier:
`float32`/`float64` tiles receive predictor 3 (floating-point differencing),
`uint8`/`int8` tiles receive predictor 1 (no predictor — byte data gains
nothing from differencing), and all other integer types receive predictor 2
(integer differencing).

Previously the light-tier `tile_to_bytes` re-encode path omitted the predictor
for ZSTD entirely, and for `uint8`/`int8` data applied predictor 2 instead of
predictor 1 under DEFLATE and LZW.

**Impact on existing files:** Any COG or GTiff file re-encoded by the light tier
with ZSTD compression will produce different (typically smaller) output bytes
when regenerated.  Decoded pixel values are unchanged — this is a pure
compression improvement with no data loss.  Downstream checks that compare
compressed bytes byte-for-byte against a stored reference will observe a
difference and must refresh their reference outputs.

### Raster-to-grid — coverage and assignment (breaking changes)

- **`gbx_rst_{h3,quadbin,bng}_rastertogrid*` now default to `coverage=complete` (breaking behavior change).** Previously, only cells that contained at least one valid pixel were returned. With `coverage=complete`, every cell whose area overlaps the raster extent is returned — cells with valid pixels carry a numeric measure, and cells covered by the extent but containing only NoData are returned with a `NULL` measure (or `0.0` for count). Queries that assumed the result set was restricted to cells with data will now receive extra rows. Add `coverage='sparse'` to any call that should preserve the old drop-empty behavior: `gbx_rst_h3_rastertogridavg(tile, resolution, 'sparse')`.

- **New `assignment` parameter on `gbx_rst_{h3,quadbin,bng}_rastertogrid*`.** Controls how pixels are assigned to cells:
  - `centroid` (default) — a pixel belongs to the cell that contains its centroid. Each pixel contributes to exactly one cell. This is the behavior prior to this release.
  - `covering` — a pixel contributes to every cell whose area it overlaps, weighted by the fraction of the pixel's area that falls within each cell. The total contribution across all cells equals the original pixel value, so `sum` and `count` are mass-conserving: summing across all overlapping cells recovers the original pixel total. Use `covering` when accurate spatial aggregation near cell boundaries matters more than sharp per-cell attribution.

  Full signature: `gbx_rst_{grid}_rastertogridavg(tile, resolution, [coverage], [assignment])`. See [Grid Raster Tessellation](./api/grid-raster-tessellation) for the full coverage/assignment/fill model and per-grid specifics.

- **`gbx_rst_{h3,quadbin,bng}_rastertogridcount` now returns `DOUBLE` (was integer).** With area-weighted assignment (`covering`), count is the sum of area fractions, which is fractional for pixels that straddle a cell boundary. The return type is `DOUBLE` on both tiers for both assignment modes. Queries that cast the count column to integer or use `COUNT(*)` aggregation over the result should be updated.

### Raster tessellate — parameter rename and new `coverage` control (breaking changes)

- **`gbx_rst_{h3,quadbin,bng}_tessellate`: the `mode` parameter is renamed to `assignment` (breaking, no alias).** The existing values (`centroid`, `covering`) are unchanged; only the parameter name changes. Code passing a named `mode=` argument must be updated to `assignment=`. Positional calls with two arguments (`tile, resolution`) are unaffected.

- **`gbx_rst_{h3,quadbin,bng}_tessellate`: new optional `coverage` parameter and changed 2-argument default.** A new `coverage` parameter (values `complete` / `sparse`) follows `assignment` in the signature: `(tile, resolution, [assignment], [coverage])`. The 2-argument form (`tile, resolution`) now defaults to `assignment='centroid', coverage='complete'` — previously it behaved like `covering`. To restore the pre-release default, pass `assignment='covering'` explicitly.

### CRS-handling fix for BNG raster-to-grid

- **A CRS-less raster fed to `gbx_rst_bng_rastertogrid*` is no longer automatically warped to EPSG:27700.** Previously, BNG raster-to-grid silently treated a tile with no declared CRS as if it were in EPSG:4326 and reprojected it to EPSG:27700 before aggregating — a different default than the H3 and quadbin variants, which pass a CRS-less tile through as grid-native. BNG now matches: a CRS-less tile is treated as already in the grid's native coordinate system (EPSG:27700 for BNG) and is not warped. This only affects tiles that carry no CRS metadata; tiles with an explicit CRS continue to be reprojected as before.

### Custom-grid raster operations (new)

- **User-defined custom grids now support the full raster-to-grid surface.** The eight raster-to-grid reducers, tessellate generator, and rasterize aggregator that were previously available for H3, quadbin, and BNG are now also available for user-defined custom grids: `gbx_rst_custom_rastertogrid{avg,count,max,min,median,sum,variance,stddev}`, `gbx_rst_custom_tessellate`, and `gbx_rst_custom_rasterize_agg`. Use these when your workflow requires a national, project-specific, or other custom projected grid rather than one of the discrete global grid systems. The `coverage` and `assignment` parameters introduced for the H3/quadbin/BNG variants are available here too, with the same defaults (`coverage='complete'`, `assignment='centroid'`). The signatures extend the H3/quadbin/BNG form `(tile, resolution, [coverage], [assignment])` by inserting a `grid_struct` as the second argument: `(tile, grid_struct, resolution, [coverage], [assignment])`, where `grid_struct` is produced by `gbx_custom_grid`. Available in both the heavyweight and lightweight tiers. See [Raster Functions](./api/raster-functions).

### Cross-raster combine and alignment (new)

- **New `gbx_rst_combine{min,max,median,sum,stddev,count}` — pixel-wise reductions over raster stacks.** Six new functions extend the existing `gbx_rst_combineavg` with additional pixel-wise reductions over an `ARRAY<tile>`: per-pixel minimum, maximum, median, sum, population standard deviation, and pixel count. Pass `collect_list(tile)` for a streamed group-by, or `array(t1, t2, ...)` for a fixed list. Each function operates band-by-band, excludes NoData cells from the reduction (all-NoData pixels yield NoData in the output), and requires the input tiles to share the same grid (same CRS, extent, and pixel dimensions — use `gbx_rst_align_to` to satisfy this precondition). Available on both the heavyweight and lightweight tiers. See [Raster Functions § Multi-raster operations](./api/raster-functions#multi-raster).

- **New `gbx_rst_align_to` — snap a tile to a reference grid.** `gbx_rst_align_to(tile, reference_tile)` resamples `tile` to match the CRS, extent, and pixel grid of `reference_tile` using nearest-neighbour resampling, so the two tiles land on exactly the same grid without fabricating interpolated values. The primary use case is preparing inputs before combining them with `gbx_rst_combine*`. Available on both the heavyweight and lightweight tiers. See [Raster Functions](./api/raster-functions).

### NetCDF reader — multi-dimension handling (new)

- **The lightweight `netcdf_gbx` raster reader gains `dimIndex`, `fanout`, and `bandDim` options for CF variables with extra (non-spatial) dimensions such as time and level.**
  - `dimIndex` pins one or more leading dimensions to a specific index — `.option("dimIndex", "time=2,level=1")` — reading a single slice. Absent dimensions fall back to index 0 (with a warning when the dimension has more than one slice); an out-of-range index raises `ValueError`.
  - `fanout` expands one or more dimensions across all their indices, emitting one `(source, tile)` row per index combination — `.option("fanout", "time,level")`. It composes with `dimIndex` (fanned dimensions expand; the rest stay pinned).
  - `bandDim` stacks one dimension's slices as bands in a single multi-band tile — `.option("bandDim", "time")` turns a `(time=3, lat, lon)` variable into one 3-band tile; an estimated decode over ~256 MiB warns and suggests `fanout` instead.

  A dimension may appear in only one of the three (conflicts raise `ValueError`). A variable that reaches the reader with an unrecognized extra dimension now emits a per-variable `UserWarning` (previously a hard `ValueError`), so a file mixing such variables still reads. See [NetCDF Reader](./readers/netcdf).

### Grid-native cell-space fill (new)

- **New `gbx_{h3,quadbin,bng,custom}_cellfill` — gap-filling over a grid-indexed table.** Four new grouped aggregators — `gbx_h3_cellfill`, `gbx_quadbin_cellfill`, `gbx_bng_cellfill`, and `gbx_custom_cellfill` (one per grid system) — fill cells whose value is `NULL` by interpolating from neighbouring cells in the same group. Call as a `GROUP BY` aggregate: `gbx_h3_cellfill(cellid, value[, k[, method[, power]]])`. The optional `k` parameter (default `1`) controls the neighbourhood radius in k-rings; `method` selects the interpolation strategy — `'mean'` (simple unweighted average of valid neighbours, default) or `'idw'` (inverse-distance-weighted average); `power` (default `2.0`) is the IDW distance exponent. Each function returns `ARRAY<STRUCT<cellid, value DOUBLE>>`, where filled and original cells are both present. Useful for smoothing patchy raster-to-grid output, imputing sparse sensor grids, or filling NoData-derived nulls in any grid-indexed table — no coordinate projection is needed, all interpolation happens in cell space. BNG cell IDs are `STRING`; all others are `BIGINT`. Available in both the heavyweight and lightweight tiers. See [GridX Functions](./api/gridx-functions).

### Grid operation parity (new)

- **Quadbin and custom grids now have `kloop` and `distance` functions, completing parity across all four grid families.** `gbx_quadbin_kloop(cellid, k)` returns the hollow ring of quadbin cells at exactly Chebyshev distance `k` from the input cell (the complement of the filled `gbx_quadbin_kring`) — matching the `kloop` functions already available for H3 and BNG. `gbx_custom_kloop(cellid, grid_struct, k)` provides the same hollow-ring operation for user-defined custom grids. `gbx_custom_distance(cellid1, grid_struct, cellid2)` returns the Chebyshev grid distance between two custom-grid cells, closing a gap that existed since the custom grid was introduced in v0.4.0. Available in both the heavyweight and lightweight tiers. See [GridX Functions](./api/gridx-functions).

### Geometry-aware kring/kloop across all grid families (new)

- **BNG `gbx_bng_geomkring` / `gbx_bng_geomkloop` (and their `*explode` variants) gain an optional `mode` parameter.** The new `mode` argument controls how cells that touch the geometry boundary are classified. The default is `'boundary-out'` (outward band around the geometry; see the mode table below), so existing three-argument calls keep working; `mode` defaults to `'boundary-out'` when omitted. Available in both the heavyweight and lightweight tiers.

  The six mode values are:

  | Mode | Behaviour |
  |------|-----------|
  | `'boundary-out'` | Default. The geometry's **boundary band** (`k=0`) plus the outward band — cells within `k` steps **outside** the boundary. The geometry's fully-interior cells are not in the result. Under the default `coverage='coveras'` (and `'core'`) `k=0` is the whole straddling band; under `'polyfill'` it is the centroid-outside cells (see the `coverage` note). |
  | `'boundary-in'` | Inward setback band — cells within `k` steps inside the outer boundary, stopping at holes. |
  | `'boundary-in-ignore-holes'` | Like `'boundary-in'` but the polygon is treated as solid (holes are not subtracted), so the band can cross a hole. |
  | `'hole-in'` | Fills each hole inward from its edge, up to `k` steps. |
  | `'hole-out'` | Band in the solid around each hole, up to `k` steps, bounded by the outer geometry. |
  | `'hole-out-ignore-geom'` | Band outward from each hole, up to `k` steps, **not** bounded by the outer geometry. |

- **New `gbx_quadbin_geomkring`, `gbx_quadbin_geomkloop`, `gbx_quadbin_geomkringexplode`, `gbx_quadbin_geomkloopexplode` — geometry-aware expansion for quadbin.** These four functions follow the same contract as the BNG variants: polyfill a WGS84 geometry into quadbin cells at a given zoom level, then expand by `k` dilation steps using the optional `mode` parameter. Cell IDs are `BIGINT` (quadbin format). Available in both the heavyweight and lightweight tiers. See [GridX Functions](./api/gridx-functions).

- **New `gbx_custom_geomkring`, `gbx_custom_geomkloop`, `gbx_custom_geomkringexplode`, `gbx_custom_geomkloopexplode` — geometry-aware expansion for custom grids.** Same contract as the quadbin and BNG variants, extended with a `grid` struct argument (from `gbx_custom_grid`) that identifies the custom coordinate system. The geometry must be in the grid's native CRS. Cell IDs are `BIGINT`. Available in both the heavyweight and lightweight tiers. See [GridX Functions](./api/gridx-functions).

- **New `gbx_h3_geomkring`, `gbx_h3_geomkloop`, `gbx_h3_geomkringexplode`, `gbx_h3_geomkloopexplode` — geometry-aware expansion for H3 (light-only).** These four functions are **lightweight-tier only** — there is no heavy (Scala) implementation. Like the other grids, they take a geometry directly and do the whole job in pure Python via the `h3` library — `h3.polygon_to_cells_experimental` for the covering set (holes handled natively) and `grid_disk` for the neighbour walk — so `gbx_h3_geomkring(geom, resolution, k, [mode])` is a single function callable identically from SQL and PySpark (it runs on Serverless, classic clusters, and locally). Use the Python column API for the most natural experience:
  ```python
  from databricks.labs.gbx.gridx.h3.functions import geomkring
  df.withColumn("kring", geomkring("geom_col", resolution=12, k=1))
  ```
  All six dilation modes work, including the hole-mode variants (`'hole-in'`, `'hole-out'`, `'hole-out-ignore-geom'`). Geometry input is WKB `BINARY` or WKT `STRING`. Cell IDs are `BIGINT` (H3 format). See [GridX Functions](./api/gridx-functions).

- **Point and line geometries are supported, not just polygons.** `geomkring`/`geomkloop` accept `POINT`/`LINESTRING` (and their `MULTI*` forms) — a point covers its containing cell, a line covers the cells it crosses, and `boundary-out` expands outward from there. (Under the default `coverage='coveras'`; `'polyfill'`/`'core'` return empty for 0-/1-dimensional inputs — see the `coverage` note below.)

- **Boundary/hole behavior.** `boundary-*` modes operate on the geometry's **outer boundary only** — polygon holes are handled exclusively by the `hole-*` modes. `boundary-out` returns the boundary band at `k=0` plus the outward band, excluding the fully-interior cells (its `k=0` follows the `coverage`: `coveras`/`core` give the whole straddling band, `polyfill` the centroid-outside cells; the outward `k≥1` rings are identical across coverages). All modes are robust to **grid-aligned** geometries (edges lying exactly on cell boundaries), and the heavyweight and lightweight tiers produce identical cell sets across every `mode` × `coverage` combination.

### Geometry-aware kring/kloop — new `coverage` parameter

- **All `gbx_{h3,bng,quadbin,custom}_geomkring`/`geomkloop`/`*explode` functions gain an optional trailing `coverage` parameter** (after `mode`), controlling how a cell is judged to belong to a region:

  | `coverage` | Meaning |
  |---|---|
  | `'coveras'` | **Default.** A cell belongs if it *overlaps* the region — inclusive, so boundary cells are kept (no false negatives). |
  | `'polyfill'` | A cell belongs if its *centre* is inside the region (standard polyfill). |
  | `'core'` | A cell belongs only if it is *entirely* inside the region (strictest; no false positives). |

  The nesting is `coveras ⊇ polyfill ⊇ core`; the default `'coveras'` is the most inclusive (boundary cells kept, no false negatives). Point/line geometries are covered only under `'coveras'` (a 0-/1-dimensional geometry has no cell whose centre is inside it or that fully contains it, so `'polyfill'` and `'core'` return empty for them). Available in both tiers; heavy and light agree across all `coverage` × `mode` combinations.


### Covering assignment performance improvement

- **Covering assignment is now computed over cell boundaries only.** The `covering` assignment mode (available on all `gbx_rst_{h3,quadbin,bng,custom}_rastertogrid*` and `*_tessellate` functions) previously computed area fractions by evaluating overlap for every pixel in the raster extent. It now uses a boundary-driven algorithm that processes only cells that intersect the raster perimeter, reducing computation proportionally to the boundary-to-interior ratio. For rasters with large solid interiors — where most cells are fully covered — this is significantly faster. Results are numerically identical; this is a performance improvement only.

### Reader and operator fixes

- **`raster_gbx`: `splitStrategy` / `sizeInMB` now bound tile size on the default virtual-tiles path.** On the lightweight `raster_gbx` reader these budget options were silently ignored while `virtualTiles` stayed at its default `"true"` — a large raster came through as a single whole-image tile, with no split and no warning, and then out-of-memoried the first pixel-touching operation (`rst_sample`, aggregations). The decoded-byte budget now bounds each **virtual** tile the same way it already bounded materialized tiles, so a raster whose decoded footprint exceeds the budget is split into multiple virtual window tiles regardless of `virtualTiles`. `splitStrategy`/`sizeInMB` now behave identically on both paths. See [Raster Readers](./readers/raster).
- **`gbx_rst_updatetype` (heavyweight) now selects a compression predictor that matches the output datatype.** Converting a Float raster to `Byte` failed because the TIFF predictor was derived from the input datatype — `PREDICTOR=3` (Float32/Float64-only) — while the output was `Byte`, so `gdal_translate` rejected the creation options (`PREDICTOR=3 is only supported with Float32 or Float64`). When a translate/calc command sets an explicit output type (`-ot` / `--type`), the predictor is now chosen from that type (`1` for Byte/Int8, `3` for Float32/Float64, `2` otherwise). The lightweight `rst_updatetype` was already correct.

## What's new in v0.5.0

Introduces **virtual tiles** — a bytes-free way to read and process huge rasters without out-of-memory — unifies both execution tiers on one tile struct, and adds the COG preparation lane (`file_gbx` + `cog_gbx`) with **VRT mosaics** for large-raster workflows, tapping the new Databricks **[FILE type](https://docs.databricks.com/aws/en/sql/language-manual/data-types/file-type)** for governed, memory-safe file access where the runtime provides it, on top of v0.4.3.

### Packaging

- **Packaging: `[light]` and `[light_all]` are removed in 0.5.0 (breaking change, no alias).** Every light-tier install now picks an explicit, runtime-pinned extra. On Serverless: install `geobrix[light_env6]` (environment v6, **recommended**) or `geobrix[light_env5]` (env 5). On classic clusters: install `geobrix[light_dbr17]`, `geobrix[light_dbr18]`, or `geobrix[light_dbr19]` to match your runtime. Full-feature-set variants (`_all`) are available for each extra. See [Installation](./installation?tier=lightweight).
- **Light-tier dependencies are now pinned to the Databricks base.** All runtime-pinned light extras (`light_env5`, `light_env6`, `light_dbr17`–`light_dbr19`) pin their transitive dependencies to the versions already present in the corresponding Databricks base environment. Installing GeoBrix Light no longer unexpectedly upgrades preinstalled packages, and `%pip install` output is quieter.
- **`earthaccess` and the EMIT downloader moved from `[stac]` to the new `[earthdata]` extra (breaking change).** Installing `geobrix[...,stac]` no longer pulls in `earthaccess`. To use `EmitDownloader` or any NASA Earthdata / LP DAAC client, add the `[earthdata]` extra — e.g. `geobrix[light_env6,earthdata]`. The `[earthdata]` extra is not included in `_all` bundles because `earthaccess` updates `fsspec`, which can conflict with cluster preinstalled packages.
- **`[overture]` is now an opt-in extra, excluded from `_all`.** The Overture Maps downloader (`overturemaps>=1.0`) ships behind the `[overture]` extra and is no longer included in `_all` bundles. Like `[earthdata]`, it changes a preinstalled base package on install — `overturemaps` 1.x bumps `click` — so it is opt-in. Add it explicitly when you need it: `geobrix[light_env6,overture]`. `_all` is now `[light_envN/_dbrN]` + `[stac]` + `[vizx]` — generic, quiet features only. Source-specific downloaders (`[earthdata]`, `[overture]`, and any future additions) follow this opt-in rule.

### Virtual tiles & tile struct

- **Virtual tiles — bytes-free windowed reads for large rasters.** The lightweight `cog_gbx` / `raster_gbx` / `gtiff_gbx` readers can emit **virtual tiles**: each row carries a source `path` + pixel `window` instead of the raster bytes, and pixels are read lazily, one window at a time, only when an operation needs them. A virtual-tile row is ~100 bytes versus 148–527 KB of materialized bytes (~1,400–5,000× smaller), so fanning a multi-gigabyte raster into many tiles no longer accumulates into a Serverless out-of-memory failure. Opt in with `.option("virtualTiles", "true")`. See the new **[Virtual Tiles](./api/virtual-tiles)** page.
- **Light raster readers now default to virtual tiles (breaking behavior change).** The lightweight raster readers (`raster_gbx`, `gtiff_gbx`, `cog_gbx`) previously materialized tile bytes by default; they now emit **[virtual tiles](./api/virtual-tiles)** by default. Code that reads a raster and immediately operates on `tile.raster` bytes — or passes the tile to a heavyweight function — will see `null` bytes until the tile is materialized. Pass `.option("virtualTiles", "false")` to restore the old behavior, or call a downstream `rst_*` function with `materialize=True`.
- **The [Tile Structure](./api/tile-structure) output shape widens from the 3-field struct to the v2 8-field struct.** The tile struct gains five fields — `path`, `window`, `clip_polygon`, `clip_crs`, `crs` — alongside `cellid`, `raster`, and `metadata`, and `raster` is now **nullable** (`null` on a virtual tile). The same 8-field struct is produced and consumed by both tiers, so consumers that assumed the 3-field shape need updating. On a materialized tile the new fields are provenance (what was applied to the bytes); on a virtual tile they are instructions (applied on read).
- **Every lightweight `rst_*` function is virtual-tile-aware.** Functions consume virtual or materialized tiles through one shared open path: metadata accessors answer from the header without reading pixels, reference/passthrough ops (`rst_clip`, `rst_setsrid`, identity `rst_transform`) stay virtual, and pixel-producing ops materialize only the window they need. Tile-returning functions gain three optional force-output params — **`virtualize_dir`**, **`virtualize_prefix`**, **`materialize`** — so you can flip a result back to a bytes-free virtual row (or force bytes) at any step. See [Virtual↔materialized advice](./api/execution-tiers#virtual-materialized-advice).
- **Both tiers accept v1 and v2 tiles and always emit v2.** The heavyweight (`rasterx`) and lightweight (`pyrx`) tiers both read the legacy 3-field tile and the new 8-field tile, and every function emits the v2 struct — so output composes directly across tiers. Heavyweight operates only on **materialized** (binary) tiles as of now, so a virtual tile passed to a heavyweight function raises a clear materialize-first error (`materialize=True`, or write it out and read it back). The lightweight tier is for both **light (virtual)** and **materialized** tiles. See [Virtual tiles and the light→heavy bridge](./api/execution-tiers#light-heavy-bridge).

### COG preparation lane

- **New `file_gbx` reader — path lister.** Lists files in a directory as path-reference rows `(path, name, extension, size, modificationTime)`, without loading any raster content. `extension` is lowercase, no leading dot, and `NULL` for files without an extension. Options: `filterRegex`, `recursiveFileLookup`. This is the entry point for the COG preparation pipeline. See [File Lister](./readers/file).
- **New `cog_gbx` writer — master-COG preparation.** Takes path-reference rows from `file_gbx` and converts each source file to a spec-valid Cloud-Optimized GeoTIFF using GDAL's `driver="COG"` creation path. Each output COG carries internal tiling and pre-built overview levels. Options: `cogBlockSize` (default `512`), `cogOverviewResampling` (default `AVERAGE`), `cogCompression` (default `DEFLATE`), plus `driverMode` for driver-orchestrated large-file preparation. Output files pass `rio_cogeo.cogeo.cog_validate`. See [COG Writer](./writers/cog) and [Large Rasters](./api/large-rasters).
- **New `cog_gbx` reader — COG-aware windowed read.** Reads Cloud-Optimized GeoTIFFs into the shared tile schema, issuing range-reads that fetch only the bytes a window needs. The reader windowing surface is **`tileSize`** (regular grid) + **`overlapPercent`**, arbitrary **`clipPolygons`** (emit only the tiles intersecting each polygon, with **`clipCrs`**), or explicit pixel **`windows`** — lists are passed as JSON strings over `.option()`. See [COG Reader](./readers/cog) and [Readers overview](./readers/overview).
- **Raster reader `splitStrategy` defaults to `none`.** The `raster_gbx`, `gtiff_gbx`, and `cog_gbx` readers default to one whole-image tile per file; splitting is opt-in via `.option("splitStrategy", "serverless")` / `"classic"`, and the `sizeInMB` power-user override remains available. For large rasters the recommended pattern is prepare-then-read: list with `file_gbx`, prepare master COGs once with the `cog_gbx` writer, then read any AOI window cheaply with virtual tiles. See [Large Rasters](./api/large-rasters).
- **VRT mosaics — tile a large source into bounded mini-COGs + a portable index.** The `cog_gbx` writer's `vrtMosaic` mode splits each source into bounded mini-COGs — read window-by-window, so the source is never fully held in RAM — and writes a lightweight, portable `mosaic.vrt` index over them; each mini-COG is small by construction, so a source too big to hold as one COG (or in per-task memory) is processed safely on Serverless. Point `raster_gbx` (or `cog_gbx`) at a `mosaic.vrt` and the reader expands it into one virtual tile per member, so every `rst_*` function processes the mosaic per-tile; `clipPolygons` restricts the expansion to only the members intersecting an area of interest. `mint_vrt` builds a transient index over an ad-hoc tile list for on-demand windowed reads, and `mosaic.vrt` opens in any GDAL tool (QGIS, gdalinfo, rio-tiler) with no GeoBrix needed. Native pixel tiling (`gridSystem="none"`) with `tileSize` / `overlapPercent`; quadbin cell-aligned tiling (`gridSystem="quadbin"` + `gridResolution`) reprojects to EPSG:3857 and tags each cell with `GBX_CELLID`, surfacing in `tile.metadata["cellid"]` after expansion; VRT is optional (`writeVrt="false"` writes tiles only). H3 grid-aligned mode (`gridSystem="h3"`) reprojects to EPSG:4326, clips each cell to its hexagon, and tags every member with `GBX_CELLID` (h3index), surfacing in `tile.metadata["cellid"]` for equi-join unification with h3-indexed tabular data. BNG grid-aligned mode (`gridSystem="bng"`) reprojects to EPSG:27700 and tags each cell with `GBX_CELLID` (BNG string id), surfacing in `tile.metadata["cellid"]` for equi-join unification with BNG-indexed data (Great Britain only). See the **[VRT & Mosaics](./api/vrt-mosaic)** page.

### CRS & coordinate systems

- **VectorX CRS functions (`gbx_st_crs`, `gbx_st_setcrs`, `gbx_st_transformcrs`) — both tiers.** Three new functions complement the Databricks built-ins `st_srid` / `st_setsrid` / `st_transform` with authority-string CRS handling: `gbx_st_crs(geom)` returns the geometry's CRS as a canonical authority string (e.g. `EPSG:4326`, `ESRI:54008`), or `NULL` for a geometry with no SRID. `gbx_st_setcrs(geom, crs)` stamps a CRS onto a geometry as a label-only change — coordinates are not moved; it raises on an authority-less CRS (raw WKT or PROJ4) because a geometry can only carry an integer SRID. `gbx_st_transformcrs(geom, target_crs[, source_crs])` reprojects coordinates; an authority-coded target (`EPSG:n` / `ESRI:n`) stamps `n` on the result, while an authority-less target reprojects and clears the stale SRID; an optional third argument supplies a source CRS for a geometry that carries no SRID. All three accept WKB/EWKB/WKT/EWKT input; the SQL surface returns `BINARY` (`gbx_st_crs` returns `STRING`). Available on both the heavyweight (`vectorx`) and lightweight (`pyvx`) tiers. See [VectorX Functions](./api/vectorx-functions#crs).
- **RasterX CRS functions (`gbx_rst_crs`, `gbx_rst_setcrs`, `gbx_rst_transformcrs`) — both tiers.** The raster counterparts of the same idea: they take and return CRS *strings*, so a non-EPSG coordinate system survives a round trip that the integer-SRID functions (`gbx_rst_srid` / `gbx_rst_setsrid` / `gbx_rst_transform`) cannot represent. `gbx_rst_crs(tile)` returns the tile's CRS as an authority string (`EPSG:4326`, `EPSG:32618`) when it carries one, and its full WKT when it does not — so it always returns a value where `gbx_rst_srid` gives `0` for a CRS with no EPSG code. `gbx_rst_setcrs(tile, crs)` relabels the tile's spatial reference **without warping pixels** — the georeference (`upperLeftX`, `scaleX`, …) and the pixel dimensions are unchanged, which is what you want when a file arrived with missing or wrong CRS metadata. `gbx_rst_transformcrs(tile, target_crs)` genuinely reprojects: it resamples the pixel grid, so both the georeference and the raster dimensions change (a 64×64 `EPSG:4326` tile becomes 55×72 in `EPSG:3857`). Both writers accept an authority code (`EPSG:3857`, `ESRI:54008`), WKT, or PROJ4, and an int-castable string (`'4326'`) is treated as an EPSG code. Available on both the heavyweight (`rasterx`) and lightweight (`pyrx`) tiers. See [Raster Functions](./api/raster-functions#rst_crs).
- **Custom PROJ grid-shift registration (`gbx.register_proj_grids`).** Stage your NTv2, NADCON, or PROJ geoid grid files to a Unity Catalog Volume, call `gbx.register_proj_grids(spark, "/Volumes/<catalog>/<schema>/proj-grids")` once at session start, and every lightweight-tier CRS transform finds them automatically on every worker — resolving the silent accuracy loss that occurs when PROJ cannot locate a datum grid. Volume-hosted grids are a lightweight-tier capability; on the heavyweight tier, stage grids to a cluster-local path instead. See [Registering custom grid files](./api/coordinate-reference-systems#registering-custom-grid-files).

### VectorX geometry operations

- **VectorX antimeridian functions (`gbx_st_shiftlongitude`, `gbx_st_wrapx`, `gbx_st_split`) — lightweight tier.** Three "distributed shapely" geometry functions that reproduce the PostGIS antimeridian-normalization pattern for lon/lat data crossing the ±180° meridian. `gbx_st_shiftlongitude(geom)` shifts longitudes from `[-180, 180]` into `[0, 360]`; `gbx_st_wrapx(geom, wrap_x_origin, wrap_direction)` wraps X coordinates back across a meridian; `gbx_st_split(geom, blade_geom)` splits a geometry by a blade, returning a `GEOMETRYCOLLECTION`. Composed with the Databricks built-in `ST_Dump`, they turn a polygon straddling the antimeridian into a clean multi-part geometry. All three accept WKB/EWKB/WKT/EWKT and return `BINARY`, preserving the input CRS. Available on the lightweight (`pyvx`) tier. See [Antimeridian](./api/antimeridian).
- **VectorX geometry validity functions (`gbx_st_makevalid`, `gbx_st_explainvalidity`) — lightweight tier.** Two "distributed shapely" geometry functions that fill the diagnosis and repair gap in the product's native `ST_IsValid`. `gbx_st_makevalid(geom[, level])` repairs a geometry to OGC-SFS validity using GEOS `make_valid`; the default `linework` level also applies `orient_polygons` so output passes the product's stricter `ST_IsValid` (which enforces ring orientation in addition to OGC topology); pass `level='ogc'` for OGC-only repair without orientation normalization. `gbx_st_explainvalidity(geom)` returns a JSON string `{valid, reason, code, location}` diagnosing the SFS violation class, a stable reason code for `GROUP BY` analysis, and the coordinate where the violation occurs. Both accept WKB/EWKB/WKT/EWKT; `gbx_st_makevalid` preserves the input CRS. Available on the lightweight (`pyvx`) tier. See [Geometry Validity](./api/geometry-validity).
- **VectorX geometry cleaning functions (`gbx_st_simplifypreservetopology`, `gbx_st_removerepeatedpoints`, `gbx_st_reduceprecision`, `gbx_st_node`, `gbx_st_snap`) — lightweight tier.** Five "distributed shapely" functions for cleaning and normalizing **already-valid** geometry. `gbx_st_simplifypreservetopology(geom, tolerance)` applies the Douglas-Peucker algorithm with topology preservation — no ring collapsing, no polygon splits — the topology-safe counterpart to the product's `st_simplify`. `gbx_st_removerepeatedpoints(geom[, tolerance])` removes consecutive duplicate (or within-tolerance near-duplicate) vertices. `gbx_st_reduceprecision(geom, grid_size)` snaps all coordinates to a precision grid (PostGIS `ST_SnapToGrid` equivalent), using GEOS `set_precision(mode="valid_output")` so the result stays valid. `gbx_st_node(geom)` nodes linework at all self- and pairwise intersections — a prerequisite for polygonization or topologically clean network analysis. `gbx_st_snap(geom, reference, tolerance)` moves vertices of `geom` onto `reference` where within `tolerance`, aligning features that should share boundaries. All five accept WKB/EWKB/WKT/EWKT and return `BINARY`. Available on the lightweight (`pyvx`) tier. See [Geometry Cleaning](./api/geometry-cleaning).
- **VectorX coverage validity functions (`gbx_st_coverageisvalid`, `gbx_st_coverageinvalidedges`, `coverage_simplify`) — lightweight tier.** Coverage validity addresses a class of spatial defect that single-geometry validity cannot catch: overlaps and gaps between polygons that are each individually valid. `gbx_st_coverageisvalid(geom, gap_width)` is a SQL grouped-aggregate that returns `true` when the polygon group has no overlaps and no gaps narrower than `gap_width` — use it with `GROUP BY` to identify which coverage groups pass. `gbx_st_coverageinvalidedges(geom, gap_width)` aggregates the group and returns the boundary segments that violate the coverage as `BINARY` (WKB/EWKB), useful for spatial debugging and highlighting problem zones on a map; empty geometry when the coverage is clean. `coverage_simplify(df, group_col, geom_col, tolerance)` is a Python-API helper that simplifies the whole coverage as a unit — shared edges between adjacent polygons are preserved exactly in both simplified polygons (topology-preserving; N rows in → N rows out). All three accept WKB/EWKB/WKT/EWKT for geometry inputs. Available on the lightweight (`pyvx`) tier. See [Coverage Validity](./api/coverage-validity).

Each takes a single-band DEM tile and returns a derived tile (Float32 for slope/aspect/TRI/TPI/roughness, Byte for hillshade, RGB(A) Byte for color_relief). Defaults mirror the gdaldem CLI (hillshade NW sun at 315° azimuth, 45° altitude; slope in degrees). Foundation for terrain-derived workflows — solar exposure, viewshed pre-processing, watershed and runoff analysis, road grading. See [Raster Functions § Terrain](./api/raster-functions#terrain).
- **Slope and hillshade auto-scale from the raster CRS (breaking default on geographic rasters).** `gbx_rst_slope` and `gbx_rst_hillshade` (and the lightweight `prx.rst_slope` / `prx.rst_hillshade`) now derive the horizontal scale from the raster's coordinate reference system by default, matching GDAL `gdaldem`. On geographic (lat/long, e.g. EPSG:4326) rasters the scale is computed from latitude (degree→metre), so a global or geographic DEM produces correct, non-saturated slope and shading without any extra argument; on projected (metre) rasters output is unchanged. Previously these two ran unscaled on geographic input, which over-steepened and saturated the result. This changes the default output for geographic rasters to the GDAL-consistent value. To pin a specific scale, pass it explicitly — `gbx_rst_slope(tile, 'degrees', 111120)` for a degree grid, or `prx.rst_slope(tile, xscale=..., yscale=...)` / `prx.rst_hillshade(tile, xscale=..., yscale=...)`. `gbx_rst_aspect` is a direction and is unaffected. See [Raster Functions § Terrain](./api/raster-functions#terrain).
- **Spectral indices (5 functions).** `gbx_rst_evi`, `gbx_rst_savi`, `gbx_rst_ndwi`, `gbx_rst_nbr`, plus a generic `gbx_rst_index(tile, formula_name, band_map)` — all compositions over `gbx_rst_mapalgebra`. Each takes user-supplied 1-based band indices, builds a per-pixel formula string, and dispatches to gdal_calc; output is a single-band Float32 GTiff sized to the input extent. The generic dispatcher ships built-in NDVI, GNDVI, MSAVI, red-edge NDVI, NDMI, and NDSI formulae and is the entry point users should reach for first for any named multi-band index; the four specialized expressions surface EVI / SAVI / NDWI / NBR with their canonical coefficient defaults (EVI: `L=1.0, C1=6.0, C2=7.5, G=2.5` per MODIS; SAVI: `L=0.5`) so vegetation, water and burn-severity workflows compose without a hand-written formula string. See [Raster Functions § Spectral indices](./api/raster-functions#spectral-indices).
- **Resample and IDW interpolation (5 functions).** Three resample wrappers (`gbx_rst_resample` by multiplicative factor, `gbx_rst_resample_to_size` to explicit pixel dims, `gbx_rst_resample_to_res` to explicit ground resolution) all delegate to `gdal.Warp` with `-tr` / `-ts` plus `-r <algorithm>`. Two IDW functions — `gbx_rst_gridfrompoints` (arrays in one row) and its UDAF counterpart `gbx_rst_gridfrompoints_agg` (one point per row) — both delegate to `gdal.Grid` with the `invdist:power=<p>:max_points=<m>` algorithm and produce a single-band Float64 GTiff tile of the requested extent / size / SRID. Algorithm names match the `gdalwarp -r` set (`near`, `bilinear`, `cubic`, `cubicspline`, `lanczos`, `average`, `mode`, `max`, `min`, `med`, `q1`, `q3`); IDW defaults are `power=2.0`, `max_pts=12`, NoData `-9999.0`. See [Raster Functions](./api/raster-functions).
- **Pixel ops + extraction (7 functions).** `gbx_rst_fillnodata` (fill NoData holes via inverse-distance from valid neighbors), `gbx_rst_sample(tile, geom)` (per-band pixel values at a geometry), `gbx_rst_setsrid` (stamp an EPSG code without reprojecting), `gbx_rst_histogram` (per-band bucket counts via `band.GetHistogram`), `gbx_rst_threshold(tile, op, value)` (binarize 0/1 via map-algebra), `gbx_rst_buildoverviews(tile, levels, [resampling])` (add pyramid overview levels), and `gbx_rst_band(tile, bandIndex)` (extract a single band). Common per-pixel and per-tile operations missing from v0.3.0; each is a thin wrapper over the matching GDAL primitive. See [Raster Functions](./api/raster-functions).
- **Analysis (4 functions).** `gbx_rst_cog_convert(tile, [compression, [blocksize, [overview_resampling]]])` re-layouts a tile as a Cloud Optimized GeoTIFF via `gdal.Translate -of COG` (HTTP-range-friendly serving from object storage). `gbx_rst_proximity(tile, [target_values, [distunits, [max_distance]]])` computes a Float32 distance raster via `gdal.ComputeProximity` — distance to the nearest non-NoData (or matching `target_values`) source pixel, in CRS units or pixels. `gbx_rst_contour(tile, levels, [interval, [base, [attr_field]]])` extracts contour LineStrings via `gdal.ContourGenerateEx`, returning `ARRAY<struct(geom_wkb BINARY, value DOUBLE)>` — pass non-empty `levels` for fixed values or `array()` plus positive `interval` for equal-step contours. `gbx_rst_viewshed(tile, observer_geom, observer_height, [target_height, [max_distance]])` computes a binary visibility mask (Byte raster, `255` visible / `0` invisible) from a DEM and an observer POINT via `gdal.ViewshedGenerate`. See [Raster Functions](./api/raster-functions).

## What's new in v0.3.0

Released 2026-05-26. Per-version highlights; full migration tables are in the per-component sections below.

- **`rst_clip` CRS axis-order fix (all-black clips).** GDAL 3+ defaults EPSG-imported `SpatialReference`s to authority-compliant axis order (lat/lon for EPSG:4326), which silently swapped axes against JTS/Databricks WKT/WKB cutlines so the clip missed the raster entirely. The reprojection now clones the source/destination `SpatialReference`s and forces `OAMS_TRADITIONAL_GIS_ORDER` before the OGR transform; caller-owned `SpatialReference`s are not mutated.
- **EWKT / EWKB support for `rst_clip`.** `JTS.fromWKT` / `JTS.fromWKB` auto-detect EWKT/EWKB; new `JTS.toEWKT` / `JTS.toEWKB` helpers emit SRID-preserving forms. `rst_clip` reprojects the cutline when its SRID differs from the raster CRS, and falls back to the raster's CRS (Mosaic-compatible) when the SRID is `0` / unresolvable.
- **`rst_transform` rejects invalid SRIDs.** `targetSrid <= 0` and unresolvable EPSG codes now surface a clear error via tile metadata `error_message` instead of returning a raster with an uninitialized CRS.
- **`/vsimem/` path-handling hardening.** `rst_memsize` / `rst_unlink` / GDAL writer in-memory byte fetch now use `startsWith("/vsimem/")` (not `contains`) and null-check `GetMemFileBuffer`, so datasets whose description embeds the substring (e.g. NetCDF subdataset selectors) aren't mis-routed through the in-memory branch.
- **`tile.raster` bytes are always self-contained (no VRT payloads).** Three RasterX operations — `MergeRasters` (`gbx_rst_merge`, `gbx_rst_merge_agg`), `MergeBands` (`gbx_rst_frombands`), and `PixelCombineRasters` (`gbx_rst_derivedband`, `gbx_rst_derivedband_agg`, `gbx_rst_combineavg`, `gbx_rst_combineavg_agg`) — used to return tiles whose `metadata("driver")` claimed `VRT` even though the on-disk file was a materialized GTiff. That mis-tag propagated through `RasterDriver.writeToBytes` (which keys both the tempfile extension AND the `-of` flag in the inner `gdal_translate` call off `metadata.driver`), causing the serialized `tile.raster` payload to be VRT XML referencing a `/vsimem/` tempfile only reachable on the producing executor. Single-node testing passed by accident; multi-executor clusters hit `file not found` when the VRT was opened elsewhere. Fix: `GDALTranslate.executeTranslate` now records the **output** dataset's driver in its returned metadata (not the input's), and `RasterDriver.writeToBytes` defensively coerces VRT to GTiff on serialization + sniffs the result to refuse shipping VRT bytes. Regression coverage in [`RST_NoVrtPayloadTest`](https://github.com/databrickslabs/geobrix/blob/main/src/test/scala/com/databricks/labs/gbx/rasterx/expressions/RST_NoVrtPayloadTest.scala).
- **`PixelCombineRasters` pixel function now actually fires (`combineavg` / `derivedband` were silently returning one of the inputs).** `gbx_rst_combineavg`, `gbx_rst_combineavg_agg`, `gbx_rst_derivedband`, and `gbx_rst_derivedband_agg` build a multi-source VRT, inject a `<PixelFunctionLanguage>Python</...>` band, and re-open it for `gdal_translate`. The previous implementation re-opened the VRT **before** mutating the XML file, so the in-memory `Dataset` handle never saw the pixel function; `gdal.Translate` then fell back to a default multi-source mosaic (last-source-wins per pixel). On co-extensive inputs (e.g. a monthly EO time-series), the output silently equaled one of the inputs — non-deterministic per partition in a distributed setting, producing visible tile-of-different-years patchwork on multi-executor clusters. Fix: `PixelCombineRasters.combine` now injects the pixel function **before** the VRT is re-opened, and pre-creates the per-JVM `NodeFilePathUtil.rootPath` staging dir itself (previously only `ClipToGeom` did, so `combineavg` would `file not found` if it was the first op to hit a fresh JVM). Regression coverage: `RST_AggregationsTest` "CombineAvg actually averages pixel values" (two constant rasters 50 + 100 → output 75).
- **`gbx_rst_merge_agg` overlap winner is now deterministic.** When merging tiles whose extents overlap, the mosaic is last-wins, so the result depends on the order tiles are folded. The aggregator previously ordered tiles by their GDAL dataset description to make that order stable, but for the in-memory (`BinaryType`) tiles a `groupBy().agg()` produces, the description is a per-open `/vsimem/<uuid>` path — so the fold order, and therefore the overlap winner, varied from run to run. The aggregator now orders tiles by their **raw serialized content** (the GTiff bytes each tile carries) — a total order intrinsic to the tile with no ties for distinct content and no random per-open component — so one tile reliably wins the overlap regardless of fold order, and the result is identical across the heavyweight and lightweight tiers (both sort on the identical bytes). This also fixes overlapping tiles that share the same geotransform origin, which an origin-based key could not separate. Non-overlapping mosaics are unaffected. Regression coverage: `RST_AggEvalTest` deterministic same-origin and offset merge cases.
- **Friendly error on `ARRAY<tile>`-function misuse.** Calling `gbx_rst_combineavg`, `gbx_rst_merge`, `gbx_rst_frombands`, or `gbx_rst_mapalgebra` on a single tile column (instead of an `ARRAY<tile>` like `collect_list(tile)`) used to surface as a raw `ClassCastException: StructType cannot be cast to ArrayType` from inside Catalyst analysis — untraceable from a notebook. The four expressions now route through `RST_ExpressionUtil.arrayOfTileRasterType`, which raises a clean `IllegalArgumentException` naming the function, the actual type received, and (where applicable) the aggregator companion the user likely wanted, e.g. `gbx_rst_combineavg expects ARRAY<tile> (e.g. collect_list(tile) or array(t1, t2, ...)), but received STRUCT<...>. To aggregate the column across rows, use gbx_rst_combineavg_agg(tile).`
- **Docs: `GDAL_VRT_ENABLE_PYTHON` for custom GDAL code paths.** Built-in `combineavg` / `derivedband` calls auto-enable VRT Python via the in-process `GDALManager.withVrtPython` bracket — no cluster config needed. The [RasterX Function Reference § VRT Python pixel functions](./api/raster-functions#vrt-python-pixel-functions) section documents how to enable the same evaluation in your own GDAL calls (Python `gdal.SetConfigOption`, cluster `spark.executorEnv`, or the JVM `withVrtPython` helper) and points to the `TRUSTED_MODULES` variant for less-trusted VRT sources. A cross-reference is added in [Security § 6](./security#6-vrt-python-pixel-functions-off-by-default-by-design) explaining why GeoBrix ships the option `NO` by default.
- **`gbx_rst_derivedband` / `gbx_rst_derivedband_agg` numerical-correctness regression coverage.** These functions share the `PixelCombineRasters` code path with `combineavg`, so they were silently no-opping in the same way (returning one of the inputs unchanged on co-extensive stacks). The ordering fix above repairs both call sites, but the existing tests only checked that the result wasn't null — they would have passed either way. This release adds explicit pixel-value assertions: `RST_AggregationsTest` covers the in-process `RST_DerivedBand` path with a doubling pyfunc and a 3-input numpy-mean pyfunc, and `RST_AggEvalTest` covers the Spark-aggregation `rst_derivedband_agg` path end-to-end (three constant-Byte tiles 10/20/30 with a "mean × 2" pyfunc must yield 40 across the result tile). Two previously-passing tests used `def myfunc(x): return x * 2` — an invalid VRT pixel-function signature — and were updated to the canonical `(in_ar, out_ar, xoff, yoff, xsize, ysize, raster_xsize, raster_ysize, buf_radius, gt, **kwargs)` shape; they only "passed" before because the pyfunc never actually ran.
- **`gbx_rst_combineavg` / `gbx_rst_combineavg_agg` math corrected (NoData, valid zeros, rounding).** With the pixel function now firing (previous bullet), several latent bugs in the average kernel surface and are fixed in this release. The pyfunc used to sum every source value blindly — including each band's NoData sentinel (e.g. 255 on Byte EO products) — and counted only strictly-positive cells in the divisor (`np.sum(stacked > 0, axis=0)`), which (a) inflated the numerator with NoData and (b) wrongly excluded valid `0` measurements from the divisor. It also used `np.divide(..., casting='unsafe')`, which **truncates** rather than rounds when casting back to an integer output dtype (Byte / UInt16), producing systematic underbias on integer EO stacks. Now the kernel reads each source band's declared NoData (via `BandAccessors.getNoDataValue`, baked into the pyfunc source as a literal list at VRT-write time), masks NoData cells out of both sum and divisor, includes valid `0`s, uses float64 internally, and rounds-to-nearest-even before the unsafe cast when the output dtype is integer. The bogus `np.clip(out_ar, stacked.min(), stacked.max(), ...)` (the bounds were contaminated by NoData sentinels) is removed. When at least one input declares NoData, that value is also stamped on the output band so downstream `GetNoDataValue` reports all-NoData pixels. Regression coverage in `RST_AggregationsTest`: "excludes declared NoData from both sum and divisor", "counts valid 0 cells in the divisor", "rounds (not truncates) when casting to integer output".
- **Scalar args without `f.lit(...)`.** Python wrappers auto-wrap `bool` / `int` / `float` / `bytes`; Scala adds typed overloads. SQL was already natively-typed. String literals still wrap in `f.lit(...)` per pyspark's column-ref convention. Details and migration examples in [Scalar values vs `lit(...)` wrapping](#scalar-values-vs-lit-wrapping).
- **Example notebooks — EO Series, xView, and enablement diagrams.** New end-to-end walkthroughs under `docs/examples/` covering EO time-series, xView object-detection rasters, and RasterX architecture diagrams.
- **Supply-chain hardening (lockdown).** Jobs pinned to the Databricks-hardened runner group (org-level allowlist, ephemeral VMs, constrained secret access); every Maven dependency, transitive dep, plugin, and plugin dependency is PGP-verified against `.maven-keys.list` before any compile or test execution; pip and Maven routed through JFrog with OIDC; init script + pinned package versions vetted; new [Security](./security.mdx) page in the docs.
- **Pre-built, hash-verified GDAL bundle.** The GDAL native install path is now a CI-built tarball (`geobrix-gdal-artifacts-v<version>-noble.tar.gz` + matching `.sha256` sidecar, attached to each release alongside a versioned `geobrix-gdal-init.sh`). Cluster start drops from ~15 minutes (legacy PPA dance per boot) to ~30–90 seconds (verify sidecar → extract → `dpkg -i`). Trust chain is now four layers: CI-side GPG fingerprint pin → per-file `SHA256SUMS` inside the tarball → outer `.sha256` sidecar in the staging Volume → the Volume's write ACL. The legacy on-cluster path is preserved as [`scripts/geobrix-gdal-init-ppa.sh`](https://github.com/databrickslabs/geobrix/blob/main/scripts/geobrix-gdal-init-ppa.sh) for bundle bootstrapping. Bundle is `amd64` / `x86_64` only (Intel or AMD CPUs); ARM-based instance types — AWS Graviton, Ampere, Apple Silicon — are not supported. See [Installation](./installation) and the rationale on the [Security](./security.mdx#pinned-gdal-native--multi-layer-trust-chain) page.

## Scalar values vs `lit(...)` wrapping

Previously, every non-Column argument had to be wrapped in `f.lit(...)` (Python) or `lit(...)` (Scala). That was a regression from Mosaic/DBR built-ins, where booleans and numerics can be passed as plain values. In 0.3.0, plain scalars are accepted across Python, Scala, and SQL bindings.

**Python** — wrappers accept `Column` or scalar (`bool`/`int`/`float`/`bytes`); non-string scalars are auto-wrapped with `f.lit(...)`. Strings still follow pyspark's column-reference convention (bare string ≈ `f.col(name)`); wrap in `f.lit("...")` to pass a string literal.

```python
# ✅ Before 0.3.0 — required f.lit for every value
rx.rst_clip("tile", "geom", f.lit(True))
rx.rst_transform("tile", f.lit(4326))
bx.bng_pointascell("pt", f.lit(1))
bx.bng_pointascell("pt", f.lit("1km"))

# ✅ 0.3.0 — scalars accepted directly
rx.rst_clip("tile", "geom", True)
rx.rst_transform("tile", 4326)
bx.bng_pointascell("pt", 1)
bx.bng_pointascell("pt", f.lit("1km"))   # string literal — still wrap in f.lit
```

**Scala** — typed overloads added for `Boolean` / `Int` / `Double` / `String` value parameters. Column args (e.g. geometry, tile) still take `Column`.

```scala
// ✅ 0.3.0 — scalar overloads resolve without lit(...)
rst_clip(col("tile"), col("geom"), cutlineAllTouched = true)
rst_transform(col("tile"), 4326)
bng_pointascell(col("pt"), 1)
bng_pointascell(col("pt"), "1km")
```

**SQL** — values are already natively accepted by Spark SQL; no change needed:

```sql
SELECT gbx_rst_clip(tile, geom, true) FROM ...;
SELECT gbx_bng_pointascell(pt, 1) FROM ...;
SELECT gbx_bng_pointascell(pt, '1km') FROM ...;
```

**When you still need `f.lit(...)` in Python:**
- **String literals**: `rx.rst_fromfile(f.lit("/path/to.tif"), f.lit("GTiff"))` — a bare string is treated as a column reference.
- **Nulls / explicit typing**: e.g. `f.lit(None).cast("double")`.

## Notable improvements and fixes

- **Python package rename:** Imports changed from `geobrix.*` to `databricks.labs.gbx.*` to align with Scala and the published artifact; update all import statements and environment references.
- **Init script / NumPy:** Init script updated to install NumPy 2.x so GDAL Python array operations execute correctly; fixes runtime failures in `gbx_rst_mapalgebra` and `gbx_rst_ndvi` when used with array-based paths.
- **Error handling:** Functions that previously threw exceptions during execution now surface errors more clearly (e.g. return null or a controlled default with error messages captured) instead of failing with opaque stack traces.
- **RasterX `rst_bandmetadata`:** A required `band` argument was added; call as `rst_bandmetadata(tile, band)` (e.g. `rst_bandmetadata("tile", f.lit(1))`) in Python/SQL/Scala.
- **GDAL reader column:** Raster DataFrames from the GDAL reader use the column name `source` (not `path`) for the file path; update any code or docs that assumed `path`.
- **BNG aggregators (`bng_cellunion_agg`, `bng_cellintersection_agg`):** Fixed a bug where aggregation buffers were shared across partitions (and across tests in the same JVM), causing incorrect `core` flags when running full test suites or with multiple partitions. Each partition now gets a fresh buffer. Chip fields are resolved by type/name in the union aggregator for robustness to struct field order. Test expectation corrected for “all core chips” intersection: result is now correctly documented as `core=true` (whole cell).
- **`rst_clip` axis-order fix for EPSG-imported CRS (fixes all-black clips):** When the clip geometry's CRS was set via an EPSG code (plain `rst_transform`-style input, EWKT `SRID=4326;...`, or EWKB with SRID), GDAL 3+ defaults that `SpatialReference` to **authority-compliant** axis order — for EPSG:4326 that means `(latitude, longitude)`. JTS / Databricks / most GIS tooling emit WKT/WKB coordinates in traditional `(x, y) = (lon, lat)` order, so the reprojection inside `rst_clip` was silently swapping the axes (e.g. `-80 14` interpreted as `lat=-80`, near the south pole) and the cutline missed the raster entirely, producing all-black output. `OSRTransformGeometry.transform` now clones both source and destination `SpatialReference`s and forces `OAMS_TRADITIONAL_GIS_ORDER` on the clones before running the OGR transform, so JTS-origin WKB is interpreted correctly. Caller-owned `SpatialReference`s are not mutated.
- **EWKT / EWKB support for raster clip (CRS mismatch handling):** `rst_clip` now accepts EWKT (`SRID=<epsg>;<WKT>`) and EWKB (PostGIS extended WKB) in addition to plain WKT/WKB. Semantics:
  - **Plain WKT / WKB (no SRID):** the geometry is assumed to already be in the raster's CRS; no reprojection is performed.
  - **EWKT / EWKB (SRID set and resolvable via EPSG):** the geometry's CRS is used and, if it differs from the raster's CRS, the cutline is reprojected before clipping.
  - If the SRID is `0` or not a valid EPSG code, the code falls back to the raster's CRS (same as the plain case) — this restores Mosaic-compatible behavior but no longer silently produces an empty/black clip when a caller forgets to set the SRID.
  `JTS.fromWKT` / `JTS.fromWKB` now auto-detect EWKT/EWKB; new `JTS.toEWKT` / `JTS.toEWKB` helpers emit SRID-preserving forms. Plain `toWKT` / `toWKB` output is unchanged (OGC, no SRID).
- **`rst_transform` invalid SRID:** `rst_transform(tile, targetSrid)` now rejects `targetSrid <= 0` and EPSG codes that GDAL cannot resolve with a clear error (surfaced in tile metadata `error_message`) instead of returning a raster with an uninitialized CRS.
- **`/vsimem/` path handling hardening:** `rst_memsize` / `rst_unlink` and the GDAL writer's in-memory byte fetch now use `startsWith("/vsimem/")` (not `contains`) and null-check `GetMemFileBuffer`, so datasets whose description happens to embed the substring (e.g. NetCDF subdataset selectors) are no longer mis-routed through the in-memory branch.
