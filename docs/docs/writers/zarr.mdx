# Zarr Writer

_Since:_ lightweight `gbx_zarr_write` **v0.6.0** · _(light-only — no heavyweight tier)_

`gbx_zarr_write` writes a [Zarr](https://zarr.dev) store **transactionally**. One write is one Delta
`MERGE` on the store's manifest table, so it is visible whole or not at all; writers that touch
different chunks both land, and writers that meet on one chunk get a clear error. This page is the
how-to: the modes, the inputs, the layout of new arrays, what happens when writers meet, and publishing a
registered store. [Zarr Stores](../formats/zarr) explains the model, and the
[Zarr Function Reference](../api/zarr-functions#gbx_zarr_write) lists every parameter and error.
To read a store back see the [Zarr Reader](../readers/zarr).

It runs in the lightweight tier, so there is no JAR to install: use the `zarr_env6` or `zarr_dbr19`
extra, as [Zarr Stores](../formats/zarr#what-you-need) describes. The examples use these names:

## Modes

| `mode` | Does | The input must |
|---|---|---|
| `"create"` | Makes a new **managed** store: the table `target` and the data root `root` | Carry the blocks, Dataset or tiles of the new arrays. Name the coordinate arrays too, or the dimensions are labelled by position only |
| `"append"` | Extends one dimension (`append_dim`, by default the first dimension labelled by CF times) | Carry that dimension's labels, all after the store's last |
| `"update"` | Writes into the existing extent | Say where it goes: blocks by their `start` and `stop`, a Dataset by its labels, tiles by their grid |
| `"overwrite"` | Replaces the named variables | The variables to replace. Chunks the input does not cover read as the fill value afterwards |

`root`, `chunks`, `shards`, `codecs`, `file_mode` and `retain` belong to `mode="create"`: in the other
modes they raise `ValueError` with a `Fix:`. A write into a registered store needs it to be registered
with `writable=True`; it goes to the store's overlay root, in the base arrays' own codecs and key
encoding, and the store itself is never written (see [Registered stores](#registered-stores-and-publish)).

Old versions stay readable until [vacuumed](../formats/zarr#lifecycle-and-retention): an `overwrite`
does not destroy what it replaces.

## Inputs

`data` is one of three things.

**Blocks**: a DataFrame in the schema [`gbx_zarr_read`](../readers/zarr#output-blocks) returns
(`BLOCKS_SCHEMA`). With `decode=True` values (the default of a read) the writer applies the array's CF
attributes the other way: times back to the array's units, packed values to their integer type, NaN to
the fill value. Blocks that still carry the array's packing attributes (a read with `decode=False`)
are written as the stored values they are.

**An `xarray.Dataset`**, held on the driver, so keep it to what fits there. Pass `spark=` because a
Dataset has no session. An `update` places it by its coordinate labels, which may include steps an
out-of-order append left unlabelled.

**GeoBrix tiles**: a DataFrame with one tile column, found by its schema (other columns may stay).
They have a section of their own, [Tiles](#tiles).

## Layouts

A new array is laid out by three arguments of `mode="create"`:

| Argument | Values | Default |
|---|---|---|
| `chunks` | `"balanced"`, `"maps"`, `"series"` or a dict of dimension to size | `"balanced"` |
| `shards` | `None` computes them, a dict sets some dimensions, `False` means no shards | `None` |
| `codecs` | The inner chunk's codec chain, as Zarr v3 codec documents (dicts) or zarr codec objects, starting with a serializer such as `{"name": "bytes"}` | `bytes`, `zstd` (level 3), `crc32c` |

An **inner chunk** is the unit of reading and writing, about 4 MiB decoded. A **shard** groups inner
chunks into one object of at most 128 MiB decoded and 4096 chunks, because on a Volume every object costs
a round trip. The last two dimensions are the spatial ones; any before them are leading dimensions
(time, level, ...).

| Preset | Chunk | Best for |
|---|---|---|
| `"maps"` | One leading step, large spatial tiles | A map at a time |
| `"series"` | 32 x 32 spatial tiles, a long run of leading steps | The time series of a point |
| `"balanced"` | 24 leading steps, spatial tiles sized to fill the rest | Both |

Only the first leading dimension takes the preset's step; any other leading dimension has chunks of 1. A
`chunks` dict sets the dimensions it names, as given (an append dimension may want chunks longer than
today's data), and leaves the others at the `"balanced"` size; presets are clipped to a dimension's length. A shard is always a whole number of chunks, and
the leading dimension's shard grows by whole chunks past the current length, so a store created small
and appended to along time keeps filling the same shards. Coordinates are written as one unsharded chunk,
long enough that appends keep landing in it.

`create` needs `root` not to exist, or to be empty. It gets an ownership ledger (the small Delta table
`_gbx_owner`, which decides which table owns the root even when several claim it at once) and the
`_gbx_store.json` marker; see [One owner per root](../formats/zarr#one-owner-per-root). `file_mode`
(`"fuse"` by default; `"auto"` or `"external"` keep `FILE` references; `"managed"` is not available in this release) and `retain` (how
long superseded versions stay readable, `"7 days"` by default) are the store's from then on; see
[File modes](../formats/zarr#file-modes). A store in `external` mode keeps `FILE` values in its manifest,
so it can be written, read and maintained only on compute that supports them; other compute refuses
before it writes anything.

If a `create` fails after it made the table but before anything committed, run it again with the same
arguments: a `create` on a manifest you own that has no commit yet adopts it. Two `create` calls that claim
one root at the same moment cannot both win, and the loser never releases the marker the winner relies on.

### Name the coordinates

A create from blocks labels a dimension only if the blocks carry its coordinate array. Read the
coordinates with the variables (`variables=["t2m", "time", "latitude", "longitude"]`, as the examples
above do). Without them the write still succeeds and logs a warning, "the blocks carry no coordinate for
...", and the new store labels those dimensions by position only.

## Appending, updating and overwriting

An `append` labels the new steps: they must come after the store's last, and on a regular axis they land
at their step, so appends may arrive out of order. On an irregular axis they land at the current length.
[Zarr Stores](../formats/zarr#transactions) shows an append, an update and a conflict.

An `update` writes into the existing extent. An inner chunk the input covers whole is encoded without
being read; a chunk it covers only in part is read at the base version, patched and written again. A
`write_id` (32 lowercase hex characters) makes a write idempotent: writing again with one that has already
committed returns its version and writes nothing.

### `variables=`: naming what you write

`variables` takes a name or a list of names. In an `update` or `overwrite` from blocks it does two jobs:

- **It is required to create a variable the store lacks.** A new variable is created on the store's
  dimensions, with the layout and codecs of a new array and the attributes of its first block. Without
  `variables=` the writer only knows the arrays the store already has, and refuses a block of any other.
- **It narrows the work.** Without it every decodable array of the store is a candidate: the write reads
  the manifest rows of all of them and moves them through its shuffle, and only then keeps the rows of
  the chunks its input touches. Naming the variables leaves the other arrays' rows out from the start,
  so on a large store name the variables you write.

### An input that is read more than once

A blocks DataFrame is read **once** by an `update` or an `overwrite`. A `create` and an `append` need the
input's extent (and an append its new labels) before they can lay the chunks out, so they make a first
pass over the block positions, which never reads the `data` column, and then the write pass. An opaque
input, such as a `mapInArrow` or a query with a join, is therefore **evaluated twice** by them. A pass
that finds the input has changed is refused ("the input changed between planning and writing"), so give
a `create` or an `append` an input that is deterministic. A table is best: stage the blocks in one first,
and the table is read once for the data.

### Blocks on the store's grid

A `create` writes blocks that each cover whole chunks (whole shards, in a sharded array) where they are
made: the task that holds a block encodes it and writes it to a data file of its own, and nothing is
shuffled. This is decided for the whole create, every variable at once: if any block cuts across a chunk
or a shard, or two blocks overlap, all of them are cut into pieces, regrouped by chunk through a shuffle
and assembled. The store is the same either way: the same documents, the same chunk rows, the same bytes
in every chunk; only the data file a chunk sits in differs.

To write the faster way, start every block on a chunk boundary (a shard boundary, for a sharded array)
and end it on one or at the edge of the array. The blocks are written by the tasks that hold them, so an
input that keeps its blocks in few partitions (a single one, say) is first spread out by block, and many
tasks write at once. A block of several shards writes their chunks in its own order, so one shard's
chunks do not sit side by side in the data file and a read of that shard takes more, smaller reads; a
block of one shard keeps them together. A 1 GB create of blocks of one shard each wrote its data
files at a median 119 MB/s through the Volume and 80 MB/s direct to storage on Databricks Runtime 19
(direct runs from 39 to 139 MB/s), and at 122 MB/s on Serverless; see
[Zarr Stores](../formats/zarr#performance).

An `xarray.Dataset` and a DataFrame of tiles are planned on the driver from what they hold, so neither
has a pass of this kind.

### Values and the array's type

Decoded values are encoded with the array's own attributes. A write is refused, as `ZarrUnsupported`
with a `Fix:`, when the values cannot be held: a NaN into an integer array with no `_FillValue`, values
that leave the stored integer range once packed, complex values into a real array, or times into an
array with no CF time units.

**Times must be whole multiples of the array's time units.** An axis stored as integer `hours since ...`
holds no half hours. A write whose times would need finer units than the array has is refused whole, and
nothing is committed:

The unit names that are understood are `days`, `hours`, `minutes`, `seconds`, `milliseconds`,
`microseconds` and `nanoseconds`, in any case and with or without the plural (`Hour` is `hours`). The
UDUNITS abbreviations, such as `h` and `hrs`, are **not** understood: reading such an axis raises
`ZarrUnsupported` ("is not a CF time unit") and writing times into it is refused too. Correct the
`units` attribute, or read the raw numbers with `decode=False`.

## Tiles

A DataFrame with a tile column writes each tile's pixels into the array of its variable, in any mode.
Tiles are placed by their decoded geotransform against the array's grid, so a clip or a change of NoData
keeps its place, and a null tile is skipped.

- **A tile cut from Zarr** by [`gbx_zarr_read(output="tiles")`](../readers/zarr#output-geobrix-tiles) still
  carries where it came from (`zarr_array`, `sliceDims`, `window`). It goes to the array it came from,
  whose grid (geotransform and CRS) must be the plane it was cut from, else `ZarrGridMismatch`. Its other
  positions are its `sliceDims`.
- **A tile with no provenance** needs `dim_cols`, a dict of dimension to the column that holds its label
  (a number or a time column), for every non-spatial dimension, and `variables="<name>"` to name its
  variable (a new store defaults to `"data"`). Most pixel-producing `rst_*` functions return such a tile,
  and so does a stack of GeoTIFFs. `dim_cols` also overrides `sliceDims`.

### A new store from tiles

`create` derives the grid from the tiles: their CRS, their cell size and the extent of all of them. A
tile with another CRS, another cell size, or an origin more than 1e-6 of a cell off the cell edges raises
`ZarrGridMismatch`. Each `dim_cols` column gives the sorted labels of its dimension; the latitude and
longitude (or `y` and `x`) labels come from the grid. A CRS other than `EPSG:4326` is carried by a
`spatial_ref` grid-mapping variable, so `gbx_zarr_read(output="tiles")` reads the CRS back.

An `append` takes the new labels of the append dimension from its `dim_cols` column; the other
`dim_cols` values must be labels the store has. `update` and `overwrite` look the values up in the store's
coordinates. Values keep the tile's type in a new store. In an existing array they are cast to the array's
type (floats to integers round half to even), and the tile's NoData becomes the array's `_FillValue`. A
tile that does not fit is refused on the driver, before any file is written.

## When writers meet

[Zarr Stores](../formats/zarr#concurrent-writers) explains the rules row by row; in short, writers
that touch **different chunks** both land, writers that only change the **shape or a shared coordinate
chunk** are rebased, and a write that meets another's **chunk** raises `ZarrWriteConflict` and commits
nothing. The limits of the rebase are worth knowing before many jobs append to one array:

- **A write retries up to 20 attempts**, waiting between them with a jittered pause that doubles up to
  16 seconds. Its data files are never rewritten.
- **Appends to one array land one at a time.** They all change the array's shape and the time
  coordinate chunk, so Delta commits one per round, and the last of N simultaneous appenders needs about
  N attempts. In measurements on Databricks one attempt, including its wait, took 16 to 28 seconds, so
  a writer that keeps losing can spend several minutes before it gives up.
- **17 or more simultaneous appenders to one array can exhaust the bound.** Sixteen simultaneous appenders
  all landed in the measurements; beyond that the last ones raise `ZarrWriteConflict` and nothing of their
  write is visible. The `Fix:` says to retry later or reduce the concurrent writers to the array: batch
  the appends into fewer, larger writes, or run the failed ones again when the others are done.
- **A coordinate label set to two different values is a data conflict.** If another writer already set
  the same coordinate cell to a different value, the write raises `ZarrWriteConflict` rather than
  keeping the last writer's. Equal values merge.

## Registered stores and publish

A store registered with `writable=True` takes the same writes. They land in its overlay root and the
store's own files are never touched, so every other registration of the store, and every plain Zarr
reader, is unaffected until you publish.

### Deleting a chunk

A chunk whose every cell is the fill value is **not stored**, in every mode, as zarr does by default. If
the chunk had a row it is deleted from the manifest; if it lies under a store's shard, the row becomes a
**tombstone**, a row with no file, and a read sees the fill value there. A read of an older version, and a
`gbx_zarr_restore` to one, still has the data. `gbx_zarr_optimize` folds tombstones away, and a publish
deletes the object.

### Publishing

`gbx_zarr_export(spark, table, method="publish")` writes the overlay into the store itself, so every
Zarr reader sees it ([Outside changes: drift, sync and publish](../formats/zarr#outside-changes-drift-sync-and-publish)
describes what it does and guarantees). The limits:

- **A publish refuses if the store changed since the last sync**, with `ZarrStoreDrift`. Run
  `gbx_zarr_sync` and publish again.
- **A write that lands on the table during a publish makes the publish fail.** The publish commits with a
  compare-and-swap on the overlay rows it turns into store objects, so if a writer replaced one of them
  after the publish read it, or Delta rejects the commit because a writer really raced it, the publish
  raises `ZarrWriteConflict` and the table does not move. The objects the publish had already written are
  in the store, and the `Fix:` says to run `gbx_zarr_sync`, which lists them (the change is `both` for a key
  the overlay also changed, and the overlay still wins), then publish again. The lock is released.

A publish records the identity of each object it wrote only after the Volume has settled the object's
modification time (a Volume moves it to the next whole second a moment after the write), so a read right
after a publish does not report drift. After looking at each object once it waits, up to 2 seconds in all, for
the times still moving to settle; an object whose time has not settled by then is recorded as it is, with a
warning, and `gbx_zarr_sync` puts its identity right. The version `gbx_zarr_export(..., method="publish")` returns is the
commit that turned the overlay rows into store objects.

## Folding after a write

Appends and updates add one manifest row per chunk they change. `optimize=True` runs
[`gbx_zarr_optimize`](../api/zarr-functions#gbx_zarr_optimize) on exactly the shards the write touched,
right after its commit; a few small writes into a big shard cost one fold of that shard, and the content
is the same either way. The version the call returns is the **write's own**; the fold, if it had work
to do, is the next version.

## Access and cleanup

`access` is how the tasks reach the store's files, as for a read: `"auto"` (default) writes straight to
cloud storage where Unity Catalog can issue credentials (dedicated compute) and through the Volume mount
everywhere else, Serverless included; `"fuse"` always uses the mount and sends no credentials; `"direct"`
raises `ZarrAccessUnavailable` where credentials cannot be had. See [Access](../readers/zarr#access) for
the credentials and the local-disk encryption note.

A pack upload that is refused or fails part way can leave an incomplete multipart upload in the bucket.
GeoBrix does not clean it up: add a bucket lifecycle rule that aborts incomplete multipart uploads
(`AbortIncompleteMultipartUpload`) to the bucket of the Volume.

Files GeoBrix writes live at `data/<array>/<write_id>/part-<id>.zpack` under the root. **Never put your own
files in that layout**: a vacuum deletes any file in exactly that shape that no readable version needs.
Files anywhere else under the root, and any other store's root, are never touched.

## Errors

Every error GeoBrix defines is a `ZarrError` and ends with a `Fix:` that says how to resolve it; a bad
argument is a `ValueError` that ends the same way. A mistake in the call is raised on the driver before any
file is written. An error raised while Spark runs the write arrives from the
action as a `pyspark.errors.PythonException`, with the GeoBrix error name and its `Fix:` line in the
message; a failed write commits nothing. The full list, with the cause of each, is in the
[Zarr Function Reference](../api/zarr-functions#errors).
